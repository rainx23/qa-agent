# 接口自动化平台操作与执行

本文件承载接口自动化平台的 Case 组织、MCP 使用、平台操作授权边界及正式报告回读规则。由 SKILL.md 按任务路由加载。

## 接口自动化平台 MCP 使用与执行边界

- 接口自动化平台是正式 Case 保存、请求执行、Step 结果、历史记录和正式报告的平台。使用前按当前 Agent 运行环境发现本项目配置的 MCP 服务，并读取本次所需工具的最新 Schema；服务配置名与工具名分开处理，具体发现及恢复规则见下文。不得硬编码 MCP 地址、凭据或某个 Agent 客户端 API。
- 只读查询 Case/Step、历史记录或查看报告原文时，不要求加载请求构造规则；创建/更新 Case/Step、Debug 或正式 Run 前，必须按入口路由实际读取 references/request-assertions.md，核对 UAT 目标、认证、请求契约和秘密保护后再操作。若需要判定报告结果，再加载 references/failure-diagnosis.md。

- 操作前先查询现有接口 Case/详情及必要历史记录，判断应复用、更新还是新增，避免重复创建。**默认一个 API Code 只维护一个当前有效的平台 Case**，该 Case 收纳该接口所有有测试价值的场景 Step；不得按功能分组、参数类型、业务主题、调试批次或场景数量拆分多个 Case。
- 只有平台明确的硬性容量/执行限制，或同一 API 确实存在无法共用环境、认证或副作用安全边界的独立运行生命周期，且经用户确认后，才允许拆分；必须记录具体原因，不得仅因 Step 多或便于管理而拆分。
- 历史上同一 API 已拆出的多个 Case，优先选取已有稳定主 Case，合并仍有效的场景 Step；其他 Case 保留历史身份与执行报告，不删除历史。平台提供 Case 级停用/归档时按平台能力标记；若只支持 Step 级停用，则在用户授权后给历史 Case 名称加 `历史停用-` 前缀并禁用全部 Step，同时在本地台账明确 `enabled_flag` 可能仍为 true；不得声称 Case 级已禁用或物理归档。
- 本地接口索引中的当前/历史 Case 与 Step 字段结构、映射及维护规则统一由 references/archive-maintenance.md 负责；本次平台操作若需同步本地索引，必须在索引读取/写入前加载该文件。平台 Case/Step 本身的查询、组织和操作仍以本文件为准。
- **Case 标题统一为 `【业务模块】业务功能-API Code`**，例如 `【示例模块】查询数据列表-demo.data.list`。`业务模块`优先使用平台/接口登记中可核实的模块名称；`业务功能`使用简洁、可读的中文名称概括接口核心用途；完整 `API Code` 放在末尾，便于按模块浏览并精准检索。模块或业务功能无法可靠确认时先核实，不猜测。标题不附加功能分组、`全场景自动化`、初始化/增量/回归、执行日期、版本、PASS/FAIL 或临时序号。**Step 名称规则保持不变**：优先采用 `{业务字段Code}-{业务名称}-{场景行为/条件}`；无法对应单一字段时，用场景主题/业务对象描述，不虚构 Code。若平台没有标题专用更新接口，标题修改必须提交完整 `step_data` 且可能重建 Step ID，则只有用户明确授权该 ID 重建及本地映射迁移后才可执行；未授权时停止。
- 是否可直接执行必须看后端真实行为，不能只凭 POST 方法或接口名称判断。确认是无数据库写入、状态变更、任务触发、消息发送及其他外部副作用的只读查询接口时，按已确认决策可由 AI 直接维护并正式执行；发现副作用或无法判断时停止，说明影响和待确认事项，不按普通查询默认执行。
- `平台调试工具` 是同步调试，报告类型为 `report_type=20`，仅用于保存前验证或受控调试；不得把 Debug 当作正式执行或正式回归证据。
- 正式执行使用平台正式执行工具触发异步 Run；触发成功不代表用例通过。AI 必须继续通过报告查询能力确认本次对应 Case 的新正式报告（`report_type=10`），核对可用的执行时间/模式/身份信息，再读取报告主信息、Step 明细和必要的单 Step 请求/响应详情。不能把历史报告误认成本次结果。

## 已验证的平台契约

本节只记录跨接口可复用、且有实际平台执行证据的能力。它们描述当前已验证的平台行为，不等于所有版本永久不变；平台升级、Schema 变化或新证据冲突时，应重新核对。不得把具体业务接口、真实 Header 名称/值、Case/Step/Report ID、内部 URL、请求响应正文写入本节。

- **Step 保存语义（平台契约 `NOT_VERIFIED`）**：历史接口记录曾将 平台保存/更新工具中的 `step_data` 字段视为完整集合替换，但当前缺少独立的保存前/保存后全量快照，尚不足以将其提升为已证实的平台契约。为避免潜在覆盖丢失，操作上继续按“可能全量替换”采取保守策略：保存前读取完整 Step 集合、每个 Step 的稳定身份和全部配置，并记录平台可用的 Case 版本/更新时间；若平台不提供版本字段，则保存完整集合的规范化指纹。提交前再次只读核对版本或指纹未变化，若变化则停止并基于最新快照重新设计；写入后重新读取完整集合，逐项核对 Step 身份、数量、全部配置及启停状态。任何不一致都停止后续写入，不盲目重试。只有取得受控非生产环境的保存前后快照并证明语义后，才可更新契约状态。
- **Case 级公共 Headers**：已验证平台支持在 Case 级配置公共 Headers，并应用于其 Step。所有 Step 共用的 Header 优先放在 Case 级；只有某 Step 确实需要不同值且 Schema/运行证据支持时，才使用 Step 级配置。具体 Header 名称、值、认证材料及菜单/组织标识必须留在本地接口配置或平台安全配置，不写入通用 Skill。
- **Validators（区分保存与 Debug）**：测试设计必须明确每个 Step 要证明的业务断言，不能把 HTTP 成功或“没有断言报错”当成业务通过。当前平台保存/更新工具 Schema 描述了保存时省略 `validators` 的默认处理；但本地历史证据记录的是 Debug 载荷省略 `validators` 后未出现默认断言，该观察只适用于当次 Debug 请求，不能反推保存端行为。保存后应只读回核实际持久化的 `validators`；Debug 前核对实际 Debug 载荷并以报告确认断言是否执行。若 Schema、保存回读与 Debug 运行表现不一致，分别记录证据并标记对应范围 `NOT_VERIFIED`，不得合并成一个平台结论。
- **请求数据类型**：`request.data` 必须按 `data_type` 和当前工具 Schema 组装，不存在统一的 JSON 字符串规则：`json` / `raw` 使用字符串；`form_data` / `x_www_form_urlencoded` 使用 Schema 定义的字段列表；`none` 不传 `data`。其他类型或 Schema 发生变化时，先重新读取当前工具 Schema，不猜测、不强制转换。
- **断言操作符**：当前已验证执行引擎不支持 `length_equals`。不得直接使用；也不得为了绕过不支持而删除断言或替换成语义更弱的检查。只有在目标环境重新验证该操作符可用后，才可更新本结论。
- **证据分层**：平台通用能力写在本节；某接口的具体参数、真实 Header、字段路径、业务预期和单次报告证据留在对应接口 JSON/需求产物。仅在一个接口或一个环境观察到的行为，若无法证明跨接口通用，标记为环境观察或 `NOT_VERIFIED`，不要提升为全局契约。

## Case 保存前的契约冻结与载荷策略

1. **先只读核对**：查询当前 Case、Step 摘要及版本；只有确实需要修改 Step 内容时，才读取完整当前 Step 集合。先判断复用/更新/新增，不重复创建 Case。
2. **一次性能力清单**：在正式保存前集中核对本次需要的 Header 层级、请求数据类型、Validators 结构、断言操作符及工具 Schema。已验证能力直接复用；未知能力不得在目标正式 Case 上逐项试错。确需探测时，只能在隔离的非生产测试对象中进行，并遵守平台写入授权；没有安全探测条件时标记 `NOT_VERIFIED`，不要赌参数行为。
3. **冻结后再生成**：先完成场景、请求、断言和启停状态设计，再一次性生成完整 `step_data`。更新时保留所有仍有效的原 Step，包括禁用项；禁止只生成 1–3 个修改 Step 后提交，也禁止通过手工复制/转义大段 JSON 拼接载荷。
4. **本地确定性校验**：提交前检查载荷可解析、`data_type` 与 `request.data` 结构匹配当前 Schema、Step 数量与计划一致、场景键唯一、必需字段齐全、场景断言目标已明确、启停状态正确，以及所有保留 Step 均包含在完整集合中。不要把保存 Schema 的默认 Validators 行为推断为 Debug 行为；保存后必须回读实际值。校验失败先修本地草稿，不调用平台写接口。
5. **一次保存、只读回核**：完成提交前版本复核、契约冻结且校验通过后再保存一次；随后读取完整 Step 集合，核对稳定身份、数量、所有配置字段及启用/禁用状态，不只检查摘要或少数关键字段。保存结果不确定时先只读查询，禁止直接重发载荷。确需二次修订时，先读取最新完整集合并与保存前快照比较，再重新校验版本和差异后执行；在替换语义未证实前始终按完整集合处理。
6. **大响应处理**：优先使用分页、列表摘要和定向 Step 查询；仅在必要时读取完整 Case。检查工具是否明确返回截断/超限/不完整标记，截断内容不得当作完整数据解析，也不得为获取相同大响应而连续重试。若工具明确返回持久化文件路径，使用该原样路径；不得猜测路径、使用宽泛 glob 或手工复制大段内容。
7. **持久化 MCP 响应解析**：复用 `skills/api-autotesting/tools/unwrap_mcp_response.py` 时，默认 `raw-json` 模式原样保留普通 JSON 结构，不自动把 `type/text` 字段猜成 MCP 包装。只有确认输入是 MCP 内容回执时才显式使用 `--mode mcp-content`，该模式支持标准 `content` / `result.content` 外壳、内容块列表或单个内容块；解析文本块时保留 `id` 等额外字段和所有非文本块。示例：`python -B skills/api-autotesting/tools/unwrap_mcp_response.py "<工具实际返回的文件路径>" --mode mcp-content --output ".qa-work/api-autotesting/<本次临时文件名>.json"`。输入来源必须是工具真实回执（脚本无法自行证明路径来源）；输出路径由脚本限制在 `.qa-work/api-autotesting/` 或系统临时目录，并以独占方式创建。脚本只输出结构摘要，不把完整业务内容打印到聊天或日志；若工具未提供持久化文件路径，则改用分页/定向查询，不自行推测文件位置。
8. **异步 Run 回读**：Run 触发后按已有实测耗时或平台提示等待一次，再做一次延迟只读回查。若新正式报告尚未出现，标记 `PENDING/UNKNOWN` 并停止自动轮询；用户后续要求继续确认时再发起新的只读查询。不得连续快速轮询，也不得因报告暂未出现而重复触发 Run。


## MCP 服务发现与 Session 故障恢复

- **服务发现**：先检查是否存在可选的本地组织配置及接口测试平台 MCP 集成配置；未配置时由用户/当前 Agent 实际提供的服务列表确认可用服务，不能假设所有环境使用同一名称。按已确认服务名定位已启用连接，再枚举实际工具及最新 Schema；服务配置名与工具名、客户端内部映射 ID/Runner ID 均需区分，不在通用 Skill 中固定连接地址、凭据、工具清单或参数。
- **错误分类**：
  - 服务未注册、已禁用或连接不可用：属于服务配置/连接层问题，不进入工具调用重试。
  - 工具不存在或参数 Schema 不匹配：重新发现工具并读取最新 Schema；不得归类为 Session 失效。
  - MCP 传输 Session 失效：只有错误明确来自 MCP/Streamable HTTP 协议层、且尚未形成正常工具结果时，才归为传输 Session 问题。
  - 平台业务 Session 失效：错误由工具正常返回，或出现在平台业务响应内容中时，归为业务会话/认证问题；按平台文档处理，不重建 MCP 连接。
  - 作用域不明：只看到 `Session not found` 文案、无法确认错误来源时，标记 `SESSION_SCOPE_UNKNOWN`，不得猜测属于哪一层。
- **传输 Session 恢复**：停止沿用失效 Session 的原请求；检查服务仍已注册、启用且可连接。仅使用当前 Agent 客户端明确支持的 MCP reconnect/reinitialize 能力重新建立会话；不得自行生成 Session ID、访问未公开端点或修改 MCP 配置。若客户端不提供恢复能力，明确报告并请用户在客户端重新连接 MCP，不转而要求用户手动触发平台正式执行。
- **恢复后探针**：重新建立连接后，重新枚举工具并读取本次所需工具的 Schema；只执行一次低成本只读探针（优先 list/get），确认工具可用后再继续。服务状态显示 healthy 不能单独证明旧 Session 仍有效；工具恢复成功也不代表平台业务 Session 已恢复。
- **业务 Session 处理**：仅按工具/平台文档明确提供的业务会话获取或续期流程处理。没有已记录的获取/续期方法时，停止并报告缺口，不把 MCP reconnect 当作业务 Session 修复。
- **不确定写操作结果**：创建/更新 Case/Step、Debug、正式 Run 等操作若在 Session 错误附近返回超时或结果不明，禁止直接重发。先用只读查询核对 Case/Step/报告/执行记录是否已产生；能确认已生效则继续后续只读步骤，能确认未生效且操作安全时才按授权重新执行；无法确认则标记 `UNKNOWN` 并停止。尤其不得因为 Run 报告暂时未出现而重复触发正式 Run。
- **重试上限**：一次故障最多执行一轮“检查→重连→重新发现→只读探针”。探针失败、恢复能力缺失或错误作用域不明时停止，不循环重试，不用本地 HTTP、脚本或 UI/Playwright 代替平台正式操作。
