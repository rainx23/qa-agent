# 执行结果判定与失败证据边界

本文件承载执行状态、失败分类、根因证据、人工核对分流、跨接口影响判断及可复用诊断经验。由 SKILL.md 在执行结果判定或失败分析前按需加载。

本规则面向不同接口的通用诊断，不绑定具体 API Code、业务模块、参数名称或某次历史错误。AI 负责分析与判断，工具只提供源码、请求、报告和配置等可复核证据。不得将错误分类写成固定脚本判断，也不得仅凭错误码、异常文案或一次请求结果认定根因。

## 单 Step 结果

- 单用例按实际行为与场景预期判定：`PASS` 为符合预期，`FAIL` 为有效执行结果违反预期，`ERROR` 为超时/连接/平台等执行层故障，`BLOCKED` 为必要数据或依赖不足。根因证据不足时单独标记 `UNKNOWN`，不因根因未知而篡改已有的用例判定。

## 整体结果

- 整体结果按本轮应执行范围判断：存在已确认 FAIL 则整体 FAIL；无已确认 FAIL 但仍有重要 ERROR/BLOCKED/NOT_VERIFIED 则 PARTIAL；所有应执行场景通过且无关键未解决项才可 PASS；无法形成有效执行结果则 ERROR。不得只按通过率或 PASS 数量下结论。

## 执行报告读取失败

- Run 异步任务未生成可确认报告、报告回读不明确或 MCP 不可用/会话故障时，标记 UNKNOWN/ERROR 并停止无效重试；按 platform-execution.md 区分 MCP 传输 Session、平台业务 Session 与作用域不明的错误。连接或会话错误属于执行证据缺失，不得误判为被测接口业务 FAIL。平台写操作结果不确定时，先只读核对是否已生效；无法确认则保持 UNKNOWN，不得重复创建、更新、Debug 或 Run。不得用本地 HTTP/脚本执行冒充 ZeroRunner 正式 Run。


## 执行状态与诊断结论分离

- **执行状态**沿用 PASS、FAIL、ERROR、BLOCKED；不得为了表达根因另造或替换平台 Step 状态。
- **失败类别**用于解释问题性质，可记录一个主要类别及必要的伴随因素：REQUEST_CONSTRUCTION（请求构造错误）、CONTRACT_SUPPORT（参数/操作符支持性或契约不明）、ENVIRONMENT_EXECUTION（环境/平台/网络执行异常）、DATA_DEPENDENCY（真实数据/权限/关联依赖）、BUSINESS_BEHAVIOR（合法请求下业务行为不符）、TEST_DESIGN_ASSERTION（场景/预期/断言设计问题）、UNKNOWN（证据不足）。
- **诊断状态**独立记录为 CONFIRMED、PROBABLE、MANUAL_VERIFY 或 UNKNOWN。执行 FAIL 不代表根因已确认；根因未知也不自动推翻已有执行结果。
- 只有在请求符合契约、目标分支确实触发、环境可用、预期有独立依据且实际行为违反预期时，才将问题判为业务 FAIL。请求本身无效或测试设计错误时，不得把它包装成业务缺陷；必要数据/依赖缺失时标记 BLOCKED；环境或执行链故障且未形成有效业务结果时标记 ERROR。

## 通用失败诊断流程

按以下顺序诊断，围绕当前失败证据按需深入，不要求每次扫描完整仓库或所有下游：

1. **固定事实**：确认 API/Case/Step、报告及结果 ID、目标环境、执行时间、实际请求（脱敏）、响应/异常、源码 SHA 和当前断言。报告不可确认时先处理报告读取状态，不推测业务根因。
2. **检查测试是否有效**：核对场景目标、请求是否真正触发声称的分支、预期是否来自需求/源码/接口契约、断言是否能证明目标行为。未触发分支、请求与场景名称不符、预期由实际响应倒推时，优先归为 TEST_DESIGN_ASSERTION。
3. **核对请求契约**：逐项比较前端控件/调用参数、序列化后的实际请求、后端 DTO/参数解析、默认值/空值处理及参数最终使用位置。检查字段名、类型、数组层级、单值/多值、缺省/null/空字符串、枚举、操作符、Content-Type 和必要 Header。请求构造不符时归为 REQUEST_CONSTRUCTION，先修正测试请求，不认定业务缺陷。
4. **判断参数或操作符是否受支持**：沿实际调用路径检查前端是否暴露/转换、后端是否接收/解析、是否进入条件分支、是否传递到下游，以及合法枚举/操作符是否由源码、配置、SDK 或契约定义。参数在某一处未出现、响应为空或返回通用错误，单独都不足以证明“不支持”或“被忽略”；继续检查动态配置、公共封装和下游处理，证据冲突时转 MANUAL_VERIFY。
5. **区分环境与数据依赖**：核对 UAT 地址、认证、网络、网关、超时、平台报告及依赖服务；另行判断场景是否要求真实记录、有效关联关系、权限或组织归属。合成值只用于源码契约允许的路径验证；不能把真实记录不存在/不可见直接归因为接口逻辑错误。
6. **定位业务差异**：仅当前述请求、场景、预期和环境均有效，且结果与独立预期不符时，归为 BUSINESS_BEHAVIOR。沿相关前后端方法、共享组件、公共方法和下游依赖追踪差异，保留能解释现象的最短证据链。
7. **检查共享影响**：若证据指向公共 DTO、参数解析器、枚举、请求拦截器、共享组件、公共方法、配置或下游服务，再按“跨接口影响”规则追踪实际调用方；普通单接口问题不强制扩展扫描。
8. **给出诊断状态和下一步**：证据闭合才标 CONFIRMED；方向有证据但链路未闭合标 PROBABLE；需要业务方/接口负责人确认契约或动态配置时标 MANUAL_VERIFY；连可靠方向都无法判断时标 UNKNOWN。不得用概率性推断冒充根因确认。

## 参数与操作符支持性判断

- 先区分“请求格式合法”“后端能够解析”“业务逻辑实际使用”“下游能够执行”四个层次；其中任一层未证明，都不能笼统声称参数完整支持。
- 参数/操作符的支持依据优先级：当前目标版本的前后端实现及配置、接口/组件契约、可追溯的运行证据、业务负责人确认。历史 Case 名称、单次成功响应、空结果、错误码或注释只能作为线索。
- 对数组/对象、枚举、模糊查询、范围条件、排序、分页等，核对实际序列化形态及后端接收/转换方式；不得为了让请求成功而擅自把数组改成字符串、替换枚举、删掉参数或变更操作符。
- 若接口明确不支持某参数，记录具体证据和影响；若证据只表明“当前路径未发现处理”，应标 UNKNOWN 或 MANUAL_VERIFY，不能直接下“不支持”结论。
- Debug/复测需要隔离变量：一次只调整当前待验证因素，记录原始请求与调整差异。没有新证据时不重复发送相同请求；超时、写入或有副作用请求不得盲目重试。

## 人工核对分流

出现以下情况之一，且源码/配置/报告无法消除歧义时，转 MANUAL_VERIFY，而不是继续猜测或反复 Debug：

- 参数、操作符、枚举或组合是否属于业务允许契约，需要接口负责人确认；
- 行为由动态配置、网关、外部 SDK/平台、白名单或运行时开关控制，当前证据无法读取；
- 错误信息同时可能由请求格式、数据存在性、权限或下游异常引起，无法可靠区分；
- 场景是否必须依赖真实 UAT 记录、特殊组织关系或业务状态，只能由业务/环境负责人确认。

交给人工核对的信息应具体且最小化：**待确认字段/操作符 → 实际脱敏入参及类型 → 已查到的前后端处理证据 → 尚不能确认的点 → 需要确认的一个问题 → 不同答案会如何影响后续测试**。不要把已经能从源码确认的事实再次交给用户，也不要要求用户代替 AI 重做整条排查。

收到用户确认后，将确认内容和来源记录到本次诊断证据，更新分类/诊断状态，再决定是否需要修改测试请求、补充场景或重新执行。重新执行仍遵循授权及平台规则；用户确认契约不等于自动授权平台写操作或正式 Run。

## 跨接口影响分析

- **触发条件**：根因证据涉及共享 DTO/参数解析、公共方法、枚举/配置、全局请求封装/拦截器、共享前端组件、公共查询/下游服务，或本次变更明确影响多个接口。
- 从共享符号、配置引用和实际调用链查找调用方；只追踪与问题相关的仓库、模块和 API Code，不因一个失败全仓扫描。
- 将关联接口分为 CONFIRMED_AFFECTED（存在直接调用/依赖且受影响路径已证实）、POTENTIAL_IMPACT（存在调用关系但具体触发条件未证实）、NOT_AFFECTED（有证据排除）和 UNKNOWN（仓库/调用链证据不完整）。不得把潜在影响写成已发生缺陷。
- 对受影响接口说明关联符号、调用证据、可能受影响的参数/场景及建议回归范围；没有可信源码或调用链证据时明确缺口，不编造接口清单。
- 只有在需要新增/调整回归场景时，才追加读取 scenario-design.md；只做调用关系定位时不强制加载场景设计全文。

## 诊断经验沉淀

- 仅沉淀已确认且可跨接口复用的规律，例如参数序列化契约、通用错误归因证据、共享组件行为或稳定的诊断步骤；将其整理为不含业务接口硬编码的规则，更新本文件对应章节。
- 单接口特例、具体参数值、某次错误响应和临时环境现象留在对应接口 JSON 的相关场景/证据记录或当前需求分析产物中，不提升为全局规则。
- 仅有假设、未确认的根因或一次偶发现象不得沉淀为通用结论；应保留 PROBABLE、MANUAL_VERIFY 或 UNKNOWN 状态及待确认事项。
- 不复制完整请求/响应、源码、日志或秘密；保存必要的脱敏摘要、来源位置、源码 SHA/报告身份和结论即可。维护本地接口 JSON/索引前，按 SKILL.md 路由加载 archive-maintenance.md。

## 通用诊断案例（用于校验思路，不是固定错误码映射）

- **请求结构错误**：源码契约要求数组，实际序列化为字符串。若本次意图验证正常查询，归为 REQUEST_CONSTRUCTION；有效路径未被验证，不判业务缺陷。若本次本来就是验证错误类型拒绝，且拒绝行为符合契约，则该负向场景可 PASS。
- **操作符支持性未知**：请求结构正确，但无法从当前源码确认某操作符是否由动态配置或下游支持。归为 CONTRACT_SUPPORT，诊断状态 MANUAL_VERIFY；先向接口负责人确认契约，不凭空结果或通用报错认定“不支持”。
- **执行环境超时**：网关/网络超时且没有可确认的正式报告。归为 ENVIRONMENT_EXECUTION，执行状态 ERROR、诊断状态 UNKNOWN；先核实平台任务/报告状态，不盲目重复有副作用请求。
- **真实数据依赖缺失**：路径验证需要一条真实关联记录，但 UAT 中无法确认该记录或权限关系。归为 DATA_DEPENDENCY，执行状态 BLOCKED；不把合成值空结果或真实记录不可见认定为业务缺陷。
- **合法请求下结果不符**：请求符合前后端契约、目标分支已触发、环境稳定、预期来自独立 Oracle，但实际业务结果不一致。归为 BUSINESS_BEHAVIOR；证据链闭合后执行状态 FAIL、诊断状态 CONFIRMED，并按共享依赖情况分析其他接口。
- **目标分支未触发**：Case/Step 名称声称覆盖某分支，但请求没有设置触发条件。归为 TEST_DESIGN_ASSERTION；不能将该 Step 的成功响应算作目标分支覆盖，修正场景后再验证。

以上案例用于检查诊断规则是否能区分不同原因；实际归类必须以当前接口的请求、源码、配置、报告和业务契约证据为准，不得照抄案例结论。

## 诊断交付最小信息

失败诊断交付应使用户能快速判断“现在知道什么、还不知道什么、下一步要做什么”，按本次情况输出：

- 执行状态与报告证据；
- 测试有效性（请求是否符合契约、目标分支是否触发、预期/断言是否成立）；
- 主要失败类别及诊断状态；
- 已确认事实、根因证据与尚存缺口；
- 如需人工核对，给出明确问题及其对后续测试的影响；
- 如涉及共享依赖，给出关联接口、影响等级和回归建议；
- 下一步动作及是否需要用户授权。

不适用的维度不必凑项；证据不足时明确标记，不以冗长模板替代判断。
