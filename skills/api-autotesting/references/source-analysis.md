# 源码分析与增量影响

本文件承载接口自动化的源码分析、AI/工具职责、可信源码版本及增量影响规则。由 SKILL.md 按任务路由加载。

## AI 与确定性工具的职责

**AI 自主负责：**
- 识别任务目标、接口身份和生命周期；理解业务含义及前后端行为。
- 追踪请求参数来源、默认值、条件分支、参数依赖/互斥、下游逻辑和响应行为。
- 发现隐藏场景，决定参数组合、用例拆分、断言内容及场景优先级。
- 判断源码逻辑是否被场景有效触发、覆盖是否充分、哪些场景可以合理合并或不单独测试。
- 分析代码变更影响、决定历史回归范围，并解释执行结果及失败归因。

**Python/Node 等工具只负责必要的确定性工作：**
- 读取文件、定位符号/方法/字段/常量，提取可静态解析的 AST 条件、调用关系、参数读写位置和配置事实。
- 按需获取 Git/Commit/Diff，计算 SHA/指纹，读写轻量 JSON，进行格式、字段类型、证据引用和明确断言的确定性校验。
- 在 AI 已决定请求和断言后，按定义发送请求、使用本地 UAT 配置、记录结果；不自行决定业务场景或业务预期。

工具输出应保留来源位置、版本指纹及解析失败/动态调用等未知信息。**没有提取到不等于不存在**。AI 可围绕当前接口和待回答问题继续定向读取源码，直到行为可解释或明确记录证据缺口；不得无边界扫描无关仓库。

代码相关任务按实际目标选择可信源码版本：复用任务内已冻结 SHA；增量更新对照历史已验证基线与本次目标版本；确需远端最新代码时，按 `config/repositories.json` 定向获取相关仓库/引用。不得为形式完整而全仓 Fetch，不得 Pull、Checkout、Reset、Clean、合并、变基或 Push。

## 前后端源码分析流程

1. **确认接口身份与上下文**：结合 API Code、路由、HTTP 方法、前后端实现位置、页面/业务入口、调用方和已有平台 Case，确认真实接口。P2/P3/P4 资料只作线索，必须回到当前源码核实。
2. **分析前端真实请求**：从页面操作或业务入口追到实际调用，理解请求方法、路由、Path/Query/Body 结构、Content-Type、参数来源、默认值、枚举、空值/缺省处理、条件传参、序列化转换、调用时机，以及全局请求拦截器和认证 Header/Cookie 对请求的影响。
3. **分析后端实际处理**：从路由/Controller 追到 DTO、类型与必填校验、默认处理、参数实际读取和使用位置、条件分支、参数依赖/互斥、下游方法/查询逻辑、异常路径及响应结构。不能只看接口声明或方法签名。
4. **交叉还原请求契约**：核对前端实际传入、后端接收和最终使用的参数。识别未传、错传、名称/类型/默认值不一致、后端支持但前端未暴露、前端转换改变语义及后端接收却未使用等情况，并判断业务影响。
5. **追踪真实调用路径**：必要时继续查看请求封装、公共方法、共享组件、配置和下游依赖。后端有实现但前端无调用时，结合需求和架构区分页面漏接与内部服务、定时任务、回调等非页面入口，不直接判缺陷；前端有调用但后端未找到实现时，继续核对网关、动态注册或其他仓库，不能静默忽略。
6. **处理证据缺口**：优先通过源码和已有配置还原请求，不要求用户逐接口提供真实 HTTP 请求。只有网关、动态逻辑、签名/加密 SDK、外部平台或证据冲突导致无法可靠还原关键行为时，才说明具体缺口并请求一次性补充材料。无法确认的部分标记 UNKNOWN，不伪装成完整分析。

## 增量影响与历史回归

增量分析不能只看 Git Diff 文件数或行数。AI 结合本次前后端变更、参数读写、调用关系、公共方法、认证/请求封装、共享查询组件、下游依赖、历史覆盖映射和可用需求线索，判断哪些行为真正受影响。

- 默认执行新增/更新的 Case，以及与变更逻辑直接相关的历史场景；有证据确认不受影响的场景可保留，不因局部变化无条件全量重跑。
- 变更涉及公共参数处理、认证、请求封装、公共方法、共享下游，影响多个业务分支/接口，或无法可靠确定影响边界时，应扩大到完整接口用例集，必要时扩大到关联接口。
- 影响范围不确定时扩大而不是缩小回归；不能因为用户以前人工测试过或本次未直接修改某参数，就默认跳过相关历史场景。
- 历史 Case 的维护建议沿用 `KEEP`、`UPDATE`、`ADD`、`RETIRE`、`REVIEW`。退役不等于删除，必须保留历史身份和执行追溯关系；平台实际停用/更新遵循其能力及授权边界。
- 每次增量关联历史与目标源码 SHA，说明影响依据、纳入/排除的场景及未知范围。没有可信历史基线时，不假装完成增量比较，应转为首次初始化或明确标记缺口。
