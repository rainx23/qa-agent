# 隐藏场景与覆盖设计

本文件承载接口场景发现、参数组合、源码与场景双向覆盖及覆盖状态规则。由 SKILL.md 按任务路由加载。

## 隐藏场景与参数组合设计

场景应从真实业务逻辑和源码行为中推导。AI 主动思考：哪些输入会改变处理路径或结果；前后端默认值是否一致；缺省、null、空字符串和显式值是否走不同分支；参数之间是否存在依赖、互斥或组合效应；边界、非法输入、异常处理和共享下游是否可能暴露遗漏。

这些是帮助分析的思考方向，不是每个接口必须逐项生成的固定场景清单。AI 根据实际证据决定哪些值得单独验证、哪些可以合并，以及哪些不适用；不机械全排列、不强制固定两两组合、不追求固定 Case/Step 数量。

- 每项有测试价值的源码逻辑、业务分支、参数边界及参数关系都必须有明确去向；不能因人工可能测过、参数本次未修改或减少执行时间而默认跳过。
- 一条场景可以覆盖多个逻辑，但请求必须确实能触发这些逻辑，断言也必须能证明目标行为；若合并后无法区分关键行为，应拆分。
- 不单独测试某项逻辑时，记录不单独测试的理由和证据；不为了覆盖数量制造重复或无业务价值的场景。
- **区分接口路径与真实数据验证（所有接口通用）**：适用于新增接口、存量接口首次初始化和增量回归，不绑定具体模块/接口。仅验证接口是否正常接收/处理请求、参数分支是否触发及执行是否异常时，ID、Code、number、组织、网点、客户、标签、供应商、人员等标识字段按前后端源码契约传入类型和结构正确的合成值即可，不要求对应真实 UAT 记录，也不得仅因缺少真实 ID 将路径场景标记为 BLOCKED。合成值的类型、数组层级、单值/多值、必填/可选、合法枚举和操作符必须有前后端证据；枚举字段使用源码/配置中的合法枚举码，普通标识字段使用明显的测试占位值，不得随意填错类型或篡改请求契约。若合成值被拒绝，先区分类型/结构/枚举错误、真实记录存在性/权限关系校验及执行层异常；只有目标分支确实依赖真实记录时，才把该依赖部分转入二期，不阻塞其他可验证路径。合成值请求成功、空结果或零行只能证明请求路径，不得证明真实过滤集合、权限/组织归属或金额/数量/聚合等业务数据准确性；这些目标需要真实记录和独立 Oracle。

## 源码与用例双向覆盖审查

设计完成后，AI 必须从两个方向复核：

1. **源码 → 场景/Case**：检查每个有测试价值的业务逻辑、分支、参数关系和异常路径是否已被覆盖、已设计待执行、受阻、有证据地排除，或仍未知。
2. **场景/Case → 源码**：确认请求能够触发所声称的逻辑，断言有需求/源码/契约依据；识别无法触发、预期无依据、重复或没有业务价值的场景。

## 初始化、需求增量与日常回归

- **首次初始化**：接口已有实现但没有可信自动化基线时，独立建立该 API 的完整场景基线；不依赖用户提供历史人工测试记录。
- **需求增量**：已有可信基线时，围绕本次需求/代码变化识别新增、修改、保留、退役及待复核场景；只更新受影响部分，必要时扩大回归范围，不重建或复制整份基线。
- **日常回归**：不因执行回归而新增场景或改变场景来源；根据变更影响选择执行范围，完整基线仍保留。
- 一个需求涉及多个 API 时，必须按每个 API 自己是否已有可信基线分别判断生命周期；不能把同一需求下所有接口统一标成初始化或增量。
- `ADD`、`UPDATE`、`KEEP`、`RETIRE`、`REVIEW` 是某次需求对场景的变更动作；它们与场景的长期来源类型不是同一维度。场景来源字段及历史追溯按 `references/archive-maintenance.md` 的唯一权威定义维护。

覆盖状态沿用既有约定：
- `COVERED`：有与目标逻辑匹配的有效执行和断言证据；仅创建 Case 或 Debug 不自动视为正式覆盖。
- `DESIGNED`：场景和断言已设计，但尚无有效执行证据。
- `BLOCKED`：因数据、环境、依赖或执行条件不足而无法验证，并记录解除条件。
- `NOT_APPLICABLE`：经证据判断不适用，并说明理由。
- `UNKNOWN`：源码、动态行为或调用链证据不足，尚不能判断。

覆盖充分性由 AI 结合业务风险作出解释。代码行覆盖率、分支计数和 Case/Step 数量只能作为辅助事实，不能单独证明业务覆盖完整。
