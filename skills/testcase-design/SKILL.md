# Testcase Design（P1）｜测试用例设计

## 能力边界

负责需求理解、业务规则分析、测试场景设计、独立 Oracle、正式用例产物组织及必要的一致性校验。

本 Skill 不默认生成 SQL，不默认拉取 Git，不默认执行人工测试，不因平台导入能力不可用而阻断核心用例设计。

本文件是普通 Markdown 执行说明，不依赖特定 Agent 的 Skill Runtime。任何执行 Agent 均可按路径读取并遵循。

## 任务意图识别

根据用户自然语言和当前对话上下文判断任务范围：

- 仅提供需求编号且没有明确任务意图：简要需求分析，不生成正式用例文件。
- 明确要求需求分析：分析并解释需求，不自动进入正式用例设计。
- 明确要求编写、生成或设计测试用例：完成需求分析和正式用例设计。
- 连续追问沿用当前任务范围；用户明确改变目标时再切换。
- 用户明确要求 SQL 时，作为独立任务处理，不与用例设计绑定。

只读取当前任务需要的规则。不能因为上下文预算而跳过必要规则，也不应读取无关平台规则或全部历史需求。

同一任务和有效执行会话内，仅当引用内容的来源/版本一致、读取完整且仍未发生变化时，复用已成功读取的规则、需求来源内容及 MCP Server/工具 Schema。若工程文件或 Skill/reference 已修改，用户纠正或补充需求，需求来源内容/版本更新，MCP Server/工具清单或 Schema 发生变化，连接/工具调用失败，已读内容不完整/失效，或用户明确要求重新获取，则定向刷新受影响的文件、来源内容或工具 Schema；无需因此重新发现或读取无关内容。正式用例任务将四份必读 reference 尽量放在一次批量读取中；确认内容仍有效时不重复读取。需求详情已包含足够完整的正文时，不再重复调用 Markdown 正文接口。知识库只在已知存在相关主题且能补充业务事实时检索，不做宽泛、低命中率搜索。

### P4 可选知识复用（需求分析/用例设计）

先从当前需求、用户业务确认与本任务已有证据建立预期和独立 Oracle；只有相关历史业务规则、页面/字段关系或质量经验能补充明确缺口时，才按需读取 `skills/knowledge-management/SKILL.md`，对目标业务模块与本任务相关的 1–2 类 JSON 作只读定向检索。不把 P4 设为必读 reference，不为知识检索自动 Git Fetch、全量 DEV 配置查询或写入知识库。

复用前核对**稳定业务对象、页面/Tab/变体、适用范围、知识状态和来源**。用户确认且适用的 `formal_reusable` 业务规则可作历史预期依据，但本次需求明确变更时先核对冲突并标记待确认；历史 SHA 技术关系只是定位线索，不自动等于当前实现或产品预期。候选、`pending_user_review`、`review_required`、历史 Bug 和 `runtime_validation=not_run` 不得直接作为独立 Oracle、正式预期或运行 PASS。

P4 没有知识、目录缺失、工具不可用、版本/环境不适用时，简要标 `NO_MATCH` / `KNOWLEDGE_UNAVAILABLE` / `UNKNOWN` 与受影响判断，继续可独立完成的需求分析与正式用例设计；不因知识缺失判断业务不存在、不扩大未决项，也不变更 P1 用例覆盖和 Manifest 发布门禁。P1 任务中只进行 P4 只读复用与候选建议，不自动加载 `knowledge-update.md` 或执行知识写入；明确批准某些候选后，才独立续接 P4 维护。

### P4 候选知识建议与用户确认（第一阶段）

1. 需求分析/用例设计随本次**聊天交付报告**附「P4｜建议沉淀知识」；仅从当前已获得的可靠需求正文、备注和用户业务确认中识别可长期复用的规则、页面/字段/条件、接口/配置关系、代表性质量经验。跳过一次性测试数据、无证据推测、重复文案；不为候选重跑需求分析、拉 Git 或扫描全库。
2. 已知相关 P4 模块时只读定向检查最相关的 1–2 类 JSON，按稳定业务对象、页面/Tab/变体、适用范围、知识状态与来源去重，区分**建议新增、建议更新、已有一致无需操作、冲突待确认**。模块不存在、不可读或未查重时标「待去重/未知」，不可声称已经确认应新增；冲突列出现有值和新依据，不静默覆盖。
3. 有可信候选时给出简短编号清单：业务含义、目标模块/对象、建议动作、证据/来源、已有知识比较与未确认点；无可信候选时写「P4｜本次无建议沉淀知识」。此段只是聊天报告，不进入正式 `testcases.md`、Oracle、XMind、Manifest，不增加 artifact role、正式版本或发布门禁，也不阻断 P1 完成交付。
4. 明确提示可回复「新增第1项、更新第3项」「全部同意入库」或「本次忽略」。**未回复、仅确认测试用例或业务规则均不授权入库**；未经用户明确批准不得加载写入流程、创建或修改任何知识文件。
5. 用户后续明确选定范围后，才加载完整 P4 `SKILL.md` 与 `references/knowledge-update.md`，在实际写入前重新检查当前知识、对象身份、来源、冲突及选定范围，依 P4 原规则最小编辑并回读；冲突或范围不清的对象停下待核实，其他已批准项目可继续。未批准/拒绝项不写，且不重新生成、发布或修改 P1 用例，不自动触发 P2/P5。

## 执行流程

### 需求分析

1. 获取并理解当前用户提供的需求来源。
   - 用户仅提供需求编号且当前对话没有需求正文时，优先使用当前执行环境可用的需求来源 MCP 获取详情；禅道环境可先检查 `getNeedDetailById`，必要时使用 `getMarkDownDetailById` 补齐正文。
   - 获取需求详情后，不能只读取 `spec` 正文：必须检查本次接口实际返回的 `keywords`/备注、非空且与业务有关的 `extendFieldList` 扩展字段，以及其他明确承载业务补充的字段；若工具 Schema 提供独立备注/评论查询，再按需定向获取。正文 Markdown 接口不替代备注读取。
   - 检查 `keywords` 是否非空以识别备注存在；`lastEditedDate` 等需求更新时间不能当作备注单独修改时间。字段达到长度上限、文本中途截断或评论列表不完整时直接请用户提供完整备注，不探索绕过限制或重复取数；不得将片段当成完整需求依据。
   - 当前需求版本中明确标注为补充、修订、纠正或最新说明的备注，优先于正文原有表述，仅覆盖对应冲突规则；若先后关系/含义不清且影响业务预期，列明差异后向用户确认。排期、负责人等管理元数据不得误当作业务规则。
   - 用户已提供足以分析的需求正文或附件时直接使用，不重复获取。MCP 工具名、参数和返回结构以当前运行环境实际 Schema 为准；工具不可用或资料不完整时明确说明缺口，不无限重试。
2. 识别业务目标、变更范围、关键业务规则、操作流程、数据/计算逻辑和风险。
3. 区分来源明确的事实、合理推导和待确认事项；先核对当前需求与用户已确认决策，避免重复询问已明确规则。
4. 只有待确认事项会实质改变业务规则、预期结果或测试范围时才向用户确认；按 `references/requirement-analysis.md` 中「待确认事项的说明与交互」章节说明背景、疑点、确认原因、影响范围及有依据的选项，并允许自由文本回答。多个独立问题可编号后一次回答；业务选项与继续、指定范围或取消等任务控制分开。
5. 未确认事项不得编造预期；只阻塞依赖该事项的判断，其他可独立分析的范围继续。用户回答后更新已确认事实并继续，不重复询问。
6. 仅在关键判断依赖外部资料时尝试获取；正文足以分析时直接继续。
7. 按用户意图输出分析结论；仅分析任务默认不生成正式归档文件。

### 正式用例设计

1. 完成需求分析，确定来源事实、合理推导、待确认事项和实际业务义务；将每个未决事项映射到受影响的业务义务、场景或预期结果，并区分不依赖该事项的独立范围。遵循 `references/quality-and-oracle.md` 中「未决事项与部分交付」章节处理未决范围，不得用猜测补齐预期。
2. 根据业务规则、影响范围、分支、依赖和证据缺口自适应判断复杂度。
3. 先依据需求来源独立建立 Oracle，再围绕业务操作与业务结果设计用例；不得从用例预期反向填充 Oracle。
4. 根据实际需求动态分组、去重并确定 P0–P4 优先级；明确未决事项和部分交付范围，不编造未知事实。
5. 在正式发布前完成一次整合语义自审：核对 Oracle 每项业务义务是否落实为具体、可执行且可判定的用例，检查分组与内容、前置条件/测试数据/步骤/预期的一致性，以及关键分支和无依据假设。按需求实际存在的风险，特别检查：枚举集合是否逐值覆盖（若采用等价代表，须有来源支持并说明覆盖边界）；二值条件是否分别验证两种取值的实际过滤结果；不同页面和查询入口是否分别验证其行为（快捷查询、通用查询不能互相替代，除非同一用例确实执行并断言各入口）；跨时间/跨对象关联是否使用同时包含命中与未命中数据的样本，分别验证应保留和应排除的结果。**同时在本次自审中核对 Markdown 正文符合 artifact-format 的可解析结构：分组、用例标题、Case ID、优先级/前置条件/测试数据、步骤/预期层级及附录位置；避免将自由说明放在合法结构之外，减少 XMind 生成阶段的格式返工。**仅检查适用维度，不建立固定矩阵、不为凑齐场景制造用例。发现问题先形成完整修正清单，再集中修正临时草稿并针对受影响部分复核；不进行多轮重复全文审查，也不额外运行 artifacts.py 做重复结构校验。
6. 所有正式候选产物先放在 `.qa-work/`。先依据需求来源独立完成 Oracle，再设计用例并完成 Case ID 分配；**在 Oracle 与用例均已独立形成后，尽量通过一次事务性文件写入批次同时创建 `oracle.json` 与 `testcases.md`**，该批次只合并文件传输，不改变 Oracle 先于用例的设计顺序，不得从用例预期反向编写 Oracle。执行环境不支持可靠批量写入时才分开写入。不要提前写入正式版本目录。
7. 完成一次语义自审后，先汇总所有需要修正的草稿内容；**尽量在一次事务性写入批次中完成全部修正，并同时创建最终 `publish-spec.json`**。如果没有草稿修正，也只需单独创建一次 spec。spec 可以在 XMind 文件生成前准备，因为它只引用临时文件路径；实际 publish 仍必须等待 XMind 生成及实际文件回读通过。所有候选文件和 spec 均放在 `.qa-work/`。
8. 只有所有草稿和发布输入均已准备完成，才调用 `manifest.py publish`。一次完整正式任务最多产生一个成功的正式版本；发布成功后不得为了修正本次内部自审遗漏而再次发布。若发布前失败，先确认没有正式版本提交，再修正临时草稿并重试；若发布成功后验签失败，停止并核查，不自动创建下一版本。
9. **优先使用一次 fail-fast 命令调用依次完成 XMind 生成及实际回读、单次 `manifest.py publish` 和最终 `manifest.py validate`**，并保留每个阶段的输出与退出码；前一阶段失败必须阻止后续阶段。只有执行环境无法可靠控制阶段顺序、失败中止或输出/退出码保留时，才拆分为多个命令调用。不得新增长期包装脚本、隐藏失败或跳过校验。
10. 清理临时文件，并汇报需求速览、用例总数、版本、文件位置、真实校验状态、预览及未决事项。

## 核心设计原则
- AI 自主承担业务理解、场景识别、复杂度判断和测试设计。
- 不设置固定用例数量上限，不按固定数量分批并反复询问是否继续。
- 不强制套用全部测试方法，不为凑齐分类或矩阵制造用例。
- 业务操作和业务结果优先；必要的技术验证单独组织。
- 同一接口/前后端实现且验证目标相同的重复技术验证尽量复用；业务行为或结果不同不得仅因代码复用而合并。
- 前置条件、测试数据和页面路径按需组织，不创建空区块或无意义导航步骤。
- SQL 与测试用例独立；不因 SQL 未生成而阻断用例交付。
- 性能目标：简单需求 3–5 分钟、中等需求 5–8 分钟、复杂需求 8–10 分钟；目标不构成硬性时限，不得为达标缩减必要业务覆盖或语义审查。
- 优先减少重复上下文读取、重复 MCP Schema 发现、低价值知识检索及重复 CLI/工具往返；相关确定性命令可在具备可靠失败隔离时合并调用，不新增长期脚本或复杂编排框架。
- 只报告可可靠测量的阶段耗时和端到端耗时；AI 分析/设计或宿主墙钟时间无法准确获取时标记 `NOT_MEASURABLE`，不得用单个 CLI 运行时长冒充端到端耗时，也不得推测 Token 数。

## 交付和证据边界

正式用例交付必须附必要的需求速览和适当深度的用例预览，并给出正式版本、实际产物位置及真实质量状态。不能编造用例数量、测试结果或校验结果。

P4 候选为聊天报告的可选建议内容，不是正式用例产物或测试质量门禁；未提出候选或用户未确认入库时，符合条件的 P1 正式用例仍应正常交付。

明确区分：
- 设计完成；
- 工程产物校验通过；
- 静态代码分析结论；
- 实际运行验证；
- 用户业务验收。

用户没有反馈人工测试结果时，不推断人工测试通过/失败，不统计实际 Bug 数量，不标记人工验证完成。

## 安全边界

遵循工程根目录 `AGENTS.md`。平台导入、生产 SQL、业务代码修改和 Push 均须满足既有明确授权；平台连接不可用时，只报告对应操作不可用，不阻断不依赖该连接的核心设计。

禅道和 ACE 使用各自现有的平台连接；禅道导入仅在可选本地 `config/organization-profile.json` 或当前执行环境已确认可用的禅道 MCP 下执行，不要求额外注册 `qa-mcp`，也不得为补充详情读取而硬编码 Zero Hub 地址或另建客户端连接。若当前平台 `getCasesByStoryId` 只返回摘要，不能把摘要回读表述为完整步骤/预期验收；但缺少详情字段本身不构成一律禁止导入的理由。

### 平台导入

- 只有用户明确提出“导入禅道/导入 ACE/导入禅道和 ACE”才进入对应平台写入流程；明确请求本身就是本次写入授权，不再重复询问是否导入。
- 导入前读取 references/platform-import.md，选择当前需求最新有效正式版本，按现有 Manifest 校验确认需求身份、完整交付资格和 Markdown 文件指纹；partial、草稿及非最新有效正式版本禁止导入。
- Markdown 是唯一用例内容源；XMind 仅为展示产物。平台载荷必须由 Markdown 独立转换，不能把 XMind 节点树直接当作 ACE 请求。
- 先按需求真实迭代和模块匹配目标路径；目标不唯一或来源元数据不完整时，停止对应写入并明确原因，不猜 ID、不降级门禁。
- 禅道使用当前已确认的禅道 MCP，按 Markdown 用例顺序逐条调用 createCasesByStoryId；每条取得 success=true、code=0 和远端 ID 后记录成功。
- 禅道写入结果明确失败时报告失败；超时、断连或无法判断是否创建成功时停止并报告 UNKNOWN_OUTCOME，不自动重试或盲目重发。正常导入不再执行写后摘要回读或逐条内容验收。
- ACE 自动读取禅道需求详情中的需求 ID/名称及真实迭代 ID/名称，再读取 ACE 项目和目录树匹配目标路径。能明确取得路径时直接使用；无法确定保存路径时，直接询问用户提供完整 ACE 路径，收到后继续导入。
- ACE 使用六项真实关联字段（product_id、dir_id、project_id、project_name、story_id、story_name），按现有优先级映射一次创建完整需求 MindMap。
- ACE 不要求目录下 MindMap 清单枚举或额外优先级 live 验真；创建接口明确返回成功和唯一 MindMap ID 时直接确认。若成功标志缺失但返回唯一 ID，则按 ID 回读核对标题、产品 ID 和完整节点树；回读缺失的目录/迭代/需求关联字段标记 NOT_PROVEN，不冒充验证通过。无唯一 ID 或回读失败时标记 UNKNOWN_OUTCOME，禁止重试。
- 任一平台写入结果不明时停止并报告，不自动重试；不因缺少非必要回读或目录清单而阻断正常导入。

## Manifest 与正式版本发布

正式用例交付和增量续接必须遵循 `references/artifact-format.md` 的 Manifest 数据契约，并使用统一工具 `tools/manifest.py`；不另建数据库、历史账本或专用版本脚本。

### 增量任务启动

1. 先运行 `manifest.py directory-name <需求编号> <需求名称>`，获取 `module_name` 和 `archive_relative_path`；需求根目录为 `output/<archive_relative_path>`，需求目录名称完整保留原始 `【模块】` 前缀。再运行一次 `manifest.py inspect`。记录其返回的 `manifest_path`、`markdown_path` 和 `latest_version`；该 `latest_version` 必须原样写入本次 publish spec 的 `expected_base_version`。`NO_HISTORY` 表示首次交付，`expected_base_version` 显式填写 `null`。
2. 对已有需求，使用一次批量文件读取同时读取最新有效 `manifest.json` 和 `markdown_path` 指向的当前有效 `testcases.md`。最新 Manifest 的 `case_snapshot` 是完整历史身份账本，包含有效及退役 Case ID；不得为收集身份而逐个读取旧 Manifest、旧 Markdown 或拆分读取每条用例。只有遇到明确的来源追溯/拆分合并疑点或验签失败，才定向读取对应历史版本。
3. `inspect` 失败时停止并定位，不从空集合重建。`inspect` 会检查全部历史有效用例指纹及退役快照连续性；相同权威 Markdown 路径只解析一次，并检查最新有效产物 SHA。它不代替全历史文件 SHA 验签。正常增量设计不额外先运行一次全历史 `validate`：`manifest.py publish` 在正式提交前会完整核验全部历史文件 SHA-256、来源追溯、历史快照和身份连续性；发布后仍必须执行最终 `validate`。
4. AI 对本次需求变更与当前有效用例集合进行一次完整语义比对，逐条分类为保留、修改、新增、明确退役或身份待核对。业务匹配和语义判断由 AI 完成，不能由 Python、标题相似度或固定关键字自动决定。
5. 只有确认存在真正新增用例时才生成 Case ID；已有历史时调用 `manifest.py ids <需求归档根目录> <需求编号> --count N --baseline-manifest <inspect 返回的 manifest_path>`，其中 N 必须等于真正新增数量。无新增时跳过 ID 生成；首次交付或无历史时使用不带 `--baseline-manifest` 的命令。发布器仍会在提交前重新验证完整历史及 ID 唯一性。
6. AI 完成语义分类后，一次性生成完整有效用例 Markdown 和独立 Oracle 内容。优先通过执行环境的结构化批量文件写入能力，在同一批次中分别完整写入 Markdown、Oracle 临时文件；不得把大量精确文本替换、逐条插入或反复读取修改作为常规增量方式。Markdown 必须包含完整有效用例集合及符合规范的附录，不得为通过解析而删除有效场景或附录。
7. 在正式发布前进行一次整合语义自审，检查所有保留/修改/新增/退役决策、Revision 预期、Oracle 义务覆盖、分组及附录。内部修正集中完成后再进入确定性发布流程，不得先发布再为内部返工创建第二个版本。
8. 某一确定性步骤失败时，先读取该步骤的错误输出，定位失败文件和原因；只修复受影响的临时内容并重跑必要的下游检查。不得盲目重试、重新读取未变化来源或重复执行已经通过且输入未变化的步骤。

### 正式发布

1. 只要仍有有效用例，当前版本的 `testcases.md` 就必须包含完整的当前有效用例集合，不能只包含本次增量；XMind 从该 Markdown 生成，Oracle 独立保留。若明确退役全部有效用例，必须逐条记录退役原因，并同时退役 Manifest 中的 Markdown、XMind、Oracle 三个角色；历史正式文件保留不删除。
2. 只把新增或更新的正式文件放入当前版本；未变化文件由 Manifest 引用原来源版本。SQL、提测分析等独立产物可以单独形成需求级版本；仍有有效用例时沿用当前用例基线，全部用例已退役时保留退役身份快照且不再要求当前 Markdown。
3. Markdown 最终内容确定后运行一次 `xmind.py` 生成并实际回读 XMind。回读失败时按诊断修复临时内容，不得删除有效业务场景或规范附录。随后调用 `manifest.py publish`；publish spec 必须携带 `expected_base_version`（首次版本为 `null`，增量版本为本轮 inspect 的 `latest_version`）。发布器先获取需求级操作系统文件锁，再在锁内读取最新历史并核对预期基线；基线已变化时拒绝发布，必须重新 inspect 并基于新基线重建输入。锁内还会核对正式版本目录集合，发布前和发布后均验证版本集合与预期完全一致。发布器继续执行全历史预检、Markdown/Oracle 结构校验、发布副本 XMind 回读、Case ID/Revision 校验，并在临时版本准备完成后原子发布。正常流程不单独运行 `artifacts.py` 重复执行 publish 已内置的结构校验。
4. 发布成功后运行一次 `manifest.py validate`，完成全部历史文件、来源链、身份快照、Revision 和指纹最终验签。检查返回的版本号、产物数量、用例数量及校验状态。若发布后验签失败，停止并保留现场，不自动创建新版本。
5. 支持时可将 XMind 生成、`manifest.py publish` 和最终 `manifest.py validate` 合并为一次 fail-fast 执行；必须保留各阶段独立输出和退出码，不得隐藏失败或跳过校验。输入未变化且某阶段已通过时，不重复执行该阶段。
6. 清理本次 `.qa-work/` 临时草稿、publish spec 和中间文件；永久保留所有正式版本。需求归档根目录同级的隐藏协调文件 `.qa-publish-<hash>.lock` 是跨进程互斥锁，必须长期保留，不得随临时文件清理。
7. 无实质内容或交付状态变化时不创建版本。纯排版、空白、标点等不影响语义的调整由 AI 判断，不应调用正式发布。

常用命令（从工程根目录执行）：

```powershell
python -B skills/testcase-design/tools/manifest.py directory-name <需求编号> "<需求名称>"
python -B skills/testcase-design/tools/manifest.py inspect output/【<模块>】/<需求编号>-<需求名称>
python -B skills/testcase-design/tools/manifest.py ids output/【<模块>】/<需求编号>-<需求名称> <需求编号> --count 3 --baseline-manifest output/【<模块>】/<需求编号>-<需求名称>/versions/<最新版本>/manifest.json
python -B skills/testcase-design/tools/manifest.py publish output/【<模块>】/<需求编号>-<需求名称> .qa-work/publish-spec.json
python -B skills/testcase-design/tools/manifest.py validate output/【<模块>】/<需求编号>-<需求名称>
```

`partial` 是本次交付状态，不改变既有有效用例基线，也不具备直接导入禅道或 ACE 的资格。本 Skill 当前不自动执行平台导入、SQL 或业务测试。
