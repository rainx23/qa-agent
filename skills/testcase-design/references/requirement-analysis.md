# 需求分析规则

## 分析目标

将需求描述转化为可理解、可验证的业务事实，至少识别与当前任务有关的：

- 业务目标及要解决的问题；
- 变更范围、涉及页面/模块/接口或数据对象；
- 参与角色及业务操作流程；
- 查询条件、筛选、排序、展示、导出等行为；
- 计算口径、字段来源、聚合关系和数据状态；
- 关键分支、异常处理、前后置状态及依赖；
- 对现有功能可能产生的影响和需要关注的风险。

不要求每个需求机械输出所有维度，只分析实际相关内容。

## 来源使用

1. 优先使用用户提供的需求正文、附件和当前对话中明确给出的事实。
2. 需求正文足以分析时，不主动反复获取 Wiki、原型或其他外链。
3. 只有关键业务事实确实依赖外部资料时才尝试获取；无法获取且影响判断时，明确说明需要用户补充的具体内容。
4. 不因局部缺证无条件阻断其他已有充分依据的分析或合格用例。
5. 不将历史需求结论、旧用例或旧 Oracle 当作当前需求事实；只有增量更新任务才按产物规则读取当前有效基线。
6. **正文与备注必须合并分析**：通过需求来源 MCP 获取详情时，检查当前接口实际返回的正文 `spec`、备注/关键词类字段（如 `keywords`）、非空业务扩展字段，以及 Schema 明确提供的评论/备注记录；不能只取正文或只取 Markdown。若备注由独立只读工具提供，按当前 Schema 定向读取；工具不可用或未暴露时，不猜接口、不声称已读取。
7. **最新备注优先**：当前需求版本中明确标注为补充、修订、纠正或最新说明的备注，优先于正文原有表述，只覆盖其明确涉及的业务规则；正文未被备注修改的部分继续有效。若备注与正文冲突且无法确认先后或含义、并会实质改变 Oracle/测试范围，列明双方来源并向用户确认。
8. **备注完整性**：`keywords` 非空可以确认有备注，不能据此确认备注比正文更新；需求级 `lastEditedDate` 不是备注独立更新时间。备注字段明显截断、疑似达到长度上限或评论分页不完整时，不得把片段当成完整备注，应直接请用户提供完整内容，不探索突破字段限制或反复调用接口；用户未提供时将受影响规则标为待确认/部分证据，不编造、不静默忽略。管理类扩展字段（如排期备注、负责人）只有在与本任务业务规则相关时才作为业务依据。

## 事实分类

分析时区分：

- **已确认事实**：需求正文、用户明确确认或可靠来源直接支持。
- **合理推导**：由已知业务规则推导，但不是来源直接陈述；说明推导依据。
- **待确认事项**：缺少证据、存在歧义或需要业务裁决。

不得把推导伪装成需求原文，不得编造字段含义、业务口径、权限、数据状态或页面行为。

## 权限和前置条件

- 普通查询条件默认视为当前测试场景可见。
- 没有需求或可靠证据时，不得假设查询条件受权限控制，也不得添加“已配置查询权限”等前置条件。
- 特殊账号、权限、环境或数据状态只有在需求或实际测试条件明确要求时才补充。
- 不将默认灰度环境、个人账号等一般经验写成绝对规则。

## Git 与 SQL

- 需求分析和用例设计默认不读取 Git、不执行 Git Fetch。
- 代码相关的开发提测影响分析由用户提供“需求编号 + 提测点”触发，遵循对应工作流。
- 不默认生成 SQL；用户明确要求时作为独立能力处理。

## 输出范围

- 用户仅提供需求编号且无明确任务意图时，默认给出简要需求分析，不自动生成正式用例及 Markdown/XMind/Oracle/Manifest。
- 用户明确要求需求分析时，按问题深度解释业务目标、变更范围、关键规则、风险及待确认事项。
- 用户明确要求正式测试用例时，将本文件识别出的业务事实传递给测试设计和独立 Oracle，不重复要求用户确认已经明确的事实。

## 待确认事项的说明与交互

只有当缺失、冲突或不明确的事实会实质改变业务规则、计算结果、预期判定或本次测试范围时，才向用户提出确认。先检查当前需求正文、用户已经确认的决策和可靠证据；不得把能够依据现有事实完成的分析转交给用户，也不得重复询问已经明确的规则。

每个会实质影响业务规则、计算结果、预期判定或测试范围的确认点，**必须表达以下四类信息**。四类信息可以合并成简短、自然的业务语言，不要求固定栏目、固定顺序或逐项单独成段，但不能省略其中任何一类：

- **业务问题**：明确当前需要确定的具体业务规则或范围，避免只抛出抽象疑问或技术缩写。
- **已知背景与依据**：说明需求、现有规则或可靠证据已经明确的内容；如来源冲突，应指出冲突双方，不把推测写成事实。
- **为什么需要确认**：明确指出现有需求或证据缺少/冲突了什么，以及为什么仅凭当前信息无法可靠判断、需要用户作业务裁决。
- **影响范围**：说明该判断会影响哪些业务义务、计算口径、页面/流程、测试场景或预期，并区分暂不能定稿的部分与不受影响的范围。

**选项和建议不是必填项，按证据决定是否提供**：存在真实且有依据的业务分歧时，可提供通常 2–4 个选项并解释各自含义，同时允许“其他”或自然语言回答；没有可靠选项时不编造。只有证据足以支持倾向时才给出建议，并说明依据；否则明确表示目前无法推荐。

推荐呈现形式（仅供表达参考，不是固定栏目；四类必需信息均须表达，可合并成简短自然语言）：

**待确认 N｜业务主题**

- **已知背景与依据**：当前需求或证据已经明确的事实。
- **需要确认的业务问题**：当前无法确定的具体业务规则。
- **为什么需要确认**：现有资料缺少或存在什么冲突，因此无法可靠判断，需要用户裁决。
- **影响范围**：受影响的页面、计算、业务场景或预期，以及不受影响的范围。
- **选项**：仅在存在有依据的真实选项时提供，说明各选项对应的业务规则和结果，并允许“其他/直接描述”。
- **建议**：仅在证据足以支持倾向时提供，并说明依据。

这只是普通 Markdown 的表达参考，不是强制表单或客户端 UI。

多个相互独立的确认点可以编号后一次列出，允许用户按编号/选项批量回答；若问题之间存在依赖，则先问最关键的一项，避免一次堆出难以回答的问题。用户可以只回答其中一部分，也可以完全自由地描述，不强制固定格式或交互表单。可示例提示“可以回复 1-A、2-C，也可以直接描述实际规则”。

业务确认与任务控制必须分开：选择某项业务规则不是“继续/仅生成指定范围/取消”之类的任务控制指令；不得要求用户用“全写”等任务口令代替业务答案，也不得把业务选项混入任务控制选项。

收到回答后，按用户原意更新已确认事实及 Oracle，继续完成相关设计；只有回答存在实质歧义或与可靠来源冲突时，才针对该点提出必要追问。已确认事项不重复询问。未回答事项保留为待确认，不得自行选定选项或编造预期结果。
