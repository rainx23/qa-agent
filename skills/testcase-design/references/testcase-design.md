# 测试用例设计规则

## 设计目标

围绕真实业务操作和业务结果设计可执行、可判断的测试用例。用例应让测试人员能够理解执行动作，并根据明确预期判断结果。

业务用例优先；必要的接口、数据结构或其他技术验证单独分组，不把技术细节无差别混入普通业务操作。

## 复杂度与测试方法

由 AI 根据业务规则数量、影响范围、交互/数据逻辑、关键分支、依赖和证据缺口自适应判断简单/中等/复杂。

- 不机械依据需求正文长度、字段数量或页面数量分级。
- 不强制八大测试方法全套。
- 根据实际风险选择等价类、边界值、判定表、场景/状态迁移、组合验证等适用方法。
- 简单需求仍须覆盖其真实业务义务；复杂需求按风险展开必要边界、状态、组合和异常场景。
- 发现新信息时可以调整复杂度和设计深度。

## 场景覆盖与去重

1. 从需求中的业务规则、操作、结果、限制和异常条件识别测试目标。
2. 覆盖正常路径及有业务依据的边界、异常、状态变化和交互。
3. 不为凑数量、方法或固定分类创建重复用例。
4. 同接口/同前端/同后端代码且验证目标相同的重复技术验证尽量复用。
5. 不同页面存在不同业务行为、条件或结果时，不得仅因代码复用而合并。
6. 可以参考知识库辅助识别关系，但知识库中的推导或待证内容不得冒充已确认事实。

## 用例结构

用例主体保持：

- 标题；
- 按需前置条件；
- 操作步骤；
- 与每一步对应的一个或多个预期结果。

具体规则：

- 标题表达“业务场景 + 核心验证目标”，清晰、具体、可区分。
- 普通业务用例将页面路径融入第一条实际操作步骤，不额外增加纯导航步骤；只有导航行为本身是测试目标时才单独设计导航步骤。
- 前置条件只描述执行前必须满足的业务状态；不需要时省略。
- 测试数据仅在数据复杂、多个步骤共用、组合较多或需要集中说明时单独组织；简单数据直接写在步骤中。
- 每个操作步骤必须有可判断的预期结果；不能只写“验证正常”。
- 不增加独立的“适用页面”字段，不增加无意义的“操作步骤”父节点。
- 不编造真实账号、数据、接口响应或环境状态；缺少真实值时描述所需数据特征。

## 分组和优先级

- 根据实际业务流程、模块和测试目标动态决定分组名称、数量及层级。
- 不设置固定分组清单或固定分组数量；不创建空分组。
- 优先级统一使用 P0–P4，由 AI 根据业务影响、数据风险和功能重要程度判断。
- 不按用例顺序分配优先级，不设置各等级数量配额，不要求每个需求包含全部等级。
- 参考语义：P0 为核心业务不可用或重大资金/数据风险；P1 为重要业务功能、关键计算或核心流程风险；P2 为一般业务功能、常规异常和边界场景；P3 为低风险展示、兼容性及辅助功能；P4 为极低风险且不影响主要使用的体验细节。

## 禁止事项

- 不把 SQL 作为默认用例步骤或必备交付。
- 不为满足平台字数限制而静默截断步骤、预期或业务条件。
- 不把内部 Case ID、Revision、来源和 Oracle 标识展示成普通用例节点。
- 不因不确定项而跳过整个合格范围；应明确待确认事项及其影响。
