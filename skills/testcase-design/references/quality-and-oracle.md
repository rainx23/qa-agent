# 质量保障与独立 Oracle 规则

## 独立 Oracle

Oracle 用于从需求来源独立识别“什么结果才算正确”，不能从已经生成的用例预期反向复制或归纳，否则会形成自证。

Oracle 应基于需求来源及已确认业务规则，识别与当前需求相关的：

- 业务义务和必须满足的规则；
- 输入条件与适用范围；
- 关键计算、字段关系及数据口径；
- 状态变化、操作结果和限制；
- 重要异常及边界行为；
- 已确认事实、推导和待确认事项。

### 首批可执行格式：testcases/oracle.json（schema_version = "1"）

AI **先依据需求事实独立编写 Oracle**，再用其检查用例是否覆盖业务义务；不得读取已生成的用例预期来反向填充 Oracle。一个业务义务可以被多条用例覆盖，Oracle 不保存用例步骤或整份需求文本。

结构示意（仅演示格式，业务内容不能直接当真实需求事实使用）：

```json
{
  "schema_version": "1",
  "requirement": {"id": "<需求编号>", "name": "<需求名称>"},
  "sources": [
    {"id": "S1", "description": "需求正文", "locator": "<需求正文定位>"}
  ],
  "obligations": [
    {
      "id": "O1", "source_ids": ["S1"],
      "rule": "根据当前筛选条件查询",
      "expected_outcome": "结果仅包含符合条件的数据",
      "certainty": "confirmed"
    }
  ],
  "open_questions": [
    {"source_ids": ["S1"], "question": "空状态文案是否指定？", "impact": "文案断言尚不能确定"}
  ]
}
```

- `sources` 记录可定位的真实需求材料/用户确认来源；`locator` 写实际可追溯位置，不得编造；`source_ids` 必须指向已登记来源。真实需求可以使用多个来源。
- `obligations` 表达独立的业务规则及对应正确结果；`certainty` 只能是 `confirmed`（来源直接确认）或 `inferred`（合理推导），推导必须在分析中注明依据，不能冒充已确认事实。
- `open_questions` 记录无法证实的业务事实、问题和影响范围；没有未决事项时可省略该字段，不得用虚假确认填补缺证。局部未决按已确认的部分交付规则处理。
- Oracle 不存储 Case ID、用例预期副本或固定业务关键词，不依赖用例数量。AI 负责业务义务的完整性、事实可信度、用例覆盖和独立性的语义复核。
- `skills/testcase-design/tools/artifacts.py` 只校验字段、来源引用和 Markdown/Oracle 需求身份一致性；工具输出 `STRUCTURE_PASS` **不证明** Oracle 的来源真实、业务预期正确、覆盖完整或独立性达到验收要求。

## 质量检查

正式用例设计至少关注：

1. 需求中的关键业务义务是否得到覆盖；
2. 用例操作是否真实、明确、可执行；
3. 每个关键操作是否有对应且可判断的预期结果；
4. 用例是否存在无依据假设、重复覆盖或遗漏的关键分支；
5. 用例与独立 Oracle 是否一致；
6. 正式 Markdown、XMind 和 Manifest 是否满足各自结构与一致性要求；
7. XMind 生成后是否已重新读取/解析实际文件，并逐项核对需求名称、业务分组及顺序、用例标题及数量、优先级、按需前置条件/测试数据、操作步骤及顺序，以及每一步对应的预期结果内容和数量。

### 正式发布前的一次性语义自审

正式发布前由 AI 完成一次整合自审，重点检查：

- Oracle 的每项业务义务是否落实为具体、可执行且可判定的用例；不能只因标题或关键词出现就认定覆盖。一个用例可以承接多项义务，但必须实际执行相应场景并断言各项结果。
- 对需求明确给出的枚举集合，逐项核对允许值是否分别有验证；只有来源或业务规则能够证明等价时才可采用代表值，并说明代表依据和未覆盖边界。不能用“任意一种”替代明确枚举的逐项验证。
- 对二值条件或正反向筛选，分别验证两种取值对应的实际结果；不仅检查选项存在，还要检查哪些数据被保留、哪些数据被排除。
- 不同页面和查询入口分别核对覆盖归属。快捷查询、通用查询或不同页面的行为不能相互代替；只有同一用例实际执行各相关页面/入口并分别断言结果时，才可共用覆盖。不能仅因底层代码复用就推定业务行为相同。
- 对跨时间、跨对象或关联粒度筛选，准备同时包含命中与未命中记录的可区分数据，验证正向和反向筛选各自应保留及应排除的记录；检查过滤是否误提升到客户、对象或全时间范围粒度。
- 每个分组名称是否准确概括组内用例；是否存在用例放错分组、遗漏或重复。
- 每条用例的标题、前置条件、测试数据、操作步骤和预期是否描述同一业务场景，数据取值与预期是否相互一致。
- 每个关键操作是否有明确、可判断的业务结果；是否存在需求来源不支持的假设、伪造数据或过度断言。
- 仅检查需求实际存在的枚举、二值条件、页面/入口和关联粒度等维度；检查深度按风险调整，不套用固定矩阵，也不为凑齐场景制造用例。

发现业务义务未覆盖、枚举值漏项、二值结果缺失、页面/入口覆盖混用或关联筛选缺少应保留/应排除断言时，先修正 `.qa-work/` 中的正式候选草稿，再对受影响内容复核。若需求事实不足以完成某项验证，明确记录缺失证据和影响；只有在交付范围确实被明确限定时才按部分交付处理，不得把未解决的范围内缺口标为完整交付。完成自审、产物生成和确定性校验后才允许正式发布；不把发布后的内部返工变成同一任务的第二个正式版本。该自审是 AI 语义判断，不得将其伪装成 Python 自动 PASS。

检查深度随需求复杂度和风险调整，不要求所有需求执行同样数量的审查轮次。

### 既有功能保留与变更前基线核对

当需求要求部分既有查询条件、字段、页面行为、模板/配置、导出/排序等保持不变，或本次只删除/修改其中一部分时，在语义自审中核对保留范围；不把此规则机械套用到没有既有功能保留要求的需求。

1. **先确定保留清单**：当前需求或可靠权威材料已经明确列出完整保留范围时，直接逐项使用该清单，不额外要求变更前基线。
2. **清单不完整时再找基线**：如果无法确定完整保留范围，且这会影响回归完整性，使用独立于变更后页面的变更前证据，例如页面/导出快照、配置或字段清单、接口契约、版本化产品资料或用户提供的历史材料。不得只凭变更后页面反推变更前完整清单。需求分析和用例设计默认不读取 Git；历史用例或 Oracle 仅可作为定位线索，不能单独证明当前业务事实。
3. **检查存在与可用**：对需要保留的项目，既检查控件/字段/入口仍存在，也按其业务用途验证实际行为和结果。明确列出的项目原则上逐项验证；只有可靠证据证明行为等价时才采用代表性验证，并说明代表依据及覆盖边界。
4. **证据不足时限定结论**：明确记录缺失的基线/证据及受影响范围，不得宣称完整保留范围已验证通过；继续设计不依赖该证据的独立场景。是否提出确认或采用部分交付，遵循现有未决事项和部分交付规则，不因这一条自动阻断整个需求。

## 轻量质量保障

- 不建设 Python 业务规则引擎或测试方法引擎。
- 不设置固定质量评分、八大方法全套、全量风险矩阵或重复全文审查门禁。
- 只有存在高组合或遗漏风险时，才按需建立覆盖核查。
- 必要的确定性检查聚焦 Case ID、结构、文件指纹、版本账本和 Markdown/XMind 一致性。
- 质量检查不能因为节省 Token 而跳过必要业务覆盖。

## 未决事项与部分交付

- 未知事项必须列明具体问题、缺失证据及影响范围，不得编造结论。
- 每项会影响用例设计的未决事项，应映射到具体业务义务、场景或预期结果；说明哪些判断暂不能定稿，以及哪些范围不受影响。
- 未确认问题只阻塞依赖它的业务判断和用例；不依赖该问题的已明确范围继续分析和设计。不得因存在一个待确认点就停止整个需求，也不要求用户先回复“继续”才处理独立范围。
- 对受影响范围，如果缺少业务规则就无法形成可靠预期，应将该判断保留为未决，不得用猜测填补；该范围的其他独立验证点仍可单独设计。
- 用户可以只回答部分问题，也可以直接用自然语言补充。对已回答项，将回答纳入已确认事实和 Oracle 并继续；未回答项继续保留为未决。只有回答存在实质歧义或与可靠来源冲突时，才针对该点提出一个必要追问。
- 部分交付必须保留已交付范围、未决范围及后续核对关系。当未决事项只阻塞部分范围，而其他范围已完成且满足设计/产物质量要求时，按既有 `PARTIAL_DESIGN_READY` 资格交付合格范围，并明确剩余范围；该资格不代表完整设计或业务验收通过。Manifest 的 `delivery_status=partial` 仍按 `artifact-format.md` 规则记录；部分设计资格及 `partial` 产物均不得用于禅道/ACE 导入。不得把待确认事项自动扩大为整个需求 BLOCKED。
- `partial` 不得用来掩盖本可修正的设计遗漏；部分交付不等于完整交付。
- 不因非关键缺证、可选资料不可用、SQL 未生成或未执行页面验证而无条件阻断全部合格用例。
- 继续使用现有 `open_questions` 结构记录未决问题及影响；对话中的选项仅用于辅助用户判断，不新增确认 JSON 字段、`confirmation.json` 或数据库。

## 验收状态边界

必须区分：

- **设计完成**：AI 已完成对应范围的需求分析和用例设计。
- **工程校验通过**：产物结构、身份、指纹或转换一致性等确定性检查通过。
- **静态分析结论**：基于源码推导的结果，不等同于运行结果。
- **运行态验证**：真实页面、接口或系统执行证据。
- **业务验收通过**：由用户根据实际业务验证结果确认。

用户未反馈人工测试结果时，不推断人工验证通过/失败、不统计实际 Bug 数量，也不将需求标记为人工验证完成。
