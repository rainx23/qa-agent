# P4 按需证据复核与新鲜度管理｜第三批

本文件为 P4 的**按需**附加规则，不是定时扫描器、全量知识重验或新的状态系统。仅在用户要求核实知识当前适用性、当前任务已有相关代码/配置变化证据、相关正式知识与新证据冲突，或 P1/P2/P3 确实需要判断“当前是否仍有效”时，由 `SKILL.md` 定向加载。没有相关性时只按原知识检索/维护流程执行。

## 确定对象与证据适用范围

1. 先确定**稳定业务对象与具体判断**：业务模块、页面/Tab/变体、字段/接口/配置 Code、查询模式及适用业务范围。只查关联的知识类别与源位置，不以整个模块或所有 SHA 为复核单位。
2. 区分来源性质：用户确认的业务口径、需求文档、Git 指定版本源码、DEV 通用查询配置、ETL、真实页面/API/数据执行及历史 Bug 是不同证据层。**一种来源变化不自动否定其他来源**：代码更新并不能证明业务规则已更改；配置更新不能证明业务代码部署；Git 分支 SHA 不能证明环境已实际部署。
3. 使用任务内**已有可信版本信息和相关证据**，不为了 P4 调用强制 Fetch、checkout、扫描全部仓库或读取所有 DEV 配置。只有当前主任务已依其规则取得真实当前源码/配置，或用户明确要求对该对象定向核实且具备权限时，才检查受影响入口。工具失败停止无效重试。
4. 如果目标任务没有可核实的当前 SHA、配置读取结果或来源证据，返回 `UNKNOWN / CURRENT_NOT_VERIFIED`，可保留旧知识作为**历史定位线索**，不能声称现在仍已验证。没有证据证明变化时也不能断言它已经失效。

## 源码版本与 SHA 的定向核查

对每条代码/调用/页面绑定技术知识，最少明确**证据版本、目标版本、仓库、源码入口和适用范围**：

| 现有与目标证据 | 决策 |
|---|---|
| 可信目标 SHA 与已有验证 SHA **相同** | 该代码事实对**同一版本与适用范围**可复用；不据此宣布运行态 PASS 或生产已部署 |
| SHA 不同，但已在两个确定版本中核实**相关文件/方法/绑定逻辑未发生影响该事实的变化** | 复用对应业务事实，必要时追加新的适用 SHA 和复核入口；不得仅凭 SHA 不同标记冲突 |
| 相关源码确有变化，但是否改变业务绑定/行为仍不明确 | 对当前目标标 `review_required` 或 `CURRENT_NOT_VERIFIED`，说明变更入口及缺失证据；保留旧版本事实 |
| 新源码与旧事实在**同一适用范围**上明确矛盾 | 将当前适用性标待复核，保留旧事实、版本和新旧来源，不静默覆盖；由确认后的新证据支持受限范围的新结论 |
| 无目标 SHA、仓库不对应、证据读取失败或仅知道远端分支名称 | 不假定新旧一致或已变化，输出 `UNKNOWN`，主任务继续可做的分析 |

**单需求提测比较只遵循本次 P2 已选定的组织与仓库基线**：如已确认使用个人/特性分支对生产基线比较，集成分支仅用于同步核对，不得代替单需求 Diff。其他技术层以 `code-impact-analysis/submission-impact.md` 和可选本地 `config/organization-profile.json` 约定为准，不在 P4 写死具体分支名。P2/P3 已冻结的 SHA 按需复用；单纯知识检索不得主动全量 Fetch。

## DEV 通用查询配置的新鲜度

1. **只针对已确认的通用配置对象**（列表列字段、快捷查询、通用筛选等）读取当前组织权威配置环境；环境可由本地 `config/organization-profile.json` 的 `config_evidence.environment` 指定，不将某一组织的 DEV→生产流程推断为所有组织通用策略。
2. 当前值确有必要时，按实际可用的只读 MCP/API Schema 定向查询具体对象，并核对字段、启用状态、展示属性及筛选参数实际传递与生效的证据；配置 Code 存在不能单独证明运行行为。
3. 记录对象、查询环境、时间、相关属性摘要及证据定位；无需保留完整响应或定时快照。当前环境配置不自动证明其他环境的值或实际部署，必须有独立证据。
4. 返回空数据、Code 未定位、API 不可用/安全阻断、缺权限、响应不完整分别标 `UNKNOWN` 及原因；**不能把失败/空值推导成配置已关闭或不存在**，更不能用旧 DEV 快照冒充当前值。
5. **默认不比较历史 DEV 配置**。只有用户要求历史变化或 Bug 根因确实依赖历史，且有可信历史快照/记录时才比较；无可靠历史证据时明确 `HISTORY_NOT_AVAILABLE`，不编造变更时间/责任版本。

## 冲突保护与最小状态修订

- 新旧证据必须先核对是否**同一稳定对象、相同业务模式、版本、环境及生效范围**。不同环境、历史版本或业务变体的合法差异，不能直接视为同范围事实矛盾。
- **仅查询/解释**：指出当前适用性与缺口，不写入知识；**用户明确授权模块知识维护**：按 `knowledge-update.md` 的最小增量规则，只修订直接受影响对象，可用现有 `review_required`、`review_reason`、`conflict_evidence` 和必要范围/版本证据；无需迁移整个六类 JSON。
- 有冲突时保留“旧事实＋旧来源/版本”和“新事实或矛盾线索＋新来源/版本”，标明尚未解决的判断点；冲突未解决不得把当前版本标 `formal_reusable`。**不能因为代码版本新就把原来用户确认的业务规则改为新规则**；技术事实更新和业务期望变更需要各自证据。
- 新证据在相同适用范围确实核实且冲突解决后，可以将受影响技术关系更新为对应版本的 `formal_reusable`；原用户业务确认、其他对象的候选/运行 `NOT_RUN` 不得无据晋级或被覆盖。写入仍需先读后写、版本冲突重读、写后回读，失败报告 `WRITE_NOT_VERIFIED`。
- 不新增状态账本、TTL、“SHA 不同即过期”门禁、全量定期巡检、额外 Python 工具或第七类 JSON。证据保留以足够支持追溯为限。

## 最小交付

对本次受影响对象，返回简要 **对象/知识定位 → 当前核实范围 → 结论（可复用 / 待复核 / UNKNOWN）→ 依据（SHA 或 DEV 读取时间）→ 尚未验证项与是否发生写入**。实际进行代码定向核对或 DEV 读取才可称相应层面验证，不能把本规则的静态测试说成真实配置/源码版本复核。P1/P2/P3 复用 P4 仍属于可选辅助，未取得知识时继续主任务；P3 缺少有效页面默认条件时依其自身规则定向探查，不能自行补写未授权的 P4 模块知识。
