# P4 知识发现与增量维护｜第二批

本文件仅在用户明确要求**建设/补充/更新某业务模块知识**时，或后续已正式接入的主 Skill 明确触发 P4 沉淀步骤时读取；不在只读检索时加载。P1/P2/P3 运行时自动沉淀接入留待后续批次，不因本文件存在就增加它们的必经步骤。当前仅建设通用维护规则时，不自动新建任何模块/Tab、不开展跨模块默认条件专项，也不修改具体业务知识。

## AI 发现有价值的知识

1. 先明确用户授权的业务系统/模块/Tab 或范围，恢复当前对话与用户最新明确确认的授权范围；存在个人本地决策记录时可作为维护参考，但不得成为公开 Skill 的强依赖，读取目标模块 README 和本次相关类别。若用户没有授权拓展某个已暂停的 Tab，不利用“自动沉淀”绕过它。若用户仅讨论架构或要求只读查询，不写入。
2. AI 根据**本次实际已取得**的需求正文、用户业务确认、指定版本的源码/调用链、当前环境配置读取、测试记录或 Bug 回执，提取可复用对象：稳定业务规则、页面/交互/字段与其技术绑定、代码/数据定位入口、代表性质量经验；一次性 SQL 结果、临时调试数据、敏感业务明细、重复文案和没有后续复用价值的信息跳过。不得为建知识强制 Fetch 全量 Git、扫描所有配置或拉取新的无关材料。
3. 分离**事实内容**与**证据性质**：用户明确确认的业务规则才可作为用户确认的正式业务规则；需求文档是需求来源，不自动代表用户已确认；具备仓库、相应版本完整 SHA、文件/方法或可靠配置读取依据的技术关系可作为对应版本的技术事实；历史 Bug/测试是历史经验，不等于当前仍有问题；AI 语义推测仅能为候选。来源不足时明确 `UNKNOWN`/待核实，**不得虚构来源、SHA、环境、时间或用户确认**。
4. 一个页面/业务对象可以关联多个组件、API、配置和源码，反之亦然；技术关系须有可追溯的实际绑定、调用或元数据。业务叫法不同不单独创建新页面或接口。

## 目标文件与状态

沿用 `knowledge/modules/<业务模块>/`，一级模块以业务域划分，不以仓库/单个页面划分；新模块**仅在用户明确要求且业务边界清楚时**建立。仅有实际知识的类别创建 JSON，不创建空类文件或第七类。已有文件按原 `schema_version`、`module_id`、`category`、对象数组名、已有字段结构维护；不要求全量迁移为统一 schema。需要新字段时仅对相关对象轻量新增。新建类别文件沿用当前 `schema_version=1`、模块 ID、类别键和与该类别对应的对象数组；目录 README 为业务可读入口。

类别：`business-rules.json`、`pages-functions.json`、`interactions-fields.json`、`interfaces-configs.json`、`code-data-locator.json`、`quality-experience.json`。代码定位类只保存轻量入口与版本证据，不复制整段实现/完整配置快照。跨类引用优先现有稳定业务对象 ID；无现成 ID 的历史对象不为“统一格式”批量改号。

知识语义只分三种：**正式可复用**（`formal_reusable`）、**候选待核实**（`candidate_pending_verification`，既有 `pending_user_review` 表示等待业务确认）、**待复核**（新记录可用 `review_required`，且必须有复核原因与冲突证据）。保留旧记录既有状态字段，不能将 `resolved` 质量处置状态当作“正式/运行 PASS”。对缺失状态的旧对象，读时视为未知，不强行补正式。状态/业务确认/技术核实/运行验证分开记录；`NOT_RUN` 不能被自动改为 PASS。

每条新知识至少包含可定位的稳定对象标识（对象类型允许使用 page ID、配置 Code、API Code、仓库＋文件＋方法、或同类唯一记录 ID）、业务含义、适用范围和实际可追溯来源。按实际证据类型记录 `business_confirmation` / `technical_verification` / `runtime_validation` 或现有等效字段；证据需要 SHA/环境/时间时仅填写真实取得的值。没有真实证据时只可作为非正式候选，**不得凭 AI 文案自行生成伪证据**。

## 增量去重与最小编辑

针对每个候选知识，只在**目标模块的相关类别**检索可能的同一对象；先确认业务含义、身份与适用范围，再执行以下决策：

| 判断 | 处理 |
|---|---|
| 已有同一稳定对象，内容及证据无变化 | `SKIP`，不改文件 |
| 已有同一对象，新证据与原事实兼容 | `UPDATE`，仅补充该对象的必要字段、关系、证据，保留原身份与有价值来源 |
| 在目标类别中无同一稳定对象且有足够证据 | `CREATE`，新增对象到原类别数组，避免重复 ID/Code |
| 只有名称相似、业务身份有歧义 | `CANDIDATE`，不与已有对象合并；证据足以独立标识时才允许新增候选，否则仅列待核实 |
| 事实、绑定、适用版本或来源出现冲突 | `REVIEW_REQUIRED`，**不得用新值静默替换旧值**；保留双方关键值与来源，标记复核原因，冲突未解决不作为当前正式事实 |
| 必要来源/身份缺失、文件不可读或用户禁止该范围写入 | `BLOCKED`，不写入受影响对象，说明缺口 |

注意：同一 API 被多个页面复用不构成重复页面；同一页面的不同业务变体不按名字合并。更新只能修改相关对象；不同接口、配置、Tab、上下游、历史候选不可因本次任务被顺带重排/删除。对不同版本的事实，保留适用 SHA 和范围，不将“当前代码改动”直接抹去旧版本事实。

## 最小写入与回读

1. **先读后写**：读取目标 JSON 当前完整对象及必要上下文，检查模块/类别身份与既有对象键；形成简短计划，包含 `CREATE/UPDATE/SKIP/CANDIDATE/REVIEW_REQUIRED/BLOCKED`、稳定标识、来源和对应类别。无需逐条让用户批准已被明确授权的模块知识任务，也不将结果不确定的操作盲目重试。
   如同一对象出现**源码版本/DEV 配置适用性疑问或新旧证据冲突**，先按 `knowledge-freshness.md` 定向复核再决定 `UPDATE / REVIEW_REQUIRED / UNKNOWN`；不能因 SHA 不同就直接覆盖旧知识，也不能因为检索历史配置失败就推断当前配置不存在。未涉及版本/配置的新建或兼容补证，不额外加载该文件或调用 Git/MCP。
2. 优先使用执行环境已提供的受控文件编辑能力（支持快照/版本对比时使用），**只提交受影响 JSON 的最小编辑**；写入前若版本已变化，重新读取受影响文件并重新判定，不覆盖其他会话的编辑；不能可靠保证写入对象与证据完整时停止该对象。不要覆盖整个文件为简化后的 schema。
3. 写后读取相同目标：JSON 可解析、`schema_version/module_id/category` 未变化、对象标识唯一、目标数据及证据正确、非目标对象未损坏，正式/候选/运行状态没有无据升级；失败立即报告 `WRITE_NOT_VERIFIED`，不能宣称更新成功。读取与编辑工具均不可用时报告 `KNOWLEDGE_UNAVAILABLE`，继续不依赖此知识的原任务。
4. 将新增或改动的**业务含义**用少量中文整理到模块 README/业务说明及本次业务验收清单（适用时）；明确业务确认、技术事实、候选和运行未验范围。说明文档不得替代 JSON 身份与证据。没有业务知识修改时不创建空验收文件。
5. 结果只报 `新增/更新/跳过/候选/待复核/受阻` 计数与关键对象，附实际文件位置、证据及用户需确认的少量语义点。**用户业务验收与工程检查分开**：文件写入通过不代表业务含义已验收、真实页面/API/SQL 已执行。

## 本批与后续阶段分界

本批建立用户明确授权维护任务中的 AI 发现与安全增量编辑规则；第三批 `knowledge-freshness.md` 只在当前版本/DEV 配置适用性或事实冲突影响结论时**按需复核**，不是每次任务自动扫描。P1/P2/P3 何时自主触发沉淀、持续/后台新鲜度监控与跨 Skill 真实联动仍为后续独立批次或不建设。未授权时不得变更已关闭、已暂停或本次未纳入范围的任何模块/Tab，不得擅自开展跨模块默认条件专项；无证据时宁可保留候选，不发布不可靠知识。
