# SQL Design｜编写、合并、验证与交付规则

本规则由 `skills/sql-design/SKILL.md` 加载，业务判断由 AI 完成；不编造表结构、业务预期或运行验证结果。**质量优先，简单次之**，不以减少 SQL 数量或 Token 为由减少必要场景。

## 需求变化驱动的独立验证（P2/P3 共用）

- **从需求变化推导验证，不依赖固定类型清单**：AI 先结合当前需求、已确认业务规则及适用基线，识别本次业务行为实际新增、修改、删除或改变的部分，再推导需要证明的业务断言、数据对象、适用条件和风险场景。不得要求需求必须命中预设的“新增维度/字段/查询条件/公式”等类别才触发分析；任何未预先枚举的变化也必须按其业务语义自主识别。示例只能帮助理解，不能成为穷举分类或机械检查矩阵。
- **先确定“正确应该怎样”，再找数据**：独立 Oracle 优先来自需求明确逻辑、用户确认的业务规则及适用的 P1 正式 Oracle。被测开发代码可按需帮助定位物理表、字段、调用链、配置和实际过滤，但不能因为代码当前这样实现，就把它当作正确业务规则；需求/Oracle 未说明的关键行为不得自行补成确定预期。
- **预期依据独立于本次被测开发结果**：Oracle 优先依据需求/产品明确提供的逻辑、上游库表字段、产品提供的取数 SQL、用户确认口径及适用的 P1 正式 Oracle。产品提供的上游 SQL/逻辑即使已经预聚合，也可以直接作为预期计算依据；不得仅因其不是明细表或已经聚合，就要求重新寻找明细或另造一套计算。禁止用本次被测变更产出的开发结果表/字段反推或替代预期。若需用 ADS 页面结果定位真实页面记录或比较实际值，必须先独立确定样本和预期，再将 ADS 作为单独的实际侧关联；ADS 不得反向筛选样本或参与预期计算。
- **样本必须证明目标场景成立且能回到页面/接口**：SQL 应返回真实可搜索的业务 Number/Code（必要时附内部 ID）、能证明该样本满足场景的关键输入/来源字段、适用业务条件，以及本次需要观察的页面/API 字段。样本筛选要围绕“什么真实数据最能验证这条需求逻辑”，而不是优先挑选 JOIN 复杂度、诊断字段数量或开发结果差异最大的记录。无法证明样本满足场景时，不将其包装成可执行案例。
- **区分设计阶段、SQL 执行结果和页面实际结果**：SQL 未由用户执行并回传前，AI 只能说明验证逻辑、预期计算方法、输出字段用途和执行方式；不得编造具体样本、单条记录的具体预期值、SQL 查询结果或页面实际值。V 的 SQL 可以按独立 Oracle 计算每条真实样本的具体预期，但这些值只有用户执行 SQL 并返回结果后才可确认。页面/API 的实际展示结果还须由用户实际查看并反馈，不能从 SQL 预期或开发结果推断。
- **SQL 结果返回后的操作化交付**：独立 P3 收到用户执行结果后，默认在聊天中按场景逐条交付，每轮一个完整场景；每条包含场景目标、SQL-01 对应逻辑/片段（注明此前一次执行，不要求重跑）、真实样本、独立 Oracle/计算依据/具体预期及页面/接口定位和核对方法。用户说“下一条”再展示下一场景；未反馈页面实际值的场景保持 PENDING。完整 SQL-01 只在尚未执行时于聊天展示一次，不得只给文件路径，也不得按场景生成重复执行 SQL。P2 委托调用继续由 P2 自己的 CHK/MV、verification-details.md 和既有推进规则管理状态与后续步骤，不启动独立 P3 人工验证会话。无页面入口时改为给出对应接口/数据核对步骤，不强行编造页面路径。
- **缺数据与缺 Oracle 分开处理**：SQL 执行成功但无样本，只能说明当前条件下未找到记录，不能直接证明业务逻辑不存在或正确；查询失败、条件/环境不匹配、样本缺失、Oracle 不明确分别说明。缺证只降级受影响的验证点，不伪造样本或预期，也不妨碍交付其他已有可靠依据的部分。
## 数据验证点与 SQL 编号

- 按 AI 根据需求逻辑和实际变更识别的“必要独立数据验证目标”建立覆盖，不按用例条数或页面全部指标机械铺开。对每个必要目标，F（寻找真实样本）与 V（按产品口径独立计算预期）是必须完成的内部职责；默认不分别交付 SQL-F/SQL-V 两份 SQL。用户明确收窄为单独找数/单独对数等窄任务时，再按实际目的执行 F-only/V-only。P2 `submission-impact.md` 委托 P3 时遵循同样的 F/V 业务职责，但 SQL 生成、格式和检查必须由 P3 规则负责。
- P2 数据验证目标包括真实业务记录/字段/维度映射、业务过滤、对象关联、数据转换/同步、计算/聚合、跨层级、列表/汇总/下钻及数据一致性等；纯 UI 样式/布局/导航等没有真实数据断言的场景为 N。不是每个 CHK/MV/Case 都机械生成 SQL，只对独立数据验证目标建立覆盖。
- 每个目标保留：业务对象、页面/Tab/查询模式、测试目标、优先级、正式 Case ID（若存在）、CHK/MV、产品口径/Oracle 来源、F/V 内部职责及 SQL-01 中对应的场景 ID/查询逻辑。建立 `验证目标 ↔ CHK/MV/Case ID ↔ SQL-01/场景 ID` 映射，不要求为 F 与 V 分别建立可执行 SQL 文件或语句编号。
- F 用于找到能回到页面定位且满足目标条件的真实样本；V 用于按产品口径/Oracle、页面相同业务集合/有效过滤/时间范围/粒度计算对照预期。F 与 V 必须覆盖同一必要验证目标；缺少必要来源或业务口径、无法正确设计时标 `BLOCKED` 并询问用户；只有部分断言已经得到验证时才标 `PARTIAL`。`UNKNOWN` 只描述证据状态，不作为场景覆盖状态。
- 默认将所有可安全兼容的必要验证目标合并为一条 SQL、一次执行；在同一条 SQL 内保留逐场景的样本筛选、独立预期和结果标识。只有数据来源、执行引擎/方言、对象粒度、有效过滤、Oracle 或输出结构存在无法安全归一的真实冲突时才拆分，并说明原因。合并后仍须逐目标保留映射和断言，不得为减少 SQL 数量牺牲覆盖。
- 缺少需求必需的表/字段/关联/过滤/Oracle 时，不臆造、不按命名猜测，也不启动无目标全链路搜索；先确认需求明确提供的表能否直接使用，再按需查看有明确业务对应关系的当前组织已确认的业务表或视图。仍无法确认时暂停受影响目标并向用户询问，标记 `BLOCKED`；其他不依赖该缺口的验证继续。真实数据验证目标不得仅因缺证而标记 N；N 仅用于确实没有真实数据断言的场景。

## 独立需求 SQL：场景清单与页面字段对照

- **适用触发**：用户在任意阶段要求“编写/生成/设计某需求 SQL”或“补充/修改已有需求 SQL”时，按需求级独立 P3 任务执行；不要求已经提测，不依赖 P2。P1 正式基线存在时优先复用，不重复获取需求正文；但若 P1 来源记录未说明已读取备注/补充字段，或当前需求版本/更新时间变化、用户指出备注有更新，则按本节执行备注专项刷新，只读取当前备注相关字段并与 P1 Oracle/场景比较，不无谓重取完整正文。P1 不存在时使用当前对话/附件中的需求内容，关键事实缺失才定向补取或询问，不自动启动 P1/P2。
- **必交场景清单**：正式需求级交付必须包含 `scenario-coverage.md`，放在 `sql/` 目录并以 `category: sql`、稳定 `role: scenario-coverage` 登记 Manifest。逐项列出 AI 判断有必要验证的场景，至少包含：场景 ID/名称、页面/Tab/入口、验证目标、关联 P1 Case ID（若有）、产品口径/Oracle 来源、必要筛选/数据前置、类型（DATA_VALIDATION / N）、SQL-01 对应查询逻辑/场景标识、页面可核对字段及覆盖状态。不得只给 SQL 文件而不列场景，也不得把所有 P1 Case 或页面指标机械转成 SQL。
- **数据场景职责**：每个必要真实数据验证场景都必须完成 F（找到并证明真实样本成立）与 V（按产品口径独立计算预期）；两项职责默认整合在 SQL-01 中，不强制拆成 SQL-F/SQL-V。F 说明页面可定位字段及样本成立依据；V 输出必要原始输入/中间值/独立预期。纯 UI/导航等无真实数据断言场景标 N 并说明理由；缺少关键来源或口径时受影响场景标 BLOCKED，只有部分业务断言确实已得到证明时才标 PARTIAL。
- **场景与 SQL 双向映射**：清单中的每个 DATA_VALIDATION 场景都必须能定位到 SQL-01 中对应的 F 样本逻辑、V 预期逻辑、场景标识及输出字段；SQL-01 中每个场景分支也必须能反向定位到清单场景和产品口径/Oracle。多个场景合并时逐一列出映射，不因复用丢失场景级断言。

## 需求正文与备注的来源优先级

- P3 需要补取需求来源时，按全局规则同时检查当前详情接口返回的正文、`keywords`/备注、非空业务扩展字段及可用的独立评论/备注记录；不能只看正文，也不能把 `getMarkDownDetailById` 当作备注来源。
- 当前需求版本中明确标注为补充、修订、纠正或最新说明的备注，优先于正文原有表述，只覆盖备注明确涉及的规则；正文其他部分继续有效。备注与正文冲突且无法判断先后或业务含义、并会改变 Oracle/验证范围时，先向用户确认。
- `keywords` 非空可识别有备注，需求整体 `lastEditedDate` 不等于备注独立修改时间；无独立依据时不可仅因备注存在认定它更新。备注达到字段长度上限、明显截断或分页不完整时不得当作完整来源，直接请用户提供完整备注，不探索突破限制、不反复调用接口；用户未提供时局部标记证据不完整。
- P1 正式 Oracle/用例及历史知识可作为复用基线，但不能覆盖当前需求的最新有效备注；发现备注改变既有预期时，只重审受影响的 Oracle、场景和 SQL，不无关重做。

## 动态分析深度（L1/L2/L3）

### 选择原则

由 AI 自主选择，用户默认无需指定。根据业务计算复杂度、原始数据粒度与 JOIN 风险、指标影响、有效条件复杂度、独立验证难度及证据不确定性综合判断；**不按需求字数、用例数量、SQL 文件数、表数量或代码行数机械分级**。分析过程中按新证据自动升级或在确认风险较低时保持当前等级。

### 等级定义

| 等级 | 适用情况 | 必须完成的分析 |
|---|---|---|
| **L1 基础核对** | 指标含义和来源明确；单一业务粒度或已确认的一对一关系；条件简单；无复杂聚合、跨层级计算或明显历史异常 | 完成目标字段/来源、唯一键与粒度、有效过滤、独立 Oracle、F/V 分类及必要 SQL 检查；确认找数样本确实满足场景，验证 SQL 输出足以对照预期；对明显相关的错误算法做基本检查，不扩展无关路径 |
| **L2 业务语义分析** | 多表关联、一对多关系、聚合/条件聚合、多维度分组、参数组合、复杂过滤、比率、列表与汇总关系或多个对象参与计算 | 为关键指标建立简明口径：业务公式及 Oracle 来源、原始对象/唯一键、源粒度与目标粒度、JOIN/去重、有效数据集合和过滤、计算阶段/精度/空值规则；核查 JOIN 放大、分母/对象集合变化及关键边界；针对高价值假设构造至少一个适用的最小反例，并检查验证 SQL 是否能区分该错误 |
| **L3 深度验证** | 跨层级/多阶段聚合、多数据源或 ETL、跨页面/API 对账、共享核心指标、成本/金额/重量等关键指标、历史结果异常、多个竞争口径或证据相互矛盾 | 还原关键数据链路及每阶段粒度、对象键、过滤和计算；提出少量有证据依据的竞争假设并逐项验证；核对对账双方的输入对象集合、日期/业务条件和精度是否一致；存在可行路径时用独立 Oracle/计算路径交叉核对；对每个高风险 V 检查能否识别适用的漏行、重复、错分组/标签、错误过滤、精度/取整等反例，确保错误算法不会仍被判 MATCH；明确排除范围、证据边界及未解决事项 |

### 自动升级与停止条件

1. 从 L1 开始后，发现一对多/多对多 JOIN、跨粒度聚合、关键条件分支、复杂分子分母或列表/汇总关系时，按证据升级到 L2。
2. L2 发现核心指标可能被错误计算、多个计算层/数据源参与、对账集合不一致、验证双方存在共同上游漏数风险、独立 Oracle 无法成立或关键证据相互矛盾时，升级到 L3。
3. 任务一开始已明确具有 L3 特征时直接使用 L3，不必机械执行 L1/L2。若关键信息不足但可能实质影响结果，至少使用 L2；必要时只询问最关键的业务澄清问题。
4. 反例应针对当前算法和真实风险，不要求每次把所有错误类型逐项模拟。优先问：如果漏掉一个业务阶段、重复一条明细、改变分组维度、切换过滤条件或提前取整，当前 V 是否仍会错误地输出 MATCH？若仍会，先修正验证逻辑或明确降级其证明能力。
5. **独立性边界**：不能把同一被测表达式复制两次并称为独立验证；但产品明确提供的上游取数 SQL/业务逻辑可以作为预期依据，即使其结果已预聚合，只要它不是本次被测变更的输出或依赖本次被测结果反推。是否需要第二条独立计算路径，由当前业务风险和可用证据决定，不为凑 L3 或证明“数据必须明细”强行另造 SQL。
6. **静态与运行边界**：手算、合成样本和反例推演用于静态检验逻辑有效性，不代表 SQL 已在目标数据库执行。没有用户执行并回传结果时，数据库状态继续为 NOT_RUN；字段/函数/方言未在目标环境验证时保持相应 UNKNOWN/NOT_VERIFIED。
7. 当适用验证点已映射、关键指标口径/过滤/粒度已核实，重要假设已证实/证伪或明确受证据限制，验证 SQL 的关键误放行风险已处理，剩余未知项已局部化，且继续扩展没有新的可验证路径时停止。不得无边界扫描全库或追求理论上的绝对覆盖。

### 交付留痕

在 SQL 交付摘要中简要记录本次 L1/L2/L3、选择依据、自动升级情况及关键验证范围。只记录可审计的业务依据、假设摘要、反例/验证结果和证据边界，不输出隐藏思维链；报告长度不代表分析深度。等级提升意味着必要推理与验证更深入，不意味着机械增加 SQL 文件、SQL 条数或工具调用。

## 来源、默认条件与数据粒度

> 独立 P3 人工验证阶段的页面知识优先级：用户明确启动页面核对后，必须先定向读取目标页面/Tab/查询模式对应的 P4 正式可复用知识，核实真实查询入口、输入标识、默认条件、后端固定过滤和页面展示字段。找数结果必须包含页面实际展示、可直接检索的业务标识；内部关联/聚合键可保留用于 JOIN、分组和计算，但不得替代页面展示/搜索标识。**具体字段映射只保留在对应 P4 知识中，P3 通用规则不得写入具体业务模块、页面或字段映射。**若 P4 未命中或证据不适用，再按需定向核查可信源码/配置；不能确认时明确标 UNKNOWN 并询问，不得猜测。P4 仍不是阻断主任务的硬依赖。
1. **预期 Oracle 独立**：业务公式、去重、粒度与页面展示规则取自需求/产品明确提供的上游逻辑（包括已聚合的取数 SQL）、用户确认或适用的 P1 Oracle；实现代码只能帮助定位物理表、JOIN、配置与请求条件。不能用本次被测变更的开发输出反推预期。无法确认关键预期时明确待人工确认，不猜测。
2. **P4 优先但非强依赖**：只读查目标模块的页面有效默认条件、来源版本和证据，按对象/Tab/变体/查询模式判断适用性；知识不全、状态 UNKNOWN 或版本不匹配时，P3 自主追踪相关前端默认展示值、实际发送请求条件、DEV 配置/字典（适用时）及后端固定业务过滤。需要运行态证明的条件不能凭静态代码称“已实际生效”。
3. **Git 只在确有代码需求时 Fetch**：已有可信任务版本/SHA 时不重取；否则根据仓库登记、目标环境/需求线索选择明确的远端引用，依 P2 Git policy 定向 Fetch、冻结 SHA。既不能从本地分支名猜目标，也不能把远端 SHA 当作实际已部署。失败后报告受影响口径，不无限重试。
4. **有效过滤与默认时间**：记录页面默认业务过滤、用户选择过滤、后端固定过滤及它们的来源/适用环境。找数 SQL 默认忽略**行/数据权限**，可以用 `where 1 = 1` 起始，但不能因此删除其他业务状态、类型或后端固定业务条件。需求未明确时间范围时，默认使用上一个自然月，并按数据表实际有效的日期/分区字段落实；不依赖可能不准确的页面默认时间，用户可按实际刷数月份或测试需要调整。
5. **先确认粒度再 JOIN**：核实原始行与目标业务对象关系（一对一、一对多、多对多）、唯一键、去重与聚合；特别避免 JOIN 放大导致将明细行数误当作目标业务对象数量、分母集合不一致等。缺证不得凭表名猜计算逻辑。
6. **可追溯证据与表来源顺序**：优先直接使用需求/产品明确提供且可由当前执行端访问的库表和字段；只有其不可访问、关键字段缺失或确实不适合作为本次业务入口时，才定向查找有业务对象/字段/粒度依据的当前组织已确认的业务表或视图。替代关系不能仅凭命名推断；仍找不到或无法确认时停止受影响目标并向用户询问，不做无目标 MCP/全链路搜索。对关键表/字段与关联、默认业务条件、Oracle 及版本记录实际来源；源码引用注明仓库/文件及 Commit SHA，配置证据注明实际环境，静态与运行态事实分别标明；不能确认的条件/字段标明 UNKNOWN、BLOCKED 影响及需要补充的信息。
7. **真实用例证据须包含正文**：已有 P1 时按最新有效 Manifest 定位并核实关联用例业务预期与 Oracle，不把 ID/条数统计或模型记忆当作已核实覆盖。相同版本和内容的可信证据可复用，不必全文重复加载所有用例。

## 业务计算反证（只针对本任务高风险指标，不另建框架）

1. **先认指标，再认字段**：按“页面/API 指标 → 业务公式及独立依据 → 源表/字段及含义 → 原始对象唯一键/粒度 → 目标粒度 → 有效过滤 → 计算路径”建立简短的内部核对记录。字段名相近、同为金额/数量、或恰好来自同表都不能证明业务含义相同；需用字段定义、上下游赋值及 API 映射区分，证据不足只影响相关指标，不能凭猜测生成绝对值预期。
2. **每一步追踪数量归属**：区分主对象级值、明细级值、分摊值、聚合值；JOIN 前后对照主对象键的重复倍数。若主对象值在多条子行重复，先按有证据的唯一键取一次/预聚合，才可 SUM；若该字段本身就是明细级分摊值，则应在对应粒度求和，**不能一律 max、distinct 或 sum**。跨层级使用相同过滤、日期和对象集合。
3. **反证比机械自审更重要**：有一对多关系、跨环节或多个汇总层时，用小样本在脑中手算：一个对象两条子记录是否把主对象值翻倍；同一对象跨两个分组是否应各出现一次；同名近义指标值不同会怎样。此项验证用于发现推理矛盾，不是实际数据库执行；简单且无此类风险的单表查询无需强制扩写说明。
4. **独立对账必须可反驳**：先判断比较双方是否来自**独立计算路径、独立业务规则或独立原始核对依据**；两列若由同一 CTE/同一表达式直接复制，即使名称叫“二级/三级”“预期/实际”，相等只是恒等式，不具备发现错误的能力。仅有同源结果时可称“内部关系自洽”，不可称“已独立验证业务正确”。需要比较被测实现的行为，需单独标注实现口径并与独立 Oracle 的结果比较。
5. **业务有效性高于通过标记**：本轮每个高风险 V 说明指标依据、粒度变化、独立比较对象，以及一条能使错误算法暴露的反例。确实缺证时写明需补的证据和受影响判断，降级相关 V；不得用大段 UNKNOWN 代替必要源码探查，也不得把 `P3_SQL_SCOPE_PASS` 或 Manifest 验签当作业务自审。

6. **计算阶段与精度不变量**：明确“原始值 → 预聚合 → 总计/分子分母 → 比值 → 展示”各步骤的数据类型和精度；未有业务明文规则时不提前 `round`/截断中间金额与权重，也不将已展示的保留位数值回灌公式。不同 V 路径若用于等值交叉核对，必须先统一参与比较的对象集合、原始类型、计算公式与取整阶段；浮点结果按业务精度/容差核对。用非整数小数的反例测试提前取整是否改变比值，不能只用整数样本作证。
7. **业务判断先列前提再判断逻辑方向**：对“行数差、去重数相等、跨组重复”等结论先写**对象唯一键、分组键、空值、同组重复允许性**，再区分“充分条件、必要条件、双向等价”。`count(*) - count(distinct key)` 一般只表示相对全局唯一键的额外记录数；除非额外排除了空键与同组重复，不能全部解释成跨组记录。同组对象可能拥有不同明细行 ID，行 ID 唯一不代表同组业务对象唯一。用“只在同组重复 / 只在不同组重复 / 空键”反例试图推翻判断；不能把单向蕴含写成等价。

## SQL 合并原则

- 比较顺序：**需求/产品提供的数据来源 → 数据粒度 → JOIN/去重 → 产品计算逻辑 → 有效过滤**；同时确认执行引擎/方言、输出行粒度和结果结构是否兼容。产品提供的上游逻辑及预聚合结果可直接用于预期，不因其聚合形态自动降级。
- **默认一条 SQL、一次执行**：F（找真实样本）和 V（独立计算预期）是验证职责，不是两份 SQL。默认把本次所有可安全兼容的必要场景整合为一条完整只读 SQL，直接返回真实业务记录、页面定位字段、样本成立证据和独立预期/必要中间值。不得仅因 F/V 职责不同或场景数量多而拆分；只有明确的执行端、权限、数据来源、粒度、过滤、Oracle 或结果结构冲突导致无法正确合并时才拆分，并说明具体原因。
- **一次扫描、控制结果行数**：多个验证目标共享安全的数据基础层或过滤条件时，优先复用 CTE/中间结果并尽可能一次扫描完成，避免每个场景重复扫描月级千万行数据。需要合并不同场景结果时，可使用明确的 `scenario_id`/`result_type` 与 `UNION ALL`，但只合并每个场景少量真实样本/核对结果，不得把各场景全量明细直接 UNION ALL。查询平台最多返回 100 行，最终输出应主动控制在 100 行以内，并按场景均衡分配样本；优先保证必要场景均有可定位样本，避免单一场景占满结果。最终输出必须是可用于页面定位和核对的真实数据记录，不以汇总统计行替代找数结果。
- **安全复用条件**：只有执行引擎/方言、数据来源、对象粒度、JOIN/去重、有效过滤、产品口径/Oracle 和输出结构相同或可安全归一时，才复用同一查询。仅共享 API、表名、字段名或相似场景标题，不足以证明可合并。仅过滤场景不同且语义兼容时，优先用参数或明确的条件切换共享查询，并写清当前启用条件与备用条件。
- **必须拆分的情况**：数据源/执行引擎不同；对象粒度、JOIN/去重、有效过滤或产品 Oracle 冲突；输出结构无法安全归一；互斥条件无法明确表达；合并会导致全量大规模明细输出、重复扫描或性能明显恶化，且无法通过共享基础 CTE、分场景少量取样解决。拆分是为了保持正确性/可执行性，不为凑场景、Case 数量或方便编写。
- **诊断查询按需提供**：主查询已经输出足够的定位字段、异常标记和判定结果时，不再额外生成重复诊断 SQL；只有主查询无法暴露关键原因，或必须先找出样本才能执行后续核对时，才提供条件执行的补充查询，并标明触发条件。
- **交付执行清单**：默认只交付一个 `SQL-01` 完整查询，列明其覆盖的全部场景 ID、各场景 F/V 逻辑位置和结果字段，用户一次执行即可取得本次可合并场景的样本与预期。只有确实不能合并时才提供多条独立语句，并明确每条的技术原因、覆盖场景和执行顺序；不得把多个语句放进一个文件后宣称只需执行一次。不得按 Case/场景机械地一项一条 SQL，也不得为减少数量牺牲必要验证覆盖。
- 在不改变业务范围/聚合口径的前提下，优先按上月默认范围及有效分区字段预过滤、复用共享 CTE、先聚合后关联、控制样本数并减少 shuffle；避免因每个场景单独 UNION/子查询而重复扫描大表。不得为了性能牺牲覆盖或改变预期；F 的样本上限不得缩小 V 的完整计算范围。

## F：找数 SQL

- 返回有用的业务对象编码/主键、证明样本成立的维度、有效业务过滤和必要原始值；不堆砌字段。
- **页面标识字段必核**：SQL 找到的数据必须能定位页面对象。对目标业务对象，区分内部 ID 与页面展示/搜索的 Number/Code：先从已确认的页面配置/请求/源码/P4 线索判定页面使用的字段；当页面字段尚不明确且两者都真实可取时，F 同时输出两列，分别使用含义清晰的英文别名（如 `internal_id`、`business_number`）；说明复制哪列、到哪个页面输入，必要时注明查询匹配方式。严禁仅通过 `as business_number` 将内部 ID 伪装成页面业务编号。不可臆造编号/编码列名；若需关联，先核实来源、关联键与一对多行数风险，取不到时明确 UNKNOWN，保留可独立执行的可靠部分。
- 优先高优先级场景，先少量有代表性的真实样本，再扩展重要边界、重复、跨对象和列表/汇总风险。样本数量由场景决定，不统一 `limit N`。
- 聚合样本应给出成立证据（如明细/去重对象数量），不能只返回编码便认为场景已成立。
- 若 V 需要 F 返回的对象 ID，明确说明复制哪个字段到哪个参数；能够用 CTE/子查询可靠自动连接的，尽量提供直接可执行查询。
- **F 使用的 sample limit 不得进入 V 的完整汇总/预期计算范围**，除非业务 Oracle 明确只针对该样本集合。

## V：独立结果验证 SQL

- 先于 SQL 明确业务公式、真实原始数据、对象粒度、去重、分子分母、筛选范围、空值、除零、精度与日期规则；不得照抄被测 SQL 作为正确性依据。
- 输出用于核对的**原始输入 → 必要中间计算值 → 最终独立预期值**，对中间值及各列标注中文业务含义，说明页面或 API 对照字段。
- 高风险聚合/跨对象指标存在真正不同且可行的计算路径时进行交叉核对；同源复制两次的 SQL 不算独立证据。
- 将数学计算结果与页面展示（单位、精度、取整、空值表现）区别；无业务规则时标待确认，不擅自假设默认四舍五入或空值处理。
- 明细与汇总数据范围保持和目标查询条件一致。验证计算不随意先 `limit` 再聚合；对同名不同业务粒度指标分别核对。

## 结果判定与 SQL 交付可靠性

1. **联合判定的优先级**：仅对“所有子项都必须成立”的联合判断，先检查全部必要子项。任一子项已有明确 `DIFF` 证据时，联合结果必须判为 `DIFF`（保留具体差异类型），不得被另一子项的 `UNKNOWN` 覆盖；没有明确差异但至少一项为 `UNKNOWN` 时，联合结果为 `UNKNOWN`；只有全部必要子项均为 `MATCH` 才能判 `MATCH`。不得为了得到单一结果而把缺证伪装成匹配，也不得用 `UNKNOWN` 遮住已证实的差异。
2. **NULL 与映射状态分开处理**：先确认 NULL 的业务含义。只有当双方 NULL 确实代表同一种、允许视为相等的“无值/未配置”状态时，双端 NULL 才可匹配；一端 NULL、另一端非 NULL 时应判差异。若 NULL 的业务语义未确认，相关比较标 `UNKNOWN`。无映射、重复映射、维表不唯一或映射歧义不是普通 NULL，不得通过 `COALESCE`、`MAX` 或简单空值相等将其压成有效匹配；应保留歧义/未知结论。使用方言专属 NULL-safe 运算符前，先确认目标方言支持。
3. **SQL 围栏纯净且可独立执行**：SQL 代码围栏内只放 SQL 语句及 SQL 注释，不放 Markdown 标题、自然语言解释、表格或操作提示；说明文字放在围栏外。复制整个 SQL 围栏时不得混入非 SQL 正文。每段 SQL 必须包含自身依赖的 CTE；参数/替换说明写成 SQL 注释或放在围栏外。互斥场景应明确一次只执行哪一段，不把互斥条件拼成一条查询。
4. **条件替换边界必须唯一**：凡要求用户切换过滤条件，必须明确替换的起止范围。若替换对象是完整谓词 `and (...)`，说明从起始 `and` 到对应右括号整体替换；若只替换括号表达式 `(…)`，明确只替换表达式本身且不得再次添加 `and`。禁止使用“替换整个括号/整段条件”等无法确定是否包含连接词的说法。不同场景统一采用同一替换边界，并在交付前做文本替换检查，确认没有重复 `and`/`where`、孤立 `or` 或括号不平衡；该检查不等于数据库方言解析。
5. **SQL 证明范围必须覆盖交付承诺**：逐项核对 SQL 的输出字段、对象集合、行粒度、分组维度、过滤范围和汇总层级是否足以回答对应 CHK/MV/验证目标。若 SQL 只输出分组行和汇总，只能声称验证了这些分组/汇总，不得宣称证明明细集合或每个对象均正确；若承诺明细/集合完整性，必须输出可识别业务对象的键及足以核对完整集合的结果。F 的样本限制不得缩小 V 的完整计算范围。权限、日期或业务范围缺少必要依据、导致无法正确设计时标 `BLOCKED` 并说明缺口；只有部分业务断言已得到验证、部分未覆盖时才标 `PARTIAL`。不得用总量相等替代集合相等。

## 数据源与执行引擎/SQL 方言

- **执行端识别与默认策略**：SQL 设计前优先识别用户明确提供的查询客户端、网关或执行平台及其解析器/方言。证据优先级为：用户明确提供的执行端/报错信息 → 当前执行平台或连接配置的实际元数据 → 同一环境下已确认的项目配置/使用说明。若用户未指定且没有更强证据，优先读取可选本地 `config/organization-profile.json` 的 `sql.default_dialect`；未配置时可暂用 Presto 假设并在文件头明确标注；仅有表名、Catalog、Schema 或底层数据源信息时，不足以推翻 Presto 默认值或确认其他解析器。
- **数据源与方言分开记录**：底层数据源/数据库（如 StarRocks、Doris、Hive）说明数据存放位置；执行引擎/解析器（如 DorisDB、Presto、Trino）决定 SQL 语法。即使 Presto/Trino 通过 Connector 查询 StarRocks/Hive，也必须按实际解析器选择方言，不能因表在 SR 就默认使用 Doris 语法。Presto 与 Trino 也不得在缺少证据时视为完全相同。
- **默认假设与证据状态分开**：没有明确执行端信息时，不将执行引擎/方言写成已确认事实；文件头记录实际选定的 `execution_engine: <engine> (default assumption)`、`sql_dialect: <dialect>`（未配置时以 Presto 为假设），解析兼容性标 `NOT_VERIFIED`，直到目标解析器或用户执行结果提供证据。若用户明确指定其他执行端，或可靠环境证据与默认值冲突，则改用实际方言并记录依据；只有方言选择会实质影响正确性/可执行性且无法按已选默认假设处理时，才询问用户一个最关键的问题。
- **方言敏感点逐项核对**：重点检查 NULL-safe 比较符（如 `<=>`、`IS [NOT] DISTINCT FROM`）、日期/时间函数、字符串聚合、JSON/数组函数、正则、LATERAL/展开语法、类型转换及窗口/聚合扩展。优先采用目标引擎支持的通用写法；替换方言语法前必须先确认原业务语义，不能为了兼容而改变 NULL、过滤、精度或分组结果。
- **报错后的完整修复**：用户提供解析报错时，根据真实错误行/列定位不兼容 token 或表达式；在本次全部 SQL 文件和独立语句中搜索同类语法，检查相同构造是否重复出现，一次修复所有已确认的同类问题。不得只修复报错的第一处，也不得通过删除业务条件、放宽过滤或改变比较符来消除报错。
- **解析验证边界**：当前环境已具备且支持目标方言的解析器时，按明确 dialect 执行静态解析；不为此新增依赖或安装重型框架。没有可用解析器时，AI 方言走查只能作为静态检查，必须将解析兼容性标为 `NOT_VERIFIED`，不能称为语法解析 PASS。实际数据库执行仍由用户完成，未回传执行结果继续为 `NOT_RUN`。

## 格式与文件组织

- **方言默认值**：用户未明确指定其他执行端、且没有证据证明当前任务使用其他解析器时，默认使用 Presto 执行引擎/SQL 方言。用户明确指定或已有可靠证据确认实际执行端为其他引擎时，按实际执行端调整；不得因底层数据源是 StarRocks、Doris 或 Hive 就自动改用其原生 SQL 方言。
- **风格**：SQL 关键字小写、逗号前置、CTE `v_` 前缀、表别名 `t1/t2` 等，默认不使用 `select *`。CTE 声明与查询体起始按物理行固定：首个 CTE 写 `with v_name as (`，后续 CTE 写 `, v_name as (`（逗号可以在新行行首）；`as (` 必须作为该行结尾，下一行缩进后以 `select` 开始，禁止将 `select` 或其他查询内容放在左括号同一行。不得在 `with` 与 CTE 名、CTE 名与 `as`、`as` 与 `(` 之间换行；带显式列名列表或 `with recursive` 时同样遵守。此要求仅规范 CTE 声明和查询体起始，不限制查询体内部换行。
- **输出字段注释（必须落实）**：每个最终 `SELECT` 输出列都必须有简短中文注释，说明该列的业务含义、对应的页面/接口字段或核对点、用于输入定位还是数值对账；F 的 Number/Code 与内部 ID 分别注明用途，V 的原始值/中间值/最终预期分别说明。页面字段无法确认时标 `UNKNOWN`，不得猜测映射。SQL 别名和中间标识符仍统一英文 `snake_case`。
- **标识符与异常**：输出字段别名、CTE 和自定义中间标识符统一英文 `snake_case`（CTE 保持 `v_` 前缀、表别名仍为 `t1/t2`），中文仅用于字段行内注释、业务说明与文件头；避免无引号中文输出别名。SQL 格式适配不得擅自改变风险比较符、有效过滤、日期或排序（如要求 `<= 0` 不得改为 `= 0`）。数据库报错区分解析/字段/方言、权限、执行引擎故障；外层 `SQLSyntaxErrorException` 不能单独证明 SQL 语法错误，不能未经定位就删减业务条件。
- **文件头与查询段说明**：文件顶部注释必须包含 `author: Rainx`、`create time`（实际生成的北京时间 `+08:00`）、`description`、`database`、`execution_engine`、`sql_dialect`。其中 `database` 描述数据库/数据源或 Catalog，不代表 SQL 解析器；未确认执行端时使用 `execution_engine: Presto (default assumption)` 与 `sql_dialect: Presto`，并将解析兼容性标 `NOT_VERIFIED`。默认一条查询使用 `SQL-01` 编号，并说明覆盖的场景 ID/名称、关联 Case ID/CHK/MV（适用时）、启用条件、必要参数、结果使用/页面核对方法、产品口径/Oracle 来源。查询内部应能识别各场景的 F 样本逻辑与 V 预期逻辑，但不要求 F/V 两项职责分别建立可执行语句或独立语句编号。不得把示例表/过滤写成真实业务事实。
- **文件组织**：需求级独立 SQL 必须同时提供 `scenario-coverage.md` 与 SQL 文件；默认一个 `sql-design.sql` 包含本次所有可安全合并的必要场景，并作为一次执行入口。只有真实数据来源/执行引擎/粒度/计算等限制导致无法正确合并时才拆分，说明拆分原因和执行次数。文件数量与独立语句数量按实际必要性控制，不按场景或 Case 数机械拆分；场景清单使用 `category: sql`、`role: scenario-coverage`，与 SQL 文件共用同一 Manifest。窄范围 SQL 追问不强制额外创建场景清单。
- 只提供用户可复制执行的**只读 SELECT/CTE 查询**；不能实际确认的字段或参数必须明确 UNKNOWN/待替换。执行端未明确时按 Presto 默认假设设计，文件头注明 `execution_engine: Presto (default assumption)`、`sql_dialect: Presto`，解析兼容性为 `NOT_VERIFIED`；不得谎称 SQL 已在数据库执行。
- **每段 SQL 独立完整**：一个分号结束后，原 CTE 即失效；同文件的多段 SQL 各自必须包含所引用的 CTE。不可运行结构检查时记录 NOT_VERIFIED，绝不以 Manifest PASS 冒充 SQL PASS。
- **轻量风格检查（正式交付前必须执行）**：先将完整 SQL 草稿放入 `.qa-work/` 临时 `.sql` 文件，执行 `python -B skills/sql-design/tools/check_sql_style.py TEMP_SQL_FILE`。发现 `P3_SQL_STYLE_FAIL` 时修复全部明确违规并重跑，不得正式发布不符合既定格式的 SQL。该脚本无第三方依赖，只检查文件头、常见 SQL 关键字大小写、顶层逗号、同一查询层级内的简单 FROM/JOIN 别名；先按最内层未闭合括号识别函数调用参数语法中的 FROM（如 EXTRACT/SUBSTRING/TRIM），再识别关系来源，避免前置 CTE/标量子查询中已结束的 SELECT 导致函数 FROM 误报。另检查支持显式列名列表的 `v_` CTE 声明单行排版、`as (` 后换行且下一行以 `select` 开始、所有投影列中的 `*` / `alias.*`、最终 SELECT 输出列中文行内注释及显式 AS 别名（含双引号引用标识符）。字符串字面量仍作为输出表达式参与注释检查，但其内容不参与关键字/结构匹配。该工具不解析 SQL 方言/完整语法，复杂子查询/表函数别名、字段存在性和业务语义仍须按本指南人工复核。
- **检查结果边界**：风格检查 PASS 只表示脚本覆盖的确定性格式项通过，不代表完整格式人工复核、SQL 方言解析、字段/表存在、数据库执行或业务正确性。目标方言解析器不可用时，解析兼容性继续标 `NOT_VERIFIED`；任一检查工具无法运行时记录 NOT_VERIFIED，不伪报 PASS。
- 用户有真实 SQL 结果回传后，结合原始值/中间值/Oracle 复核，给出正常、异常或 UNKNOWN 及理由，不替代用户业务确认。

## 独立 P3 人工数据验证（按需触发）
- 独立 P3 分为 SQL 设计和人工验证两个阶段。SQL 设计、场景清单及 SQL-only 归档完成后默认停止；只有用户明确要求列清单、开始验证或继续下一条时才启动人工验证。列清单不自动开始第一条。
- P2 委托调用不进入本阶段。P2 `submission-impact.md` 继续按自身规则管理 CHK/MV、`verification-details.md` 和用户反馈；P3 只提供所需 F+V SQL，不接管 P2 流程。
- 人工验证时优先复用当前有效 SQL；页面核对必须优先定向读取 P4 对应页面的正式知识，并确保找数 SQL、预期计算和页面实际生效的默认条件/业务过滤一致。页面入口、搜索编号或条件无法确认时标 UNKNOWN，不猜测。
- **逐场景聊天交付**：独立 P3 的 SQL 结果返回后，默认每轮在聊天中交付一个完整场景，包含对应 SQL-01 逻辑/片段、真实样本、独立预期/计算依据和页面定位核对方法；用户说“下一条”再继续。一次执行的 SQL-01 不因逐条交付而重复执行；默认不把多个场景一次性堆在同一回复。P2 委托仍由 P2 自己管理 CHK/MV 和工作稿。页面实际值只依据用户反馈。详细流程见 `references/manual-data-verification.md`。
- 沿用 `PENDING/PASS/FAIL/BLOCKED/IGNORED`。SQL 执行成功或找到样本不代表 PASS；SQL 报错、成功无样本均不直接判业务 FAIL；IGNORED 不计为通过。具体会话、续作、状态回填和收尾见 `references/manual-data-verification.md`。
- 独立 P3 验证过程保存在 `.qa-work/<需求编号>-<需求名称>/sql-design/manual-verification.md`，绑定当前 P3 Manifest 与 SQL artifact SHA；不新增 JSON/数据库账本，不自动修改正式 SQL 或发布验证结果版本。用户明确要求正式归档时，先核实 Manifest 是否支持，不绕过现有协议。
## SQL-only Manifest 正式发布与增量

1. **定位归档基线**：按 `skills/testcase-design/references/output-archive.md` 定位需求根目录。新需求先用禅道 `getNeedDetailById({id})` 校验 `module/moduleName`，再运行 `manifest.py directory-name <需求编号> <需求名称> --module-id <module> --module-name "<moduleName>"`；已有需求先沿用现存根目录/legacy locator，读取 Manifest 中冻结的模块元数据，不得因新模块路径尚不存在而另建根目录。随后执行 `manifest.py inspect <需求目录>`；`MANIFEST_BASELINE_READY` 使用返回的 `latest_version`，`NO_HISTORY` 表示首次发布、基线为 JSON `null`。其他结果停止并核查，绝不跳过历史验证。
2. **准备正式输入**：AI 先核查产品 Oracle、数据来源、实际过滤、SQL 可读性及未决，保存本次新增/变化文件于 `.qa-work/`。需求级独立 SQL 应包含 `scenario-coverage.md`（若内容未变化则沿用历史 role）及本次新增/变化 SQL；发布前核对关联用例与产品 Oracle 正文、有效业务过滤、指标来源字段与对象粒度、跨 JOIN/分层聚合的一对多放大风险、独立对账的真实比较路径、每段 CTE/参数及最终输出字段注释。直接影响必要验证目标、导致无法正确设计的缺证标 `BLOCKED`；只有部分业务断言已验证、部分未覆盖时标 `PARTIAL`。已有可靠验证内容仍可部分交付，不因非关键缺证阻断。每份文件使用固定唯一 `role`（场景清单固定 `scenario-coverage`；SQL 默认 `sql-design`，只有确实拆分时才使用多个有明确职责的 role），`source_path` 指向真实暂存文件、`path` 为 `sql/` 下正式相对路径；不创建空目录或复制未变化文件。
3. **生成 publish spec**：使用 P1 现有 `publish-spec.json` 协议，包含真实 `requirement.id` 和 `name`、`expected_base_version`、`delivery_status`、`artifacts`。其中 `expected_base_version` 首次为 JSON `null`，增量使用从 inspect 得到的 `YYYYMMDD-vN` 字符串；`delivery_status` 按真实本次交付范围决定 `complete` 或 `partial`，不代表业务正确性 PASS。SQL-only 时**省略整个 `case_changes` 字段**（空列表也会被现有发布器识别为用例变更并拒绝发布）；没有真正 P1 用例变更时也不传 `lineage`、testcases 的 `retire_artifacts`。最小结构如下（所有占位符需以真实信息替换）：

   ```json
   {
     "requirement": {"id": "需求编号", "name": "需求名称", "module_id": "禅道 module", "module_name": "禅道 moduleName"},
     "expected_base_version": null,
     "delivery_status": "complete",
     "artifacts": [
       {
         "category": "sql",
         "role": "sql-design",
         "source_path": "真实暂存 SQL 绝对路径",
         "path": "sql/sql-design.sql"
       }
     ]
   }
   ```

4. **仅一次正式发布与验签**：把 spec 置于 `.qa-work/`，运行 `python -B skills/testcase-design/tools/manifest.py publish <需求目录> <publish-spec.json>`。仅退出码 0 且 `MANIFEST_PUBLISH_PASS` 才表示确有新版本发布。随后运行 `python -B skills/testcase-design/tools/manifest.py validate <需求目录>`，仅退出码 0 且 `MANIFEST_HISTORY_PASS` 为完整历史验签通过。相同内容被拒绝“无实质变更”是正常防重，应返回无需新版本，不反复尝试。
5. **增量继承和故障保护**：SQL 角色保持稳定；同角色内容变更才生成新文件，未列入本次 `artifacts` 的角色及现有 P1/P2 文件沿历史 `source_version` 和 SHA 引用。新增角色不是删除旧角色；退役 SQL 角色仅在用户明确确认且有依据时按 P1 协议定向处理。旧基线、历史 SHA 损坏、非法路径、并发更新等应让发布器拒绝；若发布回执不确定，检查最新 Manifest 和目录后再决定操作，绝不盲目重发。发布成功后的 `validate` 失败必须保留现场，不能用再次 `publish` 掩盖。
6. **版本与身份隔离**：`schema_version = "1"` 不变；SQL-only 首次交付允许无 P1 用例，已存在 P1 用例时必须继承全部现有/退役 Case ID、Revision、原 Markdown/XMind/Oracle 的完整正式快照，不调整 P1 覆盖结论。`inspect` 返回 `markdown_path: null` 可意味着该需求还没有正式用例，并非自动错误。
7. **运行时和验收边界**：正式发布入口 `skills/testcase-design/tools/manifest.py` 当前已有可维护的 Python 源码，并非编译文件恢复桩；可维护源码的存在不代表运行环境、历史数据或跨版本发布自然通过。解释器/依赖不兼容、发布器缺失或实际执行失败时，应保留真实错误并按适用契约标 `PUBLISH_UNAVAILABLE` 等受阻状态；不得绕过 Manifest、回退旧工程或自行改写历史。SQL-only 隔离工程验收仅证明对应发布/验签场景，数据库 SQL 实际执行、SR/Presto 实库解析及独立 Oracle 数据正确性仍为 `NOT_RUN`。
8. **收尾**：清理本次 `.qa-work/` 临时文件之前确认发布及验签回执，不能删除正式历史、已存在的互斥锁或其他任务草稿。模拟设计与隔离工程集成仅在对应范围验收 PASS；任何真实需求的实库数据结果、跨 Agent 实际执行和整体业务验收均须单独验证，不得据工程测试推断业务 SQL 正确。

## 交付前自审与状态

本次适用维度检查：① AI 识别的必要数据验证目标及 F/V 内部职责；②场景 ID/Case ID/CHK/MV ↔ SQL-01 查询逻辑映射；③产品提供的表、字段及上游取数逻辑优先级；④页面定位字段、样本成立证据与有效过滤；⑤数据粒度/JOIN/去重；⑥产品 Oracle 来源、独立性边界及原始/中间/最终值；⑦默认 Presto 与实际执行端证据状态；⑧默认一条 SQL、一次执行、100 行结果上限和性能；⑨文件头、SQL 风格、最终输出列中文注释及适用结构检查；⑩未决影响及人工核对指引。
- **AI 自主做一次结果可用性走查（非新增门禁/文件）**：对每个适用 F/V，检视四件事：①查出的业务标识能否按真实页面/接口字段定位对象；②字段、单位、分母、来源版本和业务过滤是否对齐；③原始行与目标行的粒度、JOIN/去重/分组是否可能重复计数或漏行；④找数谓词/验证断言是否真正能区分正确与错误实现。尝试代入一条合理的最小反例；若只有普通样本、条件太宽、误把模拟结果当页面真实返回或存在确定矛盾，应自行修复后交付。只针对实际高风险维度展开，不为简单查询机械增加取证和反例数量。
- **交付表达要可操作**：先展示场景清单，让用户知道本需求具体要验证哪些数据场景、哪些纯功能场景不需要 SQL、哪些场景存在证据缺口；再逐场景关联 F/V 查询。找数标明“复制哪列 → 在哪一项查询/接口中使用 → 比对哪个业务字段/预期”；每个 SQL 输出列均有中文注释说明业务含义和页面对应字段。纯 SQL 核验说明结果如何判定。关键事实无法确认时局部降级，并说明需补哪项证据；不能把 DESIGN_REVIEWED、结构 PASS、已生成 SQL、F 找到样本或数据库尚未执行，写成业务问题已证实。
- **DESIGN_REVIEWED**：AI 已进行语义/静态自审，不代表实库执行。仅表示已对所声明的范围实际核对；若关键过滤/粒度/公式仍未知，不得称受影响 V 为完整准确的预期。
- **ENGINEERING_CHECK_PASS**：确实执行并通过的结构/规则类检查，列出范围与证据，不冒充业务验证。
- **NOT_RUN**：SQL 尚未由用户执行，禁止声称实际数据正确。
- **UNKNOWN / PARTIAL**：证据或口径缺失时，指出受影响查询；其余已确认部分可独立交付，不用猜测填补。 明确未知影响的是找数场景成立还是结果数值。关键 V 仍不完整时，本次 SQL-only 交付宜使用 `delivery_status=partial`；不要用 `MANIFEST_HISTORY_PASS` 代替设计质量结论。
