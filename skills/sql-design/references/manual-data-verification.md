# P3 独立人工数据验证｜按需触发

## 1. 适用范围与流程隔离

本文件只适用于用户**独立调用 P3** 后，主动要求继续人工验证的场景。

- P3 分两个阶段：
  - **阶段一：SQL 设计**。按现有规则识别必要场景、默认完成 F（真实样本）与 V（独立预期）职责，明确 F-only/V-only 时仅完成指定职责，再按指南分组并交付工作稿，明确要求当前稿正式归档时才发布。完成后默认停止，不自动进入人工验证。
  - **阶段二：人工验证**。只有用户明确要求列出验证清单、开始验证或继续核对时才启动。
- 用户只说“生成 SQL”“补充 SQL”时，只执行阶段一。
- 用户说“列出验证清单”时，只列场景和当前状态，不自动开始 SQL 执行或页面核对。
- 用户说“开始人工验证”“逐条”“开始第一条”“下一条”等，才按顺序推进。
- **对话窗口是用户交付入口**：当前场景的执行入口、场景、适用预期和对应的核对/找数步骤应直接在聊天中展示；工作记录用于 AI 跨对话续作和归档，不得只给文件路径让用户自行打开文件寻找 SQL 或理解验证内容。
- **P2 主任务优先由 P2 自己管理**：当前任务属于 submission-impact 时，继续执行 P2 的 CHK/MV 和 verification-details.md 流程。P2 调用 P3 只为 P2 设计 SQL，不启动本文件的独立验证会话，不接管 P2 状态，不改变 P2 首次聊天隐藏 SQL 正文等规则。
- 不修改 P2 的 Skill、工作流、报告模板、工作稿、路由或 Manifest 规则。

## 2. 验证会话记录

用户首次明确启动独立 P3 人工验证时，创建或续读唯一工作记录：

.qa-work/<需求编号>-<需求名称>/sql-design/manual-verification.md

记录至少包含：

- 需求编号、需求名称。
- 当前工作稿路径及 SHA，或经校验的正式 Manifest 版本及 SHA。新会话优先当前任务明确选定的版本，否则使用有对应场景清单的当前工作稿；无当前稿时用最新有效正式产物。已有会话优先续读其绑定基线。
- 当前有效 scenario-coverage.md 和 SQL 文件路径、SHA。
- 每个场景的 ID、名称、关联 SQL 编号、实际启用条件、场景查询逻辑/输出字段、F/V 内部职责及状态。
- SQL 执行结果、实际业务键（涉及页面/接口时记经证实可定位的 Number/Code、分组键或该入口支持的内部 ID，保留真实字段名与用途）、适用独立预期、用户反馈的页面/接口实际值或纯数据核对证据、结论与必要备注。
- 已在聊天中交付的场景 ID、当前等待用户反馈的场景 ID、下一待交付场景 ID；用于跨对话恢复逐条进度，不另建状态账本。

要求：

1. 这份 Markdown 是独立 P3 人工验证状态的唯一事实来源；不新增 JSON 账本、SQLite、数据库或第二套状态文件。
2. 跨对话核对绑定基线、场景清单与 SQL SHA。SQL、条件或 Oracle 变化时比较各场景 F/V 逻辑和执行范围；只将受影响或无法证明仍有效的场景恢复为 PENDING（缺前置则 BLOCKED），保留旧反馈作历史证据并继续复用其余有效结果。旧记录仍可按原正式 Manifest 与 SQL SHA 续读。工作稿正式归档且内容一致时，可更新基线引用并保留有效结果。
3. 已有工作记录时先续读，不重复要求用户提供已记录的 SQL 执行结果、页面反馈或已确认信息。
4. 工作记录保留在 .qa-work/，不自动修改正式 SQL、不自动创建新 Manifest 版本。用户明确要求正式归档验证结果时，先确认现有 Manifest 是否支持相应 artifact；不支持则说明限制，不自造发布协议或绕过 Manifest。
5. 没有需求编号时，不虚构需求编号；沿用当前任务已有的稳定工作目录。无法稳定定位时，只询问一个必要的任务标识。

## 3. 列出场景与启动人工验证

### 列清单

从当前有效 scenario-coverage.md 和 SQL 文件恢复全部场景：

- 列出需要真实数据验证的场景、关联 SQL 编号/场景查询逻辑和当前状态。
- 纯功能场景标明“无需 SQL”；证据不足的场景说明缺什么。
- 已 PASS、FAIL、IGNORED、BLOCKED、PENDING 的状态如实展示。
- 只列清单，不附全部 SQL，不自动开始执行或页面核对。

### 开始人工验证

- 先交付当前场景、成立条件、适用的预期计算与核对方法；涉及页面/接口时提供已确认的查询入口及定位方式，纯数据目标提供 SQL 结果判定方式，明确 F-only 只需对应找数方法。
- 当前场景缺有效结果时，在聊天中提供完整可复制的 SQL，或按依赖顺序提供本场景所需的完整查询。注明默认参数、复制哪列定位和核对哪列。按需说明边界样本如何切换注释；已一次返回的业务场景按场景 ID 直接定位。查询围栏内仅放 SQL 及注释。
- 已有结果时确认实际场景、查询版本及筛选范围与当前核对一致；覆盖当前场景且证据仍有效时直接使用，并说明对应入口，无需重复执行。
- 仅当场景涉及页面/接口核对且现有可信证据仍不足时，按第 5 节定向读取对应 P4 页面知识；纯数据目标不查无关页面。

## 4. SQL 结果返回后的逐场景对话核对

收到用户真实查询结果后，按以下顺序处理：

1. 先确认查询是否成功、范围和结果是否完整、是否包含当前职责需要的样本/对象/集合及场景标识；V-only 可直接使用已有可信对象或集合结果，不强制重新执行 F。SQL 报错、空结果或缺某场景结果不直接等于业务 FAIL；若 V 的独立 Oracle 明确要求空集合，并有同范围真实被测结果为空的证据，可据此核对。
2. **默认一个场景一轮聊天交付**。用户说“逐条”“开始第一条”时展示第一个待核对场景；用户说“下一条”时展示下一个场景。不得把多个场景一次性堆进一个回复，也不得要求用户自行打开工作记录查找当前场景。
3. 同一场景的场景说明、SQL 逻辑、按目标适用的真实样本或既有验证对象、独立预期及页面/接口或纯数据核对方法须在同一轮展示；明确 F-only 不强加 V，不能拆散本场景必需内容。
4. 每个场景只交付本次 F/V、F-only 或 V-only 指定职责需要的内容（不强制补另一职责）：
   - **场景与目标**：场景 ID、业务目标、本次要证明什么。
   - **对应 SQL 逻辑**：展示此前已执行查询中与本场景直接相关的片段或关键条件；该片段用于解释样本来源和计算逻辑，不要求再次执行。
   - **样本或验证对象（按职责适用）**：F/F-only 只使用用户回传 SQL 结果认定找到的真实样本，并说明场景成立依据。V-only 可以直接复用用户已提供或现有证据确认的对象/集合及真实结果，不必额外找 F 样本；不得编造对象或查询值。涉及页面/接口定位时使用已证实可用的真实 Number/Code、分组键或接口/页面实际接受的内部定位键，保留字段真实名称与用途，不重命名内部 ID 冒充业务号。先复用可信页面配置/P4 证据，必要时才定向补证；缺页面键仅影响有此需求的目标，纯数据目标不因此阻断。
   - **产品预期（适用时）**：完整 F/V 或 V-only 说明需求/上游取数逻辑/用户确认口径等 Oracle 来源，列出必要原始值、中间值、公式和已执行样本的具体预期值；不得使用被测开发输出反推预期。明确 F-only 仅交付找数证据，不强加 V。
   - **按目标核对**：页面/接口的完整 F/V 或 V-only 明确实际入口、真实定位键（Number/Code、分组键或被证实可用的内部键）、适用筛选、对照字段与独立预期；纯数据 V/V-only 用真实对象/集合和 Oracle 核对，不强制页面步骤。F-only 仅交付样本成立依据、有效条件及必要定位方法，不要求对照 V 数值。
5. 结果返回后以已执行入口的片段说明逻辑。下一场景缺有效结果时才提供其执行入口及适用的边界条件切换说明。
6. 需要找数的 F/F-only 优先展示最容易定位且足以证明目标的一条真实记录，确需多条再增加；V-only 直接用现有可信对象/集合及适用的实际结果核对，预期为空集合时不强制返回样本行。不得为凑数量堆砌记录。
7. 用户回传本次职责所需证据后立即更新记录：F-only 真实合格样本经核实后，明确写“本次 F-only 找数完成”，不强制补 V、不把找数完成冒充原 CHK/MV 或业务 PASS，也不因未做 V 将本次 F-only 持续当作 PENDING；V/V-only 依独立 Oracle 与真实页面/接口或数据结果判定。仍缺本次职责证据才保持 PENDING。用户可以反馈后说“下一条”，也可以尚未反馈当前场景就要求查看下一条；后者只推进展示进度，不得把当前场景判为通过或忽略。
8. 当前 SQL 结果已经覆盖的场景，不得因逐条展示、分多轮对话或跨对话续作而要求重复执行 SQL。跨轮只展示尚未交付的场景；已交付场景的状态和反馈从同一份工作记录恢复。
9. 用户明确要求一次性查看全部场景时，才可以在一个回复中合并展示多个场景；默认仍逐场景对话。

不得在 SQL 结果返回前编造具体样本、单条记录的具体预期值或页面实际值。面向用户使用简短自然的大白话；不要只回复文件路径、让用户自己找 SQL/预期/操作步骤，也不要重复解释无关背景。

## 5. 页面知识与默认条件

仅涉及页面/接口核对时，**优先复用本轮已确认的需求、P1 Oracle、页面配置和 P4 可信证据；确有缺口才定向只读读取 P4 对应页面/Tab/查询模式的正式知识**，重点确认：

- 页面真实路径和查询入口。
- 页面/API 实际支持的真实定位键：Number/Code、经证实分组键或该入口实际接收的内部 ID；保留其原始字段名和用途，不伪装成业务编号。
- 页面默认条件、用户选择条件和后端固定业务过滤。
- 页面实际发送并生效的查询条件。
- 页面展示字段与 SQL 预期字段的对应关系。

SQL 的数据范围必须与页面实际查询范围一致。不能只因为页面显示了某个默认值，就认定后端一定按该值过滤；也不能漏掉页面默认条件或后端固定业务过滤。

P4 未命中、知识待审核或条件适用性不明时，按需定向核查现有可信源码/配置；仍无法确认就明确告诉用户缺什么、影响哪一步，不猜测页面路径、查询字段或过滤条件。不得为了补知识自动修改 P4。

## 6. 状态和反馈

沿用现有业务验收状态，不另造状态体系。F-only 明确只找数时，以工作记录文字记载“本次 F-only 找数完成/尚未找到合格样本”，不新增业务 PASS/FAIL，也不要求其因未做 V 持续 PENDING：

| 状态 | 什么时候使用 |
|---|---|
| PENDING | 尚未完成当前目标的页面/接口或纯数据核对，或仍有证据待用户反馈 |
| PASS | 当前 V/完整 F+V 目标完成实际页面/接口或独立数据核对，结果与独立产品 Oracle 一致（含有证据的预期空集合） |
| FAIL | 当前 V/完整 F+V 目标完成实际页面/接口或独立数据核对，结果与独立产品 Oracle 不一致 |
| BLOCKED | SQL 执行、权限、环境、数据或本目标必需的页面/接口前置条件导致暂时无法继续 |
| IGNORED | 用户明确表示该场景无需验证；不计为通过 |

补充规则：

- UNKNOWN 只表示证据不足，不是验证状态，不得写入状态字段；证据不足但仍可继续时保持 PENDING，存在明确前置阻塞时标记 BLOCKED。只有用户提供与当前 V 目标相符的页面/接口实际结果或纯数据独立核对证据，且 Oracle 明确时，才可判定业务 PASS/FAIL。
- SQL 执行成功不代表业务 PASS；F 找到合格样本只证明找数职责完成，不证明业务 V 正确。
- SQL 报错不是业务 FAIL；先定位 SQL、方言、权限或环境问题。
- F/F-only 查询成功但没有找到样本，不代表业务正确或错误；记录无样本原因，按实际目标调整条件或说明未完成。V/V-only 的独立 Oracle 若明确预期为空集合，且真实被测查询在已核实的同范围下也为空，则可用空集合一致性证据判定；只看到空结果但缺 Oracle 或实际范围证据不得直接 PASS。
- 当前 V 目标所需的页面/接口实际值或独立数据核对结果未反馈时保持 PENDING；明确 F-only 的完成情况按已核实的样本证据单独说明，不等同于业务验证状态。
- 用户可直接用自然语言反馈，不要求固定格式；收到反馈后立即更新同一条记录。
- FAIL 时先分析当前场景，不要求用户重复执行已完成的操作；只有用户要求继续时才进入新的验证动作。
- 用户明确说“忽略”才标 IGNORED；不能把未验证事项自动忽略。

## 7. 最终收尾

全部场景处理后，在同一份工作记录中形成总结：

- 总场景数与适用业务验收状态 PASS、FAIL、BLOCKED、IGNORED、PENDING 数量；明确仅 F-only 的任务单列“本次找数完成/未找到合格样本”，不计作业务 PASS，也不因未执行 V 被列为本次待验。
- 已确认通过的场景。
- 未通过及其实际页面/接口表现或数据差异。
- 暂时无法验证的原因。
- 仍需用户或开发处理的事项。

IGNORED 不计入 PASS；存在 PENDING、FAIL 或 BLOCKED 时，不得把整轮写成全部通过。最终在聊天中用简短语言说明结果，不重复粘贴所有 SQL 和分析过程。
