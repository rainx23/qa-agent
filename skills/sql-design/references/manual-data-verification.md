# P3 独立人工数据验证｜按需触发

## 1. 适用范围与流程隔离

本文件只适用于用户**独立调用 P3** 后，主动要求继续人工验证的场景。

- P3 分两个阶段：
  - **阶段一：SQL 设计**。按现有规则识别必要场景、完成 F（真实样本）与 V（独立预期）职责，按指南分组并交付工作稿，明确要求当前稿正式归档时才发布。完成后默认停止，不自动进入人工验证。
  - **阶段二：人工验证**。只有用户明确要求列出验证清单、开始验证或继续核对时才启动。
- 用户只说“生成 SQL”“补充 SQL”时，只执行阶段一。
- 用户说“列出验证清单”时，只列场景和当前状态，不自动开始 SQL 执行或页面核对。
- 用户说“开始人工验证”“逐条”“开始第一条”“下一条”等，才按顺序推进。
- **对话窗口是用户交付入口**：当前场景的执行入口、场景、预期和操作步骤应直接在聊天中展示；工作记录用于 AI 跨对话续作和归档，不得只给文件路径让用户自行打开文件寻找 SQL 或理解验证内容。
- **P2 主任务优先由 P2 自己管理**：当前任务属于 submission-impact 时，继续执行 P2 的 CHK/MV 和 verification-details.md 流程。P2 调用 P3 只为 P2 设计 SQL，不启动本文件的独立验证会话，不接管 P2 状态，不改变 P2 首次聊天隐藏 SQL 正文等规则。
- 不修改 P2 的 Skill、工作流、报告模板、工作稿、路由或 Manifest 规则。

## 2. 验证会话记录

用户首次明确启动独立 P3 人工验证时，创建或续读唯一工作记录：

.qa-work/<需求编号>-<需求名称>/sql-design/manual-verification.md

记录至少包含：

- 需求编号、需求名称。
- 当前工作稿路径及 SHA，或经校验的正式 Manifest 版本及 SHA。新会话优先当前任务明确选定的版本，否则使用有对应场景清单的当前工作稿；无当前稿时用最新有效正式产物。已有会话优先续读其绑定基线。
- 当前有效 scenario-coverage.md 和 SQL 文件路径、SHA。
- 每个场景的 ID、名称、关联 SQL 编号、实际启用条件、场景查询逻辑/输出字段、F/V 内部职责及状态。
- SQL 执行结果、用于页面查询的真实业务编号/编码、SQL 算出的独立预期、用户反馈的页面实际值、结论和必要备注。
- 已在聊天中交付的场景 ID、当前等待用户反馈的场景 ID、下一待交付场景 ID；用于跨对话恢复逐条进度，不另建状态账本。

要求：

1. 这份 Markdown 是独立 P3 人工验证状态的唯一事实来源；不新增 JSON 账本、SQLite、数据库或第二套状态文件。
2. 跨对话核对绑定基线、场景清单与 SQL SHA。SQL、条件或 Oracle 变化时比较各场景 F/V 逻辑和执行范围；只将受影响或无法证明仍有效的场景恢复为 PENDING（缺前置则 BLOCKED），保留旧反馈作历史证据并继续复用其余有效结果。旧记录仍可按原正式 Manifest 与 SQL SHA 续读。工作稿正式归档且内容一致时，可更新基线引用并保留有效结果。
3. 已有工作记录时先续读，不重复要求用户提供已记录的 SQL 执行结果、页面反馈或已确认信息。
4. 工作记录保留在 .qa-work/，不自动修改正式 SQL、不自动创建新 Manifest 版本。用户明确要求正式归档验证结果时，先确认现有 Manifest 是否支持相应 artifact；不支持则说明限制，不自造发布协议或绕过 Manifest。
5. 没有需求编号时，不虚构需求编号；沿用当前任务已有的稳定工作目录。无法稳定定位时，只询问一个必要的任务标识。

## 3. 列出场景与启动人工验证

### 列清单

从当前有效 scenario-coverage.md 和 SQL 文件恢复全部场景：

- 列出需要真实数据验证的场景、关联 SQL 编号/场景查询逻辑和当前状态。
- 纯功能场景标明“无需 SQL”；证据不足的场景说明缺什么。
- 已 PASS、FAIL、IGNORED、BLOCKED、PENDING 的状态如实展示。
- 只列清单，不附全部 SQL，不自动开始执行或页面核对。

### 开始人工验证

- 先交付当前场景、成立条件、预期计算、页面查询入口和核对方法。
- 当前场景缺有效结果时，在聊天中提供完整可复制的 SQL，或按依赖顺序提供本场景所需的完整查询。注明默认参数、复制哪列定位和核对哪列。按需说明边界样本如何切换注释；已一次返回的业务场景按场景 ID 直接定位。查询围栏内仅放 SQL 及注释。
- 已有结果时确认实际场景、查询版本及筛选范围与当前核对一致；覆盖当前场景且证据仍有效时直接使用，并说明对应入口，无需重复执行。
- 页面核对前，必须先按第 5 节定向读取 P4 对应页面知识。

## 4. SQL 结果返回后的逐场景对话核对

收到用户真实查询结果后，按以下顺序处理：

1. 先确认查询是否成功、结果是否完整、是否包含可用样本及场景标识；不把 SQL 报错、空结果或缺少某个场景结果直接判为业务失败。
2. **默认一个场景一轮聊天交付**。用户说“逐条”“开始第一条”时展示第一个待核对场景；用户说“下一条”时展示下一个场景。不得把多个场景一次性堆进一个回复，也不得要求用户自行打开工作记录查找当前场景。
3. 同一场景的场景说明、SQL 逻辑、真实样本、独立预期和页面核对方法必须在同一轮完整展示，不能拆散。
4. 每个场景的聊天交付必须包含：
   - **场景与目标**：场景 ID、业务目标、本次要证明什么。
   - **对应 SQL 逻辑**：展示此前已执行查询中与本场景直接相关的片段或关键条件；该片段用于解释样本来源和计算逻辑，不要求再次执行。
   - **真实样本**：只使用用户回传的 SQL 结果；除证明场景成立的关键字段外，必须返回页面实际展示、可直接检索的业务标识。具体展示字段优先读取目标页面对应的 P4 正式可复用知识，并以实际页面列配置/API 出参核实；内部 ID 可保留作 SQL 关联证据，但不得替代页面展示标识。P4 缺失或证据不充分时，定向核查可信页面配置/请求/API 出参；仍不能确认则标记 UNKNOWN 并询问用户，不猜测。
   - **产品预期**：说明产品需求/上游取数逻辑/用户确认口径等 Oracle 来源，列出必要原始值、中间值、公式和该样本的具体预期值；不得使用被测开发输出反推预期。
   - **页面定位与核对**：明确页面路径、复制哪一列页面展示标识、必要筛选条件、核对哪个页面字段，以及该样本正确应显示什么。内部 ID 可作为 SQL 关联证据，但不得替代页面实际展示的 Number/Code。
5. 结果返回后以已执行入口的片段说明逻辑。下一场景缺有效结果时才提供其执行入口及适用的边界条件切换说明。
6. 默认优先给每个场景一条最容易定位且足以证明目标的真实记录；确需多条才能覆盖不同情况时再增加。不能为追求样本数量堆砌记录。
7. 用户反馈页面结果后，立即更新对应场景状态和证据；未反馈的场景保持 PENDING。用户可以反馈后说“下一条”，也可以尚未反馈当前场景就要求查看下一条；后者只推进展示进度，不得把当前场景判为通过或忽略。
8. 当前 SQL 结果已经覆盖的场景，不得因逐条展示、分多轮对话或跨对话续作而要求重复执行 SQL。跨轮只展示尚未交付的场景；已交付场景的状态和反馈从同一份工作记录恢复。
9. 用户明确要求一次性查看全部场景时，才可以在一个回复中合并展示多个场景；默认仍逐场景对话。

不得在 SQL 结果返回前编造具体样本、单条记录的具体预期值或页面实际值。面向用户使用简短自然的大白话；不要只回复文件路径、让用户自己找 SQL/预期/操作步骤，也不要重复解释无关背景。

## 5. 页面知识与默认条件

进入页面核对时，**必须优先定向读取 P4 对应页面、Tab、查询模式的正式可复用知识**，重点确认：

- 页面真实路径和查询入口。
- 页面查询框实际使用的 Number/Code 字段。
- 页面默认条件、用户选择条件和后端固定业务过滤。
- 页面实际发送并生效的查询条件。
- 页面展示字段与 SQL 预期字段的对应关系。

SQL 的数据范围必须与页面实际查询范围一致。不能只因为页面显示了某个默认值，就认定后端一定按该值过滤；也不能漏掉页面默认条件或后端固定业务过滤。

P4 未命中、知识待审核或条件适用性不明时，按需定向核查现有可信源码/配置；仍无法确认就明确告诉用户缺什么、影响哪一步，不猜测页面路径、查询字段或过滤条件。不得为了补知识自动修改 P4。

## 6. 状态和反馈

沿用现有状态，不另造状态体系：

| 状态 | 什么时候使用 |
|---|---|
| PENDING | 尚未完成页面实际核对，或仍有证据待用户反馈 |
| PASS | 用户实际查过页面，页面值符合 SQL 给出的正确预期 |
| FAIL | 用户实际查过页面，页面值与正确预期不一致 |
| BLOCKED | SQL 执行、权限、环境、数据或页面前置条件导致暂时无法继续 |
| IGNORED | 用户明确表示该场景无需验证；不计为通过 |

补充规则：

- UNKNOWN 只表示证据不足，不是验证状态，不得写入状态字段；证据不足但仍可继续时保持 PENDING，存在明确前置阻塞时标记 BLOCKED。只有页面实际值由用户反馈且 Oracle 明确时才判定 PASS/FAIL。
- SQL 执行成功不代表 PASS；F 找到样本也不代表 PASS。
- SQL 报错不是业务 FAIL；先定位 SQL、方言、权限或环境问题。
- SQL 成功但没有样本，不代表业务正确或错误；记录无样本原因，调整条件或标记 BLOCKED。
- 页面值未反馈时保持 PENDING。
- 用户可直接用自然语言反馈，不要求固定格式；收到反馈后立即更新同一条记录。
- FAIL 时先分析当前场景，不要求用户重复执行已完成的操作；只有用户要求继续时才进入新的验证动作。
- 用户明确说“忽略”才标 IGNORED；不能把未验证事项自动忽略。

## 7. 最终收尾

全部场景处理后，在同一份工作记录中形成总结：

- 总场景数及 PASS、FAIL、BLOCKED、IGNORED、PENDING 数量。
- 已确认通过的场景。
- 未通过及其实际页面表现。
- 暂时无法验证的原因。
- 仍需用户或开发处理的事项。

IGNORED 不计入 PASS；存在 PENDING、FAIL 或 BLOCKED 时，不得把整轮写成全部通过。最终在聊天中用简短语言说明结果，不重复粘贴所有 SQL 和分析过程。
