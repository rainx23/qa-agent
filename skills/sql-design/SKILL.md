# SQL Design（P3）｜SQL 设计

## 能力边界

- **独立需求 SQL（默认工作稿）**：用户要求设计、生成、补充或修复需求 SQL 时直接进入 P3，不依赖 P2。识别必要验证目标，形成场景清单和 F/V SQL，先保存到 `.qa-work/<需求编号>-<需求名称>/sql-design/`。按指南分组与设计，只有用户明确要求将当前稿正式归档时才发布。
- **P1 基线复用**：先定位需求最新有效 Manifest；若存在 P1 正式 `testcases.md`/`oracle.json`，核对当前有效 artifact 的 SHA 并读取相关场景、Case ID、业务操作、预期及独立 Oracle，作为需求理解和场景覆盖的首选依据。默认不重新获取需求正文、不重跑 P1；只有 P1 基线不存在或关键业务事实确实缺失时，才定向补取缺失事实或请用户补充，不自动启动 P1/P2。
- **P2 提测交接（强制遵循 P3 规则，保持调用方隔离）**：P2 `submission-impact.md` 根据本次代码变更与业务影响自主识别需要独立真实数据验证的目标，不机械覆盖页面全部指标；对识别出的每个目标默认委托 P3 完成 F（真实样本）与 V（独立预期）职责，并将 SQL 写入绑定当前 P2 基线的 `.qa-work/<需求编号>-<需求名称>/submission-impact/verification-details.md`。P2 在生成或写入任何 SQL 正文前，必须实际读取当前 `skills/sql-design/SKILL.md` 与 `skills/sql-design/references/sql-design-guidelines.md`；未完整加载两份文件前不得生成/写入 SQL，任一文件读取失败或内容不完整时停止并报告 `P3_RULES_NOT_LOADED`，不得由 P2 自行手写 SQL 替代。P3 负责 SQL 业务分析、Oracle、F/V、数据来源、方言和格式；P2 继续管理 CHK/MV、工作稿和反馈，不启动独立 P3 人工验证或 SQL-only 正式版本。BUG 根因排查、无需求代码变更等其他 P2 工作流不因此生成或要求 SQL。
- **P3 独立人工验证（按需触发）**：独立需求 SQL 阶段一完成后默认停止，不自动开始人工验证；只有用户明确要求列出验证清单、开始验证或继续核对时，才进入阶段二。列清单只展示场景和状态，不自动开始核对；SQL 结果返回后默认每轮在聊天中完整交付一个场景，用户说“下一条”再继续，具体状态与续作规则见 `references/manual-data-verification.md`。
- **共享分析核心、调用方流程隔离**：P2 委托和用户独立调用 P3 时，共用本文件引用的 SQL 业务分析规则，包括需求变化自主识别、产品口径与独立 Oracle、按需求来源优先级找数、页面可定位样本及 SQL 结果后的必要核对指导。共享的是 SQL 业务分析能力，不共享任务管理：P2 只处理当前 submission-impact 的 CHK/MV 目标，继续使用 `verification-details.md` 工作稿、首次聊天隐藏 SQL 正文及不创建 P3 SQL-only 版本；独立 P3 继续遵守需求级场景覆盖和 SQL-only 归档。不得因共享规则扩大其他 P2 工作流，也不得由 P3 接管 P2 的 CHK/MV、报告或版本管理。
- AI 负责业务理解、数据场景、独立 Oracle、有效条件探查、表/字段及数据粒度定位、SQL 设计与复核。Python 只在必要时执行确定性文件/结构检查，不创建场景分类框架或数据库执行器。
- **任务分类**：必要数据验证目标完成 F/V 两项职责，按指南确定 SQL 数量。纯 UI/导航等无真实数据断言标 N。用户明确只找数、只对数或只讨论时按实际范围执行。
- **只编写只读 SQL，由用户在获准数据库环境手动执行**。P3 不连接数据库、不执行生产 SQL 或其他环境 SQL、不执行数据变更、不 Push、不修改业务仓库或未经授权写平台。收到用户执行结果后再比较 Oracle。
- **面向用户的验证说明**：独立人工验证按场景交付，当前场景缺有效执行结果时直接给完整可复制 SQL 和切换方法。已有有效结果时复用并解释样本、预期计算和页面核对。详见人工验证规则。
- 每次执行 P3 SQL 任务前，必须实际读取本文件与 `references/sql-design-guidelines.md`，不能仅凭记忆或历史摘要声称已加载。P2 委派任务同样必须在生成/写入 SQL 前完整读取这两份文件；加载失败或内容不完整即停止 SQL 生成/写入并报告 `P3_RULES_NOT_LOADED`。独立需求 SQL 再核验最新有效 Manifest 并复用可用的 P1 正式用例/Oracle；按需加载 P2 证据和 P4 知识，不批量加载全部历史和业务模块。
- **首次交付前检查**：逐查询按指南「SQL 分组与场景切换」完成性能自审，重点核对过滤、扫描、关联和 V 计算集合。将完整 SQL 草稿放入 `.qa-work/`，执行 `python -B skills/sql-design/tools/check_sql_style.py TEMP_SQL_FILE` 和 `python -B skills/sql-design/tools/check_sql_structure.py TEMP_SQL_FILE`。修复明确违规并重跑。工具无法运行标 `NOT_VERIFIED`。静态检查结果仅覆盖相应风格与结构。
- 用户明确启动独立 P3 人工验证时，额外必读 `references/manual-data-verification.md`；按选定工作稿或正式产物的基线及 SQL SHA 续读同一份验证工作记录，并优先定向读取 P4 对应页面/Tab 的正式知识。当前任务属于 P2 `submission-impact` 时，不加载或执行独立 P3 人工验证流程，严格由 P2 管理 CHK/MV 和工作稿。
### 动态分析深度（L1/L2/L3）
- 每次 P3 任务由 AI 根据业务逻辑复杂度、数据粒度风险、业务影响和证据不确定性自主选择 L1/L2/L3；默认不要求用户指定等级。等级表示本次应完成的分析与验证范围，不代表模型能力保证。
- L1/L2/L3 的适用条件、必须完成的检查、自动升级和停止条件，以 references/sql-design-guidelines.md 的“动态分析深度”章节为准；不得只标等级而不落实对应验证。
- 分析中出现更高等级特征时自动升级，并简要记录触发原因；开始即明确属于 L3 的任务可直接进入 L3。关键信息不足且可能改变业务结论时不得为节省成本降为 L1。
- 所有等级均须完成适用的产品口径/独立 Oracle、必要验证目标的 F/V 内部职责、有效业务条件核对及必要 SQL 检查；F/V 是验证职责，不要求分别交付两条 SQL。N 仅用于没有真实数据断言的场景。L1 不代表降低基本质量义务；L3 也不意味着机械扫描所有表或生成更多 SQL。
- 交付时简要说明本次深度、选择依据、是否升级及原因、已完成的关键验证范围。只呈现可审计的依据和结果，不输出隐藏思维链；静态推导、结构检查与数据库运行验证继续严格区分。
- **P2 页面复现中的用户定向找数（P2 为主任务，P3 只提供用户当前明确要求的缺失样本）**：用户已通过 P2 得到问题，明确表示页面验证时缺少符合条件的数据且当前只要求找样本时，P3 可围绕指定 CHK 提供 F-only 查询，不机械扩展成新的整需求 P2 分析或独立正式 SQL 归档。这是用户主动收窄为“只找数”的独立追问，不改变 P2 首次提测分析对每个真实数据验证目标默认 F+V 的规则；若用户要求页面数值对账，或继续完整处理该数据验证目标，则补齐 V。F 必须返回可在页面搜索的真实 Number/Code（必要时附内部 ID）、筛选条件、关联页面输入位置及异常观察点。用户手动执行 SQL 和页面验证；F 找到样本不等于缺陷复现。
- **页面可定位的业务标识**：找数 SQL 必须区分内部主键 ID 与页面展示/查询输入的业务编号或编码（Number/Code）。优先按当前页面绑定和接口参数确认真实展示/查询字段；如果无法确定页面用哪个，且已证实两者可取得，则在 F 输出中同时提供内部 ID 与业务编号/编码，并用不同英文别名说明用途。禁止把 `<internal_id> as <business_number>` 之类的重命名当作取得业务编号，也不能凭命名猜测业务编码字段。若原始底表缺编号，仅在有证据时作定向关联；仍无法确认则标 UNKNOWN 和页面定位限制，不造字段/不额外全仓搜索。

## 自主执行流程

以下是执行顺序索引；业务判断、边界、SQL 格式和状态的完整规则在每次必须加载的 `references/sql-design-guidelines.md` 对应章节，不能仅凭此概要跳过指南。

1. **确定目标与执行端**：识别需求、对象、页面入口和实际 SQL 解析器；独立需求优先验证最新 Manifest/P1 用例与 Oracle 的 SHA，缺证才补取。执行端以用户/环境证据为先，组织配置次之，Presto 仅为注明的默认假设（指南「独立需求 SQL」「数据源与执行引擎/SQL 方言」）。
2. **建立独立 Oracle**：先核实产品规则、上游来源、对象粒度、有效过滤、计算公式与精度；产品已聚合的合法上游可用，但不能用本次被测开发输出反推预期。缺少会改变结论的事实时局部受阻，不猜测。
3. **识别必要验证目标**：根据业务变化和风险区分 DATA_VALIDATION/N，映射场景 ID、实际 SQL 编号及 Case/CHK/MV（适用时）。同来源、同粒度、同核心计算优先共享，按指南选择安全切换或拆分。
4. **定向复用 P4**：按页面/Tab/查询模式只读核对适用知识和实际生效的前端请求、后端过滤；候选/过期或未知证据不得当作已确认条件。缺知识按需核查，不自动写入 P4（指南「来源、默认条件与数据粒度」）。
5. **核实表与字段来源**：优先用需求/产品明确且可访问的表；不适用时才定向找有业务与粒度依据的替代。源码只在缺证且有用时读取；禁止猜表/全仓搜索、`pull`、切换/重置/清理工作树或 Push，不把远端源码当作线上部署。
6. **按粒度设计计算**：确认唯一键、JOIN 放大、预聚合与去重、分子分母集合、计算/取整阶段；样本限制不可改变 V 的完整计算范围。用真实 Number/Code 定位页面，内部 ID 仅作关联证据（指南「业务计算反证」「F：找数 SQL」「V：独立结果验证 SQL」）。
7. **检查重要风险与覆盖**：主动补查适用的边界、空值、重复、分组、跨对象和列表/汇总关系；可提出 P1 用例建议但不修改正式用例，不为凑数量硬套矩阵。
8. **做可反驳的静态走查**：针对实际高风险计算构造最小反例，检查 Oracle 独立性和推理方向；结构检查不等于目标方言解析或业务正确。缺必要依据标 `BLOCKED`，仅部分断言有证据时标 `PARTIAL`，其余可靠部分继续交付。
9. **工作稿交付与归档**：完成首版语义和性能自审与工具检查，交付场景清单、对应 SQL、字段用途、页面核对方法及证据状态。正式发布须用户明确授权当前稿；P2 委托按自身工作稿交付。
10. **结果后置**：用户实际执行前不得编造样本值、预期结果或页面观察；回传 SQL 结果后才给对应记录的具体预期与页面/接口核对步骤。独立 P3 人工验证逐场景续作，P2 继续管理自己的工作稿和状态。

### 通用交付闭环（适用于任意业务，按需核对）

- P3 必须把“验证目标 → 真实数据对象与字段 → SQL 结果 → 页面/接口操作 → 判定依据”连成可执行链路：F 的样本要真正满足目标场景并带可用于业务定位的真实标识，V 要在目标粒度和有效条件下按独立 Oracle 输出可对照的预期；不能仅因为 SQL 结构完整就交付。无需 UI 的纯数据核验则写清 SQL 结果如何判定，不强行增加页面步骤。
- **交付前 AI 自主走查本轮适用的关键链路**：确认页面可用的标识与内部 ID 不混淆、同名字段的业务含义/单位与计算分母一致、JOIN/去重/分组不会改变核对集合、样本条件能够区分正确与错误行为、结果与页面/接口过滤一致；发现确定错误先自行修正，不依赖用户逐轮指出。该走查复用现有 L1/L2/L3 深度与证据，不新增独立程序、强制 SQL 数量或另一套门禁。
- 若某一关键事实无可靠证据，区分证据未知与覆盖状态：缺少必要表/字段/业务口径而无法正确设计时，受影响场景标 `BLOCKED` 并向用户说明缺口；只有部分业务断言已被验证、部分仍未覆盖时标 `PARTIAL`。不得把 `UNKNOWN` 当作场景状态，不得用假字段/假预期或被测实现自证凑成完整 SQL，也不因局部缺证停止其他已具备可信依据的查询。实际数据库运行仍由用户执行，未执行标 NOT_RUN。

## SQL-only 正式归档（独立需求 SQL 按明确要求发布）
- **发布触发**：只有用户明确要求当前稿正式归档时，才启动下述发布和验签，无须再次确认。场景切换、排错、修订均先保存工作稿。允许归档未经实库执行的稿件，标明数据库执行 `NOT_RUN` 与未核实项 `NOT_VERIFIED`。
- **正式目录与暂存职责**：正式产物进入 `output/【<禅道moduleName>】/<需求编号>-<完整需求标题>/sql/<YYYYMMDD>-vN/`；需求 Manifest 位于同一需求根目录的 `versions/<YYYYMMDD-vN>/manifest.json`；一级模块目录来源、首次查询、元数据冻结及旧需求定位统一遵循 `skills/testcase-design/references/output-archive.md`，不得从标题括号推断。`.qa-work/` 用于默认工作稿交付、修订和 publish spec 暂存。需求级场景清单使用 `scenario-coverage.md`（`category: sql`、稳定 `role: scenario-coverage`），SQL 文件按复杂度采用 `sql-design.sql` 或多个独立 `.sql` 文件。
- **必经流程**：按 `references/sql-design-guidelines.md` 的「SQL-only Manifest 正式发布与增量」章节，执行 `inspect → publish → validate`；SQL-only 发布必须提供正确 `expected_base_version`，只提交 `category: sql` 且每份 SQL 使用稳定唯一的 `role`。**不要传 `case_changes`，即使它包含空的数组也不行**；不能以 SQL 发布动作改变 P1 Case ID、Revision、Oracle 或用例身份快照。
- **增量和历史**：同一个 SQL role 的内容变化形成新版引用；其他 SQL role、P1/P2 产物继承历史 source_version 和 SHA，不复制、不删除。新的 role 不代表替换旧的 role，明确废弃时须有业务依据并单独审查。相同内容不能人为制造正式新版本；发布成功后验签失败时先核查已存在版本，不盲目再发布。
- **可用性边界**：P1 `manifest.py` 已恢复为可维护源码；本 Skill 复用统一 Manifest 工具，不自建 SQL-only 发布器。每次正式发布必须以当前环境实际 `inspect → publish → validate` 的退出码和回执判断；工具不可用或校验失败时报告 `PUBLISH_UNAVAILABLE`，不得绕过历史保护。
- **工程与业务验收边界**：SQL-only 归档及模拟设计/隔离工程集成仅在各自明确范围内验收；不代表任何具体真实需求的数据库结果正确性、跨 Agent 实际执行或整体业务验收通过。SQL 仍仅供用户手动执行，本 Skill 不执行数据库 SQL。
