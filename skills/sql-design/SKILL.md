# SQL Design（P3）｜SQL 设计

## 能力边界

- **独立需求 SQL（默认正式交付）**：用户在任何阶段明确要求“编写/生成/设计某需求 SQL”或“补充/修改已有需求 SQL”时直接调用 P3，不要求开发已提测，也不依赖 P2。需求级编写由 AI 根据需求逻辑自主识别必要的真实数据验证目标，不机械覆盖页面全部指标；每个必要目标完成 F（真实样本）与 V（独立预期）职责，默认整合为一条可执行 SQL，并通过现有 SQL-only Manifest 流程正式发布；用户明确要求“讨论/评估/预览/草稿”时仅生成 `.qa-work/` 临时草稿，不发布。
- **P1 基线复用**：先定位需求最新有效 Manifest；若存在 P1 正式 `testcases.md`/`oracle.json`，核对当前有效 artifact 的 SHA 并读取相关场景、Case ID、业务操作、预期及独立 Oracle，作为需求理解和场景覆盖的首选依据。默认不重新获取需求正文、不重跑 P1；只有 P1 基线不存在或关键业务事实确实缺失时，才定向补取缺失事实或请用户补充，不自动启动 P1/P2。
- **P2 提测交接（强制遵循 P3 规则，保持调用方隔离）**：P2 `submission-impact.md` 根据本次代码变更与业务影响自主识别需要独立真实数据验证的目标，不机械覆盖页面全部指标；对识别出的每个目标默认委托 P3 完成 F（真实样本）与 V（独立预期）职责，并将 SQL 写入绑定当前 P2 基线的 `.qa-work/<需求编号>-<需求名称>/submission-impact/verification-details.md`。P2 在生成或写入任何 SQL 正文前，必须实际读取当前 `skills/sql-design/SKILL.md` 与 `skills/sql-design/references/sql-design-guidelines.md`；未完整加载两份文件前不得生成/写入 SQL，任一文件读取失败或内容不完整时停止并报告 `P3_RULES_NOT_LOADED`，不得由 P2 自行手写 SQL 替代。P3 负责 SQL 业务分析、Oracle、F/V、数据来源、方言和格式；P2 继续管理 CHK/MV、工作稿和反馈，不启动独立 P3 人工验证或 SQL-only 正式版本。BUG 根因排查、无需求代码变更等其他 P2 工作流不因此生成或要求 SQL。
- **P3 独立人工验证（按需触发）**：独立需求 SQL 阶段一完成后默认停止，不自动开始人工验证；只有用户明确要求列出验证清单、开始验证或继续核对时，才进入阶段二。列清单只展示场景和状态，不自动开始核对；SQL 结果返回后默认每轮在聊天中完整交付一个场景，用户说“下一条”再继续，具体状态与续作规则见 `references/manual-data-verification.md`。
- **共享分析核心、调用方流程隔离**：P2 委托和用户独立调用 P3 时，共用本文件引用的 SQL 业务分析规则，包括需求变化自主识别、产品口径与独立 Oracle、按需求来源优先级找数、页面可定位样本及 SQL 结果后的必要核对指导。共享的是 SQL 业务分析能力，不共享任务管理：P2 只处理当前 submission-impact 的 CHK/MV 目标，继续使用 `verification-details.md` 工作稿、首次聊天隐藏 SQL 正文及不创建 P3 SQL-only 版本；独立 P3 继续遵守需求级场景覆盖和 SQL-only 归档。不得因共享规则扩大其他 P2 工作流，也不得由 P3 接管 P2 的 CHK/MV、报告或版本管理。
- AI 负责业务理解、数据场景、独立 Oracle、有效条件探查、表/字段及数据粒度定位、SQL 设计与复核。Python 只在必要时执行确定性文件/结构检查，不创建场景分类框架或数据库执行器。
- **任务分类**：需求级“编写/生成需求 SQL”中，AI 根据需求自主识别必要的真实数据验证目标，并对每个目标完成 F（真实样本）与 V（独立预期）职责；默认整合在同一条 SQL 中，不强制拆成两份查询。纯 UI/导航等无真实数据断言场景标 N 并说明原因。用户明确收窄为单独找数、单独对数或只讨论 SQL 时，按实际目的处理，不机械扩展。P2 `submission-impact.md` 委托 P3 时遵循相同职责与交付规范。
- **只编写只读 SQL，由用户在获准数据库环境手动执行**。P3 不连接数据库、不执行生产 SQL 或其他环境 SQL、不执行数据变更、不 Push、不修改业务仓库或未经授权写平台。收到用户执行结果后再比较 Oracle。
- **面向用户的验证说明必须说人话**：独立 P3 人工验证默认在聊天中逐场景交付，每轮一个完整场景；包含对应 SQL-01 逻辑、真实样本、独立预期、复制哪一列、去哪个页面查及正确结果。用户尚未执行时，完整 SQL-01 必须直接出现在聊天代码块中，不能只给文件路径；具体样本和数值必须等用户回传真实 SQL 结果后再给。
- 每次执行 P3 SQL 任务前，必须实际读取本文件与 `references/sql-design-guidelines.md`，不能仅凭记忆或历史摘要声称已加载。P2 委派任务同样必须在生成/写入 SQL 前完整读取这两份文件；加载失败或内容不完整即停止 SQL 生成/写入并报告 `P3_RULES_NOT_LOADED`。独立需求 SQL 再核验最新有效 Manifest 并复用可用的 P1 正式用例/Oracle；按需加载 P2 证据和 P4 知识，不批量加载全部历史和业务模块。
- **正式 SQL 发布前检查**：将完整 SQL 草稿放入 `.qa-work/` 临时文件，执行 `python -B skills/sql-design/tools/check_sql_style.py TEMP_SQL_FILE` 和 `python -B skills/sql-design/tools/check_sql_structure.py TEMP_SQL_FILE`；风格检查发现明确违规时必须修复并重跑。工具无法运行时记录 `NOT_VERIFIED`，不得声称 PASS。风格检查与 CTE 作用域检查互不替代，也不代表方言解析或业务正确。
- 用户明确启动独立 P3 人工验证时，额外必读 `references/manual-data-verification.md`；按当前 P3 Manifest 和 SQL SHA 续读同一份验证工作记录，并优先定向读取 P4 对应页面/Tab 的正式知识。当前任务属于 P2 `submission-impact` 时，不加载或执行独立 P3 人工验证流程，严格由 P2 管理 CHK/MV 和工作稿。
### 动态分析深度（L1/L2/L3）
- 每次 P3 任务由 AI 根据业务逻辑复杂度、数据粒度风险、业务影响和证据不确定性自主选择 L1/L2/L3；默认不要求用户指定等级。等级表示本次应完成的分析与验证范围，不代表模型能力保证。
- L1/L2/L3 的适用条件、必须完成的检查、自动升级和停止条件，以 references/sql-design-guidelines.md 的“动态分析深度”章节为准；不得只标等级而不落实对应验证。
- 分析中出现更高等级特征时自动升级，并简要记录触发原因；开始即明确属于 L3 的任务可直接进入 L3。关键信息不足且可能改变业务结论时不得为节省成本降为 L1。
- 所有等级均须完成适用的产品口径/独立 Oracle、必要验证目标的 F/V 内部职责、有效业务条件核对及必要 SQL 检查；F/V 是验证职责，不要求分别交付两条 SQL。N 仅用于没有真实数据断言的场景。L1 不代表降低基本质量义务；L3 也不意味着机械扫描所有表或生成更多 SQL。
- 交付时简要说明本次深度、选择依据、是否升级及原因、已完成的关键验证范围。只呈现可审计的依据和结果，不输出隐藏思维链；静态推导、结构检查与数据库运行验证继续严格区分。
- **P2 页面复现中的用户定向找数（P2 为主任务，P3 只提供用户当前明确要求的缺失样本）**：用户已通过 P2 得到问题，明确表示页面验证时缺少符合条件的数据且当前只要求找样本时，P3 可围绕指定 CHK 提供 F-only 查询，不机械扩展成新的整需求 P2 分析或独立正式 SQL 归档。这是用户主动收窄为“只找数”的独立追问，不改变 P2 首次提测分析对每个真实数据验证目标默认 F+V 的规则；若用户要求页面数值对账，或继续完整处理该数据验证目标，则补齐 V。F 必须返回可在页面搜索的真实 Number/Code（必要时附内部 ID）、筛选条件、关联页面输入位置及异常观察点。用户手动执行 SQL 和页面验证；F 找到样本不等于缺陷复现。
- **页面可定位的业务标识**：找数 SQL 必须区分内部主键 ID 与页面展示/查询输入的业务编号或编码（Number/Code）。优先按当前页面绑定和接口参数确认真实展示/查询字段；如果无法确定页面用哪个，且已证实两者可取得，则在 F 输出中同时提供内部 ID 与业务编号/编码，并用不同英文别名说明用途。禁止把 `<internal_id> as <business_number>` 之类的重命名当作取得业务编号，也不能凭命名猜测业务编码字段。若原始底表缺编号，仅在有证据时作定向关联；仍无法确认则标 UNKNOWN 和页面定位限制，不造字段/不额外全仓搜索。

## 自主执行流程
1. **识别目标和来源**：从用户要求、需求正文及已确认规则确定业务对象、页面/Tab/查询入口、数据库/数据源、执行环境和 SQL 解析方言；数据库/数据源与执行引擎必须分开记录，不得仅凭表所在数据库推断解析方言。用户未指定且没有更强的实际执行端证据时，优先读取可选的 `config/organization-profile.json` 中 `sql.default_dialect`；未配置时保留 Presto 作为可明确标注的默认假设，不冒充已确认实际执行引擎；已确认实际执行端或用户明确指定其他方言时，以其为准。已有信息不重复提问。需求级独立 SQL 先定位最新有效 Manifest；有 P1 正式用例时核对 SHA，定向读取 `testcases.md`、`oracle.json` 及关联 Case ID，复用其业务场景和独立 Oracle，不重复拉取原始需求。若 P1 尚未正式归档，优先使用当前对话/附件中的需求内容；仅当关键事实确实缺失时才补取需求来源或请用户补充。没有 P1 时不虚构正式 Case ID。

2. **建立产品口径与独立 Oracle**：写 SQL 前确认产品定义的业务逻辑、字段语义、对象/唯一键、目标粒度、有效过滤、分子分母、数据类型、精度/取整和展示规则。需求明确提供的上游库表、字段、取数 SQL 或计算逻辑可以直接作为预期依据，包含产品已经聚合的中间结果；不得仅因其已预聚合就要求重新寻找明细或另造一套计算。预期必须独立于本次被测开发输出：不得用本次变更产生的 DWD/DWS/ADS 被测结果反推或替代产品预期。相似字段不得凭名称替代；默认按产品定义的计算阶段和精度执行。若产品材料之间与用户确认口径冲突，暂停受影响目标并询问用户；关键表/字段/逻辑缺失时不猜测，按数据来源规则处理。
3. **按需求自主识别必要验证目标**：AI 根据需求逻辑、实际变更、指标之间的业务关系和风险，自主确定哪些独立业务断言需要真实数据验证；不机械覆盖页面全部指标，不按字段数量或固定模板扩展场景。纯 UI/导航等没有真实数据断言的目标标 N 并说明原因。建立 `验证目标 ↔ P1 Case ID/Oracle（若有）↔ SQL-01 查询逻辑/场景 ID ↔ 页面可核对字段` 映射。F（找真实样本）和 V（按产品口径独立计算预期）是每个必要验证目标必须完成的内部职责，不要求分别交付 SQL-F/SQL-V。默认将所有可安全兼容的目标整合为一条只读 SQL、一次执行；场景差异通过场景 ID/结果标识区分。只有执行引擎/方言、数据来源、对象粒度、JOIN/去重、有效过滤、Oracle 或输出结构存在真实冲突，且无法安全归一时才拆分并说明原因。不得为了减少 SQL 数量缩小验证范围，也不得为了追求覆盖而机械增加无价值场景。窄范围 F-only/V-only 追问及 P2 调用按各自边界执行。

4. **先复用可信知识**：必要时调用 P4 `skills/knowledge-management/SKILL.md` 的只读检索，定向获取当前页面/Tab、pageType、查询模式和目标版本适用的默认条件/字段线索；核对对象 ID、来源、`knowledge_status`、适用 SHA/环境，候选、过期或待审核记录不得当作已确认依据。区分 UI 显示默认值、请求实际传递且参与筛选的参数、后端固定过滤，只将证据支持实际生效的条件用于 F/V。P4 未命中、不可读或映射不明时标记 `NO_MATCH` / `KNOWLEDGE_UNAVAILABLE` / `UNKNOWN`，按需定向探查，不忽略默认过滤、不编造条件；P3 调用不得触发 P4 知识写入。可靠 P4 线索只需定向复用，不重复全模块搜索；确需新源码证据时按步骤 5 定向 Fetch，P4 调用不强制 Git/全量读取 DEV；不得自动新增/修改 P4 六类 JSON，也不要求其他模块专项知识先完成才设计 SQL。
5. **数据来源优先级与按需读取源码**：先直接使用需求/产品明确提供且可由当前执行端访问的库表、字段和上游取数逻辑，不因表名看起来不像常规业务表就启动无目标探查。只有明确表不可访问、字段缺失或该表不适合作为本次业务入口时，才定向查看当前组织已确认的业务表/视图（可从 `config/organization-profile.json` 获取可选视图前缀线索）；替代关系必须有业务对象、字段和粒度依据，不能只凭命名推断，也不能用本次被测开发输出替代预期来源。仍找不到或无法确认时停止受影响 SQL 并向用户询问，不猜表/字段、不做全仓或全链路搜索；若证据显示产品提供的数据来源本身有误，明确反馈并交用户确认。源码仅在字段、关联、计算粒度或有效条件确实缺证且源码能解决该缺口时按需读取；先复用可信 SHA，确有需要才根据 `config/repositories.json` 和 Git policy 定向 Fetch 并记录 SHA。不得无关仓库全量 Fetch，不 `pull`/切换/重置/清理工作树/Push；不能把远端代码直接说成线上实际部署代码，Fetch 失败或分支不明确时明确 UNKNOWN。
6. **按指标粒度与计算阶段设计查询**：确定每项指标的原始对象和唯一键，必要时先归一/预聚合，再按目标维度汇总，逐层追踪 JOIN 后的粒度与主对象值是否重复累计。比例按相同有效集合的原始分子、分母计算；**对照 SQL 的计算精度、类型和取整阶段必须一致**，不能把展示用的已取整金额再次作为计算输入，除非业务规则明确如此。跨页面/层级对账要区分两条独立计算路径与同一表达式重复命名；F 返回样本，V 返回输入/中间值/预期。详见指南“业务计算反证”。
7. **主动检查覆盖**：根据真实风险查边界、重复、空值、跨对象、聚合、排序、分页等缺少的数据验证点；给 P1 提建议但不修改已确认正式用例。不增加不适用场景或硬套固定矩阵。
8. **业务反证优先于结构 PASS**：针对当前高风险计算，用最小反例核查与本次需求相关的真实风险；对去重/计数/分组推论明确成立前提及逻辑方向，不机械套用固定反例清单。只有语义检查完成，才检查 Case/Oracle、过滤、日期、实际执行引擎/SQL 方言及参数；目标方言解析器可用时按对应方言解析，不可用时将解析兼容性标记 `NOT_VERIFIED`。`check_sql_structure.py` 只检查 CTE 跨语句作用域，不代表 SQL 方言/语法解析 PASS。已发现的推理矛盾必须明确修正或说明；缺少必要需求信息/数据来源时，将受影响目标标 `BLOCKED` 并询问用户；只有部分业务断言已得到验证、另有断言未覆盖时才标 `PARTIAL`。其他可靠部分继续交付；未执行数据库仍为 NOT_RUN。

9. **交付与复核**：需求级独立 SQL 默认交付场景清单、业务预期/未决说明和一条整合后的 SQL；清单逐场景标明场景 ID、必要验证目标、F/V 内部职责完成情况、Oracle 来源、对应 SQL-01 查询逻辑及页面核对字段，不再强制 SQL-F/SQL-V 双编号或双语句。SQL 最终输出必须返回真实可定位业务记录及其独立预期/必要中间值，不得只返回汇总统计；每个最终输出字段均说明业务含义、页面对应字段和核对用途。F 明确复制哪列到哪个页面输入项，V 明确页面哪个字段与哪列预期值对照。默认使用已确认的实际执行端方言；无法确认时按组织配置或注明 Presto 假设，按指南填写完整文件头和查询段说明；正式发布前执行风格检查与结构检查并记录结果。收到用户手动执行数据后再比较 Oracle；一次 SQL-01 取数后，独立 P3 按 `references/sql-design-guidelines.md` 的人工逐场景闭环规则逐场景聊天交付。已有 SQL 增量只更新受影响验证点，不重复探索无关条件。
10. **结果后置的具体验证指导**：SQL 执行前不得把尚未返回的记录描述成已找到的样本，也不得给出未经查询结果支持的单条具体预期值或页面实际值；先说明 SQL 用途、执行方式和输出列含义。用户执行并回传结果后，再基于真实返回行给出可直接照做的页面/接口定位步骤、搜索标识、观察字段及该行的具体 Oracle 预期；页面实际结果只依据用户反馈填写。
### 通用交付闭环（适用于任意业务，按需核对）

- P3 必须把“验证目标 → 真实数据对象与字段 → SQL 结果 → 页面/接口操作 → 判定依据”连成可执行链路：F 的样本要真正满足目标场景并带可用于业务定位的真实标识，V 要在目标粒度和有效条件下按独立 Oracle 输出可对照的预期；不能仅因为 SQL 结构完整就交付。无需 UI 的纯数据核验则写清 SQL 结果如何判定，不强行增加页面步骤。
- **交付前 AI 自主走查本轮适用的关键链路**：确认页面可用的标识与内部 ID 不混淆、同名字段的业务含义/单位与计算分母一致、JOIN/去重/分组不会改变核对集合、样本条件能够区分正确与错误行为、结果与页面/接口过滤一致；发现确定错误先自行修正，不依赖用户逐轮指出。该走查复用现有 L1/L2/L3 深度与证据，不新增独立程序、强制 SQL 数量或另一套门禁。
- 若某一关键事实无可靠证据，区分证据未知与覆盖状态：缺少必要表/字段/业务口径而无法正确设计时，受影响场景标 `BLOCKED` 并向用户说明缺口；只有部分业务断言已被验证、部分仍未覆盖时标 `PARTIAL`。不得把 `UNKNOWN` 当作场景状态，不得用假字段/假预期或被测实现自证凑成完整 SQL，也不因局部缺证停止其他已具备可信依据的查询。实际数据库运行仍由用户执行，未执行标 NOT_RUN。

## SQL-only 正式归档（独立需求 SQL 默认发布）
- **默认发布触发**：用户明确要求“编写/生成/设计某需求 SQL”或“补充/修改已有需求 SQL”时，默认按独立 P3 正式交付执行 SQL-only Manifest 发布；不要求用户再补一句“正式归档”。“讨论/评估/预览/草稿”只保留 `.qa-work/` 工作稿，不发布。用户明确要求单独 F-only/V-only 时遵从其收窄范围，不强制扩大成需求级全场景交付。
- **正式目录与暂存职责**：正式产物进入 `output/【<模块>】/<需求编号>-<需求名称>/sql/<YYYYMMDD>-vN/`；需求 Manifest 位于同一需求根目录的 `versions/<YYYYMMDD>-vN/manifest.json`；`.qa-work/` 仅用于草稿、场景清单、SQL 修改和 publish spec 暂存，不作为最终交付目录。需求级场景清单使用 `scenario-coverage.md`（`category: sql`、稳定 `role: scenario-coverage`），SQL 文件按复杂度采用 `sql-design.sql` 或多个独立 `.sql` 文件。
- **必经流程**：按 `references/sql-design-guidelines.md` 的「SQL-only Manifest 正式发布与增量」章节，执行 `inspect → publish → validate`；SQL-only 发布必须提供正确 `expected_base_version`，只提交 `category: sql` 且每份 SQL 使用稳定唯一的 `role`。**不要传 `case_changes`，即使它包含空的数组也不行**；不能以 SQL 发布动作改变 P1 Case ID、Revision、Oracle 或用例身份快照。
- **增量和历史**：同一个 SQL role 的内容变化形成新版引用；其他 SQL role、P1/P2 产物继承历史 source_version 和 SHA，不复制、不删除。新的 role 不代表替换旧的 role，明确废弃时须有业务依据并单独审查。相同内容不能人为制造正式新版本；发布成功后验签失败时先核查已存在版本，不盲目再发布。
- **可用性边界**：P1 `manifest.py` 已恢复为可维护源码；本 Skill 复用统一 Manifest 工具，不自建 SQL-only 发布器。每次正式发布必须以当前环境实际 `inspect → publish → validate` 的退出码和回执判断；工具不可用或校验失败时报告 `PUBLISH_UNAVAILABLE`，不得绕过历史保护。
- **工程与业务验收边界**：SQL-only 归档及模拟设计/隔离工程集成仅在各自明确范围内验收；不代表任何具体真实需求的数据库结果正确性、跨 Agent 实际执行或整体业务验收通过。SQL 仍仅供用户手动执行，本 Skill 不执行数据库 SQL。
