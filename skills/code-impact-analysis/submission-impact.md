# 开发提测影响分析工作流

## 工作流定位与触发

本文件是 `code-impact-analysis` Skill 下的开发提测影响分析工作流，由总入口在用户明确告知开发已提测，并提供“需求编号 + 提测点”后路由执行。

本工作流的目标是：以需求业务预期为起点，取得本次相关远端最新代码和必要配置/平台证据，双向核对需求、可用 P1 正式用例与实际开发改动，识别实现缺口、额外实现、真实影响范围和必要回归建议。

**提测点是定位起点，不是完整变更清单或影响范围上限。** 必须双向核对需求预期与实际实现，并按下方规则发现和复核真实影响范围。

本工作流只负责分析、证据整理和测试建议：
- 不生成或修改 P1 正式测试用例；可以指出覆盖缺口和用例增量建议。
- **P2→P3 数据验证（仅本工作流）**：P2 先完成需求与实际代码变更影响核对、识别必要的独立数据验证目标，再按 `references/p3-sql-delegation.md` 的两阶段判断决定是否进入 SQL 设计；不机械按页面指标或 CHK/MV 数量生成，纯 UI/导航无数据断言则不生成。目标映射、F/V 职责与 SQL 分组、P3 规则完整加载、`P3_RULES_NOT_LOADED`、受阻说明、`verification-details.md` 工作稿、首次聊天隐藏 SQL 和逐条验证均遵循上述统一委派契约。不得由 P2 自写 SQL，SQL 只读且由用户手工执行，P2/P3 不连接数据库。
- 不执行 SQL/ETL，不做数据库写入或业务数据修改。
- 不导入禅道/ACE，不调用 createBug，不修改平台记录，不 Push；若用户明确要求提交已确认缺陷，转交独立 bug-submission.md，本工作流不执行提交。
- 不修改业务代码、配置或仓库文件。
- P4 非硬依赖，满足公共入口条件时仍须定向必查；未建设或不可用时说明线索范围限制，继续完成当前可做的分析。
统一报告结构、CHK/EV/MV 编号、问题性质、运行验证状态和人工核对规则，必须遵循 references/report-format.md，本工作流不另建报告格式。

## 输入识别与需求基线

### 启动输入

启动所需的核心信息：
- 需求编号。
- 开发已提测的明确说明。
- 开发提供的提测点或本次提测范围描述。

其他信息均按需获取，不要求用户在启动前一次性提供：
- 需求正文、产品说明、原型、附件或验收标准。
- 仓库、模块、开发分支、Commit、PR/MR 或 Diff。
- 前端配置项、接口、SQL、ETL 任务、表或字段。
- 已有 P1 正式用例、用户补充的日志/截图/请求样例。

如果当前对话或项目上下文已经包含这些信息，不要求用户重复提供。若缺少需求编号、无法确认开发已提测，或没有任何可用于定位的提测点，只询问继续执行所必需的最少信息。

### 获取并冻结需求预期

1. 优先使用当前对话中用户提供的完整需求及权威业务材料。
2. 需求正文不在当前上下文时，使用当前执行环境已授权且可用的需求来源/MCP，按需求编号定向获取；不全量扫描其他需求。
3. 获取详情后，除 `spec` 正文外，必须检查当前接口实际返回的 `keywords`/备注、非空且与业务有关的扩展字段，以及其他明确承载业务补充的字段；若 Schema 提供独立评论/备注查询，按需定向读取。Markdown 正文接口不能替代备注读取，也不得猜测未发现的工具名或参数。
4. 对明确标注为补充、修订、纠正或最新说明的当前备注，以备注作为对应业务规则的优先依据，只覆盖冲突部分；正文其他内容仍有效。若冲突无法判断先后/语义且会实质改变分析结论，列出差异并向用户确认。
5. `keywords` 非空代表存在备注，但需求整体 `lastEditedDate` 不是备注单独修改时间，不得据此声称备注较新。字段达到长度上限、文本明显中断或评论分页不完整时，不得视为已完整获取；直接请用户提供完整备注，不探索突破长度限制或反复调用接口，并说明受影响 CHK，不编造、不静默忽略。
6. 对需求附件、原型或外链，仅在其内容会实质影响业务预期且当前材料不足时获取。已获取且内容未变化的资料不重复抓取；一次获取失败后停止无效重试。
7. 记录需求来源、需求编号/名称、版本或更新时间（来源提供时）、获取时间、正文/备注等实际取得范围及不完整项。
8. 将需求拆解为独立业务义务、页面/功能、字段、查询条件、配置、接口参数、数据处理和最终业务结果等核对对象。矩阵粒度仍按业务核对点，而不是技术对象。
9. 需求原文、当前有效备注及权威业务规则是业务预期来源。P1 用例、开发提测点、当前页面或当前代码均不能单独替代需求预期。
10. 需求存在歧义时，先用现有材料和源码证据判断能否缩小范围；只有歧义会实质改变结论时，提出最关键的业务澄清问题。不得自行编造业务规则。

需求资料获取失败时，保留用户已提供的需求内容和其他证据，说明缺失材料及受影响的 CHK；继续不依赖该资料的代码分析，不无限重试。
## P1 正式用例的可选交叉核对

1. 先检查该需求是否存在最新有效的 P1 正式版本及 Manifest。
2. 如存在，按 Manifest 读取当前有效的用例 Markdown（必要时读取 Oracle 或相关用例信息），记录版本目录、Manifest 版本和文件证据；不默认读取全部历史版本正文。
3. 只把最新有效 P1 用例作为交叉核对依据：核对需求义务是否被覆盖、实际代码变化及其业务影响是否被覆盖，以及用例预期是否与需求/实际实现冲突。
4. 需求是业务预期来源。用例遗漏不自动证明开发遗漏；用例与需求冲突时明确反馈冲突，不以用例覆盖需求。
5. 没有 P1 正式用例、Manifest 不可用或用户未提供用例时，记录“无可用 P1 正式用例”及原因，仍继续需求与代码双向分析，不阻断。
6. 用户在当前任务中直接提供用例文件/版本时，可作为补充交叉核对输入，记录其来源和版本；除非有 Manifest 或用户明确依据，不宣称其为最新有效正式版本。
7. P2 对 P1 产物只读，不修改、重排、退役、发布或接管 P1 用例、Oracle、XMind、历史版本及 Manifest 中既有 P1 记录。

## 代码仓库与版本基线

### 远端代码获取原则

本场景的本地仓库路径优先从工程根目录 `config/repositories.json` 读取；缺失时按 `references/git-repository-policy.md` 核实用户提供的本地仓库；仓库定位、定向 Fetch、SHA 冻结/刷新和失败边界统一遵循 `references/git-repository-policy.md`。每个独立提测分析只获取实际涉及的仓库和必要远端引用；成功后冻结完整 SHA，同一需求的后续追问默认复用，不重复 Fetch。只有用户明确要求更新基线、提供新提交/版本或目标分支发生明确变化时，才刷新受影响的引用。

1. 开始代码分析前，先识别本次需求实际涉及的仓库和分支，再对这些仓库的相关远端分支获取最新代码。
2. 只 Fetch 本次涉及的仓库和目标分支，不对无关仓库、所有远端或所有分支做全量 Fetch。
3. 不以可能过期的本地分支状态作为“最新代码”依据。记录远端引用、Fetch 时间、实际 base/head 完整 Commit SHA。
4. 对每个仓库记录比较基线、目标分支/版本、比较方式和完整 Commit SHA；有必要时记录 merge-base。Diff、源码和历史证据必须对应明确 SHA。
5. 结合变更文件清单、重命名/删除、Diff、相关 Commit 历史和目标版本源码分析。不得只看文件名、提交备注或 Diff 摘要。
6. 如果仓库、远端分支或目标版本无法从当前上下文和仓库配置中可靠确定，且会影响结论，只询问最关键的定位信息；不得猜测分支或使用未经确认的历史版本。
7. Git 获取或仓库访问失败时，记录仓库、目标引用、失败现象及受影响范围；保留已取得证据，停止无效重试，继续其他可完成分析。

### 按技术层采用已确认的比较基线

比较策略优先读取可选本地 `config/organization-profile.json` 的 `git_baselines`；未配置时依据当前任务、仓库和发布证据确定真实 base/head，不把其他组织的分支名称当作默认值。个人/特性分支必须从本次提测信息取得，不从 `from_task` 占位符猜测。分支名需由 Git 远端核实，Fetch 并冻结完整 SHA。

| 技术层 | 基线确定规则 | 取证与差异归因 |
|---|---|---|
| 前端源码 | 如组织策略为 `feature_vs_production`，生产引用是 base、本需求个人/特性分支是 head；共享集成分支只作集成核对 | 对比指定 base → head，并结合实际提交、merge-base、调用链区分本需求和其他合并改动；不能将多人集成分支直接作为单需求 Diff |
| 后端接口 | 依组织配置的生产引用（base）与本次提测引用（head）对比；组织未配置则核对当前任务真实基线 | 特殊情况下用户确认生产已夹带本需求代码且指定上一生产版本时，以该历史版本替换差异归因 base；仍单独读取当前生产 SHA 供现状核对 |
| ETL | 以该组织当前有效生产引用作为 base，与本次目标代码比较 | 使用 Git 证实 SQL/Groovy 等源码及 Diff；必要时补充具备权限的数据血缘证据 |
| 其他技术层 | 根据任务和仓库实际约定确定 | 不机械套用上述任何分支命名或比较策略 |

前端若采用特性分支相对生产的单需求比较，须分别核实生产 base 和特性 head 的远端引用及 SHA；检查 merge-base 和历史关系。如果生产不是特性分支的祖先或包含其他合并内容，则说明混入的变更及归因边界。共享集成分支只用于按需确认需求改动进入集成环境，不能代替单需求的变更归因。无法定位个人分支时只询问必要信息，不直接改用共享集成分支。

后端特殊历史基线只在用户明确说明并提供可靠历史生产引用时启用：该历史版本替代通常的差异归因 base，提测代码仍为 head；当前生产引用继续单独冻结 SHA 用于说明生产现状。缺少该历史版本时不得冒充默认比较已完整覆盖；只阻断受影响归因。其余场景依组织指定的真实生产/提测引用分析，不假设分支一定名为 main/gray。

ETL 基线由该任务的组织配置和证据决定，不套用前后端默认链路。任何 Git 基线均不单独证明实际部署时间或运行状态。

### 配置 MCP 的使用边界

1. 先从实际页面、接口、配置绑定与证据缺口选择工具。若存在本地 `config/organization-profile.json`，读取 `config_evidence.environment`、`menu_config_tool`、`dictionary_tool`；无配置时依据当前 MCP 目录和任务线索确认工具及环境，不能照搬其他公司的工具名、DEV 配置流转或参数。
2. 页面通用查询配置（列字段、快捷查询、通用筛选条件等）通过当前环境确实提供的配置工具定向读取。若工具契约含 `searchKey`、`selectedId`、`searchCode`，则按实际 Schema 定位并读取；工具采用其他参数时依最新 Schema，而非凭旧工具名称猜测。
3. **数据字典按需必查**：需求、变更或调用链涉及枚举、快捷查询选项、维度或筛选值时，先定位实际绑定的字典 Code，再调用组织已配置且当前可用的字典工具核实当前环境。允许一次查询多个已定位 Code，但不得凭页面名猜测 Code，也不能以页面配置查询替代字典核对。
4. 针对工具实际返回的代码/值、显示文案、顺序等字段与需求及前端使用路径核对；不能只因字典有返回就判定页面已绑定、参数已传递或运行结果正确。
5. 逐项区分查询成功但无数据、Code/对象未定位、工具失败、权限不足和响应不完整。证据缺失只影响相关 CHK，不推断配置不存在或自动生成缺陷；其他 Git 与业务分析继续。
6. 当前配置读取只证明指定环境、指定时间的状态，不能证明历史配置、同步或真实生产部署。只有组织/需求已确认配置来源环境时才使用对应环境；不得默认将所有组织的生产配置等同于 DEV。
7. 开发提测点并不等于完整配置变更清单：结合需求、前端绑定和已获取源码识别其他相关配置或字典线索；不全量扫描无关配置。P4 未命中时也不得把知识缺失当作配置未实现。


## 分析范围发现与提测点完整性核对

提测点只用于启动定位，实际范围由需求义务、Git 变更、当前目标版本源码、配置证据及真实调用/数据依赖共同确定。

### 从提测点向代码核实

对每项开发提测点：
- 定位其对应仓库、文件、接口、组件、配置键、任务、表或字段。
- 核实该对象是否真实存在于本次目标版本。
- 若 Diff 中存在变化，检查完整上下文及调用链，不只检查变更行。
- 若 Diff 中没有变化，检查目标版本当前实现和适用配置，区分“功能已由既有实现满足”“本次无需修改”“提测点定位错误”“确实未实现”。
- 不得仅凭 Diff 未出现代码就认定需求未实现，也不得仅凭目标版本存在同名字段就认定正确接入。

### 从实际变更反向检查提测点

- 遍历本次相关仓库的实际变更清单，包括新增、修改、删除、重命名及必要的关联提交。
- 将每项有业务含义的变化映射到需求业务义务、页面/功能和调用链。
- 识别实际变更中未出现在开发提测点的内容，判断是否属于漏报范围、内部实现调整或额外业务行为。
- 对提测点未列出但可能改变业务行为、兼容性或影响范围的变更，必须纳入分析并说明影响。
- 对需求中明确要求但 Diff 未显示变化的内容，继续核对目标版本当前源码/配置和已有实现；确认没有满足需求的实现时，才报告实现缺口。

### 变更性质分类

将实际变化区分为：
- 满足需求所必需的内部技术实现，且没有额外业务行为。
- 不改变业务行为的整理、重构、性能或可维护性调整。
- 需求明确要求的业务行为变化。
- 需求未明确描述、但可能改变业务行为、兼容性、数据范围或影响对象的额外实现。
- 无法确认业务含义或影响的变更。

不因需求没有逐字描述内部技术实现就直接判缺陷；也不得把未说明且可能影响业务的额外行为默认为已获需求授权。需要业务确认时给出具体问题、证据和影响，不猜测结论。

### 用户提供的改动点清单与需求范围核对

当用户提供配置/代码改动点清单，且说明其中可能混有其他需求内容时，按以下顺序处理：

1. **保留并盘点原始清单**：逐项保留用户给出的对象标识，统计原始条目数、唯一对象数和重复项；不得因为按业务归组、合并展示或判断范围外而改变原始数量。发现重复、别名或命名差异时，说明归并依据。
2. **先定位，再判断范围**：依据需求中的页面、功能、字段和业务义务，结合页面绑定源码/元数据及按需可用的 P4 线索，定位每个配置 Code/代码对象实际服务的页面或功能。将其关系说明为“本需求相关”“有证据确认属于其他需求”或“关联暂无法确认”；不能仅凭名称相似或用户说“可能涉及其他需求”就直接排除。
3. **范围外只做必要确认**：对有证据确认属于其他需求的对象，记录其范围外依据即可；不继续读取其全部 fieldContent、不展开其字段行为或整条实现链路，除非它与本需求存在真实共享调用或跨页面依赖。
4. **从需求反向查遗漏**：根据本需求明确涉及的页面/功能/字段，结合真实页面配置绑定关系，推导本需求应涉及的配置/代码对象，并与用户清单逐项比较。发现需求相关对象未出现在提测清单时，继续核对目标环境当前配置/目标版本源码，判断是否由既有实现满足、确实遗漏，或证据不足；不能因用户清单已列出若干对象就认定清单完整。
5. **只深入本需求范围**：对本需求相关配置按「配置 MCP 的使用边界」小节读取 DEV 当前权威值并逐项核对；对明确范围外对象不做完整业务回归。关联暂无法确认的对象说明缺少哪条页面绑定/业务映射证据，不猜测为范围外或本需求遗漏。
6. **报告数量闭合**：报告原始条目数、唯一对象数、重复项数，以及本需求相关/明确范围外/关联未明的对象数量；分类数量必须与唯一对象总数相符，并明确本需求反向发现的清单外对象。若用户明确表示只关注本需求是否有遗漏，不为其他需求对象扩展回归范围。

## 需求到实现：正向业务核对

### 建立业务核对点

从需求和权威业务材料中逐项提取业务义务，按用户可理解的业务场景/结果形成 CHK。每项至少回答：
- 用户在什么页面或业务场景进行什么操作。
- 需求要求什么字段、查询条件、配置、参数、计算规则或业务结果。
- 预期依据来自需求的哪个章节/原文或哪条已确认业务规则。
- 实际实现由哪些真实技术层和调用链支撑。
- 当前证据是否足以证明实现存在、接入完整且行为符合预期。

不能以文件、接口或 SQL 对象作为默认矩阵行；一个业务核对点可以跨多个技术层。

### 端到端检查

按实际涉及的链路逐段确认，不强制遍历无关层级：

1. 页面/入口：需求涉及的页面、组件、路由、操作入口是否存在，行为和范围是否符合需求。
2. 前端配置：相关字段、列、查询条件、快捷查询、展示规则等配置是否存在且取值正确；配置类变更必须使用配置 MCP 核对当前配置。
3. 参数传递：页面控件/配置产生的参数是否正确传递，字段名、类型、默认值、空值和枚举映射是否一致。
4. 接口接收：后端接口是否接收该参数/字段，是否经过 DTO、校验、转换、服务层并被实际使用；不能只检查接口定义。
5. 后端逻辑：条件分支、过滤、排序、聚合、计算、默认值、NULL/0、日期边界和返回结构是否符合需求；只检查本次实际涉及的规则，不机械套用无关检查项。
6. SQL/数据处理：实际 SQL、查询构造、字段来源、关联条件、过滤、聚合和转换是否支撑业务预期。
7. ETL/血缘：如果需求结果依赖 ETL 表或字段，确认对应任务/表/字段的真实代码来源和可验证数据依赖；按需补充 Bigdata MCP 证据。
8. 最终业务结果：将实现链路映射到页面字段、列表/汇总/图表/导出等最终业务结果，判断静态证据能够证明到哪一层。

参数在前端存在但后端未接收、已接收但未使用、SQL 已改但调用任务未接入、字段来源或映射错误等，均需按实际证据识别，不得因单个技术对象存在就判定端到端通过。

对简单字段新增等逻辑明确的变更，优先快速完成字段配置、接口返回、前后端映射、字段来源、格式化和关联调用方核对；不强制展开与本次业务无关的层级或通用检查项。

### 实现缺口判定

需求有明确业务义务时：
- 目标版本不存在所需实现，且没有其他已存在的有效实现：记录需求实现缺口。
- 实现只完成部分链路、参数未传递、接口未使用、配置未生效或结果不符合预期：记录具体缺口及证据。
- 目标版本已有实现且静态证据证明符合需求，即使本次 Diff 未涉及，也应记录“由既有实现满足/本次未发现实现缺口”，不得误报。
- 证据不足以判断时记录证据缺口或待业务确认，不得写成已确认缺陷。

### 漏斗、筛选条件与查询参数的完整静态链路核对

当需求涉及漏斗、快捷查询、筛选条件或其他由页面参数驱动的查询时，必须从业务条件出发追踪实际代码链路，不能只按开发提测点、字段名称或 Diff 命中进行判断：

1. **配置与页面绑定**：依据「配置 MCP 的使用边界」小节读取当前 DEV 权威配置，核对菜单/页面、配置 Code、字段、启用状态、查询类型及字段内容；继续从页面源码确认页面实际读取该配置、绑定关系正确且控件/选项按预期生成。配置记录存在不等于页面已使用。
2. **页面交互与参数生成**：追踪控件值、事件处理和页面状态如何进入查询参数；按需求核对参数名/别名、类型、格式、枚举/区间转换、默认值、空值、清空、单独筛选及组合筛选逻辑。只检查本需求涉及的行为，不机械扩展无关参数。
3. **请求与接口接收**：确认实际请求构造和调用位置，核对请求参数是否传出、字段名/类型是否匹配；继续检查后端路由/Controller、DTO/请求对象、参数校验和转换，不能只凭接口定义或 API 文档判定已接收。
4. **后端实际使用**：沿 Service、公共方法、查询构造器和条件分支追踪参数；确认参数实际参与查询/过滤逻辑，而不是仅被声明、接收后丢弃，或被其他默认值/条件覆盖。
5. **SQL 与业务消费结果**：检查最终实际使用的 SQL/查询表达式是否生成对应过滤条件，并确认过滤字段、比较方式、空值处理及条件组合符合需求。若同时存在列表、汇总、图表或导出，分别追踪其真实查询路径，比较是否遵循相同业务筛选口径；若口径有意不同，必须有明确需求/业务依据，不能自行假定一致或不同。
6. **共享实现与全量映射**：公共参数处理、公共查询方法、公共 SQL 或组件必须追踪全部实际调用方。需求范围内的字段/参数映射逐项核对；若多个对象确实走完全相同的实现路径，可以合并展示，但必须列出完整对象、映射关系和例外，不得抽样代替全量核查。
7. **证据与结论**：每个适用链路环节保留指定 SHA 下的文件/行号，配置使用当前 DEV MCP 返回证据，并关联 EV。仅有关键词搜索命中、同名字段、配置记录、接口声明或孤立 SQL 片段，不足以判定端到端静态 PASS；必须打开上下文并证明真实连接关系。存在多个 CTE、相似表名或别名时，grep 等关键词搜索仅用于定位，必须回到完整 CTE/查询块核实定义与引用关系，不得依据孤立片段跨块归属表、字段或别名。

### 静态 PASS 门槛与人工核对收敛

- **静态核对 PASS**：需求预期明确，且所有适用的配置、页面、参数、接口、后端使用、SQL/查询及结果消费环节均有充分证据支持正确接入；只对实际涉及的链路判定，不要求无关层级。
- **已确认问题**：源码/配置证据已直接证明需求要求的配置缺失或未绑定、参数未传递、接口未接收/未使用、过滤条件缺失或业务逻辑不符时，直接报告问题和证据，不再要求用户重复操作来证明同一静态事实。
- **潜在风险/证据不足**：动态路由、反射、运行时拼接、远端封装或可见源码范围不足以证明完整链路时，说明已确认部分、未知部分及其影响；不得把未查清写成 PASS，也不得仅凭缺少静态证据认定缺陷。
- **人工核对**：静态分析无法回答的具体运行态问题、已识别问题/风险所需的页面复现或业务确认，仍按最小人工任务原则生成 MV；此外，每个需要用户执行 F+V SQL 并对照页面/业务预期的独立数据验证目标，必须进入一个 MV 或映射到已有 MV。多个 CHK 只有在同一次操作能回答同一验证问题时才可合并；不按 CHK 数量机械创建 MV。回归建议、纯 UI 静态 PASS、NOT_RUN 或用例覆盖缺口本身不自动生成 MV。
- **当前范围**：本工作流以静态源码/配置/调用链分析为主，不建设或要求接口自动化、UI 自动化测试框架。静态分析不能证明的运行态行为保持未验证状态，必要时只提出最小定向人工核对。
- **MV 最小性复核**：每个 MV 只回答一个具体未决问题；在生成前检查该问题是否已由 CHK 的静态证据回答、是否与其他 MV 重复，以及是否属于用户当前分析范围。静态 PASS 的 CHK 只有在 MV 对应独立的运行态问题时才可关联；NOT_RUN 本身不构成 MV 理由。若一个 MV 包含多个页面/操作，必须说明它们为何能由同一次最小操作回答；否则拆分真实独立问题，或删除不必要的人工任务。


### 公共业务语义推理与反例验证

本节是公共方法在开发提测场景中的具体执行要求；分析深度、通用步骤和停止原则以 `references/analysis-reasoning-framework.md` 为准，本节不重复定义 L1/L2/L3，也不替代前述端到端链路、筛选参数和共享调用方规则。

1. **建立业务行为模型**：围绕每项核心业务义务/CHK，以及每项可能改变业务行为的实际代码变更，明确业务对象、用户操作/入口、适用条件、输入参数、状态/时间范围、数据粒度、预期结果和结果消费方；记录预期来自需求原文、正式业务规则还是用户确认。不得把当前代码现状直接当作业务预期。
2. **推导适用约束**：从需求义务和已确认业务规则推导本次必须成立的业务关系，按需选择对象范围、过滤条件、数据粒度、去重/聚合、计算公式、单位/精度、字段映射、状态、时间边界、权限、默认值/NULL/0、排序分页及兼容性等约束。不是每项 CHK 都要检查全部维度；从代码现状推导出的关系只能先作为待验证假设，不能自动升级为正式业务规则。
3. **正向核对业务语义**：在「端到端检查」小节的技术链路核实之外，继续确认各环节处理的是否为正确业务对象和数据范围、条件是否作用于正确字段、聚合粒度和计算口径是否满足业务约束、转换后的值是否被正确消费。涉及派生指标或多层汇总时，必要时用最小样例推导中间值和最终值，核对分子/分母、去重、过滤及边界条件；不得仅因参数已传递、字段已返回或 SQL 已包含表达式就判定语义正确。筛选参数仍按「漏斗、筛选条件与查询参数的完整静态链路核对」小节执行，不重复或弱化其完整链路要求。
4. **反向分析额外行为**：对「实际开发改动到需求：反向核对」章节中识别的实际变更，除映射需求外，还要判断变更前后哪些业务条件、对象范围、数据粒度、结果值、状态或调用方行为发生变化。区分必要内部实现、无业务行为变化的重构、需求明确要求的行为变化，以及需求未明确但可能改变业务行为的额外实现。额外行为没有明确业务预期时，不直接判为缺陷；说明证据、可能影响，并按现有规则标记潜在风险或待业务确认。需求明确要求但本次 Diff 未涉及的行为，继续检查目标版本既有实现和适用配置，不因 Diff 无变化直接判缺失。
5. **提出并验证高价值假设**：当存在复杂计算/聚合、关键分支、多个业务对象或消费方、共享实现、核心指标、额外业务行为或证据矛盾时，围绕真实路径提出少量假设。每个重要假设说明触发条件、业务约束、实际代码路径、可能矛盾、业务影响、验证证据及反证条件；选择与问题相关的最小反例，例如单条/多条、重复/唯一、空值/0/负数、边界日期、条件组合、不同粒度或不同状态。必要时对照列表、汇总、详情、图表、导出或共享调用方，但只有业务规则要求语义一致时才判定不一致为问题，不得预设所有消费方必须使用相同公式或结果。
6. **明确证据强度与结论**：将源码逻辑推导、人工构造样例明确标记为“静态推导/构造示例”，不得写成真实数据计算或运行验证。只有明确业务预期与指定 SHA 下实际实现之间存在可复核矛盾时，才能确认缺陷；预期不明确时列待业务确认，链路或运行态无法证明时列证据边界/潜在风险，不得猜测 PASS。
7. **按证据停止**：需求义务已映射、实际变更已逐项归类、适用业务约束已核对、高价值假设已证实/证伪或明确受证据限制、共享实现的实际调用方已核查，且没有新证据指向新的业务路径时停止扩展。每次扩大范围必须对应具体未决问题或新证据，不做无边界全仓扫描。

分析等级由总入口按公共方法自主选择；本工作流不因“提测点少”或“Diff 小”自动降为 L1，也不因所有业务核对点都存在就自动判定 PASS。简单字段新增仍可采用 L1，但必须完成其适用的字段来源、映射、实际使用和业务结果核对。

### 数据口径一致性检查与用户 SQL 验证

本工作流的 CHK 同时来自需求业务义务和实际实现中发现的质量约束。需求未逐条描述指标公式或聚合关系，不代表可以跳过实现自洽性检查；实现层一致性属于当前功能内在质量，不属于无依据的范围外扩展。

出现同一指标跨层级/接口/组件、列表与汇总并存、多层聚合、派生指标、一对多/多对多 JOIN、父级字段下沉到明细、复用既有接口组合或结果矛盾时，必须按公共推理方法完成：
- **指标公式矩阵**：提取各路径真实表达式，核对来源字段、分子/分母、过滤范围、去重、聚合函数、单位、精度和取整。
- **数据粒度矩阵**：核对原始行粒度、JOIN 键与基数、JOIN 后粒度、去重/窗口、GROUP BY、聚合输入粒度、输出粒度、页面列表行粒度及汇总粒度；重点检查 JOIN 扩行和父级字段重复累计。
- **跨层级/消费方对照**：比较对象集合、筛选条件、时间范围和公式，说明差异是否有业务依据；只在相同集合、相同过滤、相同粒度且指标可加时验证上层汇总与下层合计等数值关系，不对比例、平均值或重叠集合套用简单等式。
- **既有接口自洽性**：旧接口未改动、被复用或需求写明“沿现状口径”均不构成免检理由。发现差异时区分历史既存、本次引入和组合后暴露，不把历史问题误报为本次引入，也不因其历史存在而忽略。
- **报告证据**：触发时在统一报告中呈现公式矩阵、粒度矩阵、适用数值关系、差异解释和 EV；未触发时说明不适用，不机械填表。

本工作流的独立数据验证目标由 P2 根据本次需求、真实代码变更及影响链路自主识别，可以涉及真实记录、字段/维度映射、过滤、对象关联、转换、聚合、跨层级或列表/汇总一致性，不只选已发现 BUG，也不机械覆盖所有页面指标。先说明必要目标、相关 CHK 与可定位的数据来源线索，再按 `references/p3-sql-delegation.md` 进行 SQL 设计阶段判断；可设计目标由 P3 完成 F/V 职责，并按现行 P3 分组策略确定 SQL 数量与执行入口，用户限制或确实无可靠线索的目标保留具体 BLOCKED/证据缺口。**CHK/MV/P1 Case ↔ P3 场景 ↔ SQL 编号/有效条件/字段映射、最小 MV、P3 规则加载和 SQL 接收检查由委派契约统一规定**；不以缺少数据库执行权限阻断 SQL 设计，首次聊天隐藏 SQL，用户在有权限环境手工执行。

## 实际开发改动到需求：反向核对
1. 对本次相关仓库所有实际变更按业务行为归纳，不能只检查开发提测点列出的对象。
2. 将变更与需求义务逐项对应；没有直接需求对应的变化，继续判断是否为必要内部实现或无业务行为变化的重构。
3. 对可能改变业务结果、查询范围、参数语义、字段含义、聚合逻辑、兼容性或其他调用方行为的额外实现，必须单独形成核对项。
4. 对额外实现说明：变更前后行为、涉及调用方、证据、可能业务影响，以及是否需要产品/业务确认。
5. 不能仅因需求未逐字描述实现细节就认定为问题；也不能仅因开发提交已完成就默认额外行为合理。
6. 对无法证明业务影响的关联仅标记潜在影响并说明缺失证据，不扩大成确定受影响范围。

## 按技术层追踪真实影响范围

### 前端源码

按「按技术层采用已确认的比较基线」小节，以本次需求个人/特性分支完整 SHA 为分析目标，选用当前组织已确认的生产引用作为差异 base（可读取本地 `config/organization-profile.json` 的 `git_baselines.frontend.production_ref`），结合 base → 特性分支的真实 Diff、需求义务及调用链核对页面、组件、参数、字段绑定、格式化和交互。个人分支混有其他需求时须根据提交与业务证据排除无关改动；组织已确认的共享集成引用仅用于按需核对同步或集成影响，不能代替单需求 Diff。各引用均需 Fetch 后冻结 SHA；Git 本身不能证明环境已实际部署。

### 前端配置

按「配置 MCP 的使用边界」小节，从本次组织权威环境及当前已确认的配置工具定向获取最新值，核对页面/字段/查询条件的实际绑定、启用和业务行为。代码无 Diff 不代表配置未变化；当前配置正确不证明历史或其他环境状态。

### 后端接口及公共调用方

按「按技术层采用已确认的比较基线」小节，先由本次任务和可选 `config/organization-profile.json` 确定后端生产 base、提测 head 与完整 SHA，然后分析 Controller/路由、DTO/参数、Service、公共方法和实际调用链。用户确证生产版本已夹带本需求代码且提供可靠历史生产引用时，历史引用替换差异归因 base，提测 head 不变；当前生产引用仍单独冻结以核对生产现状，不能继续用普通 base/head 差异冒充完整归因。对公共接口、共享 Service、公共 SQL 或公共组件：
- 从真实定义出发追踪全部实际关联调用方。
- 逐个确认调用路径、参数、条件、业务用途和受影响行为。
- 相同行为可以在报告中合并展示，但必须保留完整调用方清单及差异。
- 不得以高风险抽样、文本搜索命中数或少数代表调用方替代全部实际调用方核查。
- 动态路由、反射、配置驱动等静态无法完全解析的部分，记录证据边界，不虚构调用关系。

### SQL 与数据逻辑

只读检查源码中实际使用的 SQL、SQL 模板、查询构造及调用关系。核对需求涉及的字段来源、过滤条件、JOIN、聚合、计算、NULL/0、时间范围和结果映射。公共 SQL 或被多个任务/接口引用的 SQL，必须追踪全部实际关联调用方。

P2 不执行 SQL，不得写入、更新或删除数据库数据。`submission-impact.md` 按 P3 委派规则，对每个独立真实业务数据验证目标默认调用独立 P3 完成 F/V 职责；不以静态分析是否已能确认问题、是否发现 Bug 或是否已有可描述结论作为跳过理由。纯 UI/导航等没有真实数据断言的场景不生成 SQL；也不按所有 CHK/MV/Case 机械生成，按来源、粒度、核心计算与 Oracle 分组复用或合理拆分，每个场景映射到具体 SQL 编号、有效条件和输出字段。F/V 覆盖映射、MV 关联和报告要求见本节“数据口径一致性检查与用户 SQL 验证”。SQL 正文写入 `verification-details.md`，首次聊天不展示；逐条验证时返回对应目标的完整 F+V。SQL 正文修订更新同一详细记录工作稿，不创建独立 SQL 文件或 P3 SQL-only 版本。
### ETL 与按需数据血缘证据

1. 按本次组织实际 ETL 仓库的生产引用（如 `git_baselines.etl.production_ref`）与本次提测目标引用获取真实源码及 Diff，核对 SQL/Groovy、任务入口及提交历史。
2. 仅当任务/表/字段依赖影响结论时，才按当前 MCP 服务与 Schema 定向查询任务、字段或表的血缘；服务标识可来自本地 `integrations.lineage_mcp`，不得默认假设任何公司服务存在。
3. 可用工具及参数、环境、上下游深度均以当前服务实际返回为准；有限层级不代表全链路完整，报告记录本次实际查询层数、覆盖方向和证据缺口。
4. 如返回结构包含嵌套 `children`，按实际结构递归读取可用节点，不只读取顶层字段；不得超出工具声明的层数或伪造缺失节点。
5. 数据血缘 MCP 只证明特定环境和查询时间下的平台元数据/血缘返回，不能替代 Git 历史源码，也不能证明某个历史 Commit 的运行状态或数据库实际数据结果。
6. 默认环境选择不得凭旧样本猜测。依据当前任务、用户指定环境和当前工具 Schema 确定；若环境选择会改变结论且无法确定，先询问最关键的环境信息。
7. 不执行 ETL、不触发调度、不写入平台或数据库。

## 共享实现、调用方与数据链路完整性

本节适用于共享实现、多消费者、跨页面、共同业务义务或用户明确要求全面覆盖的任务；局部独立变更仅核查实际相关路径。提测点只是线索，不是范围上限。搜索范围、命令、扩展和停止条件统一遵循 `references/git-repository-policy.md`。

执行时：
1. **发现候选**：结合需求、P1 用例、提测点、当前页面/功能和有效配置反查业务入口；满足公共入口条件时定向检索 P4。P4 非硬依赖，缺失、过期或不可用时仍从当前代码和配置发现。仅本类任务在 `.qa-work` 维护临时 `coverage-candidates.json`（JSON 数组，每项含非空 `id`、`source`，`kind` 默认为 `object`）。按实际业务入口/功能、接口和不同业务行为变体登记，不用分支或模块代替对象；合并同 ID 来源，保留已发现对象，不与报告同步删项；未核实项保留 UNKNOWN。
2. **核查调用链**：按 Git 规则从各相关仓库的模块起点搜索；打开上下文确认真实调用/绑定，追踪入口、参数、条件和返回值使用直至业务结果。检查无 Diff 消费者、间接调用、独立参数/计算及特殊触发；知识缺失/过期或公共定义不可得，不得停止其他可查路径。
3. **处理未解析范围**：不能枚举的边界以独立 `kind: unresolved_scope` 登记且只能 UNKNOWN，不得作为停止补查的理由。解析后保留原 ID/source，改为 `kind: resolved_scope`，`resolved_to` 填非空且唯一的真实候选 ID 数组；报告原标识以 N/A 和对应 EV 记录映射，真实对象另行核查，不得借用其他对象证据。
4. **覆盖表格式**：报告使用唯一、顶格且不在注释/代码块/隐藏内容中的 `### 覆盖对账` 小节，声明 `覆盖完整性：COMPLETE` 或 `覆盖完整性：PARTIAL`，其后使用固定四列表格 `| 对象标识 | 静态核查 | 解析目标 | CHK/EV或理由 |` 及 `|---|---|---|---|`。每个候选一行，行首尾为 `|`，单元格不得换行或含 `|`；状态仅 `PASS/FAIL/UNKNOWN/N/A/OUT_OF_SCOPE`。普通对象和 unresolved_scope 的解析目标为 `-`；resolved_scope 原标识用 N/A，目标为与清单一致的 JSON 数组。AI 逐项核实 PASS/FAIL 的 CHK/EV、N/A 的不适用/解析依据、OUT_OF_SCOPE 的用户明确授权及 UNKNOWN 的具体缺口；CHK/EV 定义和引用必须真实、可见、唯一且对应对象，不得只藏在链接目标或代码块。相同行为可共享证据，不复制正文。存在 UNKNOWN、未决范围或未解决证据缺口时声明 PARTIAL。COMPLETE 仅表示登记对象结构一致，不代表发现完整、证据真实或业务通过。
5. **发布前复核**：AI 在同一次反向审查中核实候选来源与保留、核查状态、排除授权、映射及证据对应性。对实际 `impact-analysis.md` 执行 `python skills/code-impact-analysis/tools/check_coverage.py <候选清单> <报告>`；工具只核对候选与固定表的对象、状态和映射，不验证证据真实性。INVALID 时定向补查复验；仍有缺口则 PARTIAL 交付。临时清单不进入 Manifest。

## 问题性质、验证状态与回归建议

每项 CHK 分开记录：
- 问题性质：已确认缺陷 / 潜在风险 / 待业务确认 / 无问题。
- 静态核对：符合预期 / 发现不符合 / 证据不足 / 不适用。
- 验证情况：静态已核实 / 待人工验证 / 无需人工验证。
- 实际运行验证：未执行时 `NOT_RUN`；只有真实执行并取得证据后才记录 PASS/FAIL/BLOCKED。

已确认缺陷必须有充分证据证明实际行为违反明确业务预期。缺陷等级仅对证据充分的已确认缺陷，按公司现有 P0/P1/P2/P3 标准评估；不另建高/中/低等级或风险分数。潜在风险、待业务确认不自动分配缺陷等级。

回归建议围绕有证据的业务影响提出，并关联 CHK，说明：
- 回归对象（页面、功能、查询条件、接口消费者、数据链路或指标）。
- 具体验证内容和必要操作。
- 提出原因及对应影响证据。
- 明确预期结果。

不把所有关联模块都列为回归范围；没有真实依赖或合理影响依据的模块不纳入。

## MCP 故障与证据缺口处理

1. 先完成需求、提测点和代码初步定位，再确定实际涉及的技术层和 MCP 能力；不全量调用 MCP。
2. 调用前确认当前工具可用性、Schema、查询对象和环境；仅查询本次判断需要的对象。
3. 某个 MCP 调用失败、超时或返回不完整时，记录服务/能力、对象、可观察到的失败现象、查询时间和受影响 CHK。
4. 区分查询成功但无数据、对象不存在、调用失败、返回不完整；不得混为一类，也不得把工具故障写成业务缺陷。
5. 保留已有 Git、源码和其他 MCP 证据，继续完成不依赖缺失证据的分析；停止无效重试，不因单个 MCP 故障终止整个任务。
6. 证据缺失本身不自动生成 MV。只有用户确实能够执行且可回答具体问题的验证，才放入 `manual-verification.md`；否则在主报告说明分析限制。
7. 不得将 MCP 当前元数据推断为历史配置、历史代码、生产部署版本或数据库运行结果。

## 静态分析与人工验证边界

优先通过需求、Git Diff、指定 SHA 源码、配置 MCP 和真实调用/数据依赖完成静态核对，减少用户重复人工检查。

静态证据足以证明实现符合需求的项目，记录“静态核对通过/可免除重复人工源码核对”，不要求用户再次逐字段检查相同源码或配置。

开发提测影响分析在存在需要用户实际复核/确认的事项时生成 `manual-verification.md` 与 `verification-details.md`：包括静态证据无法回答的运行态事实，以及 AI 已识别为已确认问题、潜在风险或待业务确认且确实需要用户复现页面/核实行为/作业务确认的项目。每个需要用户执行 F+V 并对照页面/业务预期的独立数据验证目标，即使关联 CHK 已静态 PASS，也必须进入一个 MV 或映射到已有 MV；静态 PASS 不免除这项独立数据验证。不得把所有 CHK 或回归建议自动转成 MV；其余静态 PASS 仅在存在独立运行态问题时纳入。前者保持简要待办，后者逐个 MV 记录完整描述、AI 分析结论、关联 CHK/EV/数据验证目标、代码证据、环境/前置、可执行步骤、明确预期、实际结果回填位置及适用 SQL。没有符合条件的事项时两份文件均不生成空文件。

数据库验证由用户执行，P2 不连接数据库。首次提测分析对识别出的每个必要数据目标按 `references/p3-sql-delegation.md` 判断生成条件：可设计时委派 P3 完成 F/V 并按契约写入 `verification-details.md`；确无来源线索或用户明确禁止生成 SQL 正文时，保留目标、CHK/MV 映射、具体阻塞及恢复条件，不编造 SQL。每个需要用户执行 F+V 并与页面/业务预期核对的目标必须进入一个 MV 或映射现有 MV；受阻目标不因无法生成 SQL 而从报告消失。用户逐条验证时返回已具备的 F/V、步骤与证据，未实际执行时保持 NOT_RUN，不宣称运行 PASS。

## P5｜接口自动化维护建议（确认式联动，仅开发提测）

本节仅随 P2 分析形成**候选建议**，不执行 P5、ZeroRunner 操作或修改 P2 的 CHK/MV/SQL。仅选择本需求直接或通过实际调用链、共享依赖间接受影响的 API；纯 UI/布局或无接口影响时写「本次无建议维护接口」，不初始化页面全部历史接口。

1. **接口身份与影响证据**：核对真实 API Code/路由、前后端调用绑定、业务行为、对应 P2 CHK/EV、代码 base/head SHA 与路径/行号；不能只按开发提测点、文件名或 API 名称认定新增/变更。
2. **可信基线证据**：只对受影响 API 定向只读检查 `output/api-automation/index.json`、`interfaces/<API Code>.json` 的当前/历史 Case、Step 与覆盖记录；按 P5 `SKILL.md` 加载 `references/archive-maintenance.md` 后查询。若平台 Case/Step 会改变分类且有已授权只读工具，按 P5 `references/platform-execution.md` 定向回读；不可用则说明缺口，停止无效重试。**本地无索引不等于平台无 Case，仅有 Case 不等于可信完整覆盖**，缺证标「基线待核实」，不强制全量扫描/Run。
3. **动作分类**：有旧版及目标版证据确认本轮真正新增的接口 → 新接口初始化；原本存在且经可信证据核实尚无 P5 覆盖基线 → 存量接口首次初始化（完整建立有测试价值的前后端场景，不只补本次需求）；已有可信基线且受影响 → 增量更新（保留历史有效场景，评估 ADD/UPDATE/KEEP/RETIRE/REVIEW）；证实无行为/依赖变化 → 无需维护；身份、关联或基线缺证 → 待核实，可给条件性建议，不能强行判断初始化或增量。
4. **交付**：`impact-analysis.md` 和首次聊天的原有结论、静态 PASS、问题/风险、MV、NOT_RUN、正式路径之后，分别附「P5｜接口自动化维护建议」编号清单，给出 API 身份、影响/CHK/EV、覆盖基线依据、建议动作、建议初始化/增量场景重点与「待你确认」；无可靠候选则写本次无建议维护接口。**该清单不是 CHK/MV 或已完成的 P5 产物/运行证据，不新增 Manifest role、版本或平台 Case。**
5. **确认式续接**：用户明确批准清单中的指定接口（如「执行第1、3项」「全部维护」）才启动独立 P5；未回复、只确认 P2 结论、拒绝或部分批准时其余候选不执行。P5 复用已有最新有效 P2 报告和 SHA 作为线索，执行时仍独立核对当前前后端源码、接口及覆盖基线，不重跑 P2、不重复 Fetch P2 的同一基线或发布新 P2 版本。P5 平台写入/Debug/正式 Run 保持自身授权和安全边界。

## 报告、聊天交付与正式归档

### 完整分析报告
每项任务默认生成一份完整 `impact-analysis.md`，遵循 `references/report-format.md`。报告必须包含全部业务核对点，包括静态 PASS、已确认缺陷、潜在风险、待业务确认、影响范围、回归建议、未决事项和 EV 证据索引；不得按技术层拆成多份完整报告。

**开发提测报告的可读性要求：** 第一屏必须列出静态 PASS 的全部 CHK 编号及业务名称、已确认缺陷、潜在风险、待业务确认、用例覆盖缺口、人工核对 MV 和运行验证 NOT_RUN；每类分别给出数量/编号、中文状态、下一步。不得把“其他待确认/范围边界”作为混合类别。业务核对矩阵每个 CHK 必须明确是否需要人工核对及对应 MV；静态证据已足够回答的项目标明无需人工重复核对。

- **分析深度**：记录本次选择的 L1/L2/L3、选择依据、是否发生自动升级及触发原因、实际采用的关键业务约束视角；只记录可审计的分析摘要，不输出隐藏思维链。

EV 证据至少记录：
- Git：仓库、分支、base/head 完整 Commit SHA、比较范围、文件路径和行号。
- 源码/历史：指定 Commit、文件路径和行号；提交时间不冒充发布时间。
- MCP：服务/能力、查询环境、对象、实际查询时间、关键返回和完整性边界。
- 需求/用例：来源、需求编号、章节或 P1 有效版本。
- 运行证据：实际环境、版本、操作和真实结果。

### 分析模式与人工核对清单交接

本工作流支持两种分析模式。默认使用“正常提测分析”；只有用户明确要求独立分析、盲分析、换 Agent/模型对比或“不参考上一轮结论”时，才使用“独立分析”。

**正常提测分析（默认）：**
- 每次用户明确启动的新一轮正式提测分析，均作为新的 P2 分析版本发布；不以代码是否发生变化作为是否创建版本的判断条件。
- 正常提测分析开始时，先从需求目录读取最新整体 Manifest，执行 inspect/validate 并校验当前有效 P2 artifact SHA；再读取当前有效 `impact-analysis`、可选 `manual-verification` 和 `verification-details`。不得从 P1 基线自己的旧 Manifest 寻找当前 P2 产物。
- 同一轮未发布分析的跨对话续作或逐条人工验证，检查固定工作稿 `.qa-work/<需求编号>-<需求名称>/submission-impact/verification-details.md`。其 front matter 必须绑定 `workflow: submission-impact`、需求编号、最新整体版本/Manifest SHA，以及当前 P2 各 role 的 path/SHA。工作稿与当前 P2 artifact 基线匹配时优先续读工作稿；只有工作稿不存在时才以当前正式 `verification-details` 为续读来源。
- 若最新整体版本仅因 P3 等无关发布变化、而 P2 artifact path/SHA 未变化，核对后更新工作稿基线指针并继续。若 P2 artifact 发生变化，按 MV ID 对照工作稿记录的旧基线和当前正式 artifact，合并无冲突的用户反馈、SQL、实际结果及状态；存在冲突、基线无法验证或元数据缺失时，保留工作稿、不覆盖、不回退旧 SQL，停止自动合并并报告 WORK_DRAFT_CONFLICT。正式发布成功后将工作稿基线指针更新到新版本和新 artifact SHA；正式文件不原位修改。
- 正常模式读取上一轮报告、清单和详细记录后，逐项结合本轮 CHK、最新代码/配置/运行证据复核：仍适用且未完成的事项保留原 MV ID、状态和必要内容，并同步保留对应 SQL、代码证据及已回传的实际结果；新发现事项分配新 MV ID；已 PASS/IGNORED 的事项不重复要求核对（IGNORED 不计为验证通过）；旧事项已不再适用或已有充分静态证据可回答时，从本轮待办中移除，并在主报告记录处置原因。
- 本轮未评估、证据不足或状态不明的旧事项继续保留，不得因本轮未重新提交清单而清空。独立盲分析不得读取或继承正常模式的 `.qa-work` 工作稿。
**独立分析（明确触发）：**
- 分析开始前不得读取上一轮 P2 报告正文、业务结论、CHK/EV/MV 内容、人工核对操作与预期或 `verification-details.md`，避免结论污染。
- 允许读取最新整体 Manifest 的版本号、需求身份、P1/P3 artifact 路径与 SHA 等元数据，以确定本轮 expected_base_version、P1 用例基线和需保持不变的产物；允许读取最新有效 P1 用例及其 Oracle，但不得读取上一轮 P2 结论。
- 独立分析报告必须记录分析模式、执行 Agent、模型/版本（当前环境可确认时）、分析时间（北京时区，精确到秒）、P1 基线和代码 base/head SHA，并明确“上一轮 P2 正文：未读取”。
- 独立分析的 CHK/EV/MV 编号仅在本次 P2 版本内有效；MV 使用本报告内编号，跨版本唯一引用为“P2 版本号 + MV ID”。不得继承上一轮 MV 内容或状态。只有本轮报告已完成并冻结后，用户明确要求比较时，才读取历史 P2 报告进行差异比较。
- 独立分析不得继承旧 `manual-verification`、`verification-details` artifact 或正常模式 `.qa-work/<需求编号>-<需求名称>/submission-impact/verification-details.md` 工作稿：若本轮有待人工事项，则发布本轮新清单和详细记录替换当前有效 role；若本轮没有待人工事项，则仅依据 Manifest 中 role 的存在性，在 publish spec 使用 retire_artifacts 退役旧 role，不读取旧文件正文。旧文件仍保留在历史版本。
**人工核对清单与发布后反馈：**
- 仅在本工作流专用生成条件满足时创建 `manual-verification.md` 简要清单和 `verification-details.md` 详细记录。简要清单只保留 MV 编号、关联 CHK、简要任务、预期、状态和详细记录引用；完整业务描述、AI 原始判断、代码证据、环境/前置、页面步骤、实际结果、SQL 及执行反馈统一保存在详细记录中，状态以详细记录为事实来源，清单只镜像状态。
- 如果本轮所有人工待办均已明确处置且没有新增人工事项，新版本可通过 retire_artifacts 退役简要 `manual-verification` role；但只要 `verification-details.md` 保存了最终 SQL、实际结果或结论，就必须保留其当前有效 role，不能随待办清空而一并退役。后续新分析确认详细记录已不再适用时，才可退役该 role；历史文件永久保留。
- 正式发布后收到人工反馈或需要修订报告时，必须形成新的 P2 正式版本，不得原位修改已发布报告、清单、详细记录或历史 Manifest。SQL 反复修订期间先在固定 `.qa-work/<需求编号>-<需求名称>/submission-impact/verification-details.md` 工作稿中更新当前 SQL，不为每次试错单独发布版本；CHK/MV 结果确认或用户要求正式归档时，按本文件「需求级归档与 Manifest」节通过 `manifest.py publish` 发布新版本。正式发布前的草稿修订也使用同一固定工作稿；同一轮任务最多发布一个成功版本。
- 只读取、解释或引用已有分析结果不创建新版本；继续同一轮尚未发布的分析只更新临时草稿。新一轮提测或明确要求的独立分析即使代码未变化，也必须形成新的正式 P2 版本。
### 需求级归档与 Manifest

有明确需求编号时，统一使用 `output/【<禅道 moduleName>】/<需求编号>-<完整需求标题>/` 作为需求级归档根目录，P1/P2/P3/P5 共用 `YYYYMMDD-vN` 版本序列。一级模块名按 `skills/testcase-design/references/output-archive.md` 从禅道需求详情 `moduleName` 获取；不得从需求标题括号推断，也不得回退到未分类目录。需求目录保留完整原始标题（包括 `【】`）。已有需求先定位现存根目录并沿用 Manifest 冻结模块元数据；P2 不再归档到 P1 基线目录内原位更新，也不建立 Agent 专属目录或独立版本账本。

版本定位必须区分两个概念：
- **最新整体版本**：manifest.py inspect 返回的最新 latest_version，它决定本次发布的 expected_base_version；可能是 P1、P2 或 P3 创建的版本。
- **最新有效 P1 基线**：从最新整体 Manifest 的有效 artifact 清单中识别 category=testcases 的 markdown、oracle、xmind，并沿来源版本确定实际 P1 用例版本。没有 P1 时明确记录“无可用 P1 正式用例”，继续分析，不得虚构基线。

正式 P2 产物结构：

```text
output/【<禅道moduleName>】/<需求编号>-<完整需求标题>/
├── versions/<YYYYMMDD-vN>/manifest.json
└── analysis/<YYYYMMDD-vN>/
    ├── impact-analysis.md
    ├── manual-verification.md   # 仅有待人工核对事项时创建，简要待办/状态
    └── verification-details.md  # 仅开发提测且存在人工事项时创建，详细步骤/证据/SQL/结果
```

正式发布使用现有 manifest.py inspect → publish → validate：
- publish spec 显式填写 expected_base_version=<最新整体版本>；不得误填最新 P1 基线版本。
- `impact-analysis.md` 使用 category=`test-impact-analysis`、role=`impact-analysis`、path=`analysis/impact-analysis.md`；人工清单存在时使用同类别的 `manual-verification` role；开发提测存在人工验证事项时同时登记同类别的 `verification-details` role。若现有 publisher 不接受该 role，停止正式发布并报告 PUBLISH_UNAVAILABLE，不手工绕过 Manifest。
- 新版本 Manifest 保存在 `versions/<版本号>/manifest.json`；P2 artifact 的 path 指向 `analysis/<版本号>/` 下的对应文件，source_version 为本次版本；首次登记为 added，已有同 role 时为 updated，并记录真实 SHA-256。
- 通过现有发布器继承全部未变化 P1、P3 和其他有效 artifact；不复制或修改未变化文件。必须保持 P1 用例的 case_id、revision、content_sha256 及退役原因等身份/内容信息不变，case_snapshot 中的轮次状态 status 由现有 publisher 按当前版本计算（例如 P1 首次发布 added → 后续 P2-only 发布 unchanged）；不能要求 case_snapshot 整个对象逐字段不变，也不能将正常轮次状态变化认定为修改用例。case_count、retired_case_count、validation 和 P1 artifact 路径/SHA 必须保持不变；P3 SQL 及其他非 P2 artifact 原样继承。
- 新版本顶层 delivery_status 沿用最新整体 Manifest 原值，不得用 P2 报告的 PARTIAL/COMPLETE 覆盖 P1 交付状态。P2 自身的分析状态只写在报告中。
- 历史版本文件和 Manifest 永久保留。发布前后均不得手工覆盖历史文件或绕过 Manifest；发布后必须执行 manifest.py validate 并核对新旧 P1/P3 artifact 路径/SHA、P1 用例身份/内容指纹/退役信息、计数与 validation，轮次 status 按 publisher 语义单独校验。
- 如果没有既有需求级 Manifest，仍可继续 P2 分析；首次 P2-only 发布必须由现有 publisher 实际接受并通过 validate。若不支持，报告 PUBLISH_UNAVAILABLE 并停止正式发布，不得手工创建 Manifest 或退回原位写入。

没有需求编号的 BUG/CODE 任务继续使用各自独立任务目录和版本序列，不受本条需求级归档规则影响。

### 聊天交付

正常 P2 首次分析聊天回复必须与报告并行交付，严格按 `references/report-format.md` 的对话交付模板展示结论、静态核对通过项、问题/风险、简要人工核对事项、实际运行验证状态和正式产物路径；适用时列出 `verification-details.md` 路径，但不展示其中 SQL 正文。用户逐条验证 CHK/MV 时，再返回对应项目的完整描述、步骤、预期、代码证据和可复制 SQL。
不得只给文件路径，不得隐藏静态 PASS，也不得把静态核对结果写成页面/接口运行 PASS。没有人工核对事项时明确说明无需人工核对。

聊天回复还必须列出静态 PASS 的全部 CHK 编号及简短业务名称；需要用户处理的 MV 必须列出编号、中文 + 机器状态、操作和预期。FAIL 表示已执行后不符合预期，不要求用户重复执行；BLOCKED 说明解除条件；PASS/IGNORED 不再重复核对。不得只给汇总数字，不得把覆盖缺口写成代码缺陷。

首次提测聊天报告末尾还须附 P5 建议清单或明确「本次无建议维护接口」，但仅是待确认的选择，不视为 P5 已执行。

正常业务分析不附带 Codex 验收提示词；Codex 独立验收只用于 QA Agent 工程建设/规则修改，或用户明确要求时。

## 完成前检查

交付前逐项确认：
- 已取得并记录需求预期；未把提测点或用例当作唯一业务依据。
- 已对相关远端分支定向 Fetch，并记录各技术层实际 base/head 完整 SHA；未全量拉取无关仓库。
- 已从需求到实现、从实际变更到需求双向核对。
- 已识别开发提测点未覆盖的实际变更，以及提测点未在 Diff 中出现时的既有实现/配置核查结果。
- 已按实际涉及层级完成源码、配置、接口、SQL/ETL 和真实依赖核对；未机械扩展无关层级。
- 已按本节及 Git 规则完成动态范围发现、实际消费者核查和定向反向审查；记录 P4 检索/不可用情况、模块 pathspec、真实标识及范围扩展依据。AI 复核候选保留、核查状态、排除授权、映射和证据对应；运行 `check_coverage.py` 对账。工具只证明已登记对象结构一致，未核实范围仍须标 PARTIAL。
- P1 最新有效用例（如有）仅作为只读交叉核对输入；缺少用例未阻断分析。

- 已按公共方法选择并记录 L1/L2/L3 及选择/升级依据；没有仅凭文件数、Diff 大小或提测点数量决定分析深度。
- 对适用的核心业务约束完成语义核对；重要假设有触发条件、实际路径、反例/反证及证据，静态构造示例未冒充运行结果。
- 已判断是否触发数据口径一致性检查；触发时完成指标公式矩阵、数据粒度矩阵及适用数值关系核对，或明确记录证据限制和用户 SQL 验证交接。
- 已按 `references/p3-sql-delegation.md` **逐个必要数据验证目标核对两阶段实际分支及证据**：无真实数据断言的场景说明不适用、不生成 SQL；用户明确限制本轮不生成 SQL，或完全无可靠来源线索且无法定位的目标，保留 CHK、必要 MV/目标映射、具体 `BLOCKED` 原因、覆盖缺口和恢复条件，不要求提前完整加载 P3 两份规则，亦不误报 `P3_RULES_NOT_LOADED`；来源线索可信但尚不完整的目标，允许 P3 按契约定向核实。**仅当实际准备生成、补充、修改或写入 SQL 正文时**，检查当前任务完整加载两份现行 P3 规则及 `P3_RULES_LOADED` 证据；实际读取失败或不完整才报告 `P3_RULES_NOT_LOADED` 并停止相关 SQL 正文，不阻断其他分析，不由 P2 手写兜底。对可生成的目标核对 P3 F（样本成立依据及页面定位）和 V（独立产品 Oracle）、按现行 P3 分组策略复用或合理拆分并映射到具体 SQL 编号/有效条件/输出字段、CHK/MV/P1 Case 与 P3 场景/输出字段映射、`verification-details.md` 锚点、方言/格式/输出列注释/结构检查、样本数量按场景需要与平台限制决定且 F 限量不截断 V 完整计算集合等既有接收要求；未完成目标如实按现有状态记录 `PARTIAL/BLOCKED` 与证据缺口，不得为满足清单伪造 F/V、SQL 或运行 PASS。SQL 只读，由用户手动执行；P2/P3 不连接或执行数据库，运行验证未执行保持 `NOT_RUN`。
- 每项业务核对点有 CHK，证据有 EV；静态结果、问题性质和实际运行状态没有混淆。
- 只把确实需要用户执行且有明确预期的事项列入 MV。
- 正式产物发布到本轮新的需求级 YYYYMMDD-vN/analysis/，通过 manifest.py inspect → publish → validate 登记；expected_base_version 使用最新整体版本，不在 P1 基线 Manifest 中原位更新。
- 已核对本轮受影响 API 及 P5 基线证据，在报告和首次聊天提供建议或说明无候选；未经确认不触发 P5 写入/Run。
- 未修改业务代码/配置/P1 用例，未执行 SQL/ETL，未导入平台，未 Push。
