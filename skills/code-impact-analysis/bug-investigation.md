# BUG 根因排查工作流

## 工作流定位与触发

本文件是 code-impact-analysis Skill 下的 BUG 根因排查工作流，由总入口在用户描述实际异常、错误或业务结果不符合预期，并要求定位原因、排查 BUG 或分析根因时路由执行。

**不要求需求编号、Bug 单号或完整技术定位信息。** 用户提供异常现象即可开始。需求编号、页面、接口、字段、参数、日志、截图、发生时间、环境、仓库、分支和 Commit 均为可选线索；有则使用，没有不阻断启动。

本工作流的目标是：先理解当前实际行为，再用有限、定向的代码定位确认问题路径；结合 Git 历史反向追溯相关代码变化；按实际技术层选择公司 MCP 补充当前配置、血缘或业务证据；判断根因证据、全部实际关联调用方、业务影响和回归范围。

本工作流只负责分析、证据整理和修复/回归建议：
- 不修改业务代码、配置或仓库文件。
- 不执行 SQL/ETL，不写入数据库或业务数据。
- 不导入禅道/ACE，不修改平台记录，不 Push。
- 不生成或修改 P1 正式测试用例；可以提出测试覆盖缺口和用例增量建议。
- 不依赖 P4；P4 未建设或不可用时，仍使用 Git、源码和按需 MCP 完成可完成的分析。
- 不自动创建 Bug 单，不调用 createBug；分析完成后，如用户明确要求提交已确认缺陷，才将对应证据交接给独立 bug-submission.md。

统一报告结构、CHK/EV/MV 编号、问题性质、缺陷等级、运行验证状态和人工核对规则，必须遵循 references/report-format.md，本工作流不另建报告格式。

## 输入识别与问题范围

### 启动输入

启动所需的核心信息只有：
- 用户描述的实际异常、错误或不符合预期的业务结果。
- 用户希望定位原因、排查 BUG 或分析根因的意图。

以下信息均为可选定位线索，不得设为启动前的必填清单：
- 发生异常的页面、菜单、操作入口或业务模块。
- 接口名称、请求 URL、请求参数、响应字段、异常码或错误信息。
- 具体字段、指标、查询条件、计算结果或数据对象。
- 日志、堆栈、请求/响应记录、截图、录屏或附件。
- 发生时间、时区、频率、首次发现时间、最近一次正常时间。
- 生产/测试/开发环境、仓库、模块、分支、Commit、发布版本。
- 关联需求、P1 最新有效正式用例或历史 Bug 记录。

先使用当前对话、附件、已授权项目文件和已有上下文中的信息，不要求用户重复提供。不得为了补齐可选字段而延迟已经可以开展的定位。

### 问题范围初步界定

先将用户描述整理为：
1. **实际现象**：用户看到了什么异常，或操作后实际发生了什么。
2. **预期结果**：用户明确说明的预期；如未说明，不擅自编造。
3. **发生范围**：已知页面、接口、字段、对象、用户范围、环境及时间范围；未知项明确标记未知。
4. **复现特征**：稳定/偶发、全部/部分对象、特定条件触发等；仅记录用户提供或证据支持的事实。
5. **当前可用线索**：选择最有定位价值的线索作为第一步，不要求所有线索同时具备。

如存在与异常相关的最新有效 P1 正式用例，可只读核对其预期和既有回归覆盖；需求或权威业务规则仍是业务预期来源，用例不得替代需求。没有可用 P1 用例不阻断 BUG 排查。

如果用户只描述了无法区分具体异常的笼统现象，先询问一个最关键的澄清问题；不要发送多项技术信息收集表。

## 有限、定向的定位策略

### 第一轮定向定位

根据现有线索选择最短定位路径，例如：
- 页面/字段：定位页面、组件、字段配置读取和数据映射，再追踪其真实接口。
- 接口/参数：定位路由、Controller、DTO、Service 和参数使用位置。
- 日志/堆栈/异常码：从异常文本、类名、方法名或调用栈定位实现及触发条件。
- 计算/数据结果：从展示字段或接口响应反向追踪计算逻辑、SQL/ETL 来源和数据依赖。
- 仓库/分支/文件：从用户给出的具体对象直接进入相关实现。
- 时间线：将发生时间用于筛选相关提交、发布记录或日志；不得仅凭时间相近就认定因果关系。

第一轮只检查与现象直接相关的模块、符号、接口和必要调用路径。先理解当前实际实现，不从提交备注或文件名直接推断根因。

### 一次有限范围扩展

第一轮仍无法定位，或发现现象可能跨层传播时，允许进行**一次有限范围扩展**，仅扩展到与已知线索直接相邻的范围，例如：
- 从页面扩展到其实际调用接口，或从接口扩展到直接使用的 Service/SQL。
- 从异常方法扩展到其直接调用方、关键依赖或最近相关变更。
- 从目标字段扩展到实际来源字段、映射关系或对应 ETL 任务。
- 从一个共享实现扩展到其真实引用和调用方。

有限扩展不等于可以抽样遗漏调用方：一旦识别到公共接口、公共 SQL、公共组件或其他共享实现，必须按「关联调用方与业务影响」章节完整追踪全部实际关联调用方。

不得借一次扩展为由全量扫描所有仓库、所有分支、无关模块或全部 MCP。不得重复进行多轮无边界关键词扫描。

### 停止扫描并询问

完成第一轮定位和一次有限扩展后，如果仍缺少决定性定位信息：
- 停止继续扩大搜索范围。
- 简要说明已经定位到的内容、尚不能确定的关键点及其影响。
- 只询问一个最有助于继续定位的信息，例如具体页面/字段、接口请求 URL、异常日志片段、仓库名称或大致发生时间及其时区。
- 用户补充后，只针对新增线索继续，不重复已完成的无效扫描。

如果现有证据已足以完成部分结论，不因其他独立证据缺失而停止全部分析；按统一报告规范交付已完成范围及证据限制。

## 代码基线与当前实际行为

本场景的本地仓库路径优先从工程根目录 `config/repositories.json` 读取；缺失时按 `references/git-repository-policy.md` 核实用户提供的本地仓库；仓库定位、定向 Fetch、任务内 SHA 冻结/刷新和失败边界统一遵循 `references/git-repository-policy.md`。先按本文件识别生产或非生产环境及其代码基线，再只获取实际涉及的仓库和环境引用；同一任务后续追问复用已冻结 SHA。

### 先识别问题环境

先根据用户说明和可验证信息判断问题发生于生产还是非生产环境。环境不明确且会实质改变代码基线时，只询问最关键的环境信息；不得把测试环境问题默认当作生产问题，或把生产问题默认套用开发分支。

### 生产 BUG 的默认代码基线

生产 BUG 默认以**当前最新生产代码**作为源码分析基线，不要求用户默认提供生产部署 SHA。

执行规则：
1. 根据仓库配置、远端引用、项目既有约定及可用发布信息，识别该仓库实际使用的生产分支/引用；不得仅凭习惯假设生产分支一定叫 main/master。
2. 只对本次定位涉及的仓库及其生产引用获取最新远端代码，不全量 Fetch 无关仓库或所有分支。
3. 记录仓库、远端生产引用、获取时间和最新完整 Commit SHA，后续源码、行号和历史分析均绑定该 SHA。
4. 先在该基线上还原当前代码实际行为：入口、参数、条件分支、默认值、空值处理、计算/过滤、调用关系、返回值及异常处理。将这些行为与用户描述的异常逐项对应。
5. 如存在可用的发布/部署记录 MCP 或可靠发布记录，且需要确认线上实际运行版本或发布时间，再按需读取补充证据；不得把获取部署 SHA 设为用户启动前置条件。
6. 如果只能取得生产分支最新代码、没有实际部署记录，报告应称其为“当前最新生产分支代码基线”，并明确它不能单独证明线上实例当前运行的确切版本。不得把分支最新 Commit 静默表述为已验证的线上部署 SHA。

生产代码基线是理解当前实现的起点，不代表根因一定来自最近一次提交，也不代表问题一定由当前代码首次引入。

### 非生产 BUG 的代码基线

非生产问题按用户指定的环境、仓库、分支、Commit 或当前实际运行版本定位。用户未指定但仓库约定能够可靠识别时，使用对应环境的最新相关代码并记录完整 SHA；无法可靠识别且影响结论时，询问一个关键定位信息。不得机械套用生产分支规则。

### 当前行为优先于历史猜测

先解释当前基线中的实际代码行为，再追溯历史：
- 明确异常对应的入口、触发条件、关键变量/参数、处理逻辑和结果。
- 检查调用方传参、配置读取、返回值消费和异常处理，不能只看单个方法片段。
- 区分代码中明确存在的行为、基于静态调用链推导的行为，以及尚需运行态证据确认的行为。
- 不能因为找到一条可疑 Commit 就跳过当前实现核对。

## Git 历史反向追溯与时间证据

### 历史追溯方法

在当前代码行为和问题路径明确后，从「代码基线与当前实际行为」章节中实际选定的环境代码基线向历史反向追溯：生产问题沿当前最新生产代码基线追溯；非生产问题沿「非生产 BUG 的代码基线」小节确定的对应环境基线追溯，不得切换到生产基线而遗漏该环境独有的变更。
1. 使用相关文件/符号的 Git 历史、blame、Commit Diff 和必要的前后版本源码，定位与异常逻辑相关的代码变化。
2. 重点检查逻辑首次出现、条件/参数/默认值变化、调用关系变化、配置读取变化、重构时遗漏、回滚/合并及后续修复。
3. 必要时比较最近已知正常代码与当前代码，缩小可能引入问题的 Commit 范围。
4. 检查相关提交的上下文和关联文件，不以 Commit message、文件名、单行 Diff 或时间接近作为根因证据。
5. 记录相关仓库、分支、完整 Commit SHA、文件路径、行号、父版本/对比范围和实际获取时间。

只追溯与问题路径有证据关联的历史，不全量遍历无关提交。若无法取得足够历史，保留当前代码行为结论并明确历史追溯缺口，不伪造引入 Commit。

### 代码变化时间与目标环境发布时间必须分开

必须区分以下时间：
- **代码提交/变化时间**：Git Commit 的 author/committer timestamp 及代码差异所对应的历史时间，只能说明仓库记录的提交时间和版本变化。
- **实际发布时间/部署时间**：代码实际发布到本次 BUG 所在目标环境的时间；生产 BUG 对应生产发布时间，非生产 BUG 对应相应环境的发布时间。须由部署记录、发布平台/流水线记录、可靠运维日志或用户提供的上线记录支持。
- **问题首次出现时间**：用户反馈、监控、日志或业务记录中的实际观察时间，须注明来源和时区。

Git Commit 时间不能直接当成目标环境的实际上线时间。合并、Cherry-pick、回滚、延迟发布、分批发布等都可能导致提交时间与发布时间不同。

### 问题引入时间结论

有证据时，分别记录：
- 相关代码变化首次出现的 Commit 及提交时间。
- 最近已知正常版本/时间与最早已知异常版本/时间。
- 本次 BUG 所在目标环境的实际发布时间及其来源；生产 BUG 记录生产发布时间，非生产 BUG 记录对应环境发布时间。
- 用户首次发现/监控首次告警时间及来源。

没有部署记录或其他可靠发布时间证据时，必须明确写出“目标环境实际引入时间未能确认”；生产 BUG 应具体写为“生产实际引入时间未能确认”。可以给出候选代码变化时间或版本区间，但不得把它升级为目标环境实际引入时间。若只有当前代码和提交历史，结论限于代码历史，不推断历史环境部署状态。

## 按技术层选择公司 MCP

### 先定位，再选择 MCP

先通过用户线索、当前源码和 Git 初步分析，识别本次 BUG 实际涉及的技术层及关键证据缺口，再按需选择对应公司 MCP。不得在启动时全量调用 MCP，也不得为了证明“已查”而调用与问题无关的服务。

- Git：负责源码、所选环境代码基线、Commit、提交历史和版本差异。
- 公司 MCP：补充其所属领域的当前配置、平台元数据、数据血缘或业务记录。
- 用户提供的日志/截图/请求：作为对应时间和环境下的实际现象证据，记录来源、时间及时区。
- MCP 当前返回不能替代 Git 源码/历史，也不能在缺少部署或运行记录时证明历史代码部署状态、历史配置或数据库实际运行结果。

只使用当前执行环境已授权且可用的工具；参数与能力以当次 MCP Schema 为准。不要在 Skill 中硬编码连接地址、凭据或客户端专属调用方式。

### 前端配置

如果定位结果涉及前端配置、字段配置、查询条件、快捷查询或页面展示配置：
1. 按项目权威规则调用配置 MCP，获取相关对象的 **DEV 最新配置**，只查与当前 BUG 相关的配置项。
2. 记录配置环境、对象/配置键、查询时间、关键值及返回完整性，并映射到实际页面/组件/字段的配置读取代码。
3. 按已确认的配置同步机制，生产配置由 DEV 配置同步而来，因此 **DEV 最新配置是当前生产配置的来源和核对基准**。报告必须记录实际查询环境为 DEV，并说明该结果用于核对当前生产配置；不得由当前配置推断 BUG 发生时的历史配置、历史配置变化或历史错误时间。
4. 如果问题涉及历史配置、历史变更或 BUG 发生时的生产配置，而当前配置 MCP 不具备历史审计/版本查询能力，明确记录该证据缺口；只有存在可靠历史配置来源时才继续追溯。
5. 若 DEV 最新配置正常，只能结论为“当前生产配置未发现异常，历史配置状态无法通过该 MCP 判断”，不得据此排除历史配置问题。若 DEV 最新配置与当前需求/预期不一致，可确认当前生产配置核对存在差异，但仍须结合代码读取路径、配置同步机制、实际触发条件及其他证据判断其是否为本次生产 BUG 根因，不得仅凭配置差异直接认定根因。

### ETL、SQL 与数据血缘

如果 BUG 涉及 ETL、SQL、任务、表、字段或数据流：
1. 通过 Git 定位对应仓库的版本化 SQL/Groovy/任务源码、「代码基线与当前实际行为」章节选定的环境代码基线、相关 Commit 和历史变化；生产 BUG 使用生产基线，非生产 BUG 使用对应环境基线。若需核对生产现状或生产影响，可另行记录生产基线，但不得用它替代非生产问题的环境基线。
2. 仅当任务/表/字段依赖关系会影响根因或影响范围判断时，按需调用 Bigdata MCP 的任务血缘、字段血缘或表血缘能力；工具名、参数、环境及层级以当前 Schema 为准。
3. 记录查询环境、对象、实际查询时间、返回方向/层数和完整性边界。有限层级的血缘不得表述为完整全量血缘。
4. Git 证明指定版本源码及历史；Bigdata MCP 证明特定环境和查询时间下的平台元数据/血缘返回。二者不能互相替代。
5. 本工作流不执行 SQL、不触发 ETL 调度、不写入或修改数据库/平台数据。若实际数据结果是必要证据，说明需要用户提供或执行的只读验证及预期；是否生成 MV 按统一报告规范判断。

### 其他领域 MCP

只有当问题路径确实涉及对应领域，且该 MCP 返回会改变判断时，才调用相关平台、业务记录或日志查询能力。查询对象必须从已定位的代码/业务路径中得出，不凭猜测扩大范围。

### MCP 失败与证据缺口

MCP 调用失败、超时或返回不完整时：
- 记录服务/能力、查询对象、环境、实际调用时间、可观察到的失败现象和受影响的 CHK。
- 明确区分查询成功但无数据、对象不存在、调用失败、返回不完整；不得混为一类，也不得把工具故障判为业务缺陷。
- 保留已取得的 Git、源码、日志及其他 MCP 证据，继续完成不依赖缺失证据的分析。
- 不做无效重试，不因单个 MCP 故障终止全部分析。
- 缺少 MCP 证据不自动转化为用户人工验证事项；只有用户存在可执行且能回答具体问题的验证方式时才生成 MV。

## 根因判断与证据要求

### 建立可复核的因果链

根因分析必须围绕以下链路展开，并为关键环节提供 EV 证据：
1. 用户描述或日志/监控证明的实际异常现象。
2. 触发异常的页面、请求、参数、数据对象或业务条件。
3. 当前代码/配置/数据链路中的实际处理路径。
4. 具体发生偏差的条件、逻辑、映射、调用或数据依赖。
5. 该偏差如何导致用户观察到的异常结果。
6. 相关历史变化是否能证明该逻辑何时进入当前代码，以及是否有实际发布时间证据。

不能仅凭“某 Commit 改过这个文件”“代码看起来可疑”或“两个时间接近”就确认根因。必须说明证据如何把异常现象与具体实现联系起来。

### 根因结论分层

报告中明确区分：
- **已确认根因**：现有证据已建立异常现象、实际触发路径和具体错误行为之间的可复核联系。说明这是代码/配置/数据逻辑层面的确认，还是已有运行记录进一步确认；不得扩大证明范围。
- **潜在原因**：存在合理的触发路径或可疑实现，但缺少把它与本次异常直接关联的证据。列出已证实部分和缺失证据。
- **已排除原因**：已有证据足以排除该原因在本次问题路径中的作用。说明排除依据；没有查到证据不等于已排除。
- **待确认事项**：业务规则、实际环境、历史配置、部署时间、数据状态或其他关键事实尚不明确，需要明确指出由谁/通过什么来源确认。

根因尚未确认时，仍应交付已完成的代码行为分析、候选原因、已排除原因和证据缺口，不得强行给出单一根因。

### 静态结论与运行态结论

- 静态证据可确认源码中存在错误条件、参数错接、计算逻辑偏差或调用遗漏时，可以确认相应代码层问题，但必须说明静态证明边界。
- 只有日志、请求/响应、监控或受控实际运行记录能够支持的运行态事实，才可以写为已验证的运行表现。
- 未执行实际运行验证时，统一标记 NOT_RUN；不得将代码存在、Git Diff、MCP 元数据或静态推导写成运行验证 PASS。
- 代码层根因已确认，不等于生产环境中的触发频率、实际数据影响量或线上修复效果已验证。

### 公共业务语义推理与竞争根因假设验证

本节将公共业务语义推理方法落实到 BUG 根因场景；分析深度、通用推理过程和停止原则以 `references/analysis-reasoning-framework.md` 为准。本节不重复定义 L1/L2/L3，也不替代「输入识别与问题范围」章节的现象识别、「代码基线与当前实际行为」章节的当前行为与环境基线、「Git 历史反向追溯与时间证据」章节的历史追溯、「按技术层选择公司 MCP」章节的 MCP 证据、「建立可复核的因果链」小节的因果链及「静态结论与运行态结论」小节的静态/运行态边界。

1. **分离现象、预期与实际行为**：先分别记录用户/日志/监控实际观察到的异常、明确的业务预期，以及指定环境和 SHA 下当前代码实际行为。预期依据必须标明来自用户明确说明、需求/正式业务规则或用户明确确认的业务预期；如参考已确认用例，只能用于交叉核对，并应追溯其对应的需求、权威业务规则或用户明确确认的业务预期。用例本身或“用例已确认”不得单独或唯一作为业务预期来源；无法追溯到上述依据的用例只能作为线索，不能据此确认缺陷。尚未确认的推导须标记为假设；没有可靠预期时不得用代码现状补造预期，也不得仅凭“看起来不合理”确认缺陷。只有预期歧义会阻断关键判断时，才按「停止扫描并询问」小节询问一个最关键问题。

2. **建立本次异常的业务行为模型**：按需明确业务对象及身份、触发入口、输入/筛选条件、数据和状态范围、发生环境与时间、数据粒度、预期结果、实际观察结果及结果消费方。用户提供的请求、日志、截图、样例数据和最近正常表现分别作为对应事实记录；未提供的字段标记未知，不为补齐模型而要求用户一次性提交完整资料。
3. **提出少量竞争根因假设**：围绕异常与当前实际处理路径提出有证据关联、能够区分验证的候选原因，而不是只围绕第一处可疑代码展开。每个重要假设说明触发条件、适用业务约束、实际代码/配置/数据路径、如何导致当前异常、预期可观察差异、支持证据、反证条件及仍缺少的证据。候选范围只覆盖本次已定位或有证据指向的技术层；可按现象考虑参数/映射、分支/计算、聚合/过滤、配置、数据来源/状态、环境/部署或共享调用等原因，但不得把这些类别机械列成每次必查清单。
4. **优先验证能够区分假设的证据**：优先检查能确认或排除多项候选原因的关键变量、条件分支、实际调用、配置读取、数据依赖、历史差异或用户已提供的样例。对于数值/数据异常，按实际业务语义核对对象范围、数据粒度、过滤条件、去重/聚合、分子分母、单位/精度、NULL/0/负数及时间边界等适用约束；不得仅凭结果字段相同、参数同名或某段 SQL 表达式存在就认定口径正确。列表、汇总、详情、图表和导出只在有业务规则要求时比较一致性，不预设所有消费方必须采用相同公式或结果。
5. **构造最小反例并主动反证**：根据异常触发条件选择最小的正常/异常对照样例，必要时比较单条/多条、重复/唯一、空值/0/负数、边界日期、条件组合、不同数据粒度、状态或消费方。构造样例和源码逻辑推导必须明确标记为“静态推导/构造示例”，不得冒充真实数据结果或运行验证；不执行 SQL/ETL。对每个高价值假设检查其他分支、公共封装、有效配置、业务例外或相反证据；被证据推翻的假设应从根因候选中排除或说明排除依据，不得继续当作缺陷。
6. **区分根因、触发条件与伴随因素**：说明哪个错误行为直接造成异常，哪些输入/状态/配置/时间条件只是触发因素，哪些因素扩大影响或与异常同时出现但未证明存在因果关系。允许存在多个共同作用因素；分别说明证据，不为迎合单一结论强行合并。Commit 时间接近、配置当前异常、数据血缘有关联或多个现象同时发生，单独都不足以确认根因，仍须建立「建立可复核的因果链」小节要求的完整可复核因果链。
7. **形成有边界的根因结论并停止**：沿用「根因结论分层」小节的已有结论类别，不新增状态。只有异常事实、触发路径、具体偏差和结果之间建立可复核联系时才列为已确认根因；否则保留潜在原因、已排除原因或待确认事项，并说明最关键证据缺口。分析深度按公共方法自主选择和自动升级；出现数据粒度/聚合矛盾、多个竞争原因、跨层依赖、共享调用方或证据冲突时按证据升级。候选原因已验证/排除或明确受证据限制、因果链及实际影响范围已核查、剩余未知项已列明且没有新证据指向新路径时停止，不进行无边界扫描。

## 关联调用方与业务影响

当定位到公共接口、公共 SQL、公共组件、共享 Service、共享函数或其他共享实现时，必须从定义出发追踪并核查**全部实际关联调用方**：
1. 定位共享实现定义及其实际输入/输出。
2. 搜索引用后逐项打开调用位置，判断是真实调用、有效配置引用或数据依赖，而非注释、测试夹具、文档、无效死代码或同名文本。
3. 对每个实际调用方确认入口、传入参数、调用条件、返回值使用方式、业务用途及可能受影响行为。
4. 沿真实调用/数据依赖追踪到最终业务功能、页面、指标、报表或任务消费点，直到证据边界。
5. 业务行为相同的调用方可以合并展示，但必须保留全部调用方及其差异；不得抽样替代。
6. 对反射、动态路由、配置驱动或跨仓库依赖无法完整解析的部分，列出已确认调用方、未确认范围及原因；不得将“搜索无结果”写成“没有调用方”。

影响范围按统一规范区分：
- **直接影响**：证据证明异常逻辑直接作用于该业务路径。
- **间接影响**：有真实调用关系、共享实现或数据依赖支撑的关联业务路径。
- **潜在影响**：存在合理关联，但调用/数据依赖或实际影响尚未证实；必须说明证据缺口。
- **无影响**：现有证据足以支持该业务路径不受本次问题影响。

不得仅凭文件相邻、关键词相同、文本搜索命中或 Diff 文件数量扩大影响范围。

## 问题性质、缺陷等级与修复建议

### 问题性质和缺陷等级

每项 CHK 分别记录问题性质和验证情况，按 `references/report-format.md` 的分类及实际证据边界执行：
- 问题性质：已确认缺陷 / 潜在风险 / 待业务确认 / 无问题。
- 验证情况：静态已核实 / 待人工验证 / 无需人工验证。
- 实际运行验证：未执行时 NOT_RUN；真实执行后按证据记录 PASS / FAIL / BLOCKED。

缺陷等级只对证据充分确认的缺陷，依据公司现有 P0/P1/P2/P3 标准和实际影响判断。公司等级标准或影响证据不足时，明确标记待确认，不自行猜测等级。潜在风险、待业务确认事项不得仅凭推测分配缺陷等级；不得另建高/中/低等级或风险评分。

### 修复建议

对已确认缺陷给出与根因对应的修复建议，尽量明确：
- 建议修复的代码/配置/数据链路位置。
- 应修正的条件、参数、映射、计算或调用行为。
- 需要保持的兼容行为及可能影响的其他调用方。
- 如存在多种方案，说明主要差异及需要业务确认的部分。

潜在原因只提出验证方向或候选处理方式，不写成确定修复方案。修复建议是分析产物，不代表已修改代码或已完成修复；本工作流不直接实施业务代码/配置修改。

## 回归建议

回归建议必须基于已确认的根因、实际关联调用方和有证据支持的影响范围提出，并关联 CHK。每项说明：
- 回归对象：页面、业务功能、字段、查询条件、接口消费者、任务、数据链路或指标。
- 具体验证内容：正常路径、触发异常的条件、边界/空值/异常分支及必要兼容场景。
- 提出原因：对应的根因、调用关系或影响证据。
- 明确预期结果：可观察、可判定的业务结果。

必须覆盖全部已确认的实际受影响调用方；相同业务行为可以合并说明，但保留调用方清单和差异。潜在影响单独标注，不得写成确定回归范围。没有真实依赖或合理影响依据的模块不纳入。

回归建议不等于人工核对任务，也不等于已生成 P1 正式用例。P2 只提供建议，正式测试用例仍由 P1 testcase-design 管理。

## 完整报告与归档

### 统一报告要求

每项 BUG 排查均按 references/report-format.md 生成完整 impact-analysis.md。报告必须保留全部实际核对项及证据，至少包含以下 BUG 专属内容；可在统一报告结构中调整章节标题或交叉引用，但不得遗漏：

1. **BUG 现象及问题范围**：实际表现、预期依据、环境、对象、发生范围和可用定位线索。
2. **当前实际代码行为**：代码基线、入口、触发条件、参数/数据处理、关键分支、调用链和当前结果。
3. **根因分析及证据**：因果链、已确认根因、潜在原因、已排除原因和待确认事项。
4. **Git 历史追溯**：相关 Commit、完整 SHA、代码变化、前后版本差异和历史证据。
5. **问题引入时间证据边界**：代码提交/变化时间、目标环境实际发布时间、首次发现时间分别记录；生产问题对应生产环境，非生产问题对应其环境，不能证明的时间明确未知。
6. **关联调用方和业务影响**：公共接口/SQL/组件等全部实际关联调用方，以及直接、间接、潜在和无影响范围。
7. **问题性质及缺陷等级**：问题性质、证据状态、公司现有缺陷等级或等级待确认。
8. **修复建议**：与根因对应的建议、兼容性注意事项和未决决策。
9. **回归建议**：有证据支持的回归对象、操作/验证内容、原因及明确预期。
10. **EV 证据索引**：Git 源码/历史/Diff、MCP、日志/截图和运行记录的可复核定位及边界。
11. **CHK 业务核对矩阵**：保留全部静态通过、问题、风险、待确认及无影响核对项。
12. **MV 人工验证清单**：仅在满足统一报告规范的生成条件时提供。
13. **业务语义推理摘要**：记录本次 L1/L2/L3、选择依据及自动升级原因；按实际情况简述关键业务约束、重要竞争假设及其验证/反证结论。只记录可审计的假设摘要、验证过程和证据，不输出隐藏思维链。

报告不得把 Git Commit 时间当成生产发布时间，不得把 MCP 当前状态当成历史状态，不得把静态分析写成运行验证通过。

### 人工核对清单

仅当静态分析无法确认、用户确实能够执行页面/接口/环境/数据验证，且该验证能够回答明确问题并有可判定预期时，才生成 manual-verification.md。每项使用 MV 编号并关联 CHK，按 references/report-format.md 记录对象、原因、环境/前置条件、操作步骤、预期、状态和结果回填位置。

没有符合条件的人工验证事项时，不创建空的 manual-verification.md，并在聊天回复中明确说明无需人工核对。MCP 故障或缺少证据本身不自动生成 MV。

### 归档与版本

BUG 根因排查按照本节独立任务归档规则执行；不套用开发提测分析的旧版原位归档方式或版本策略，分析工作流间各自保持已定义的范围与归档边界。
- 有明确需求编号时，归档到 `output/【<模块>】/<需求编号>-<需求名称>/analysis/<YYYYMMDD>-vN/`；Manifest 位于该需求根目录的 `versions/<YYYYMMDD>-vN/manifest.json`。模块目录名保留需求标题中第一个非空全角 `【...】` 标识（包括括号）；没有标识时使用 `【未分类】`。需求目录保留完整原始标题，沿用该需求统一版本序列，不覆盖或修改 P1 正式用例及历史记录。
- 没有需求编号时，归档到 `output/impact-analysis/BUG-<主题>-<YYYYMMDD>/vN/`。
- 每个正式版本默认保存完整 impact-analysis.md；仅存在符合条件的人工核对事项时，同时保存 manual-verification.md。
- 无需求编号时，同一 BUG 分析任务的后续正式更新递增原任务目录下的 vN；新的独立 BUG 任务新建日期目录并从 v1 开始。有需求编号时，后续正式更新仍沿用需求级 YYYYMMDD-vN 序列，不另建 BUG 版本序列。
- 历史正式版本永久保留，不覆盖旧报告。不得为 BUG 分析另建 JSON 证据库、SQLite、数据库或第二套版本账本。

## 完成前检查

交付前逐项确认：
- 已从用户实际异常现象启动，没有强制要求需求编号或全套定位资料。
- 已先利用现有线索定向定位；最多进行一次有限范围扩展，缺少关键定位信息时已停止扫描并询问最关键的一项。
- 已明确问题环境和本次代码基线；生产 BUG 使用当前最新生产代码作为源码基线，未要求用户默认提供部署 SHA。
- 已先说明当前实际代码行为，再进行 Git 历史反向追溯；相关源码、Diff 和历史均绑定完整 Commit SHA。
- Git Commit 时间、代码变化时间、目标环境实际发布时间和首次发现时间没有混淆；缺少发布时间证据时已明确说明。
- 涉及前端配置时已按需读取 DEV 最新配置，并未由当前配置推断历史配置。
- 涉及 ETL/SQL/数据血缘时已按需选择对应 Git 源码和 Bigdata MCP 证据，未执行 SQL/ETL。
- Git 与 MCP 的职责、查询环境、时间、完整性和证明边界均已说明；MCP 失败没有触发无效重试或阻断独立分析。
- 根因结论有证据支持，已区分已确认原因、潜在原因、已排除原因和待确认事项。
- 公共接口、SQL、组件等共享实现已追踪全部实际关联调用方，或明确列出无法确认的范围及原因。
- 直接、间接、潜在影响分别有依据；没有因关键词或文件数量扩大影响范围。
- 问题性质与缺陷等级分开判断；只对证据充分的已确认缺陷按公司 P0/P1/P2/P3 标准定级。
- 已提供与根因和影响范围对应的修复建议及回归建议；没有修改业务代码或 P1 正式用例。
- 已按公共方法选择并记录 L1/L2/L3、选择依据及必要的自动升级原因；没有按文件数、提交数量或异常描述长短机械分级。
- 对重要竞争根因假设已检查支持证据和反证条件；已区分异常现象、明确预期、当前实际行为、根因、触发条件及伴随因素。静态构造样例未冒充真实数据或运行验证。
- 完整报告按 report-format.md 生成，包含 EV、CHK 和必要的 MV；无人工验证事项时没有创建空清单。
- 静态核对、实际运行验证及业务验收严格区分；未执行运行验证时标记 NOT_RUN。
- 遵守 P2 只读、安全、归档及版本管理边界；不依赖 P4。
