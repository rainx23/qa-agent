# P2 Git 仓库定位、代码搜索与任务版本快照规范

## 适用范围与权威配置

本规范由 code-impact-analysis 的三个分析工作流共同引用，适用于开发提测影响分析、BUG 根因排查和无需求代码变更分析。

- 业务仓库本地注册表为工程根目录 `config/repositories.json`；未配置时可由用户明确提供一个实际 Git 仓库路径/远端，核实后继续相关分析。`config/repositories.example.json` 仅用于初始化，不会被当作实际业务仓库。
- 组织环境与比较基线（如生产/集成远端分支、配置查询工具、SQL 方言）优先从可选本地 `config/organization-profile.json` 获取；公开示例 `config/organization-profile.example.json` 不代表任何真实环境。无本地配置时由用户、PR/MR/仓库和当前任务证据确认，无法确认则只问关键的一个基线信息，严禁猜分支。
- 本文件负责仓库定位、按任务动态确定代码搜索范围、搜索命令结果处理、Fetch 与任务内 SHA 冻结；各场景在实际组织基线范围内选择 base/head。注册表只记录仓库与 remote 定位，不证明远端存在、代码最新或线上部署。

## 本地仓库定位
1. 优先按任务线索在 `config/repositories.json` 中定位已登记仓库；文件不存在或未登记时，可采用用户明确提供的仓库路径，先核实其确为 Git 仓库，再选择实际 remote。缺少可验证路径时仅询问必要信息，不在磁盘上盲扫。
2. 核实目录、Git 元数据、当前实际 remote 和非空远端 URL；只有登记/确认的 remote 可用于 Fetch，URL 不复制进报告或配置。直接提供路径不等于已确认分支或版本。
3. 不得把本地当前分支名当作远端最新分支，也不得因为本地存在某个分支就认定它是本次提测分支或生产分支。
4. 如果仓库未登记，只有在用户线索明确指向某个已登记分组目录时，才允许在该目录下做一次定向的一级目录发现；确认具体目录为 Git 仓库且 remote 可用后，才能补登记。存在多个候选、仓库位于未登记分组或无法确认时，只询问一个最关键的仓库定位信息，不扫描整个磁盘或无关目录。
5. 新增仓库登记前，必须实际核实本地路径、Git 仓库根目录和 remote 名称；不得仅凭目录名猜测。

## 代码搜索范围与执行效率

本节是 P2 三个只读工作流的搜索唯一规则；仓库和模块路径按当前任务确定，不固化业务目录。

### 范围确定与扩展
1. 依据需求/异常、Diff、页面或功能入口、接口标识、配置绑定、P4 线索及仓库映射，从注册表选出相关仓库，再分别识别各仓库的模块路径；不为找模块递归扫描工作区或全部仓库。
2. 从变更文件、模块目录及必要配置开始；真实共享定义、同族实现、实际引用或未闭合调用链可触发同仓扩展。跨仓仅对第 1 项所列可复核任务线索定位的具体相关仓库，使用真实标识及相关路径定向查询；引用尚未确认时允许发现性查询，核实命中上下文后才认定依赖。模块未知时仅在该仓有限发现。当前仓未找到定义不足以触发工作区/仓库组扫描；无具体仓库定位依据时记录外部依赖证据缺口。
3. 仅在模块无法识别、需穷举共享对象消费者或新证据指向模块外时，扩大到相关仓库级搜索；先明确对象、触发证据和待回答问题，并限制文件类型/标识。打开命中上下文确认真实调用/绑定及业务用途，排除注释、测试夹具、死代码和同名文本。
4. `NO_MATCH` 不证明无依赖。先核实引用、pathspec、文件类型、大小写和生成方式；继续追踪其他可见链路，无法枚举的动态/配置边界如实记录。不得无依据反复扩大关键词。
5. 满足以下条件即停止：业务义务已映射、相关仓库/模块已识别、真实依赖触发的消费者已核查、关键链路已追踪到结果消费点、剩余动态边界已记录。每次扩展必须回答具体问题；不扫描无关模块，也不以节省成本省略必要核查。

### 命令与证据复用
1. 已跟踪源码优先使用带 pathspec 的 `git grep`；文件系统递归仅用于确需检查的未跟踪、忽略或生成文件，并限制在已确认范围。
2. 先列本阶段待回答问题；同一仓库、冻结引用和路径范围内可并行的只读 Git 检查，合并到一次 PowerShell 调用。每条原生命令分别标记结果并立即保存 `$LASTEXITCODE`；不同仓库/引用或依赖前置条件不同的查询分开执行，不为批量提前扩展范围。
3. 仅需判断任一相关标识是否命中时，可用多个 `-e` 合并；需要逐标识独立结论时，在同一批调用内分条执行并分别保存输出与退出码。历史查询优先按冻结 base/head 与相关 pathspec 一次限定；仅有新证据表明范围不足时扩展，不反复扫描或扩大历史窗口。
4. `git grep` 退出码：`0` = MATCH、`1` = NO_MATCH、`>1` = ERROR。PowerShell 每条命令后立即保存 `$LASTEXITCODE`，不得用多个原生命令中最后一个退出码代表全部结果。
5. 搜索完成并保存结果/退出码后，才用 `Select-Object -First` 等方式限制展示；结果过大优先缩小 pathspec/标识，不重跑宽搜索只为截短。
6. 复用已取得的 Diff、SHA、搜索、源码和配置证据；仅在基线变化、范围被新证据改变、结果不完整或上下文丢失时重查。现有报告简要记录仓库/SHA、模块 pathspec、真实标识、扩展依据及 MATCH/NO_MATCH/ERROR；不新增日志、索引、脚本或正式产物。

## 远端 Fetch 规则

1. 只有选定工作流确实需要远端最新代码或缺失的远端引用时才 Fetch。P1 需求分析和用例设计不 Fetch Git。
2. 只 Fetch 本次分析涉及的仓库和明确需要的远端分支，不全量 Fetch 所有仓库、所有远端或所有分支。
3. 目标分支必须由对应工作流、用户指定版本、PR/MR 元数据或可验证的仓库约定确定；不得从本地当前分支、分支命名习惯或文件更新时间猜测。
4. 对需要确认最新远端分支的任务，Fetch 后解析并记录远端跟踪引用的完整 Commit SHA。可使用定向 refspec 更新单一远端跟踪引用，例如：

   ```bash
   git -C "<repository_path>" fetch --no-tags "<remote>" "+refs/heads/<branch>:refs/remotes/<remote>/<branch>"
   git -C "<repository_path>" rev-parse "refs/remotes/<remote>/<branch>^{commit}"
   ```

   分支名必须替换为已经确认的真实分支；不得将占位符原样执行。若仓库登记的 remote 不存在，不静默切换到其他 remote。
5. Fetch 只更新必要的 Git 远端跟踪元数据，不等于更新本地工作分支或工作区文件。严禁为了获取最新代码擅自执行 `pull`、`checkout/switch`、`reset`、`clean`、合并、变基或 Push。
6. Fetch 失败、超时或目标引用不存在时，记录仓库、remote、目标引用、失败现象和受影响范围；停止无效重试。不得使用旧的本地分支或缓存 SHA 冒充远端最新代码。其他独立证据链路继续执行。
## 一次分析任务内的 Fetch 复用与 SHA 冻结

1. 一个独立分析任务中，每个“仓库 + remote + 目标分支引用”最多执行一次成功 Fetch；同一仓库需要比较多个分支时，每个必要引用各自只获取一次。
2. Fetch 成功后立即解析完整 Commit SHA。后续 Diff、源码、历史、行号及证据引用均绑定该 SHA，不再跟随可能变化的分支指针。
3. 同一任务的连续追问、结论解释、报告补充和局部复核，默认复用首次冻结的 SHA，不重复 Fetch。
4. 正式 `impact-analysis.md` 必须记录仓库标识/路径、remote、目标引用、Fetch 时间、完整 SHA、base/head 用途及必要的 merge-base。后续对话继续同一任务时，优先读取该任务最新报告中的 Git 基线；报告尚未生成时，复用当前任务上下文已记录的快照。
5. 用户明确告知开发又提交了新代码、提供了新 Commit/PR/MR、要求刷新到最新远端，或分析目标环境版本已明确变化时，只重新获取受影响的仓库和引用，并记录新旧 SHA 及刷新原因。不得为了刷新一个仓库而重新 Fetch 其他仓库。
6. 新的独立分析任务重新按其场景要求获取远端最新基线；不得把上一个需求或 BUG 的冻结 SHA 当作新任务的最新代码。
7. 若无法从当前任务上下文或已有报告恢复 SHA 快照，不得声称已经复用；根据当前任务是否需要最新远端重新获取必要引用，或明确报告证据缺口。

## 本地工作区与历史 Commit 的特殊处理

1. 无需求代码变更分析若只分析用户明确纳入的本地 staged/unstaged 工作区改动，且当前 `HEAD` 与工作区快照足以回答问题，不为形式完整而 Fetch；记录当前 `HEAD` SHA、文件状态和快照时间。
2. 只有比较目标涉及远端分支、PR/MR 版本或本地缺失的 Commit 时，才定向获取所需远端引用。
3. 用户指定的历史 Commit 已在本地且无需证明远端最新状态时，可直接按该 Commit 分析；若对象缺失，才按需获取包含该对象的相关引用。
4. 不将本地未提交工作区内容伪装成远端 Commit；不得为本地改动创建虚构 SHA。

## 场景规则与本规范的关系

- 开发提测影响分析：必须遵循 `submission-impact.md` 选择技术层基线，并对实际涉及的远端目标分支获取最新代码；本规范负责仓库路径解析、定向 Fetch 和任务内 SHA 冻结。
- BUG 根因排查：按 `bug-investigation.md` 先识别生产/非生产环境，再获取该环境对应的最新代码基线；历史追溯沿已冻结的环境基线进行。
- 无需求代码变更分析：按 `code-change-analysis.md` 选择用户指定版本、PR/MR、Commit 或本地工作区基线；只有实际需要远端引用时才 Fetch。
- 三个分析场景都不得将 Git Commit 时间等同于实际部署/发布时间；Git 证据边界仍遵循统一报告规范。

## 安全边界
- Git 操作默认只读；允许为取得远端证据而定向 Fetch。
- 不修改业务仓库中的源码、配置、分支、暂存区或工作区文件。
- 不执行 `pull`、切换分支、重置、清理、合并、变基或 Push。
- 不因仓库路径或 Git 获取失败而无限重试；按证据边界部分交付。
