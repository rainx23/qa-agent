# P2 统一分析报告规范

## 适用范围与交付文件

本规范由 code-impact-analysis 的三个分析工作流共同引用，适用于开发提测影响分析、BUG 根因排查和无需求代码变更分析。每项已实施的 P2 分析任务默认生成一份完整 Markdown 报告：

- impact-analysis.md：唯一完整分析报告，保留全部业务核对项、静态核对结论、问题、风险、影响范围、回归建议、未决事项和证据索引。
- manual-verification.md：仅在确实存在用户可执行的人工验证事项时生成，包括静态分析无法确认的运行态事实，以及开发提测影响分析中 AI 已识别的问题/风险需要用户复现或业务确认的项目；没有此类事项时不创建空文件。开发提测影响分析另生成 `verification-details.md`，集中保存逐条验证的完整描述、代码证据、步骤、预期、实际结果和适用 SQL。
同一任务涉及前端源码、前端配置、后端接口、SQL、ETL 等多个技术层时，默认仍只生成一份完整报告，不按技术层拆分。各技术层可以分别取证，但必须在同一报告中关联到业务核对点。

## 编号与交叉引用
- CHK-001、CHK-002……：业务核对点编号。按单份报告内的业务核对点顺序编号，不按文件、接口或 SQL 对象编号。
- EV-001、EV-002……：证据编号。按单份报告内首次引用顺序编号；同一证据可以被多个 CHK、问题分析和回归建议引用。
- MV-001、MV-002……：人工核对编号。每项 MV 必须关联至少一个主报告中的 CHK。

- CHK、EV 在单份当前报告内编号。正常连续提测分析的 MV 编号在同一需求中保持事项身份，未决事项跨正式版本保留原 MV ID；独立盲分析的 MV 编号仅在本 P2 版本内有效，跨版本唯一引用为“版本号 + MV ID”，不继承其他版本的 MV 状态或结论。
## impact-analysis.md 完整报告结构

报告按以下结构组织。某一章节确实不适用时可简要说明不适用原因，不为凑齐格式填充无关内容；但不得省略实际存在的业务核对项或有证据支持的问题。

### 分析概览

记录：
- 分析任务类型：开发提测影响分析 / BUG 根因排查 / 无需求代码变更分析。
- 需求编号与名称；无需求任务则说明无需求编号及独立任务主题。
- 分析日期、分析范围、涉及仓库/项目。
- 代码基线：仓库标识及本地路径（按 `config/repositories.json` 定位）、remote、目标分支/引用、比较基线、base/head 完整 Commit SHA、Fetch 时间及必要的 merge-base；本地未提交工作区则记录 HEAD SHA、staged/unstaged/untracked 纳入范围和快照时间。未取得的字段明确标记未知或未取得。
- 证据来源：需求/业务材料、测试用例（如有）、Git、源码、公司 MCP、用户提供的日志/截图及实际运行记录。
- P2 分析溯源：分析模式（正常/独立盲分析）、执行 Agent（ChatGPT/Codex/CodeBuddy/UNKNOWN）、模型/版本（当前环境可确认时，否则 NOT_RECORDED）、分析时间（北京时区，精确到秒）、最新有效 P1 基线版本（或无）、上一轮 P2 报告是否读取及其版本；独立盲分析必须明确记录“上一轮 P2 正文：未读取”。
- 分析状态及限制：已完成范围、未完成范围、缺失证据和受影响判断。

### 结论摘要

以业务语言简洁说明总体结论，并必须把以下类别分开呈现：
- **静态核对通过（PASS）**：列出全部通过的 CHK 编号和简短业务名称；只说明静态证据实际证明的范围。
- **已确认问题**：只列有充分证据确认的问题；没有时写“0 项”。
- **潜在风险**：列出合理影响路径及证据缺口，不得写成已确认缺陷。
- **待业务确认**：单独列出需要产品/业务明确的规则或预期，不与潜在风险、人工待办混写。
- **用例覆盖缺口**：单独说明未覆盖范围；明确“覆盖缺口不等于代码缺陷”。
- **需要人工核对**：列出 MV ID、中文 + 机器状态及下一步动作；无事项时写“无需人工核对（0 项）”。
- **尚未执行（NOT_RUN）**：列出尚未完成的真实页面、接口或数据验证；NOT_RUN 不自动意味着需要用户人工验证。

**首屏“结论速览”必须让用户不看正文也能区分通过项和待办项。** 表格至少使用以下列：分类、数量/编号（注明统计对象）、状态（中文 + 机器标识）、说明/下一步。按实际情况逐项展示；没有事项时明确写“0 项”，不得省略后让用户猜测。

| 分类 | 数量/编号（注明统计对象） | 状态（中文 + 机器标识） | 说明/下一步 |
|---|---|---|---|
| 总体结论 | 1 项结论 | 沿用现有总体状态 | 说明已完成与未完成边界 |
| 静态核对通过 | N 项 CHK，列出全部编号及业务名称 | 静态核对通过（PASS） | 说明静态证据证明到哪一层，以及为何无需重复人工核对 |
| 已确认问题 | N 项 CHK，列出编号 | 已确认缺陷 | 说明业务影响及处理建议；没有时写 0 项 |
| 潜在风险 | N 项 CHK，列出编号 | 潜在风险 | 说明合理影响路径及证据缺口，不得写成已确认缺陷 |
| 待业务确认 | N 项 CHK，列出编号 | 待业务确认 | 说明待确认规则、确认对象及影响 |
| 用例覆盖缺口 | N 组/项，列出覆盖主题或 CHK | 覆盖缺口（不等于代码缺陷） | 说明未覆盖范围及是否需要 P1 补充用例 |
| 需要人工核对 | N 项 MV，列出仍需处理的编号及状态 | 按 PENDING / FAIL / BLOCKED / PASS / IGNORED 分列 | 给出用户下一步；没有时写 0 项/无需人工核对 |
| 尚未执行的运行验证 | N 项，列出对应 CHK/验证对象 | 未执行（NOT_RUN） | 说明缺少哪类真实页面、接口或数据证据 |
统计口径必须明确：静态通过、已确认问题、潜在风险和待业务确认按不同 CHK 事项统计；覆盖缺口按实际覆盖组/项统计；人工核对按 MV 事项统计；NOT_RUN 按未执行的运行验证事项统计。它们属于不同维度，**数量不可直接相加作为总核对项数**。同一 CHK 可以同时有静态结论和运行验证状态。

静态 PASS 清单必须列出全部通过的 CHK 编号及简短业务名称，不能只写“静态检查通过 N 项”而不说明通过了什么。范围外事项单独标注“范围外”，不得混入待确认或人工待办。

**状态表达边界：**
- `PASS` 必须带验证类型和对象，例如“静态核对 PASS（CHK-01：配置字段存在且绑定正确）”“运行验证 PASS（MV-001：已实际执行）”或“工程校验 PASS（Manifest 历史验签）”；禁止只写一个没有对象的 PASS。
- 静态核对 PASS 只代表源码、配置、调用链等静态证据支持该项结论；不得写成页面/接口/数据运行 PASS。
- `NOT_RUN` 只表示相应运行验证尚未执行；不自动意味着必须由用户人工验证。只有存在用户可执行且能回答明确问题的验证，才建立 MV。
- 总体 PARTIAL 时，必须明确列出已通过范围和未完成范围；不得把 PARTIAL 理解为全部失败，也不得隐藏已通过项。
- 不新增总体状态、CHK 状态或 MV 状态枚举；沿用本规范及工作流已有状态。

### 分析范围与依据

说明本次实际分析的需求预期、代码/配置变更、仓库与版本范围、相关技术层、可用测试用例及 MCP 查询范围。明确：

- 需求或权威业务材料是业务预期的主要来源。
- P1 正式用例（如有）用于交叉检查覆盖和预期一致性，不能替代需求。
- 无需求代码变更分析以变更前后实际行为为比较对象，不虚构需求。
- 开发提测点是初始定位线索，不等于完整变更清单。
- 用户提供有限的配置/代码改动点清单时，记录原始条目数、唯一对象数及重复项；依据本需求的页面/功能/业务义务和真实绑定关系逐项核对其关联，再反向检查本需求应有对象是否遗漏。报告中的本需求相关、明确范围外、关联未明对象数量应与唯一对象总数相互校验；不得把“可能包含其他需求”直接当成所有未核对项均属范围外，也不得将整张清单全部扩展为本需求分析范围。
- 证据缺口、未取得资料及其影响范围。
### 变更概览

按业务功能或行为变化归纳，不按文件逐项堆砌。说明：
- 本次实际发生的主要行为变化。
- 必要的内部技术实现或无业务行为变化的整理/重构。
- 可能改变业务行为、影响范围或兼容性的额外实现。
- 与需求预期不一致或需求未说明的变化。

文件、接口和 Commit 的详细定位放入 EV 证据索引；变更概览只保留帮助理解业务影响的必要内容。

### 需求、用例与开发改动交叉核对

有需求时必须覆盖两个方向及可用用例：

1. 需求 → 实际实现：逐项核对需求业务义务是否已实现、完整接入且行为符合预期；识别缺失、部分实现、错接和行为不符。
2. 实际实现 → 需求：反向识别需求未明确描述的代码/行为变化，区分必要内部实现、无业务行为变化的整理，以及可能改变业务行为或兼容性的额外实现。
3. P1 用例 → 需求及实际实现：如存在最新有效正式用例，检查需求义务覆盖、实际变更及其业务影响覆盖，并识别用例预期与需求或实际实现的冲突。没有正式用例时说明未提供/不存在，不阻断分析。

需求与用例冲突时以需求/权威业务规则作为预期来源并明确报告冲突，不得擅自用用例覆盖需求。需求有而开发未实现，必须反馈实现缺口；开发有而需求未说明且可能影响业务，必须反馈额外实现及其影响。

无需求代码变更场景不强行套用以上需求对照，改为对照变更前后行为和业务影响。没有需求编号的 BUG 排查按异常现象、可靠预期依据、当前行为及根因证据组织核对；历史版本仅按定位需要追溯，不强制先取得变更前后版本。预期无法确认时明确列为待确认，不虚构需求或用当前代码证明自身正确。

### 业务核对矩阵

这是报告的核心。**每一行代表一个独立业务核对点，不代表一个代码文件、接口、SQL 或配置对象。** 所有实际核对项均须保留，包括静态核对通过项；不得只列问题。

建议字段如下：

| 字段 | 必填要求 |
|---|---|
| CHK | 当前报告内唯一业务核对编号 |
| 业务场景/核对点 | 用户能理解的业务操作、规则、结果或兼容性检查点 |
| 业务预期 | 明确、可判定的预期结果；无需求代码变更写明比较前后的行为基准；BUG 排查写明可靠预期依据，无法确认时列为待确认 |
| 预期依据 | 需求章节/原文、权威业务材料或已确认规则；测试用例不得作为唯一业务预期来源 |
| 实际技术实现链路 | 仅列实际涉及的前端、配置、接口、公共组件、SQL、ETL、数据或展示链路，并关联真实调用方 |
| 静态核对结论 | 符合预期 / 发现不符合 / 证据不足 / 不适用 |
| 问题性质 | 已确认缺陷 / 潜在风险 / 待业务确认 / 无问题 |
| 验证情况 | 静态已核实 / 待人工验证 / 无需人工验证 |
| 实际运行验证 | 未执行时为 NOT_RUN；实际执行后记录 PASS、FAIL 或 BLOCKED，并附运行证据 |
| 影响类型与范围 | 直接影响 / 间接影响 / 潜在影响 / 无影响；说明具体业务范围及依据 |
| 回归建议 | 对应的回归对象、具体验证内容、提出原因和预期结果；无必要回归时说明原因 |
| 人工核对安排 | 必填。明确写“无需人工核对（静态证据已回答）”、对应的 `MV-编号`（具体操作见人工核对清单），或“暂不生成 MV（没有用户可执行的验证方式）”；不得只写“建议回归” |
| 证据索引 | 关联一个或多个 EV 编号；没有证据时明确缺口，不得伪造编号 |

矩阵填写规则：

- 业务核对点按业务义务、场景或业务结果拆分，不按文件数量拆分。
- 同一共享实现服务多个调用方时，只有业务行为和核对结论确实相同时才可合并展示；必须列出全部实际关联调用方及各自差异，不得抽样。
- 需求有明确义务但代码缺失/未接入/不符合时，静态核对结论写明发现不符合，并在问题性质中按证据判定。
- 需求未说明的额外行为不能自动判为缺陷；可能影响业务时标记待业务确认或潜在风险，并说明理由。
- 静态证据足以证明当前源码/配置/调用链符合预期时，可标记静态已核实；不得因此声称页面或数据运行验证通过。
- 证据不足时不得填写无问题或 PASS；说明缺失内容和对判断的影响。

### 数据口径一致性

仅在实际触发指标跨层级/接口/组件、列表与汇总并存、多层聚合、派生指标、一对多/多对多 JOIN、共享既有计算路径或结果矛盾等条件时展开；未触发时简要说明不适用原因，不机械填表。

触发时必须给出可审计的矩阵：

**指标公式矩阵**

| 指标/业务语义 | 层级/接口/消费方 | 实际表达式 | 来源字段 | 分子/分母 | 过滤与数据范围 | 聚合/去重 | 单位/精度 | 差异解释与结论 | EV |
|---|---|---|---|---|---|---|---|---|---|

**数据粒度矩阵**

| 路径/接口 | 原始行粒度 | JOIN 键与基数 | JOIN 后粒度 | 去重/窗口 | GROUP BY | 聚合输入/输出粒度 | 页面列表/汇总粒度 | 风险与结论 | EV |
|---|---|---|---|---|---|---|---|---|---|

**数值关系验证**：记录待验证的等式/关系、成立前提（对象集合、筛选、时间范围、粒度、单位及可加性）、静态推导或用户 SQL 实际结果、结论和 EV/MV。只有前提成立时才验证上层汇总与下层合计；比例、平均值、重叠集合不得直接套用简单加总。公式不同或结果不等不自动等于缺陷，必须说明业务依据或列待确认。

旧接口未改动、被复用或需求写明“沿现状口径”均不是免检理由；报告应区分历史既存问题、本次变更引入问题和组合后暴露问题。

- 对涉及配置、筛选参数、接口过滤或数据查询的 CHK，静态 PASS 必须由证据证明所有适用链路环节真实连接：配置/页面绑定、控件与参数生成、请求传递、接口接收、后端实际使用、SQL/查询过滤及相关列表/汇总消费路径。只出现同名字段、配置记录、接口参数声明或孤立 SQL 条件，不足以证明端到端实现正确。
- 对同一公共实现的多个参数/调用方，可以在实现路径和行为完全一致时合并说明，但必须列出完整对象及差异；不得以抽样、搜索命中或开发提测清单代替完整核对。
- 动态调用、反射、运行时拼接或外部封装导致链路无法静态证明时，应标记证据不足/潜在风险并说明边界；不得猜测 PASS，也不得仅因证据不足直接判定缺陷。
- 人工核对只针对静态分析无法回答、且用户可以通过明确且最小的操作取得结果的具体问题。回归建议、覆盖缺口和 NOT_RUN 不自动转为 MV；静态证据已回答的内容不得要求用户重复验证。

### 问题、风险与待确认事项

问题详情按业务影响组织，并关联 CHK 和 EV：
- 已确认缺陷：说明明确业务预期、实际不符合行为、复核证据、受影响范围和建议处理方向。
- 潜在风险：说明合理的影响路径、已证实部分、尚未证实部分及证据缺口；不得写成确定缺陷。
- 待业务确认：提出具体业务问题、已知背景、需要确认的原因、可能选项及对业务预期/范围的影响；选项必须有证据依据。
- 无问题：保留在矩阵中；若有必要，可在摘要或通过项汇总中简洁说明，不重复展开。

问题性质和缺陷等级是两个维度。只有证据充分确认的缺陷才按公司现有 P0/P1/P2/P3 标准判断等级；潜在风险和待业务确认事项不得仅凭推测分配缺陷等级。不得另建高/中/低等级或风险评分体系。

### 影响范围与回归建议

影响类型定义：
- **直接影响**：证据证明本次变更直接作用于该业务路径。
- **间接影响**：有真实调用关系、共享实现或数据依赖支撑的下游/关联业务路径。
- **潜在影响**：存在合理关联，但调用/数据依赖或实际影响尚未证实；必须写明证据缺口。
- **无影响**：现有证据支持该业务路径不受本次变更影响。

回归建议必须关联 CHK，逐项说明：
1. 回归对象（页面、业务功能、查询条件、接口消费者、数据链路或指标）。
2. 具体验证内容和必要操作。
3. 提出该建议的业务/代码影响依据。
4. 明确预期结果。

回归建议不是自动生成的人工核对任务。静态证据已足以回答的问题，不要求用户重复核对相同源码/配置/调用关系；只有静态分析不能证明且用户可执行的运行态事项才进入 manual-verification.md。

### 未决事项与证据缺口

列出尚不能确认的业务规则、实现范围、调用方、版本、配置、血缘、环境或运行结果，并说明：
- 已取得的证据。
- 缺少的具体证据。
- 该缺口影响哪个 CHK 及哪项结论。
- 是否存在用户可以实际执行的验证方式。

MCP 故障、无数据、对象不存在和返回不完整必须分别描述。证据缺失不自动意味着业务有问题，也不自动意味着必须让用户人工验证。

### 实际运行验证记录

静态分析与实际运行验证分开记录。未实际执行时写明：

- 实际运行验证：NOT_RUN。
- 未执行原因或本次分析范围不包含运行验证。
- 哪些结论仅由静态证据支持。

若确实执行了运行验证，记录真实环境、版本/Commit、执行时间、操作步骤、输入条件、实际结果及证据 EV。只有实际执行且结果符合预期才能标记 PASS；不符合为 FAIL；因环境/前置条件无法完成为 BLOCKED。不得将源码静态核对、MCP 元数据查询或推测结果作为运行验证。

### 数据验证 SQL 覆盖与人工交接（仅 `submission-impact.md`）

P2 首次提测分析由 AI 根据本次实际代码变更、需求义务和业务影响识别必要的独立真实数据验证目标；不只选择已发现问题/静态未通过的目标，也不机械覆盖页面全部指标。每个目标由 P3 完成 F（真实样本）与 V（独立预期）两项内部职责，默认整合为一条 SQL-01、一次执行；只有存在真实技术限制导致无法安全合并时才拆分。

- **覆盖摘要**：impact-analysis.md 逐目标列出验证目标、关联 CHK/MV/P1 Case ID、P3 场景 ID、SQL 编号（默认 SQL-01）、输出/页面核对字段、覆盖状态及 verification-details.md 正文锚点；不再要求 F 与 V 分别编号。状态使用 READY / NO_SAMPLE / PARTIAL / BLOCKED；UNKNOWN 只作为证据描述，不作为场景状态。
- **F 找数**：说明样本条件、场景成立依据和证明字段；返回真实页面可输入/展示的 Number/Code，必要时同时返回内部 ID，并说明复制哪一列、到哪个页面/接口入口定位。聚合场景必须提供必要明细/去重对象依据，不能只返回汇总统计。
- **V 独立预期**：说明需求/产品上游逻辑、用户确认或适用 P1 Oracle 的来源，按页面相同业务对象集合、有效过滤、时间范围和目标粒度计算预期，输出必要原始值/中间值/最终值及页面对应字段。产品明确提供的上游 SQL/预聚合结果可作为 Oracle；不得使用本次被测变更输出反推预期。ADS 只可在独立样本/预期确定后作为实际侧辅助关联。
- **合并与覆盖**：默认一条 SQL 一次执行；只在执行端/权限、数据来源、粒度、过滤、Oracle 或输出结构确实不兼容时拆分并说明原因。逐目标保留场景映射，不因合并丢失断言；所有需要用户执行 SQL 并页面/业务对照的目标必须进入一个 MV 或映射到已有 MV。
- **详细记录**：verification-details.md 保存 SQL 正文、场景映射、F/V 逻辑、Oracle 来源/独立性、P3 规则加载状态及文件读取证据、执行引擎/方言/解析兼容性、输出列注释、结构检查命令与结果、页面对照方式和用户反馈。首次聊天只展示 SQL 覆盖摘要，不展示正文。
- **执行边界**：SQL 正文由 P3 规则负责设计；P2 管理 CHK/MV 与工作稿，不连接或执行数据库。用户在获准环境手动执行。SQL 结构检查只证明其实际覆盖的结构范围，不代表方言解析、数据库执行或业务 PASS。区分查询失败、权限/环境问题、执行成功但无样本和数据断言不符。

### EV 证据索引

EV 证据索引直接内嵌在 impact-analysis.md 中，使用 Markdown 表格或条目，不另建 JSON、SQLite、数据库或重复证据存储。

每条证据至少记录：

| 字段 | 说明 |
|---|---|
| EV | 当前报告内唯一证据编号 |
| 证据类型 | 需求/业务材料、测试用例、Git Diff、Git 源码、Git 历史、公司 MCP、实际运行、用户提供日志/截图等 |
| 来源定位 | 仓库/服务/工具/文件/对象/页面或材料标识 |
| 版本与范围 | 分支、完整 Commit SHA、比较基线、文件行号；MCP 则记录环境和查询对象 |
| 获取时间 | Git/MCP/运行证据的实际取得时间；无法取得时如实说明 |
| 关键内容 | 只摘录支持判断的必要事实，不整份复制 Diff、源码或 MCP 原始返回 |
| 完整性与限制 | 返回是否完整、覆盖范围、失败情况和不能证明的内容 |

证据细则：

- **Git Diff**：记录仓库标识/本地路径、remote、目标分支/引用、Fetch 时间、base/head 完整 Commit SHA、文件路径及 Diff 行范围；同一任务后续追问复用冻结 SHA，刷新时记录新旧 SHA 和刷新原因。仓库注册配置只用于路径定位，不作为远端版本新鲜度或部署状态证据。
- **Git 源码/历史**：记录指定 Commit、文件路径和行号；提交记录可证明代码历史及提交时间，不单独证明生产发布时间。
- **公司 MCP**：记录服务/能力、查询环境、查询对象、实际查询时间、关键返回及完整性边界。明确区分查询成功但无数据、对象不存在、调用失败、返回不完整。
- **实际运行**：记录环境、版本、操作、实际结果和日志/请求等定位信息。
- **需求/用例/用户材料**：记录来源文件、需求编号、章节、用例版本或附件标识；用例只作为交叉核对依据，不替代需求预期。

EV 编号在单份报告内独立；多个 CHK 可以引用同一 EV。不得只写“代码已确认”“MCP 已查”而没有可复核定位。

### P5 接口自动化维护建议（仅开发提测影响分析）

仅 `submission-impact.md` 在完整分析及 EV 证据后附「P5｜接口自动化维护建议」，可用编号表说明真实 API、影响业务和 CHK/EV、当前可信基线来源/缺口、建议新接口初始化/存量首次初始化/已有基线增量更新/无需维护/待核实，以及拟维护场景。无受影响 API 时写「本次无建议维护接口」。索引缺失不等于平台无 Case，有 Case 不等于已有可信完整覆盖；缺证标待核实。该章节仅供用户选择，不额外计入七类首屏 CHK/MV/NOT_RUN、不新增 Manifest role 或 P5 产物、不视为已执行；用户确认后另启 P5，其他 P2 工作流不变。

### 对话框交付

正常 P2 业务分析完成后，聊天回复按以下顺序简洁交付，不重复完整报告：
1. **总体结论**：OVERALL 状态及一句话解释；明确 PARTIAL 不等于全部失败，也不等于运行验收通过。
2. **静态核对通过（PASS）**：列出通过的全部 CHK 编号和简短业务名称；说明仅为静态核对通过，不代表运行 PASS。
3. **已发现问题/潜在风险/待业务确认**：分别列出 CHK 编号，区分已确认缺陷、潜在风险、业务待确认和用例覆盖缺口；覆盖缺口明确不是代码缺陷。
4. **需要用户处理的 MV**：列出 MV 编号、中文 + 机器状态、具体操作和预期；PENDING 才是待执行，BLOCKED 说明解除条件，FAIL 说明已执行后的异常及下一步，PASS/IGNORED 不再要求重复执行。
   - 首次提测分析聊天不展示 `verification-details.md` 中的 SQL 正文；适用的数据验证目标应在报告中列出 F/V 覆盖摘要，SQL 正文保存在详细记录。用户逐条验证某个 CHK/MV/数据验证目标时，必须返回对应完整 F+V、操作步骤、预期和代码证据定位；仅纯 UI/导航等无真实数据断言的事项不提供 SQL。
5. **尚未执行（NOT_RUN）**：列出未做的真实页面、接口、数据运行验证及其原因；不要与静态 PASS 或 MV 待办混在一起。
6. **正式文档在哪里**：分别列出完整分析报告、人工核对清单和（开发提测适用时）人工验证详细记录的用途、文件名及完整路径；说明用户先看哪份。不得只写“见产物”或把路径埋在长文末尾。
7. **P5 维护建议（仅开发提测）**：按受影响 API 给出编号、基线状态、初始化/增量维护或待核实建议（无候选时明确说明），等待用户选择。此项只是建议，不执行平台写入或正式 Run。

聊天回复不得只给汇总数字而不列 CHK/MV 编号；不得用“其他待确认”把潜在风险、业务待确认、范围外事项和人工待办混在一起。

报告正文的第一屏必须包含“结论速览”表，按静态通过、已确认问题、潜在风险、待业务确认、用例覆盖缺口、需要人工核对和尚未执行分组，并给出数量/编号、中文状态及下一步。人工清单第一屏必须先给用户状态总览及待办表，状态同时显示中文和机器状态。
正常 P2 业务分析不附带 Codex 验收提示词，也不要求用户将业务分析再交给 Codex。

## manual-verification.md 人工核对清单
### 生成条件
#### 按工作流区分
- **开发提测影响分析（`submission-impact.md`）**：满足以下任一条件时生成 `verification-details.md`；其中需要用户执行 SQL、页面对照或业务确认的事项同步生成 `manual-verification.md`：
  1. 存在静态证据无法回答的运行态事实；或 AI 已识别为已确认问题、潜在风险、待业务确认，且确实需要用户复现页面、核实真实运行行为或作业务确认；
  2. 存在真实业务数据验证目标，按 P2 数据验证规则需要用户执行 F+V SQL 并对照页面/业务预期。
- **BUG 根因排查、无需求代码变更及 Bug Lifecycle**：沿用原规则，仅当静态分析无法回答、且用户能够执行并反馈明确验证结果时，才生成原有完整人工核对项；不创建、不要求 `verification-details.md`。
- 所有工作流均不得把所有回归建议、所有 CHK、用例覆盖缺口、NOT_RUN 或理论边界机械转为人工任务。P2 提测按独立数据验证目标建立 F+V 和必要 MV，不按每个 CHK/MV/用例机械生成。静态已核实且无需额外数据运行证据的纯 UI PASS 不进入清单；MCP 故障或证据缺失本身不自动生成 MV。用户没有可执行验证方式时，只记录证据缺口和影响。
**人工核对最小性与一致性检查：** 每项 MV 必须对应一个明确的人工问题。开发提测可包含 AI 已识别问题/风险所需的页面复现或业务确认；其他工作流仍按静态证据缺口规则执行。核对原因须引用 CHK/EV 或明确业务待确认点，操作只保留回答该问题所需的最少步骤。某个 CHK 已静态 PASS 时，只有 MV 验证的是与静态结论不同的独立运行态行为，才允许继续关联；不得为了页面未打开或状态为 NOT_RUN 就把该 CHK 整体交给用户重复核对。不得把多个需要分别打开页面、分别操作的独立任务包装成一个 MV；只有一次操作确实覆盖相同实现路径和预期时才可合并。生成前检查是否已被源码/配置/调用链证据回答、是否重复，以及是否属于当前工作流范围。
没有符合条件的事项时，不创建 manual-verification.md 空文件，并在聊天回复中明确说明无需人工核对。

**人工清单第一屏必须先给出状态总览，再给出用户待办表。** 总览分别统计当前清单中 PENDING、FAIL、BLOCKED、PASS、IGNORED 的数量；状态同时显示中文和机器标识。待办表列出 MV 编号、关联 CHK、状态、简要任务、预期结果；开发提测清单另列详细记录引用。
状态总览示例（按当前清单实际数量填写；没有的状态写 0）：

| 状态 | 数量 | 处理说明 |
|---|---:|---|
| 待人工核对（PENDING） | N | 按简要任务和详细记录引用执行；其他工作流按本清单步骤执行 |
| 实际未通过（FAIL） | N | 已执行但不符合预期，交由 Agent 继续分析 |
| 暂时受阻（BLOCKED） | N | 先解决环境、数据、权限或前置条件 |
| 实际通过（PASS） | N | 已验证通过，不再重复执行 |
| 已忽略（IGNORED） | N | 已确认无需处理，不计为验证通过 |


用户待办表示例：

| MV 编号 | 关联 CHK | 状态 | 简要任务/用户要做什么 | 预期结果 | 详细记录引用（仅开发提测） |
|---|---|---|---|---|---|
| MV-001 | CHK-01 | 待人工核对（PENDING） | 在对应页面复现指定场景 | 写明可判定的业务预期 | verification-details.md#MV-001（非提测填 —） |

- PENDING（待人工核对）：用户尚未执行；开发提测按简要任务和详细记录引用执行，其他工作流按完整 MV 步骤执行，并提供明确预期。
- BLOCKED（暂时受阻）：说明缺少的环境/数据/权限/前置条件及解除方式，不得伪装成已执行。
- FAIL（实际未通过）：表示用户已执行且结果不符合预期；保留实际结果，交由 Agent 针对该项继续分析，不要求用户重复执行同一操作。
- PASS（实际通过）：表示已实际执行且符合预期，不再要求重复核对。
- IGNORED（已忽略）：表示用户确认无需处理，不计为验证通过，也不再要求重复核对。

PENDING 与 BLOCKED 是尚未完成的人工事项；FAIL 是已执行但需要后续分析的结果；PASS 与 IGNORED 是已处置事项。不得把整份清单中的所有 MV 都描述为“你还需要执行”。

- **IGNORED**：用户确认或用户与产品确认该项不是问题/无需处理；记录忽略依据。IGNORED 不计为验证通过。
- PASS 和 IGNORED 不再要求重复核对；未反馈项目不得自动变更状态。
- 开发提测影响分析：有需求编号时，人工结果及必要依据回填到最新整体 Manifest 指向的当前有效 P2 版本。正式发布后的人工反馈必须创建新的需求级 P2 版本，不得原位修改历史报告、清单或 Manifest；正常连续分析保留仍适用未决 MV 的原 ID，独立盲分析使用本 P2 版本内的 MV 编号。无 P1 基线时继续分析，不虚构 P1 版本；是否可首次 P2-only 发布以现有 Manifest publisher 的实际校验结果为准。BUG/CODE 任务按各自工作流的归档规则回填。

## verification-details.md 人工验证详细记录（仅开发提测影响分析）

`verification-details.md` 是逐条人工验证与 P2 数据验证 SQL 的唯一详细记录。仅当开发提测分析存在人工核对事项，或识别出需要用户执行 F+V 的真实数据验证目标时创建；不创建空文件。
每个 MV 使用独立小节并关联 CHK；同一条记录持续更新，不为 SQL 试错拆分文件。

每项至少记录：

- **身份与描述**：CHK、MV、页面/功能/指标、AI 分析时的原始结论与问题性质、需要人工回答的具体问题。
- **代码证据**：关联 `impact-analysis.md` 的 EV；记录仓库、分支、base/head Commit SHA、文件路径/行号及支持结论的关键事实。不得复制整段源码或完整 Diff。
- **环境与前置**：建议验证环境、版本、账号/权限前提、查询条件、时间范围及必要数据状态；未知项明确标 UNKNOWN，不自行补猜。
- **操作步骤**：从页面入口到筛选、下钻、输入数据、触发操作和观察位置的可执行步骤。
- **预期结果**：明确且可判定的正确业务表现；必要时同时写明异常表现及其区分方式。
- **SQL（适用时）**：F/V 类型、查询目的、数据库方言、建议执行环境、参数/过滤、输出字段说明、当前完整可复制 SQL 正文及预期判断。若无需 SQL，简要写明原因；不能取得可靠来源时标记限制，不编造 SQL。
- **SQL 执行反馈**：用户执行环境/时间、成功/失败、返回行数、关键结果或错误信息；区分查询报错、权限/环境失败、成功无数据和断言不符。
- **页面实际结果**：用户实际操作后的表现、截图/日志/请求/样本标识及与预期的差异；未反馈时留空并保持待验证。
- **最终判断与状态**：仅按现有 PENDING/PASS/FAIL/BLOCKED/IGNORED 状态更新；PASS 必须有用户真实执行且符合预期的反馈，IGNORED 不计为通过。

### SQL 修订与版本

每个验证项只保留当前可执行 SQL 正文；SQL 有误时在同一工作稿中替换正文，并用简短修订说明记录修改原因，不在同一文件堆叠每次失败的完整 SQL。

开发提测工作稿固定路径为 `.qa-work/<需求编号>-<需求名称>/submission-impact/verification-details.md`。文件顶部以轻量 YAML front matter 记录 workflow、requirement_id、base_latest_version、base_manifest_sha256，以及当前 P2 的 impact-analysis/manual-verification/verification-details artifact path 与 SHA；不存在的 role 记为 null，未发布基线记为 UNPUBLISHED。该元数据直接保存在 MD 内，不新增 sidecar、JSON 账本或工具。

每次跨对话续作必须先读取最新整体 Manifest 并 validate 当前有效 artifact，再读取工作稿。工作稿绑定的版本和 P2 artifact path/SHA 匹配时，以工作稿作为当前验证内容；若最新整体版本因 P3 等无关发布变化，但 P2 artifact path/SHA 未变化，核对后更新基线指针并继续。若 P2 artifact 变化，按 MV ID 对照工作稿绑定的旧基线与当前正式 artifact，合并无冲突的用户反馈、SQL 和实际结果；存在冲突、基线无法验证或元数据缺失时，保留工作稿、不覆盖、不回退旧 SQL，报告 WORK_DRAFT_CONFLICT 并请求确认。工作稿不存在时才从当前有效正式详细记录续读；不得回读已退役历史 role。独立盲分析不得读取或继承正常模式工作稿。

正式发布成功后，更新工作稿中的基线指针至新版本及新 artifact SHA；正式归档文件和历史 Manifest 永不原位修改。首次正式发布前工作稿标记 UNPUBLISHED，发布后再绑定实际版本。

逐条验证时一次交付一个 CHK/MV 的完整详细记录；首次提测分析聊天不展示 SQL 正文。SQL 由 P3 设计，P2 调用方负责将 SQL 写入上述绑定基线的工作稿；用户在有权限环境手动执行，P2/P3 不连接或执行数据库。F 命中仍需回页面复现；V 结果不自动证明页面运行正确。
## 报告长度与展开深度

- 不设固定字数、页数、CHK 数量或 EV 数量上限，不因控制长度而删减必要业务覆盖、静态核对通过项、问题、风险、影响范围、回归建议或证据。
- 结论摘要保持简洁，优先说明对用户决策有影响的结论。
- 变更概览按业务功能归纳，不按文件数量堆砌。
- 静态核对通过项简要说明核对范围、结论和证据。
- 已确认缺陷详细说明违反的业务预期、实际实现、证据定位和影响。
- 潜在风险说明合理影响路径、已证实事实和证据边界。
- 待业务确认事项明确提出问题、原因和影响。
- 影响范围及回归建议保留必要对象和依据。
- EV 集中记录可复核定位，不重复粘贴完整 Git Diff、源码或 MCP 原始返回。
- 矩阵中的核对项不得因在问题章节展开而删除；其他章节可通过 CHK/EV 编号交叉引用，避免重复叙述。
- 简单变更保持简洁；复杂业务链路按需充分展开，不为格式统一增加无关内容，也不增加报告长度质量门禁。
