# P2 → P3 SQL 委派与接收契约

适用范围仅限 P2 submission-impact 开发提测影响分析。BUG 根因排查、无需求代码变更、P1 和独立 P3 任务不因本文件自动生成 SQL。

## 1. 职责边界

- **P2 负责**：结合本次需求、实际代码变更、已确认业务规则及影响链路，识别必要的独立真实数据验证目标；建立 CHK/MV/P1 Case ID ↔ P3 场景 ID 映射；管理 verification-details.md、首次聊天隐藏 SQL、用户反馈和 P2 状态。
- **P3 负责**：SQL 业务分析、产品口径/独立 Oracle、F（真实样本）与 V（独立预期）职责、数据来源与粒度、有效过滤、执行引擎/方言、SQL 正文、格式和结构检查。
- P2 委派是**职责委派**，不依赖某个 Agent 的专有 API。P2 可以向 P3 提供需求、CHK/MV/Case、变更点、可信代码证据、页面/过滤线索和已确认业务口径；不得绕过 P3 规则自行另写 SQL、另造 Oracle 或以开发实现替代产品预期。
- 只验证本次需求和实际变更影响下必要的业务断言，不机械覆盖页面全部指标，也不按 CHK/MV/Case 数量生成 SQL。P2 负责识别跨指标依赖和回归范围；P3 只设计已识别目标的独立数据验证。

## 2. 两阶段判断与 SQL 生成前强制加载

### 阶段一：P2 识别目标后，按需决定是否进入 SQL 设计

P2 先完成本次需求、源码、影响链路与 CHK 核对，识别必要的独立真实数据验证目标，并收集可定位的数据来源/业务预期线索；这一步**不要求提前完整加载两份 P3 规则**。逐目标判断：

1. **无独立真实数据断言**：纯 UI、布局、导航等不需要 SQL，标不适用；不加载 P3，不机械创建 SQL 或人工任务。
2. **明确禁止本轮生成 SQL**：用户只允许静态分析或明确限制不生成 SQL 正文，保留 CHK、必要 MV 与阻塞原因/恢复条件，不加载 P3；不能把“按需尚未读取”误报为 `P3_RULES_NOT_LOADED`。
3. **有可定位来源线索并准备设计 SQL**：从需求、代码、可信血缘/知识中找到可查证的表、字段、过滤或 Oracle 线索后，进入 P3 设计。来源尚不完整但有可靠路径时，允许 P3 依据自身规则定向探查，**不能因为 P2 没有完整字段/独立 Oracle 就提前一概阻断**。P2/P3 本来只设计 SQL，不连接或执行数据库；没有生产连接权限、没有真实样本结果，不是设计 SQL 的阻断理由。
4. **无任何可靠数据来源线索且无法定位**：仅该数据目标暂记 `BLOCKED`，明确缺少的来源/业务证据及后续恢复条件；保留 CHK、必要的人工核对/目标映射和报告覆盖缺口，不编造表名、Oracle 或 SQL，不为无法生成的目标提前加载两份长规则。后续发现线索再恢复委派。

`BLOCKED` 仅表明对应目标受实际证据或用户范围限制，不能把未加载规则当成已加载；只有**实际尝试加载且失败/不完整**才用 `P3_RULES_NOT_LOADED`。已进入 P3 后如仅个别目标的来源或 Oracle 不充分，由 P3 依现有规则局部 `PARTIAL/BLOCKED`，不得因此取消其他可完成目标。数据目标的 F/V 责任与对应 MV 规则不因阶段划分减少。

### 阶段二：实际生成、补充、修改或写入 SQL 前完整加载规则

每次 P2 提测任务准备生成、补充、修改或写入任何 SQL 正文之前，必须在**当前任务**中实际读取以下两个文件的完整当前内容：
1. skills/sql-design/SKILL.md
2. skills/sql-design/references/sql-design-guidelines.md

执行要求：

- 使用当前环境可用的项目文件读取能力；不得只读片段、搜索摘要、历史聊天、模型记忆或上一轮缓存来代替。
- 如果单次读取因长度限制未返回完整内容，必须按连续范围补读，直至两个文件均完整；确认没有缺页、截断或读取失败。能取得文件版本/读取修订号时一并记录。
- 若任一文件不存在、读取失败、内容不完整或无法证明已完整加载，立即报告 P3_RULES_NOT_LOADED，停止所有 SQL 生成、修改和写入；不得由 P2 手写 SQL 兜底。非 SQL 的代码影响分析继续完成，受影响的数据验证目标标记 BLOCKED，说明缺少哪个文件/证据。
- 在 verification-details.md 记录 P3_RULES_LOADED、两个文件路径、可取得的版本/读取修订号及完整读取证据；无需复制整份规则正文。
- 如果任务过程中发现 P3 规则文件已变化，后续 SQL 修改前重新完整读取受影响文件。

## 3. 交给 P3 的最小必要输入

逐个目标提供：

- 验证目标及其关联 CHK/MV/P1 Case ID（若有）。
- 本次真实代码变更、影响层级、业务对象、受影响字段/指标及页面/Tab/查询入口。
- 需求/产品提供的数据表、字段、上游 SQL/计算逻辑、用户已确认口径和适用 P1 Oracle；注明来源及可信状态。
- 已确认的页面有效业务过滤、默认条件、查询参数及适用环境；P4 知识仅在确有帮助时按需提供。
- 已确认的执行端/SQL 方言证据；没有证据时明确未知，不从底层数据源猜测。

不得把开发变更表达式、被测 DWD/DWS/ADS 结果或页面当前实际值包装成产品 Oracle。缺少关键来源时由 P3 按自身规则局部 BLOCKED 并提出具体缺口；不允许 P2 猜表、猜字段或扩大无目标探查。

## 4. P3 交付内容与 SQL 约束

### 场景映射

impact-analysis.md 与 verification-details.md 必须逐目标映射：

CHK/MV/P1 Case ID ↔ P3 场景 ID ↔ SQL 编号 ↔ 有效条件 ↔ SQL 输出字段/页面核对字段

SQL 数量与执行入口按现行 P3「SQL 分组与场景切换」确定：同来源、同业务粒度、同核心计算且执行端与输出兼容的场景优先复用同一条 SQL；不同来源、粒度（如运单与线路）、Oracle 或合并后产生大量无关关联、排序、明显性能冲突时按需拆分。场景条件相似且安全时，用 `-- and ...` 注释切换，公共有效过滤始终生效，人工切换尽量集中在一处。F（真实样本）与 V（独立预期）是验证职责，不固定一条或两条 SQL。每个场景必须映射到具体 SQL 编号、有效条件和输出字段，不因复用丢失断言。样本输出数量根据场景需要和真实平台限制决定；F 找数的候选限量只能限制候选对象，不得截断 V 计算所需的完整数据集合。

### F：真实样本

- 说明样本筛选逻辑、场景成立条件及 SQL 中证明条件成立的字段/计算。
- 输出真实可定位的页面/接口 Number/Code；必要时同时输出内部 ID，并分别说明用途。
- 聚合场景须给出足以证明样本成立的明细/去重对象依据；不能只返回一个编码或汇总数字。
- SQL 未由用户执行并回传前，不得声称已经找到具体样本或编造样本值。

### V：独立预期

- 记录产品口径/Oracle 的具体来源、公式、业务对象粒度、有效过滤、必要原始值/中间值/最终预期。
- 需求/产品明确提供的上游 SQL 或预聚合结果可作为预期依据；不得用本次被测变更输出反推预期。
- ADS 仅在独立样本和预期确定后作为页面定位/实际值辅助侧；不得反向筛选样本或参与预期计算。验证漏数时保留未匹配样本。

### 方言、格式与性能

- 数据源与 SQL 解析方言分开记录。执行端未确认时使用 execution_engine: Presto (default assumption)、sql_dialect: Presto，解析兼容性标 NOT_VERIFIED；有可靠实际执行端证据时按实际执行端调整。
- SQL 只允许只读 SELECT/CTE。关键字小写、逗号前置、CTE 使用 v_ 前缀、表别名 t1/t2、输出别名/中间标识符使用英文 snake_case；最终 SELECT 的每个输出列均有中文注释，说明业务含义、页面/接口对应字段及定位/对账用途。
- 默认上一个自然月，按真实有效日期/分区字段过滤；页面默认业务过滤和后端固定业务条件必须按 P3 规则核实，不得为方便找数擅自放宽。
- 多场景复用时优先共享安全的基础 CTE，按真实日期、分区和有效业务条件尽早过滤，避免重复扫描和无效聚合；共享 CTE 前按目标引擎的复用/内联行为评估扫描成本。样本输出数量根据场景需要和真实平台限制决定，不为固定上限或找数限量截断 V 计算所需的完整明细集合。禁止用占位/状态/汇总行替代真实样本。

### 检查与状态

- 将 SQL 正文原样提取到 .qa-work/ 下的临时 .sql 文件，依次执行：
  1. `python -B skills/sql-design/tools/check_sql_style.py TEMP_SQL_FILE`
  2. `python -B skills/sql-design/tools/check_sql_structure.py TEMP_SQL_FILE`
  在工作稿记录临时文件路径、两条完整命令、各自退出结果及输出；风格检查明确 FAIL 时必须退回 P3 修复并重跑。无法执行任一检查时，对应项标 NOT_VERIFIED 并说明原因。
- `P3_SQL_STYLE_PASS` 只证明脚本覆盖的确定性格式项通过；复杂子查询/表函数别名和其他未覆盖格式仍须人工复核。`P3_SQL_SCOPE_PASS` 只证明跨语句未加引号 v_ CTE 作用域检查通过。二者均不代表方言解析、数据库执行或业务正确性。
- 验证准备状态使用 READY / NO_SAMPLE / PARTIAL / BLOCKED：READY 仅表示 SQL 已设计、具备执行条件；NO_SAMPLE 仅在用户执行后确实无样本时使用；PARTIAL 必须列出已覆盖和未覆盖断言；BLOCKED 必须说明阻塞点及需补信息。UNKNOWN 仅描述证据未知，不作为场景状态。P2 自身 CHK/MV 状态仍由 P2 管理。
## 5. P2 接收检查与工作稿

P2 将 P3 交付写入绑定当前 P2 基线的 .qa-work/<需求编号>-<需求名称>/submission-impact/verification-details.md，并在 impact-analysis.md 逐目标登记覆盖摘要。写入前逐项检查：

1. P3 两份规则已完整加载并留有 P3_RULES_LOADED 证据。
2. 每个必要验证目标均映射到 P3 场景 ID、SQL 编号及输出/页面核对字段；纯 UI/无真实数据断言目标标 N 并说明原因。
3. F 有样本成立逻辑、成立证据字段和真实页面定位字段；聚合场景有必要明细/去重对象依据。
4. V 有明确产品 Oracle 来源、计算逻辑和独立性说明；没有使用本次被测输出自证。
5. 执行引擎、SQL 方言、证据来源及解析兼容性状态如实记录；默认 Presto 假设不得写成已确认事实。
6. SQL 只读、格式符合 P3 规则；已执行轻量风格检查并记录命令/结果，最终输出列逐列中文注释；样本输出数量符合场景需要和真实平台限制，未因限制 F 候选数量而截断 V 计算的完整数据集合。
7. 结构检查记录实际命令和结果；未执行不得伪报 PASS。
8. 每个场景均映射到具体 SQL 编号、有效条件和输出字段；SQL 按 P3 分组策略复用或合理拆分，拆分时记录来源、粒度、Oracle 或性能等技术原因及对应执行入口。
任一项不通过，P2 不得把该目标标记为已完成；将问题退回 P3 规则职责修正，不能由 P2 绕过规则补写。SQL 正文只写入工作稿；首次聊天只展示目标、映射、覆盖状态和必要缺口，不展示 SQL 正文。P2 不创建 P3 SQL-only Manifest/正式版本，不连接或执行数据库，不修改业务数据；用户执行并反馈后，仍由 P2 更新当前 CHK/MV 与工作稿。
