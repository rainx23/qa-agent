# P2 公共业务语义推理方法

> 状态：ACTIVE（2026-11-05 深层推理增强第一批；2026-11-09 数据口径一致性与人工 SQL 验证闭环增强）
> 适用范围：D:/qa-agent / skills/code-impact-analysis
> 使用方式：由 code-impact-analysis/SKILL.md 统一入口在执行任一 P2 分析工作流前加载；三个分析工作流共享本方法，但不共享任务状态或归档。
## 目标与边界

本方法用于把 P2 从“检查技术节点是否存在”提升为“判断实际业务行为是否满足适用预期”，通过业务行为建模、约束推导、真实实现追踪、缺陷假设、反例/反证和证据闭环，尽可能发现静态可证明的问题并减少重复人工核对。

本方法落实已有完整调用链核对与人工事项收敛要求，不替代或削弱完整链路核查，也不把任一单个历史需求扩展为专项硬编码清单。

执行边界：

- AI 负责业务理解、语义推导、假设与反例分析；Python 只处理必要的确定性工作，不建设 Python 业务推理引擎。
- 不把当前代码“怎样实现”直接当成产品“应该怎样”；业务预期必须来自适用的需求、用户/产品确认或正式业务规则。
- 不假设列表与汇总永远相等、所有字段必须同公式或所有页面必须共享实现；是否一致须有业务依据。
- 不机械检查全部语义维度或所有技术层，只分析本任务真实涉及的路径。
- 不修改业务代码/配置，不执行 SQL/ETL，不导入平台、不 Push；不建设接口/UI 自动化框架、数据库、证据库、状态账本或复杂审批机制。
- 不承诺静态分析能够证明所有运行态、数据态或外部依赖行为。

## 通用执行原则

1. 从用户当前任务和已有材料出发，不要求重复提供上下文中已有的信息。
2. 先明确业务预期及其来源，再核对实现；预期不清且会实质改变结论时，提出最关键的澄清问题。
3. 从真实业务入口追踪实际实现和结果消费，不以名称相似、文件相邻或关键词命中代替调用/绑定/数据依赖证据。
4. 对关键业务关系主动思考其失效条件，不因技术参数或字段名称一致就提前判定语义一致。
5. 先提出少量高价值假设，再用源码、配置、历史或其他有效证据验证并尝试推翻；不扩展无触发条件的泛化猜测。
6. 区分已确认缺陷、潜在风险、待业务确认和无问题；静态核实、运行验证及人工核对状态沿用现有报告规范。
7. 只展示可审计的业务依据、假设摘要、验证过程、结论和证据，不记录或输出隐藏思维链。

## 通用业务推理流程

### 建立业务行为模型

先根据当前任务回答与结论相关的问题：

- 谁在什么页面、场景或流程中，对什么业务对象执行什么操作？
- 输入、筛选条件、配置、状态、时间范围和上下文是什么？
- 系统应产生什么业务结果，该结果由哪些页面、列表、汇总、图表、导出或下游流程消费？
- 预期依据是什么：需求原文、用户/产品确认、正式业务规则，还是尚未确认的推导？
- 当前已知限制、歧义和证据缺口是什么？

不同工作流的预期锚点保持独立：

- 开发提测分析：以需求和权威业务规则为预期来源；用户提测点是初始定位线索，不是完整变更范围；最新有效 P1 用例仅作可选交叉核对依据。
- BUG 根因排查：以用户描述的实际异常、明确预期（如有）及可取得的业务依据为起点；先还原当前实际行为，不擅自补造预期。
- 无需求代码变更分析：比较变更前后的实际行为，识别业务影响和兼容性；不虚构需求或产品预期。

### 还原真实实现路径

从业务入口沿当前任务实际涉及的链路追踪，典型路径可能包括：

入口/操作 → 页面与配置绑定 → 控件和状态 → 参数生成 → 请求/调用 → 接口与服务 → 条件判断/转换/计算 → SQL 或数据处理 → 返回/存储 → 列表、详情、汇总、图表、导出或其他消费方。

执行要求：

1. 以真实调用、引用、配置绑定和数据依赖为依据，不凭名称相似或关键词命中推断关系。
2. 打开关键实现上下文，确认字段/参数在哪里被实际读取和使用，不停留在声明、定义或孤立 SQL 片段。
3. 共享实现或共同业务义务须核查实际关联消费者（含无 Diff 的既有消费者）；按所选工作流从变更和业务入口双向发现范围，行为相同可合并，但保留对象及差异。
4. 多消费路径比较真实计算、过滤、转换和消费语义；结论前定向反查间接调用、独立参数/计算、特殊触发及结果消费分支，不重复已核实路径或机械扫描无关功能。
5. 只追踪有证据关联的技术层；动态调用、反射、运行时配置、远端封装等无法静态解析的部分明确记录证据边界，不猜测。
6. Git、配置 MCP、P4、运行证据的版本、SHA、环境和时间边界，继续遵循权威决策及当前工作流。

### 推导适用业务约束

AI 应从业务行为和真实实现中识别当前任务中“哪些关系必须成立”，再按需选择约束视角。下表是思考提示，不是每次必须逐项执行的检查表。

| 约束视角 | 按需思考的问题 |
|---|---|
| 对象身份与范围 | 页面、接口和数据查询是否指向同一业务对象集合？是否漏数、重复或扩大范围？ |
| 数值与单位 | 金额、数量、重量、票数、比例等的分子、分母、单位、精度和转换是否符合业务含义？ |
| 过滤与选择 | 条件是否作用于正确字段？默认值、空值、清空和组合条件是否改变筛选范围？ |
| 粒度与聚合 | 明细、任务、业务单据、线路、用户等粒度是否一致？去重、分组、加总和汇总是否符合口径？ |
| 映射与转换 | 前后端字段、枚举、别名、类型、时间、状态和数据来源是否正确映射？ |
| 多结果一致性 | 列表、详情、汇总、图表、导出、缓存或异步结果之间，哪些按业务要求应一致，哪些允许不同？ |
| 状态与流程 | 状态迁移是否合法？前置条件、重复操作、回退、终态和异常分支是否正确？ |
| 排序与分页 | 展示值、排序字段、分页游标和过滤后顺序是否一致？边界记录是否遗漏或重复？ |
| 空值与边界 | NULL、空字符串、0、负数、极值、缺省值、单条/多条及无数据如何处理？ |
| 权限与隔离 | 用户、组织、租户、角色或数据权限是否在所有实际入口和查询路径生效？ |
| 时间与版本 | 日期边界、时区、跨天、有效期、版本兼容和新旧状态是否正确？ |
| 并发与可靠性 | 重试、幂等、重复提交、缓存、并发更新、失败回滚和降级是否影响业务结果？ |
| 依赖与兼容 | 公共方法、接口契约、上下游任务或历史调用方是否因变更产生行为差异？ |

### 数据口径一致性与指标公式/粒度核对

本节按真实业务路径和触发条件执行，不要求每个需求机械生成完整矩阵；一旦触发，必须完成可审计的公式、粒度和适用数值关系核对，不能只在报告中笼统写“已检查 SQL”。

**触发条件：**
- 同一业务指标出现在多个层级、接口、页面组件或消费路径中。
- 页面同时存在列表、汇总、详情、图表、导出或下钻结果。
- 存在 SUM/MAX/AVG、窗口函数、去重、多层聚合、派生指标或比例计算。
- 存在一对多/多对多 JOIN、父级字段下沉到子级明细、共享 SQL/接口或复用多个既有接口。
- 出现结果矛盾、同名指标取数列不同、过滤范围可能不同，或需求描述“沿现状口径/复用旧接口/保持原逻辑”。

**触发后必须完成以下核对：**

1. **指标公式矩阵**：按实际业务指标逐项提取各层级/消费方的真实 SQL 表达式，记录来源表和字段、分子、分母、CASE/条件表达式、过滤范围、去重方式、聚合函数、单位、精度/取整及最终输出字段。必须打开表达式上下文并沿调用链确认实际使用位置，不能仅按字段名或注释推断语义。
2. **数据粒度矩阵**：明确原始数据一行代表什么业务对象；逐段核对 JOIN 键与关联基数、JOIN 前后行粒度、是否一对多/多对多、去重/窗口处理、GROUP BY 粒度、聚合输入粒度、最终输出粒度，以及页面列表行粒度和汇总计算粒度。重点识别父级实体字段被复制到子级组合行后再次 SUM、JOIN 扩行、错误去重或 MAX 任意取值等风险。
3. **跨路径语义比较**：比较不同层级、接口、列表/汇总/图表/导出的对象集合、筛选条件、业务粒度和公式。相同指标名称不自动代表公式必须相同；公式不同也不自动代表缺陷。必须说明差异是否由业务范围、指标定义或非可加性造成；缺少权威依据时列待业务确认/潜在风险，不猜测产品口径。
4. **数值关系与最小反例**：只有在对象集合、过滤条件、时间范围、去重规则、单位和统计粒度一致，且指标具备相应可加性时，才验证“上层汇总 = 下层合计”等式。比例、平均值、重叠分组和非互斥集合不得直接套用简单加总等式。按实际风险构造最小反例，静态推导必须标记为构造示例，不冒充数据库实测。
5. **既有实现不得免检**：旧接口/组件未发生 Diff、被多个层级复用或需求声明“沿现状口径”，均不能作为跳过自洽性检查的理由。若发现差异，继续区分历史既存问题、本次变更引入问题，以及本次功能组合后暴露的问题；不得将历史问题误归因于本次，也不得因其历史存在而免检。
6. **报告留痕**：触发时在报告“数据口径一致性”章节呈现公式矩阵、粒度矩阵、适用的数值关系、差异解释、结论和 EV。未触发时简要说明不适用原因，不填充无关表格。

先确定业务关系，再选择相关约束。若业务预期不明确，标记待业务确认，不用代码现状替代业务决策。

### 形成缺陷假设

对复杂业务行为、异常迹象或高影响路径，主动提出少量高价值假设。每个假设至少具备：

1. 触发条件：什么输入、状态、数据形态或操作组合可能触发？
2. 预期约束：哪条需求、业务规则或已确认关系要求系统怎样表现？
3. 实际路径：当前代码具体如何处理该条件？
4. 可能矛盾：哪个转换、判断、计算、调用或消费环节可能违反约束？
5. 失败结果：假设成立时，用户会看到什么错误结果或业务影响？
6. 可验证证据：需要核查哪些源码、调用方、配置或历史证据？
7. 反证条件：出现什么证据可以推翻该假设？

假设必须关联真实代码路径或明确业务约束。没有触发条件、影响路径和可验证依据的泛化猜测不列为问题。

### 构造反例并尝试推翻假设

对重要业务约束，不只确认“有没有实现”，还要思考“在什么情况下它会不成立”。按当前逻辑选择有价值的反例：

- 最小数据样例：用少量记录推导公式、聚合、去重或过滤结果。
- 边界值：0、NULL、空值、负值、极值、上下边界和无数据。
- 条件组合：单条件/多条件、默认/自定义、开启/关闭及不同模式组合。
- 粒度变化：单条/多条、重复/唯一、明细/聚合及不同对象粒度。
- 分支差异：不同枚举、状态、角色、配置、参数缺省或异常分支。
- 多消费方对照：列表与汇总、页面与导出、接口与异步任务、当前与共享调用方。
- 变更前后对照：相同输入下旧逻辑与新逻辑的行为差异。

反例可以是源码逻辑推导或人工构造的最小示例，不要求真实执行 SQL、接口或 UI 自动化。报告必须标明这是静态推导/构造示例，不能冒充实际运行结果。

对每个高价值假设，至少进行一次有针对性的反证：检查其他分支、公共封装、业务例外或有效配置是否能解释差异。找到足以推翻假设的证据后，不再把它作为缺陷；证据不足则按现有规则保留为潜在风险、待业务确认或证据不足。

### 证据闭环与根因确认

不同证据只证明其实际覆盖范围：

- 需求、用户/产品确认及正式业务规则：证明适用的业务预期。
- 指定仓库和完整 SHA 下的源码：证明该版本的实现方式。
- Git Diff/历史：证明版本间发生的代码变化，不能单独证明部署或运行。
- 配置 MCP：证明特定环境、对象和读取时间下的当前配置返回。
- P4：提供定位线索和历史知识，不替代当前需求、源码、配置或业务确认。
- 日志、请求响应、数据样例、页面表现和用户反馈：仅在实际取得时证明相应运行态事实。

只有明确预期与实际实现之间存在可复核的矛盾，才能确认代码缺陷。缺少业务预期时，不以“代码看起来异常”直接判缺陷；缺少运行态证据时，不宣称实际运行结果已验证。

### 人工 SQL 验证结果的证据判定

用户执行 P3 提供的 SQL 并回传结果后，AI 必须回到原始 CHK 和业务断言进行判断，而不是只看 SQL 是否执行成功：
- 记录用户实际执行的环境、时间、参数/过滤范围、返回行数及关键结果；SQL 报错、权限不足、环境不可用、成功无数据和结果不符合断言必须分开处理。
- V 查询结果与预期一致，只能确认该查询覆盖的数据断言；若页面展示、接口运行或部署状态仍未验证，继续标记相应运行验证 NOT_RUN。
- V 查询结果违反明确业务断言时，结合源码公式、数据粒度和独立对照路径判断是否构成缺陷；不能仅凭单条异常记录扩大为全量结论。
- F 查询命中只表示找到候选样本，必须由用户继续在页面/接口执行对应复现步骤；F 未命中也不能直接证明页面无数据或实现缺陷。
- 用户回传结果后，AI 应主动解释结果、判断假设成立/被推翻/仍证据不足，并回填对应 CHK/EV/MV。正式 P2 报告已发布且结论发生实质变化时，按需求级版本规则创建新版本，不原位修改历史产物。

### 影响范围与最小人工核对

1. 从已确认的根因或风险出发，沿真实调用方、数据依赖和结果消费路径确定直接、间接及潜在影响。
2. 共享实现的真实调用方必须完整核查；不能因只发现一个入口就断言只有一个受影响对象。
3. 静态证据已足以回答的代码事实直接交付，不进入 MV，也不要求用户重复核对相同静态实现。
4. 默认情况下，只有静态证据无法回答、且用户能够通过明确的最小操作得到可判定结果时，才建立 MV；每个 MV 只回答一个具体问题，写明环境、操作、预期和静态无法证明的原因。**开发提测影响分析按 submission-impact.md 的现行 MV 规则执行**：AI 已识别为已确认问题、潜在风险或待业务确认，且确需用户页面复现/核实行为/业务确认的，也可建立 MV；不得要求用户重复核对源码本身。
5. 回归建议、用例覆盖缺口、NOT_RUN 和理论上的所有边界场景不自动转为人工待办；开发提测仍仅将确需用户复现/确认的问题或风险纳入，不把所有 CHK 机械转为 MV。
6. MCP 故障或证据缺失本身不自动成为 MV；若用户没有可执行且能回答问题的验证方式，记录证据缺口和影响即可。
## L1/L2/L3 动态分析深度

### 选择原则

由 AI 自主选择，用户无需指定等级。依据业务逻辑复杂度、潜在影响和证据不确定性综合判断，不按文件数、代码行数、提测点数量或仓库数量分级。

重点考虑：是否存在计算/聚合/过滤/状态或复杂分支；是否涉及多个业务对象、数据粒度或上下游；是否修改共享实现；是否影响金额、成本、权限、核心指标或关键流程；是否跨页面、接口、SQL、ETL、配置或外部服务；是否存在历史异常、结果矛盾、需求歧义或关键证据缺口。

若信息不足但可能实质影响结论，不得为了节省成本直接降为 L1；应至少选择 L2，或先询问最关键的澄清问题。

### 等级定义

| 等级 | 适用情况 | 必须完成的分析 |
|---|---|---|
| L1 快速静态分析 | 逻辑简单、影响局部、映射明确，无复杂计算、共享调用或跨层行为变化 | 完成必要业务链路；核对字段、参数、来源、映射、格式化和实际调用方；对明显相关分支做基本反证，不扩展无关场景 |
| L2 业务语义推理 | 存在查询条件、参数组合、条件分支、数据转换、多个关联对象、排序/分页或共享组件 | 建立业务行为模型；推导适用约束；追踪真实实现和调用方；针对关键约束构造边界/组合反例；验证高价值假设 |
| L3 深度缺陷推理 | 复杂计算/聚合、多数据源、跨模块共享逻辑、关键权限/状态、核心指标，或存在浅层分析无法解释的异常/证据矛盾 | 完整还原关键业务链和数据粒度；提出并验证多个竞争假设；构造最小反例并交叉对照多个消费方、调用方或分支；追踪真实影响范围；明确排除项和证据边界 |

L1 不代表可以省略适用业务义务或必要证据；L2/L3 也不意味着机械扫描所有语义维度。

### 自动升级与停止条件

- 从 L1 开始后，发现计算/聚合、多个关键分支、共享调用方、跨技术层依赖或结果矛盾时，按证据自动升级到 L2/L3。
- L2 发现核心业务结果可能被错误计算、数据范围可能变化、共享实现影响面扩大或关键证据互相矛盾时，自动升级到 L3。
- 任务一开始已明确具有 L3 特征时，直接使用 L3，不必机械执行 L1。
- 升级时简要记录触发原因；不因“想更全面”而无依据升级。
- 发现问题后继续核查有证据支持的影响范围，但不以发现一个问题为由无边界扫描整个仓库。
- 当业务义务已映射、适用链路已核实、关键假设已证实/证伪或明确受证据限制、共享调用方已核查、剩余未知项已列明，且继续扩展不再产生新的可验证路径时停止。
- 每次扩展必须由具体未决问题或新证据触发；遵守工作流的仓库、MCP、搜索和询问边界，不无限重试或无边界关键词扫描。

## 结论、报告与留痕

沿用现有总体结论、CHK、EV、MV、“已确认缺陷/潜在风险/待业务确认/无问题”、静态核对状态、NOT_RUN 及五种人工状态；不新增状态枚举、风险评分或第二套编号体系。

静态 PASS 必须能够说明：

- 本 CHK 的业务预期及适用范围；
- 已核对的真实实现链路；
- 关键业务约束及为何满足；
- 对重要风险是否进行了反例/分支核对；
- 指定 SHA、文件/方法/行号及 EV 证据；
- 明确无需重复人工核对的范围。

仅证明字段存在、参数已传递、接口调用成功、SQL 含有条件或多个路径使用同名参数，不足以证明业务行为正确。

报告结论速览或分析范围中简要记录本次 L1/L2/L3、选择依据、是否自动升级及原因、实际采用的关键约束视角。只记录可审计的依据、假设摘要、验证过程、结论和证据，不输出隐藏思维链。报告按实际复杂度展开，不以报告长度衡量推理深度。

## Token、耗时与工具调用控制

1. 简单任务使用 L1；复杂或高影响任务才使用 L2/L3，避免统一深度造成无效成本。
2. 复用当前任务已冻结 SHA、已读取源码和仍有效的上下文，不重复 Fetch、读取或调用 MCP。
3. 从真实业务入口和具体假设定向取证；只有新证据指出必要关联时才扩展仓库、调用方或技术层。
4. 只使用当前任务适用的约束视角，不要求逐项执行全部视角。
5. 优先验证业务影响大、源码路径明确且能被当前证据证伪/证实的假设，不展开低价值泛化猜测。
6. MCP 只按当前涉及的技术层与实际证据缺口调用；失败后停止无效重试，保留已有证据并说明缺失范围。
7. 每次扩展说明其对应的未决问题；达到停止条件后结束，不追求理论上的无限覆盖。
8. 不设置会牺牲必要证据的 Token 硬上限；通过动态深度、复用和去重降低无效成本。
9. 不以报告长度衡量分析深度；简洁呈现结论，保留完整必要证据。Token、耗时或调用统计只有运行环境能可靠提供时才记录，不得编造。

## 三个分析工作流的场景锚点

| 工作流 | 推理起点 | 场景重点 |
|---|---|---|
| 开发提测影响分析 | 需求义务、用户提测点、本次实际变更和当前灰度代码 | 从需求到实现、从实现回到需求双向推导；主动发现提测点未提及但影响业务结果的实现问题；保留灰度 SHA、配置 MCP 和 P1 边界 |
| BUG 根因排查 | 实际异常、明确预期（如有）和当前实际行为 | 先还原现状，再提出竞争根因假设并逐项反证；沿真实调用和数据路径定位；保留生产/环境基线及有限定位边界 |
| 无需求代码变更分析 | 变更前后源码/行为和实际调用方 | 比较行为差异，识别隐含业务契约、兼容性和调用方影响；不虚构需求或产品预期 |

公共方法只复用推理方法，不合并三个分析工作流的触发条件、输入要求、代码基线、归档、任务状态或安全边界。具体场景规则以所选工作流和权威决策为准。
