# Code Impact Analysis（P2）｜代码影响分析

## 能力定位与本批边界

本 Skill 是 P2 代码影响分析的唯一统一入口，负责识别用户意图、选择一个工作流并执行 P2 公共约束。P2 包含三个只读分析工作流，以及两个独立的平台动作工作流：禅道 Bug 提交、Bug 回归与关闭。Lifecycle 复用只读分析工作流的推理方法和报告格式，但不替代或混入其业务职责。

P2 独立于 P1 和 P4：

- P1 的正式测试用例由 testcase-design 独立设计、修订、发布和管理。
- P1 最新有效正式用例可以作为 P2 的可选分析输入，但缺少用例不阻断 P2；P2 不得修改、发布或接管 P1 用例。
- P4 尚未建设或不可用时，P2 仍须依靠自身的 Git、源码和按需 MCP 证据完成可完成的分析；不得把 P4 作为硬依赖。

原 P2 三个分析工作流及统一报告规范均已实施。新增 Bug Submission 作为独立写入动作工作流，第一批实现文字 Bug 草稿、逐条人工授权和禅道创建回执，不改变三个分析工作流的业务分析范围。P2 深层推理增强按独立批次推进：第一批已完成公共推理方法及统一入口接入；后续工作流场景化细化和历史样本盲测按独立批次实施。路由目标文件仍须在执行前确认存在且已实施；若缺失或内容不完整，必须明确返回 NOT_IMPLEMENTED 并停止缺失范围，不得假装可用或回退到 P1/P4 代替。

## 自然语言意图识别与路由

| 场景 | 触发条件 | 路由目标 |
|---|---|---|

| BUG 根因排查 | 用户描述实际异常、错误或业务结果不符合预期，并要求定位原因、排查 BUG 或分析根因。页面、接口、字段、请求参数、日志、截图、发生时间、仓库等线索均为可选输入，不要求启动前全部提供 | bug-investigation.md |
| 无需求代码变更分析 | 没有需求编号，用户明确要求分析代码变更、重构、优化、技术整改或其他独立代码调整的行为差异和业务影响 | code-change-analysis.md |
| 禅道 Bug 提交 | 用户明确要求提交/登记已确认缺陷、准备提交草稿，或继续处理当前唯一待授权的 Bug 草稿；仅发现缺陷、确认缺陷事实或要求分析不触发提交 | bug-submission.md（命中后先重新读取完整工作流） |
| Bug 回归与关闭 | 用户提供禅道 Bug ID，要求回归、复测、验证修复或关闭 Bug | bug-lifecycle.md（命中后先重新读取完整工作流） |
| 读取已有 P2 分析结果 | 用户要求读取/查看/引用最新 P2 报告或基于报告继续，但未要求重新分析 | 本 Skill 内只读检索 Manifest 当前有效 P2 artifact，不启动三个分析工作流 |

**P2 → P5 候选建议与确认后续接（仅开发提测）**：`submission-impact.md` 完成需求和真实代码影响分析后，向完整 P2 报告与首次聊天追加 P5 接口维护建议（或明确无候选）；P2 为此仅按需只读定位目标接口及 P5 可信覆盖证据，不直接启动 P5 创建/更新 Case、Debug、正式 Run 或自动归档。用户明确选择建议中的接口范围后，续接独立 P5 `skills/api-autotesting/SKILL.md`，不因回复「执行第 N 项」误启动新一轮 P2 分析/Fetch/发布；P5 执行时须复核实际源码、索引及平台覆盖。P5 证据无法读取时说明待核实，不阻断 P2；Bug/无需求改动等其他工作流不默认附 P5 候选。

**只读检索已有分析结果：** 这是 P2 产物读取动作，不是新的分析工作流。先定位 `output/【<模块>】/<需求编号>-<需求名称>/`，读取 `manifest.py inspect` 返回的最新整体版本及其 `versions/<最新版本>/manifest.json`；从当前有效 artifact 清单中选择 category=`test-impact-analysis`、role=`impact-analysis`，并按需读取 `manual-verification`。仅当当前报告工作流明确为开发提测影响分析（`submission-impact.md`）时，才读取 `verification-details` role 并校验 SHA；其他 P2 工作流不查找、不要求创建该 role。开发提测逐条验证的工作稿续读按本文件下一节执行。最新 P2 文件可能位于早于最新整体版本的目录（例如最新整体版本是 P3 SQL 版本），不得直接把最新版本目录当作最新 P2 报告，也不得回到 P1 基线自己的旧 Manifest 寻找当前报告。当前 Manifest 没有有效人工清单时，明确说明当前无待人工清单；若没有有效 `verification-details`，不得回退读取已退役的历史详细记录。只读检索不得 Fetch Git、调用分析工作流、修改文件或创建新版本；用户明确要求重新分析/独立分析时才切换到对应工作流。
**已有 P2 开发提测风险的逐条人工验证（不是新分析）：** 仅当当前有效 P2 工作流明确为 `submission-impact.md` 时，用户说“开始逐条验证”、指定 CHK/MV 或要求“下一条”才启用。先读取最新整体 Manifest 并 validate 当前有效 P2 artifact，校验 SHA；随后检查固定路径 `.qa-work/<需求编号>-<需求名称>/submission-impact/verification-details.md` 中绑定该正式基线的当前工作稿。工作稿绑定的版本及相关 P2 artifact path/SHA 匹配时，以工作稿作为当前验证内容，正式 artifact 作为基线；若最新整体版本因 P3 等无关发布变化但 P2 artifact path/SHA 未变化，核对后更新基线指针并继续；若 P2 artifact 变化，按 MV ID 对照旧基线与当前正式 artifact 合并无冲突反馈，冲突/元数据缺失时保留工作稿并报告 WORK_DRAFT_CONFLICT，不覆盖、不回退旧 SQL。工作稿不存在时才读取当前有效 `verification-details`；不得读取已退役历史 role。独立盲分析不得读取或继承正常模式工作稿。一次交付一个项目，返回 AI 分析描述/问题性质、代码证据定位、页面与环境、前置条件、具体步骤、明确预期及适用时的可复制 SQL；不重跑 P2、不重新 Fetch Git、不重新全量探查。
- **P2→P3 数据验证委派（仅 `submission-impact`）**：P2 先完成需求/源码与 CHK 核对，识别必要数据目标及 CHK/MV/P1 Case 映射；是否调用 P3、目标 BLOCKED、默认 F/V SQL-01、工作稿和接收校验均以 `references/p3-sql-delegation.md` 为唯一详细契约。开发提测任务先读取该 P2 委派契约完成阶段一判断；**只有实际准备生成、补充、修改或写入 SQL 正文前**，才必须完整加载现行 P3 `SKILL.md`、`sql-design-guidelines.md`；失败报告 `P3_RULES_NOT_LOADED`，停止 SQL 正文，非 SQL 分析继续，禁止 P2 自写 SQL。无数据库运行权限不阻断 SQL 设计；首次聊天不展示 SQL 正文，不创建独立 P3 SQL-only 版本。
- **反馈与留档**：用户指出 SQL 有误时更新同一工作稿中的当前 SQL，不另建 SQL 文件；用户回传 SQL 结果和页面实际表现后更新对应实际结果及 CHK/MV 状态。正式归档依照 `submission-impact.md`「需求级归档与 Manifest」节，通过 `manifest.py publish` 创建新 P2 版本，历史文件不覆盖。SQL 只读且由用户执行，P2/P3 不连接或执行数据库；F 命中不等于页面复现，V 结果不自动证明页面运行正确。
**平台动作工作流强制加载：** 每次识别到“禅道 Bug 提交”或“Bug 回归与关闭”意图后，在调用任何禅道 MCP 工具（包括只读查询、Schema describe 和写入）前，必须重新读取对应子工作流的完整当前内容。不得以会话开头读过的旧副本、上一轮对话内容、入口路由表或工具说明代替。MCP 工具说明和 Schema 只约束工具能力、参数类型及枚举，不覆盖工作流中的业务判断、字段默认值、完整预览、Draft ID 授权、创建/关闭回读、归档和收尾检查。目标文件读取失败或内容不完整时，停止平台动作并报告 WORKFLOW_NOT_LOADED。

**归档校验按动作分开：** createBug 成功并回读后，核验 Bug Submission 回执、唯一 Manifest role、SHA 和 Manifest validate；closeBug 成功并回读 closed 后，核验 Bug Lifecycle 独立文件。当前 Manifest 不支持 bug-lifecycle category，因此关闭流程不要求 bug-submission role，也不得复用该 role。

三个分析场景保持独立。Bug Submission 是单独的写入动作，不负责缺陷分析；必须消费已有的已确认缺陷证据，或用户已人工验证确认的缺陷。Bug Lifecycle 是针对已登记 Bug 的修复影响分析、回归验证及经授权关闭，不替代 bug-investigation 的异常根因定位或 submission-impact 的开发提测整体分析。若用户只要求排查/分析，不得主动进入提交流程；若用户同时要求分析与提交但尚无确认结论，先完成对应分析并暂停，待用户明确要求准备提交后再进入 bug-submission.md。单次 P2 阶段只执行当前匹配的一个工作流，不得把分析与平台写入混为自动连续动作。
## 路由优先级与冲突处理
1. 以用户当前明确表达的主要目标为准，不仅凭关键词或是否出现需求编号判断。
2. “提测分析/继续提测分析”是明确的 P2 意图；若当前对话或项目中已有对应需求编号、提测点、P2 报告或人工清单，直接恢复 submission-impact.md，不得要求用户重复提供，也不得因本轮没有重复说“开发已提测”而回退到 P1。
3. 用户当前明确提供需求编号、开发提测点并要求分析提测影响时，直接路由 P2；提测点是初始定位线索，不代表完整代码影响范围。首次启动时若确实缺少需求编号或任何可定位的提测信息，只询问最关键的缺失项。
4. 用户只提供需求编号、要求普通需求分析，或明确要求编写/设计测试用例时，仍按 P1 testcase-design 的既有路由处理；不得仅因出现需求编号就启动 P2。
5. 用户描述 BUG 并要求根因排查时，不要求先提供完整技术定位；先使用已有线索开展有限、定向定位。只有缺少的信息会实质影响结论时，才询问最关键的一个定位问题。
6. 无需求编号的代码优化、重构或技术整改分析，不虚构需求，也不强行套用需求/用例对照。
7. 如果同一请求明确包含两个彼此独立的 P2 分析场景，先询问用户希望优先执行哪一个；不得混合多个分析工作流，也不得将分析与 Bug 提交自动串联。
8. 连续追问默认沿用当前已选工作流；只有用户明确改变目标才重新识别意图。
9. 选定工作流后，先确认对应文件存在且已实施，再按该文件执行。文件缺失、内容不完整或状态不明时停止在缺失范围，不得用其他场景的流程兜底。

## 公共输入识别

- 优先使用当前对话、用户已提供的需求正文、提测点、代码链接、分支、Commit、截图、日志、附件及已授权项目文件；不得要求用户重复提供当前上下文中已经存在的信息。
- 不要求用户在启动前一次性提供所有技术定位信息。先判断已有信息是否足以开始，再按实际证据缺口请求必要补充。
- 开发提测场景中的需求编号和提测点用于定位业务预期及初始检查范围，不得将提测点视为完整变更清单。
- BUG 场景从异常现象和已有线索开始，不把页面、接口、字段、参数、日志、截图、时间和仓库清单设为强制输入。
- 无需求代码变更场景使用用户提供的代码范围、仓库、分支、Commit、PR 或 Diff 等定位线索；没有需求编号时不得编造需求来源。
- 如果存在最新有效的 P1 正式用例，可作为交叉核对输入；如果不存在或用户未提供，继续基于需求和实际代码分析，不阻断任务。

### P4 按需业务知识输入（可选）

当本次提测点、Bug 现象、无需求代码改动或 Bug 回归需要已有业务规则、页面/API/配置绑定、源码定位线索或历史质量经验辅助定位且当前材料不足时，按需读取 `skills/knowledge-management/SKILL.md`，以已明确的模块、业务对象及变体只读检索最相关的 1–2 类。已有需求和源码证据足够时跳过；不要求每个工作流必查 P4，尤其不能改变 Bug Submission 的独立授权/回执门禁。

只消费与当前业务范围直接关联、具有对象 ID/Code、来源和必要 SHA 的知识。`formal_reusable` 也须检查适用版本、环境与业务范围：用户确认的业务规则可作预期依据，历史代码绑定只是定位提示。**实际实现仍由 P2 冻结的目标源码、真实 Diff 与按需读取的当前 DEV 配置独立验证**；前端单需求差异遵循 `prod → 个人/特性分支`、`gray` 仅按需集成核对，后端和 ETL 按原基线。不能用 P4 的旧 SHA 替换当前核验版本。

候选、`review_required`、历史 Bug、运行 `NOT_RUN` 不得冒充当前缺陷、静态 PASS 或运行 PASS；冲突影响结论时按需核实，SHA 不同不直接认定业务行为改变。P4 未命中、文件不可读、工具失败或证据不适用时说明 `NO_MATCH` / `KNOWLEDGE_UNAVAILABLE` / `UNKNOWN` 对判断的影响，继续 P2 的调用链、双向核对、反例和必要 MV；**知识缺失不构成实现遗漏，也不自动产生人工任务**。不得因该调用自动写 P4、跳过工作流报告或改变 Manifest/平台动作权限。

## 公共分析约束

### 需求、用例与实际开发改动双向交叉核对

有需求时，必须同时执行以下方向的核对：

1. **需求到实现**：逐项识别需求业务义务，核对当前实际代码、配置、接口参数传递、调用关系及数据链路是否存在、完整接入并符合需求预期。需求有明确要求而实际实现缺失、部分实现、错接或行为不符时，反馈为实现缺口；不得仅因目标分支 Diff 中没有某段代码就认定未实现。
2. **实现到需求**：反向检查实际开发改动，识别需求未明确描述的代码或行为变化。区分必要的内部技术实现、无业务行为变化的整理/重构，以及可能改变业务行为、影响范围或兼容性的额外实现。可能影响业务的额外行为必须反馈证据、影响和待确认点；不得把未说明的额外业务行为默认为已获需求授权。
3. **测试用例交叉核对**：如有最新有效 P1 正式用例，核对需求义务覆盖、实际代码变化及其业务影响覆盖，并识别用例预期与需求或实际实现不一致的情况。需求是业务预期来源，用例不能替代需求；用例与需求冲突时明确反馈。没有 P1 用例时仍继续分析。
4. **无需求代码变更场景**：不虚构需求或强行套用需求对照，改为比较变更前后的实际行为、识别业务影响及必要回归范围。没有需求编号的 BUG 排查仍沿异常定位与根因工作流执行，不因缺少需求编号而要求先取得变更前后版本。

### 调用关系、影响范围与回归

- 以独立业务核对点组织分析，不以文件、接口或 SQL 对象作为业务矩阵的默认粒度。
- 对公共接口、公共 SQL、公共组件及其他共享代码，必须追踪并核查全部实际关联调用方；不得以抽样替代完整调用方核查。相同行为可以合并展示，但必须保留调用方清单及各自差异。
- 只沿真实调用、共享实现或数据依赖追踪实际涉及的技术层，不为填充报告强行扩展无关层级。
- 影响范围明确区分直接影响、间接影响、潜在影响和无影响。潜在影响必须说明合理关联及尚缺少的证据，不得写成确定受影响。
- 回归建议必须关联业务核对项，并说明回归对象、具体验证内容、提出原因和预期结果；不得把没有真实依赖或合理影响依据的模块纳入回归范围。
- P2 可以提出测试覆盖缺口和用例增量建议，但正式测试用例仍由 P1 testcase-design 管理。

### Git、MCP 与证据边界

- P2 本地仓库路径优先从工程根目录 config/repositories.json 解析；缺失时按 references/git-repository-policy.md 核实用户明确提供的本地 Git 仓库；仓库定位、定向 Fetch、任务内 SHA 冻结/刷新和失败边界统一遵循 references/git-repository-policy.md。三个分析工作流不得各自维护重复仓库路径或冲突的 Fetch 生命周期规则。

- Git 用于取得源码、分支、Commit、提交历史和版本差异等代码证据；具体基线和比较方式由所选场景工作流进一步规定。
- 当前执行环境可用的 MCP 按实际涉及的技术层和证据缺口按需调用，不在任务开始时全量调用。MCP 用于补充当前配置、平台元数据、血缘或业务记录等领域证据，不替代 Git 源码和历史。
- 只有确认某项 MCP 证据确实影响当前判断时才调用。调用失败、超时或返回不完整时，保留已有 Git、源码和其他 MCP 证据，记录缺失能力及受影响结论，停止无效重试并继续不依赖该证据的分析。
- 区分查询成功但无数据、对象不存在、调用失败和返回不完整；不得把工具故障误判为业务问题。
- Git Diff 证明版本间变更，源码证明指定版本的实现，MCP 证明特定查询环境和时间下的返回；均不得在缺少证据时推断生产部署状态或数据库实际运行结果。

### 静态核对与实际运行验证

- 优先使用源码、Git 差异、配置和可验证调用/数据依赖完成静态核对。
- 静态核对通过只表示当前静态证据支持该项结论，不代表页面、接口、数据库或业务运行验证通过。
- 未实际执行的运行验证必须标记 NOT_RUN；不得把静态推导、代码存在或 MCP 元数据查询写成运行验证 PASS。
- BUG 根因排查、无需求代码变更及其他 P2 工作流：只有静态分析不能回答、且用户确实能够执行并反馈结果的事项，才进入独立人工核对清单。开发提测影响分析另按 `submission-impact.md` 的现行人工验证规则执行：AI 已识别的问题/风险若确需页面复现或业务确认，也可进入 MV。所有工作流均不因 MCP 故障、证据缺失、NOT_RUN 或回归建议本身自动生成 MV。
### 公共业务语义推理与动态分析深度

- 在执行任一已实施的 P2 分析工作流前，必须读取并使用 references/analysis-reasoning-framework.md。该文件是三个分析工作流共享的公共推理方法，不是新的独立 Skill，也不合并各工作流的任务状态和归档。
- AI 自主选择 L1/L2/L3，依据业务逻辑复杂度、潜在影响和证据不确定性，而非文件数、代码行数、提测点数量或仓库数量：
  - **L1 快速静态分析**：逻辑简单、影响局部、映射明确；完成必要业务链路、字段/参数/来源/映射/格式化及真实调用方核对，并对明显相关分支做基本反证。
  - **L2 业务语义推理**：涉及查询条件、参数组合、条件分支、数据转换、多关联对象、排序/分页或共享组件；建立业务行为模型、推导适用约束、追踪真实实现，并对关键约束构造反例、验证高价值假设。
  - **L3 深度缺陷推理**：涉及复杂计算/聚合、多数据源、跨模块共享、核心指标、关键权限/状态，或存在浅层分析无法解释的异常/证据矛盾；还原关键链路和数据粒度，验证多个竞争假设，交叉核对相关消费方/调用方并说明证据边界。
- 分析过程中发现计算/聚合、关键分支、共享调用方、跨层依赖、结果矛盾或核心业务结果风险时，按证据自动升级并简要记录原因；任务一开始已具备 L3 特征时直接选择 L3。信息不足但可能实质影响结论时，不得为节省成本降为 L1。
- 只选择当前任务适用的业务约束视角，不机械执行全部维度；每次扩展由具体未决问题或新证据触发，达到公共方法规定的停止条件后结束。
- 报告可在结论速览或分析范围中简要记录分析等级、选择/升级原因和关键约束视角；只输出可审计的业务依据、假设摘要、验证过程和证据，不输出隐藏思维链。沿用现有状态、CHK/EV/MV 和报告规范，不新增评分或状态。
- 公共方法不改变工作流各自的触发、输入、代码基线、Git/SHA、MCP、归档及安全边界；静态可回答的事实不转人工核对，NOT_RUN/回归建议/覆盖缺口不自动生成 MV。

## 公共报告与人工核对交付

- 每项已实施的 P2 分析工作流均须按 references/report-format.md 生成完整 Markdown 分析报告 impact-analysis.md；不能只在聊天中给出结论。证据不足、根因未确认或存在待业务确认事项时，也必须交付已完成分析、证据边界和未决内容。
- 开发提测影响分析存在需要用户实际复核/确认的事项时，生成 `manual-verification.md` 简要待办及 `verification-details.md` 详细记录；范围包括静态证据无法回答的运行态事实，以及 AI 已识别为已确认问题、潜在风险或待业务确认且确实需要用户复现/确认的项目。不得把所有 CHK 或回归建议自动转为 MV；静态 PASS 仅在需要独立运行态验证时纳入。详细记录保存完整描述、代码证据、环境/前置、操作步骤、预期、实际结果及适用 SQL。没有人工事项时不生成空文件；`verification-details.md` 仅适用于 `submission-impact.md`，不扩展到其他 P2 分析工作流。
- **聊天交付与正式报告并行**：首次 P2 分析的聊天回复保持原有结论交付，不展示 `verification-details.md` 中的 SQL 正文；仍须展示静态核对通过项及 PASS、发现的问题/风险及性质与业务影响、需要人工核对的 MV 项及简要操作/预期、实际运行验证状态，以及本轮 P2 正式版本和 `impact-analysis.md` / `manual-verification.md` /（适用时）`verification-details.md` 的完整路径；另行标注所引用的 P1 基线版本。逐条验证时再返回对应项目的完整步骤、预期、代码证据和 SQL。
- **Codex 边界**：正常 P2 业务分析不输出 Codex 验收提示词，不要求用户再次交给 Codex；只有 QA Agent 自身 Skill/规则/代码工程变更需要独立验收，或用户明确要求时，才提供对应验收提示。
- 报告使用业务核对点 CHK 编号和报告内独立的 EV 证据编号；人工核对项使用 MV 编号并关联 CHK。编号仅在单份报告内有效，不建立全局编号服务。
- 报告长度由实际业务核对点、问题复杂度和证据数量决定，不设固定字数、页数或核对项数量上限，不为控制长度删减必要覆盖或证据。
- **归档与 Manifest**：
  - 有需求编号的三个只读分析工作流共用需求级 YYYYMMDD-vN 版本序列，不按 Agent 建目录。开发提测分析每次明确启动的新一轮正式分析均创建新版本；独立分析/模型对比即使代码 SHA 未变化也创建新版本。正式发布后的报告实质修订或人工反馈另建新版本；同一未发布任务的草稿续作、只读查询/解释不创建版本。
  - 开发提测分析使用 manifest.py inspect → publish → validate，将 `impact-analysis.md`、可选 `manual-verification.md` 和适用时的 `verification-details.md` 发布到本次新版本的 analysis/，登记 `test-impact-analysis/impact-analysis`、可选 `manual-verification` 及 `verification-details` role。publish 的 expected_base_version 使用最新整体版本，不是最新 P1 基线版本。新 Manifest 继承未变化的 P1、P3 和其他有效 artifact；不得原位覆盖历史文件或历史 Manifest。
  - 正常提测分析读取最新有效 P2 报告/人工清单并延续未决 MV；独立分析在报告完成前不得读取历史 P2 结论，执行来源、模型（可确认时）、分析模式、时间、P1 基线和代码 SHA 写入报告。只读读取最新 P2 时从最新整体 Manifest 的有效 artifact 定位并验 SHA，不触发新分析或新版本。
  - P2-only 发布必须保留最新整体 Manifest 的顶层 delivery_status、P1 用例身份/Revision/内容指纹/退役信息、计数/验证字段及所有未变化 P1/P3 artifact；case_snapshot.status 轮次状态由现有 publisher 计算（如 added → unchanged），不要求整份快照逐字段相同。P2 报告自身的 PARTIAL/COMPLETE 不得覆盖 P1 的 delivery_status。人工待办全部处置时可在新版本退役简要 `manual-verification` role，但若 `verification-details.md` 含最终 SQL/实际结果/验证结论，必须保留其当前有效 role，不得随待办清空一并退役。
  - 独立盲分析不继承上一轮 `manual-verification` 或 `verification-details` 内容：本轮有人工事项时生成本轮新清单和详细记录并替换当前有效 role；本轮没有人工事项时，仅依据最新 Manifest 中 role 的存在性，在 publish spec 使用 retire_artifacts 退役不再适用的旧 role，不读取旧文件正文。历史文件仍保留。
  - Bug Submission 在创建回读成功后，使用现有 manifest.py register-bug-receipt 生成 analysis/<登记时的latest_version>/bug-submissions/BUG-<BugID>.md 并登记唯一 bug-submission-<BugID> role。Bug Lifecycle 继续按 Bug ID 使用 analysis/bug-lifecycle/BUG-<BugID>/ 独立目录；当前 Manifest 验证器不支持 bug-lifecycle category，因此只保存 Lifecycle 文件并报告 MANIFEST_REGISTRATION_NOT_SUPPORTED，不得复用 test-impact-analysis 身份。无需求编号的 BUG/CODE 任务沿用各自既有独立任务目录和版本序列。

## 安全与能力边界

- P2 默认只读；仅 bug-submission.md 可以在每条草稿完成独立预览且收到针对该 Draft ID 的明确授权后调用禅道 createBug；仅 bug-lifecycle.md 可以在原缺陷及必要回归通过、完成独立关闭预览并收到针对当前 Bug ID 的明确授权后调用禅道关闭操作。分析工作流绝不自动创建或关闭 Bug。除上述两类受控动作外，不得导入禅道/ACE、修改平台记录、执行 SQL/ETL、写业务数据或 Push。该门禁是 Agent 工作流规则；当前 MCP createBug 本身不带审批令牌，不能宣称已具备服务端不可绕过的硬拦截。
- SQL 设计由独立 P3 完成；P2 不直接编写或执行 SQL。仅 `submission-impact.md` 按 P3 委派职责为每个独立真实业务数据验证目标默认调用 P3 配对 F+V；纯 UI/导航等没有真实数据断言的场景不生成 SQL，不按 CHK/MV/Case 数量机械生成。该默认义务不扩展到 BUG 根因排查或无需求代码变更工作流。SQL 正文及查询说明保存在绑定当前 P2 基线的 `verification-details.md` 工作稿，首次聊天不展示正文，逐条验证时返回对应目标完整 F+V；后续新增数据验证目标时补齐对应 SQL。证据不足时局部标记 PARTIAL/UNKNOWN。SQL 只读且由用户在获准环境执行并回传；P2/P3 不连接或执行数据库，不执行 ETL。
- 不新增 JSON 证据库、SQLite、数据库、重复状态账本或不必要的自动化框架；证据索引直接内嵌在 Markdown 报告中。
- P2 不得修改 P1 正式用例、Oracle、XMind、历史用例文件或 Manifest 中既有 P1 记录。开发提测分析的每个新正式版本只能通过现有 Manifest publisher 新建需求级版本，并登记本轮 P2 artifact；不得在旧 P1/P2/P3 版本目录内原位修改文件或 Manifest。新版本必须原样继承全部未变化 P1/P3 artifact 的路径与 SHA，并保持 P1 用例身份/内容信息及 Manifest 计数、validation、顶层 delivery_status 不变。人工待办全部处置时只按现行 MV 处置规则决定是否退役简要 `manual-verification` role；含最终 SQL/实际结果的 `verification-details` 不得一并退役。Bug Submission 和 Bug Lifecycle 的既有独立归档边界保持不变。P2 不依赖 P4。
- P2 深层推理增强独立分批推进：第一批公共推理方法及统一入口接入已完成；工作流场景化细化、历史样本盲测及 Codex 独立能力验收属于后续批次。
