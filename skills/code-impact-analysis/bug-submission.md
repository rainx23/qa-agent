# 禅道 Bug 提交工作流

## 工作流定位与触发

本文件是 P2 code-impact-analysis 下独立的平台写入动作工作流，不属于缺陷分析工作流，也不负责重新分析代码或需求。

用户明确要求提交/登记一个已确认缺陷、准备该缺陷的禅道提交草稿，或继续处理当前唯一待授权的 Bug 草稿时，进入本工作流。单纯发现缺陷、确认缺陷事实或要求生成分析报告，不构成创建授权；准备草稿也不构成创建授权。

**强制重载与规则优先级：** 每次本工作流被路由命中时，必须在本轮任何禅道 MCP 调用前重新读取本文件完整当前内容。不得以会话早期已读内容、P2 入口路由表或 MCP 工具描述代替。MCP Schema 只用于核对参数类型、必填项和枚举；用户交互、默认值、预览、授权、回读、归档及收尾均以本工作流为准。工具描述要求字段齐全，不等于每个字段都要向用户逐项询问。

缺陷证据来源只允许：

- P2 分析报告中明确标记为“已确认缺陷”，且有可靠业务预期、实际实现偏差和可复核证据的 CHK。
- 用户明确说明已经人工验证确认的缺陷，并提供当前对话中可用的操作、实际结果和预期依据。

潜在风险、待业务确认、用例覆盖缺口、NOT_RUN、尚未建立因果关系的可疑代码，均不得作为可提交缺陷。证据不足时停止创建草稿或要求补齐关键事实，不得把风险改写成已确认缺陷。
如果用户要求“分析并提交”但尚无已确认缺陷，先执行匹配的分析工作流；分析完成后暂停。只有用户明确要求准备提交时，才进入本工作流。分析工作流不得直接调用 createBug。

## 最高安全门禁

1. 每条 Bug 独立生成草稿、独立展示完整预览、独立取得人工授权、独立调用一次 createBug。
2. 不允许批量授权，不允许一次“都提交/全部提交”授权多条 Bug。
3. 只有当前唯一待授权草稿的 Draft ID 与最终预览完全一致，且用户明确回复“确认提交 <Draft ID>”，才允许调用 createBug。
4. “可以”“确认”“提交吧”“没问题”等不含当前 Draft ID 的泛化回复，不构成提交授权。
5. 用户修改标题、步骤、实际结果、期望结果、需求/产品/模块/迭代、优先级、严重程度、环境、Bug 类型或指派人员中的任何一项，原草稿和授权立即失效；重新生成 Draft ID、重新展示完整预览并重新取得授权。
6. 一条授权只允许调用一次 createBug。不得因超时、无回执或结果不明确而自动重试。
7. 取消草稿、切换到其他 Bug 或无法确认当前草稿快照时，原授权失效。
8. 当前对话中的授权不跨新对话继承；新对话必须重新读取证据、生成预览并取得授权。
9. 不得把缺陷事实确认、草稿审核、需求信息查询或人员选择当作提交授权。

**技术边界：** 当前 createBug Schema 没有审批令牌或服务端授权参数。本工作流落实的是 QA Agent 行为门禁，不代表禅道 MCP/服务端已经具备不可绕过的硬拦截。不得宣称其他客户端或直接 MCP 调用也已被技术阻断。若后续要求服务端级强制门禁，需要单独改造 MCP/网关，只允许通过带一次性授权校验的受控入口创建。

## 可提交缺陷的准入判断

进入草稿前逐项确认：
- 缺陷性质为“已确认缺陷”，不是潜在风险或待业务确认。
- 实际问题描述有证据支持。
- 业务预期来自当前需求、权威业务规则、已确认契约或用户明确确认，不得仅用当前代码行为证明自身正确。
- 如果来源是静态分析，必须明确标记“静态分析确认，未实际运行复现”；只有静态证据已建立业务预期、错误实现和结果偏差之间的联系时才允许提交。
- 如果来源是人工验证，按用户实际验证内容描述，不擅自补写未执行的步骤。
- 没有可靠预期、实际结果或必要定位证据时，先询问一个最关键的问题，不生成可提交草稿。

## 当前需求与禅道关联信息

### 确定需求 ID

createBug 必须关联需求，story 为必填整数。当前 MCP Schema 不支持无需求创建。

- 优先从当前 P2 任务、当前分析报告或本轮对话中读取唯一且明确的需求 ID。
- 不能把上一个无关任务、历史对话或最近提到的其他需求 ID 当成当前需求。
- 当前上下文有且只有一个明确需求 ID 时直接使用，不重复询问。
- 当前上下文没有需求 ID 时，询问用户提供需求 ID。
- 存在多个可能的需求 ID 且无法确认当前 Bug 归属时，询问用户选择；不得猜测或自动选最近一个。
- 没有需求 ID 时可以说明当前无法创建禅道 Bug，但不得伪造 story 或用其他需求代填。

注意：MCP 不会凭空识别“用户此刻正在处理哪个需求”。Agent 负责从当前任务上下文确定需求 ID；MCP 负责按该 ID 查询需求关联信息。

### 获取产品、模块和迭代

确定需求 ID 后，调用禅道 MCP：

- getNeedDetailById({ id: 需求ID })

将返回的真实值映射为：
- story：当前需求 ID。
- product：产品 ID。
- module：模块 ID。
- project：迭代 ID。

预览中同时展示产品、模块和迭代名称及 ID（返回名称时）。不得使用其他需求的历史值、硬编码 ID 或凭页面名称猜测。需求归档根目录按 `skills/testcase-design/references/output-archive.md` 定位：优先沿用当前需求已有 Manifest/legacy locator；已有 Manifest 冻结的 `module_id/module_name` 不因本次禅道详情变化而自动移动目录，发现不一致时停止并报告。只有首次建立需求归档或历史 Manifest 缺少模块元数据时，才使用本次真实 `module/moduleName` 建立/补齐模块元数据。

若查询失败、返回不完整，或 product/module/project 任一必填 ID 缺失，停止提交并说明缺失字段；不得猜测或回退到其他需求的缓存值。需求正文/业务预期不在返回内容中时，继续使用当前任务已提供的需求正文或权威业务材料；不能把需求元数据查询冒充为已取得完整需求正文。

### 获取指派人员候选

按 MCP 要求调用一次：

- getTaskFinisherInfos({ id: 需求ID })

该结果只作为候选名单和核对信息。最终指派人员由用户提供或从候选名单中明确选择；AI 不自动选择、不根据历史习惯猜测、不把需求负责人自动当成 Bug 指派人。

- assignedTo 必须是用户明确提供/选择的员工工号字符串。
- 如果用户提供的工号不在候选名单中，提醒用户核实；用户明确确认仍使用该工号后才可进入最终预览。
- 候选查询失败或结果无法解析时，停止创建，不伪造候选名单；说明 MCP 查询失败及影响。

## Bug 字段与默认值

createBug 当前必填参数共 10 个：story、title、pri、severity、env、type、assignedTo、product、module、project。step、stepResult、expectation 在 Schema 中是可选字段；只要证据充分，仍应按本工作流要求提供可读内容。

| 字段 | 提交值规则 |
|---|---|
| 需求 ID（story） | 当前任务明确需求 ID；必须通过需求详情查询 |
| 产品 ID（product） | getNeedDetailById 返回值 |
| 模块 ID（module） | getNeedDetailById 返回值 |
| 迭代 ID（project） | getNeedDetailById 返回值 |
| 优先级（pri） | 从本地 `config/organization-profile.json` 的 `bug_defaults.pri` 读取默认值；本次用户另有明确值时采用用户值，缺失则按当前平台 Schema 确认 |
| 严重程度（severity） | 从本地 `bug_defaults.severity` 读取默认值；用户明确覆盖时采用本次值，无有效默认时按当次平台确认 |
| 环境（env） | 从本地 `bug_defaults.env` 读取默认值；用户明确覆盖时采用本次值，无有效默认时按当次平台确认 |
| Bug 类型（type） | AI 按缺陷性质从 MCP Schema 枚举中推荐；预览展示中文，用户可要求修改 |
| 指派人员（assignedTo） | 用户提供/选择员工工号，不自动决定 |
| 标题（title） | AI 按固定格式拟稿，用户审核 |
| 复现步骤（step） | 根据真实操作或明确标记的静态定位路径整理 |
| 实际结果（stepResult） | 人话描述实际表现，并可附代码定位 |
| 期望结果（expectation） | 优先根据当前需求的明确预期整理，并标明需求依据 |

MCP 的 createBug 需要 pri、severity、env、type、assignedTo 等参数时，以实际 Schema 为准。pri/severity/env 先使用本次用户明确指定值，否则使用已配置的 `config/organization-profile.json` 中 `bug_defaults`；配置有效时直接填入草稿及最终参数并完整预览，不重复询问。无可用默认且平台必须传入时，仅询问必要的缺失值，不得沿用其他公司的优先级或环境。Bug 类型由 AI 推荐并预览，指派人员由用户提供/选择；平台写入仍按逐条草稿独立授权执行。

### Bug 类型枚举

当前 createBug Schema 提供 13 种枚举；没有发现独立的 Bug 类型查询接口。类型来源以当次 MCP Schema 为准：

| 用户可见类型 | MCP 提交枚举 |
|---|---|
| 漏合多合代码 | mergecode |
| 接口未订阅 | interfacenotsub |
| SQL 未执行 | sqlnotrun |
| 优化建议 | suggestions |
| 代码缺陷 | codeerror |
| 用户体验 | others2 |
| 需求设计缺陷 | designdefect |
| 配置相关 | config |
| 性能问题 | performance |
| 安全相关 | security |
| 跨部门缺陷 | others4 |
| 功能未实现 | other5 |
| 其他 | othernew |

类型选择原则：
- 代码逻辑、参数处理、计算或分支错误，通常推荐“代码缺陷”。
- 配置项缺失、错误或未生效，通常推荐“配置相关”。
- 性能、安全、需求设计、功能未实现等按实际缺陷性质选择对应类型。
- 只有证据确实符合时才选择“漏合多合代码”“接口未订阅”或“SQL 未执行”。
- AI 推荐后必须在预览中让用户审核；类型无法可靠判断时先询问，不默认选择“其他”规避判断。
- MCP 枚举变化时以最新 Schema 为准，不沿用过期编码。

## Bug 标题与内容编写规范

### 标题

固定格式：

【模块】页面名称，问题描述

规则：
- 模块名称使用用户能理解的业务模块名称。
- 页面名称优先使用当前任务、截图或需求中可确认的实际页面名称；不得用未经确认的组件名或接口名冒充页面。
- 问题描述简明说明关键触发条件、异常行为和业务影响，避免把完整操作步骤堆入标题，也不写空泛的“功能异常”“数据错误”；精简不得丢失区别于其他缺陷的必要条件。
- 页面名称无法确认且会影响标题准确性时，询问用户，不猜测。

示例：

【模块名称】页面名称，关键操作未按预期生效

### 复现步骤（step）

- 优先使用用户真实执行或人工验证过的操作步骤，按业务操作顺序编号；`step` 中每个操作独占一行，以换行分隔（如 `1. ...\n2. ...`），不得把多个步骤挤在同一段或用分号、句号串成一长行。步骤覆盖进入页面、关键条件/操作及观察点；不为凑步骤重复拆分。
- 步骤中的页面导航路径使用纯文字，如“进入模块名称 > 页面名称，打开对应页面”；只在 Bug 标题中用“【模块】”标识模块，**不得把步骤里的整段导航路径再包成“【模块 > 页面】”**。页面实际名称自带符号时保留，不机械删除合法括号。
- 步骤写给产品、测试和开发都能看懂的人，不堆叠类名、方法名、接口路径或代码术语。
- 如仅通过静态代码分析确认，复现步骤必须明确标注“静态分析定位路径，未实际运行复现”；可以写出由代码证据支持的入口和条件，但不得伪装成用户已经执行过的步骤。
- 无法从证据还原操作路径时，明确写“真实复现步骤待补充”，不得编造点击路径。

### 实际结果（stepResult）

按以下顺序组织，**实际表现必须在前，技术信息按实际证据有选择地补充**；仍只使用禅道现有的 `stepResult` 字段，不新增 MCP 参数：
1. **实际表现（必填）：** 用人话说明在什么条件下出现什么结果，影响用户什么操作或业务结果。必要时补充真实数值、请求条件、日志 ID 等关键证据；不以冗长代码内容替代业务现象。
2. **代码问题（有可靠证据时）：** 说明具体错误逻辑、为何导致该现象，以及可确认的仓库/版本、文件、方法和行号；区分“源码已证明的行为”和“尚待验证的根因”。只有线索、未完成定位时写“疑似”或“代码定位待确认”，不得编造代码路径、逻辑、行号或把静态推导当成运行复现。
3. **修改建议（能给出有依据的方向时）：** 针对代码问题提出可操作的修复方向、必要的前后端或关联分支保护、最小回归关注点；可给关键修改位置或简短伪代码，但不强制开发采用某一实现方案，也不自动修改业务代码。证据不足时可省略具体方案或标注“待定位后确定”，不能凑一个猜测的实现。
4. **证据边界：** 人工验证与代码静态分析各自注明实际证据范围；必要时说明日志报错文案、实际运行效果或代码版本尚未取得，不能把不确定内容写成已确认结论。

简单缺陷不强制堆满全部技术段落；复杂缺陷保留必要事实与数据，不复制整份 P2 报告、SQL 或完整堆栈。代码问题和修改建议属于 `stepResult` 的辅助分析，不进入复现步骤或期望结果；正文按后文“正文排版与富文本兼容”规则分段。

### 期望结果（expectation）

- 第一优先级：当前需求原文中的明确预期。尽量引用相关章节/条款或简短原文，并说明需求 ID。
- 第二优先级：当前需求没有明确写出时，使用可追溯的权威业务规则、已确认契约或用户明确确认的预期，并说明来源。
- 用业务结果描述修复后应该表现为何种正确行为，与“修改建议”的技术实现手段分开；不得把 AI 推荐的某种实现方式直接当作唯一验收标准。
- 不得仅根据当前代码行为推导“正确预期”，也不得把测试用例作为唯一预期来源。
- 需求存在但当前没有取得正文时，不得声称期望结果来自需求原文。
- 业务预期仍有歧义时，停止提交并向用户澄清；不能为了填满字段自行编造。

### 正文排版与富文本兼容

禅道对 `step`、`stepResult`、`expectation` 字符串字段中的普通换行符 `\n` / `\n\n` 不保证按预期显示为分段；内容可能被整体包装在一个 `<p>` 中。因此，**正文默认使用 HTML 结构标签控制分段，不依赖裸换行符实现视觉换行**。本规则采用现有禅道提交规范中已使用的 `<h4>`、`<p>`、`<table>` 方式。

- **字段映射保持不变：** `step` 仍只放复现步骤，`stepResult` 仍放实际结果及有证据的补充分析，`expectation` 仍放业务期望及其依据；不把完整正文整体搬入 `step`，不改变 `createBug` 参数契约。
- **`step`：** 每个复现操作使用独立段落，例如 `<p>1. 进入模块名称 > 页面名称。</p>`、`<p>2. 设置查询条件并执行查询。</p>`。页面导航保持纯文字，不重复添加字段标题。
- **`stepResult`：** 先写实际表现，再按证据补充业务影响、代码问题、修改建议和证据边界；每段使用 `<p>...</p>`。内容较复杂、需要区分多个小节时，可用 `<h4>业务影响</h4>` 等标题分段；没有内容的小节直接省略。人工已复现与静态分析未运行的证据边界要求保持不变。
- **`expectation`：** 正确业务结果使用 `<p>...</p>`；需要追溯时，另用一个 `<p>` 补充“预期依据：需求编号及条款/已确认业务规则”。不写强制实现方案。
- **表格：** 仅在影响量化、明细拆分等确有必要时使用 `<table>`；属性统一使用单引号，例如 `<table border='1' cellspacing='0' cellpadding='4'>`，内部使用 `<tr>`、`<th>`、`<td>`。数字加千分位，占比保留两位小数。
- **标签范围：** 正文使用 `<h4>`、`<p>` 及表格所需的 `<table>` / `<tr>` / `<th>` / `<td>`；不使用 Markdown 标题、加粗标记、代码围栏或 `<br>` 代替结构分段。简单 Bug 不强制套用九段式模板，按缺陷复杂度保留必要内容。
- **预览一致性：** ChatGPT 可以将 HTML 结构以易读的标题、段落和表格形式展示，但内容、顺序和层级必须与最终传给 `createBug` 的 HTML 字符串一致，不得预览一套内容、提交另一套内容。
- **验证边界：** 当前 QA Agent 的 createBug 页面渲染尚未单独创建测试 Bug 实测，因此采用该格式不等于本工程已取得页面渲染验收 PASS；不得宣称已实测。未经用户单独授权，不为验证格式创建测试 Bug。


## 截图与附件边界

第一批只支持通过文本字段提交内容，不支持图片/附件上传；字段正文可按上述规则包含 HTML 结构标签：
- ChatGPT 可以读取用户在当前对话提供的截图，提取可辨认的页面名称、操作、字段、提示信息和实际表现，并转写为 Bug 描述。
- 截图中无法确认的内容标记未知，不猜测。
- 可以在文字描述中说明“依据用户提供截图整理”，但不能伪造截图文件路径或附件地址。
- 当前 createBug Schema 没有图片/附件参数，已探查的禅道 MCP 工具中未发现可用的附件上传及关联 Bug 能力。
- 不得将截图链接、截图文字摘要或“已分析截图”表述为“图片已上传禅道”。
- 后续只有在附件上传和关联 Bug 的 MCP 能力实际可用并完成 Schema 验证后，才扩展图片上传。


## 独立草稿、预览与授权

### 草稿身份

每条 Bug 生成一个仅在当前对话有效的唯一 Draft ID，建议格式：

BUG-DRAFT-<需求ID>-<YYYYMMDD>-<序号>

Draft ID 只是 Agent 草稿标识，不是禅道 Bug ID。每条 Bug 独立编号；同一批多条 Bug 逐条处理，同一时刻只保留一个待授权草稿，避免授权对象混淆。

### 完整预览

授权前必须以普通 Markdown 表格完整展示本条 Bug 的所有提交字段和内容，至少包括：
- Draft ID、缺陷来源、关联 CHK/人工确认依据。
- 需求 ID/名称、产品 ID/名称、模块 ID/名称、迭代 ID/名称。
- 标题、复现步骤、实际结果（含实际表现、按证据提供的代码问题与修改建议）、期望结果及需求预期来源。
- 优先级、严重程度、环境（已确认本次值或本地 `bug_defaults`，不要求反复确认已明确的值）、Bug 类型、指派人员。
- 截图说明（如有），明确第一批不会上传图片。
- 尚未确认或缺失的字段。

预览必须与即将传给 createBug 的参数逐项一致。ChatGPT 预览可以将字段标题加粗以便阅读，但这只是聊天界面的展示样式；实际提交字符串不得因此加入 Markdown/HTML 标记。预览前由 AI 一次性检查标题与步骤中的格式符号是否误用、路径是否使用纯文字、是否重复赘述、业务现象与技术推断是否混淆、代码问题/修改建议是否有实际证据及与期望是否冲突；仅修正有证据的错误，不机械删除页面名称中的合法符号，不增加 Python 检查器、独立质量门禁或额外审批轮次。所有必填字段齐全且证据准入通过后，才可请求用户授权。存在缺失字段时只请求最关键的缺失信息，不展示“可提交”状态。
### 独立人工授权

完整预览后，明确要求用户回复：

确认提交 BUG-DRAFT-<需求ID>-<YYYYMMDD>-<序号>

只有用户明确回复与当前唯一待授权 Draft ID 完全匹配的授权语句，才可进入提交。授权前不得调用 createBug，也不得预先发起任何写入请求。

任何字段变化都必须作废旧草稿并生成新 Draft ID；旧授权不得迁移到新草稿。用户授权其他 Draft ID、一次授权多条、泛化同意或授权对象不清晰时，均不得提交。

## 禅道创建与回执

只有授权通过后，才允许调用一次 createBug。参数必须按当次 Schema 映射：

- story = 需求 ID
- title = 标题
- step = 复现步骤
- stepResult = 实际结果（先业务表现与必要证据，按证据附代码问题、修改建议和证据边界）
- expectation = 期望结果（含需求依据）
- pri = 优先级
- severity = 严重程度
- env = 环境
- type = Bug 类型对应的枚举
- assignedTo = 用户确认的员工工号
- product = 产品 ID
- module = 模块 ID
- project = 迭代 ID

提交结果处理：
- MCP 明确返回创建成功及 Bug ID：报告“创建回执成功”，展示 Bug ID 和本次提交摘要。
- MCP 明确返回失败且能够确认未创建：报告失败原因，不自动重试；修正草稿后必须重新预览并重新授权。
- MCP 超时、连接中断或返回无法判断是否写入：标记“结果未知”，停止重试；先由用户在禅道核查是否已创建，确认前不得再次提交。
- **queryBugs 实测能力（2026-11-05）**：`BUG_ID`、`STORY_ID`、`ITERATION_ID` 三种查询方式均有真实只读调用证据，分别可按已知 Bug ID 回读单条记录、按需求/迭代查询关联 Bug 候选；这只证明基本查询能力，不证明结果完整。
- **status 过滤实测结论：NEED_FIX / NOT_RELIABLE**：初次样本没有排除性，不能证明过滤生效；后续独立反例确认返回记录可能不符合请求的 status 条件。另一个组合样本中 `assignedTo` 与请求一致，但 `status` 仍不匹配。因此调用方不得依赖 status 参数缩小结果，也不得把返回结果标注为已通过状态过滤；故障层级（网关或后端）尚未定位。
- **不存在记录的响应**：按不存在的 Bug ID 查询可能返回 HTTP 500、业务 `code=-1` 及“记录不存在”类 message；应结合业务 code/message 识别目标不存在，不得只按 HTTP 状态判断 MCP 服务不可用。
- **已观察到的返回字段**：包括 Bug 标题、需求/产品/模块/迭代标识及名称、Bug 类型、状态/解决方案、优先级、严重程度、环境、指派人/创建人/最后修改人及其名称、创建/修改/解决时间、解决版本等，可用于已知 Bug 的基本回读和关联需求/迭代的候选列表检查。
- **能力限制**：当前工具 Schema 没有分页、limit、totalCount 或标题关键词参数；不同查询样本的返回字段并非完全一致。部分自定义字段在已测样本中返回 null，不能据有限样本推断字段归属或所有查询模式均稳定返回。当前样本不能证明大需求/大迭代查询结果完整。
- **使用边界**：`BUG_ID` 可用于已知 Bug ID 的只读回读；`STORY_ID`/`ITERATION_ID` 可用于检索相关 Bug 候选。AI 可基于返回标题、状态、模块、指派人及描述可见信息提示疑似重复项，但由于缺少分页/总数/关键词查询且尚未验证全量性，“未查到相似项”不能证明不存在重复 Bug。创建结果未知时，查询只能辅助人工核查候选记录，不能自动认定成功或触发再次创建；必须由用户确认查询到的记录是否为本次提交。
- 不因创建成功而自动提交同批其他 Bug；下一条必须重新独立预览和授权。

第一批不建立 JSON、SQLite 或数据库授权状态库。Draft ID、当前草稿快照和授权只在当前对话中有效；跨对话不恢复授权。

### 创建成功后的本地自动归档（强制收尾）

1. `createBug` 必须明确返回成功及 Bug ID；随后只用 `queryBugs(queryType=BUG_ID, queryData=<BugID>)` 做创建回读，不传 `status`（该过滤已实测不可靠）。核对返回 Bug ID、标题和关联需求均与本次最终预览一致。未完成回读不得生成成功回执。
2. 从需求归档根目录执行 `python -B skills/testcase-design/tools/manifest.py inspect <requirement_root>`，使用返回的 `latest_version`；不得自行创建 P2 版本或覆盖历史版本。
3. 将最终提交预览、createBug 成功回执、指派人、提交时间、需求依据、缺陷证据和代码定位组装为临时 receipt JSON。`creation_status` 必须为 `success`；内容必须来自最终预览和实际证据，不能补造原始正文。
4. 执行 `python -B skills/testcase-design/tools/manifest.py register-bug-receipt <requirement_root> <latest_version> <receipt_json>`。该现有命令负责生成 `analysis/<登记时的latest_version>/bug-submissions/BUG-<BugID>.md` 并登记唯一 Manifest 记录（`category=test-impact-analysis`、`role=bug-submission-<BugID>`）；禁止手工覆盖既有回执或直接改写其他 P2/P1 身份。
5. 注册命令后必须执行只读确定性核验：
   `python -B skills/code-impact-analysis/tools/verify_bug_archive.py submission <requirement_root> <BugID>`
   核验器会读取 `manifest.py inspect` 返回的当前最新版本 Manifest，确认其中恰好存在一条 `bug-submission-<BugID>` role、category 正确、登记路径对应本 Bug 回执、文件存在且 SHA-256 与 Manifest 一致，并要求 `manifest.py validate <requirement_root>` 返回 `MANIFEST_HISTORY_PASS`。**回执文件可能位于早期版本目录，但由当前最新 Manifest 延续引用；不得错误要求回执路径必须位于 latest_version 目录。**
6. 核验器返回 `BUG_SUBMISSION_ARCHIVE_PASS` 后，才可清理临时 receipt JSON 并报告归档完成。注册命令失败/超时/结果未知时，先运行核验器检查真实状态；核验 PASS 可确认归档已完成，核验失败则停止并报告 `ARCHIVE_PENDING`/`ARCHIVE_FAIL`。不得盲目重跑注册命令、覆盖回执或再次调用 `createBug`。
7. 只有创建成功、创建回读通过且本地归档核验通过，才可报告本次 Bug 提交任务完成。创建失败、结果未知、查询失败、字段不匹配或归档不完整均不得生成成功回执。无可用正式需求版本时报告 `ARCHIVE_BLOCKED_NO_BASELINE`，不得虚构版本。

“直接输出/无需记录文档”只适用于当轮静态分析结论，不豁免已成功平台写入的本地归档。该能力复用现有 `register-bug-receipt` CLI，并新增只读核验工具；不修改 P1 Manifest 运行模块，不新增数据库或授权状态库。

## 完成前检查

调用 createBug 前必须逐项确认：
- 当前缺陷满足“已确认缺陷”准入标准，证据来源可追溯。
- 当前需求 ID 唯一明确，getNeedDetailById 已成功返回产品、模块、迭代必填 ID。
- getTaskFinisherInfos 已按要求调用；assignedTo 是用户明确提供/选择的工号。
- 按当前平台实际 Schema 填齐 pri/severity/env/type/assignedTo；pri/severity/env 在已有用户输入或本地 `bug_defaults` 时自动填入并预览，不重复询问；未有可信默认且必填时只询问缺失值。type 由 AI 推荐并供审核；assignedTo 必须由用户提供/选择。
- 标题符合“【模块】页面名称，问题描述”，必要触发条件清楚且不堆砌完整步骤。
- 复现步骤使用纯文字页面路径，无多余“【模块 > 页面】”包装、孤立括号或无意义重复，且没有把静态推导伪装成实际复现。
- 实际结果先用人话说明，按证据补充代码问题与可操作的修改建议；未经证明的根因和修复方向不得冒充已确认事实。
- 期望结果有需求/权威规则/用户确认的可靠来源，描述业务正确行为而非强制实现方案；没有可靠预期时停止。
- 所有必填参数与最终预览完全一致。
- 当前唯一待授权 Draft ID 与授权语句完全一致。
- 用户授权发生在最终预览之后，且草稿内容此后没有变化。
- 本次只调用一次 createBug；没有授权绝不调用，结果未知不重试。
- 未上传图片；只有对本次提交返回的 Bug ID 实际调用 `queryBugs` 并核对关联需求、标题及关键字段后，才可声明该条创建回读已验证。其他 Bug 的查询结果不能证明本次创建成功。
- 若本轮调用过 `createBug` 且明确成功，必须完成本地回执登记及 `verify_bug_archive.py submission` 核验；缺少回执、唯一 role、SHA 一致性或 Manifest validate 任一证据时，任务状态必须为 `CREATED_ARCHIVE_PENDING`/`ARCHIVE_FAIL`，不得报告整体完成。
- 若 `createBug` 结果未知，不重试、不生成成功回执；先按 Bug ID 由用户核查，确认本次创建记录后再决定是否继续归档。
- `closeBug` 不属于本工作流；不得对关闭动作要求 `bug-submission-<BugID>` role，应执行 bug-lifecycle.md 的独立文件核验规则。
