# 无需求代码变更分析工作流

## 工作流定位与触发

本文件是 `code-impact-analysis` Skill 下的无需求代码变更分析工作流。用户没有需求编号，主要希望分析代码优化、重构、技术整改、性能优化、依赖升级、公共逻辑调整或其他独立代码变更的行为差异和业务影响时，由总入口路由执行。

本工作流分析的是**代码变更本身**，不要求用户虚构需求、补建需求或提供正式需求预期。核心目标是比较变更前后的实际行为，识别有依据的业务影响、兼容性风险和必要回归范围。

路由边界：
- 用户描述已经发生的异常/错误，并要求定位原因时，使用 `bug-investigation.md`，不以本工作流替代 BUG 根因排查。
- 用户明确告知开发已提测并提供“需求编号 + 提测点”时，使用 `submission-impact.md`。
- 本工作流仅处理没有需求编号、以理解和审查独立代码变更为主要目标的场景。
- 单次 P2 任务只执行一个匹配工作流；意图无法区分且会改变分析路径时，只询问一个关键澄清问题。

本工作流只负责只读分析、证据整理和测试建议：
- 不修改业务代码、配置或仓库文件。
- 不执行 SQL/ETL，不写入数据库或业务数据。
- 不导入禅道/ACE，不调用 createBug，不修改平台记录，不 Push；若用户明确要求提交已确认缺陷，转交独立 bug-submission.md，本工作流不执行提交。
- 不生成或修改 P1 正式测试用例；可以提出回归建议和用例增量建议。

## 输入识别与分析意图

用户可提供仓库/项目、分支、Commit、PR/MR、Diff、文件清单、变更说明、优化目标、技术方案、截图或其他定位线索。这些均为可选线索，不要求启动前一次性提供全部信息。

先从用户说明和现有上下文识别本次变更目的，例如：
- **行为保持型优化/重构**：目标通常是改善实现方式、可维护性或性能，同时保持既有业务行为；必须验证是否存在意外行为差异。
- **技术整改/缺陷预防**：目标可能是调整异常处理、数据保护、稳定性、兼容性或资源使用；核实实际解决的问题及可能的副作用。
- **明确的行为调整**：用户说明了希望改变的行为；按其说明理解目标，但不把未说明的业务规则补成既定事实。
- **目的不明确的代码变更**：先客观识别变更前后行为差异；只有当变更意图会实质影响结论时，才向用户询问一个最关键的问题。

用户提供的变更说明、PR/MR 描述、Commit message、代码注释和技术文档可作为意图线索，但证据效力不同：用户明确说明和可靠的变更说明优先；Commit message 或代码注释不能单独证明业务目的或业务规则。

如果现有信息足以识别仓库和变更对象，直接开始定向分析。若无法识别目标仓库，或无法确定比较基线且这会实质改变结论，应说明已掌握的信息并只询问一个最关键的定位问题；不得猜测仓库、分支或比较版本。

## Git 比较基线与版本选择

本场景的本地仓库路径优先从工程根目录 `config/repositories.json` 读取；缺失时按 `references/git-repository-policy.md` 核实用户提供的本地仓库；仓库定位、定向 Fetch、任务内 SHA 冻结/刷新和失败边界统一遵循 `references/git-repository-policy.md`。本地工作区改动在当前 HEAD 和工作区快照足以回答问题时不 Fetch；只有实际比较目标涉及远端分支或本地缺失的 Commit 时，才按需获取相应引用。

**必须先确定变更前（base）和变更后（head）的可复核版本，再开展行为差异分析。** 不得仅凭分支名称、文件更新时间或 Commit message 猜测比较范围。

### 基线选择顺序

1. **用户明确指定 base/head 或两个版本**：按指定版本比较，核实仓库、引用存在且解析到完整 Commit SHA；若引用含义冲突或无法解析，停止该部分并说明。
2. **PR/MR**：优先使用对应 PR/MR 的真实目标分支、源分支及其 base/head SHA；按目标分支与源分支的实际合并基点计算变更范围。记录 PR/MR 编号、目标/源引用和完整 SHA。
3. **单个普通 Commit**：默认比较该 Commit 的直接父版本与该 Commit；若 Commit 没有父版本或父版本不可取得，明确限制。不得只依据提交时间判断其部署状态。
4. **Merge Commit**：先确认用户要分析的是合并进入目标分支后的整体变化，还是某个源分支/PR 的独立变化。只有目标语义明确时才选择对应父版本或 PR/MR 元数据；父版本选择会改变差异范围且无法确认时，先询问，不静默猜测。
5. **仅提供分支**：优先通过真实 PR/MR 元数据识别目标分支；没有 PR/MR 时，只有仓库约定或项目配置能可靠证明比较目标，才使用对应目标引用及合并基点。仅有 Git upstream/tracking 关系不当然等于 PR 目标分支。
6. **本地工作区改动**：以当前 `HEAD` 作为 base，分别识别 staged 和 unstaged 变化；untracked 文件单独列为候选，只有用户明确纳入本次范围或证据能够证明其属于本次变更时才作为变更内容分析。记录实际纳入范围，不改变工作区状态。
7. **用户提供 Patch/Diff**：将提供的 Patch/Diff 作为本次变更范围证据；若仓库和前后版本可定位，继续核实上下文及实际行为。若缺少前后源码或比较基线，只能给出 Diff 层面的有限结论，并明确不能证明的行为。

### 基线记录与获取边界

- 报告记录仓库、远端、目标引用、已提交 base/head 的完整 Commit SHA、合并基点（如适用）、Diff 范围和实际获取时间；若 head 是未提交工作区，记录其 `HEAD` SHA、staged/unstaged/untracked 纳入范围、文件清单及快照时间，不生成虚构的 head SHA。
- 用户未指定生产环境比较时，不自动将 `main`、`master`、`gray` 或 PROD 当作统一 base；以真实 PR/MR 目标、用户指定版本或可验证的仓库约定为准。
- 不把当前生产分支自动当成所有代码优化/重构的比较基线；只有用户明确要求与生产比较，或本次 PR/MR 的真实目标就是生产引用时，才使用该基线。
- 只获取本次分析所需的仓库和引用；必要时定向获取缺失的远端引用，不全量 Fetch 无关仓库或所有分支。
- 获取失败时记录仓库、引用、失败现象和受影响范围，保留已有证据并停止无效重试；不得用本地过期引用冒充最新远端版本。
- Git Diff 证明两个版本间的代码变化，指定 SHA 的源码证明该版本实现；两者均不能单独证明实际部署、运行结果或业务效果。

## 变更范围识别与上下文核实

先从确定的 Diff、PR/MR 文件列表、Commit 或 Patch 识别实际变更对象，再按业务行为组织分析，不以文件数量作为影响范围。

1. 归纳变更涉及的模块、入口、接口、组件、配置、任务、SQL、表/字段及其技术层；只列本次实际涉及的内容。
2. 对每个关键变化打开变更前后完整上下文，核实函数/类/配置的定义、调用条件、输入输出、异常处理和副作用；不能只阅读 Diff 片段。
3. 检查相关调用方和被调用依赖，确认参数、返回值、默认值、数据格式及调用时序是否发生变化。
4. 识别新增、删除、重命名、移动、条件调整、默认值变化、依赖升级、配置变化、数据结构变化和行为变化；对纯格式或无业务影响的整理不作无依据扩大。
5. 对无法从当前仓库证明的跨仓库依赖、动态路由、反射或配置驱动关系，明确记录已确认范围和证据边界；不得把搜索无结果写成没有依赖。
6. 如果变更范围很大，先按真实业务入口和依赖关系划分可独立分析的范围；不全量扫描无关模块。关键定位信息缺失且会影响结论时，停止扩大搜索并询问一个最关键的问题。

## 变更前后实际行为比较

本工作流以**变更前的实际实现行为**作为比较基线，以**变更后的实际实现行为**作为目标状态；变更前行为是事实基线，不自动等于正确的产品需求或业务规则。

对每个有业务意义的变更，按实际适用情况比较：
- 入口、调用条件、输入参数、默认值及参数传递。
- 业务分支、过滤条件、排序、聚合、计算和边界处理。
- NULL、空字符串、空集合、0、负数、重复值、缺省字段及异常输入。
- 返回结构、字段映射、精度、格式化、枚举/状态和接口兼容性。
- 配置读取、数据来源、SQL/ETL 依赖、任务调度和数据消费。
- 权限、可见范围、事务、幂等、异常处理、重试、缓存和副作用。
- 性能相关的调用次数、算法复杂度、查询形态、资源占用、并发和时序；仅在本次变更实际涉及或用户提出时分析。

不得为了填充清单而机械检查无关维度。每项差异应说明变更前行为、变更后行为、触发条件及业务含义；如果无法从源码确认，标记证据缺口。

### 建立变更业务行为模型与预期锚点

在已有变更前后行为比较基础上，围绕本次实际变化建立业务行为模型，按结论需要明确业务对象、真实入口/调用方、触发条件、输入与状态、变更前行为、变更后行为、结果消费方，以及用户说明的变更目的。

预期与比较依据必须区分来源和证明范围：

1. 用户明确说明的变更目的、行为要求和兼容要求，可作为本次变更意图依据；正式业务规则、已确认的接口/数据契约及其他权威业务约束，可作为适用业务约束。
2. PR/MR 描述、技术方案、Commit message、代码注释等用于理解变更意图的线索，按其可靠程度交叉核实；Commit message、文件名或代码注释不得单独证明业务规则或产品预期。
3. 变更前实际行为是事实比较基线，不自动等于正确的业务预期。只有用户明确要求行为保持，或有适用的兼容契约/规则时，才将相关既有外部行为作为本次需要保持的兼容目标；若本次目的是修复旧缺陷或明确改变行为，不得要求新实现继续保持已知错误行为。
4. 最新有效 P1 正式用例仅作为可选回归参考和交叉核对材料，不是无需求场景的业务预期来源，也不得单独或唯一作为正确性判据；发现用例与权威规则冲突时，记录冲突，不以用例覆盖规则。
5. 变更意图或适用预期不明确时，先客观描述可证明的前后行为差异及可能影响。只有该歧义会实质改变判断时，才询问一个最关键的问题；不得虚构需求或把未知意图补成业务规则。

### 按实际变化推导适用业务约束

根据已确认的 Diff、前后实现上下文和真实调用路径，判断本次变化涉及哪些业务关系必须成立；按需选择对象范围、过滤条件、数据粒度、去重/聚合、计算公式、单位/精度、字段映射、默认值/NULL/0、时间、状态、权限、排序分页、异常处理、幂等、兼容性或性能等约束。上述视角仅为按需提示，不是每次必查清单。

1. 对行为保持型优化/重构，使用相同或等价输入比较前后真实处理路径和可观察结果，核查是否出现非预期的业务差异、副作用或兼容性破坏；不能仅凭代码结构相似、测试用例通过或 Diff 较小认定等价。
2. 对明确行为调整，核实变化是否符合用户说明及适用规则，并识别未说明的额外行为变化。
3. 对缺陷修复或技术整改，区分被修复的既有错误行为、修复后预期行为及可能引入的新回归；不得把旧行为无条件当成正确基准。
4. 对每项重要差异说明触发条件、变更前后具体处理、受影响业务对象和结果消费方。参数或字段存在、调用链连通、方法返回成功均不足以证明业务语义正确。
5. 对列表、详情、汇总、图表、导出或共享调用方，只在存在适用业务规则或兼容契约时核对一致性；不预设所有消费方必须使用同一公式或得到相同结果。

### 提出高价值业务影响与回归假设

当 Diff 涉及核心业务计算、关键分支、默认值/过滤变化、数据转换、共享实现、权限/状态、接口契约或其他可能改变业务结果的路径时，围绕真实变化提出少量高价值假设，不对每个文件机械生成风险。

每个重要假设应说明：触发条件；适用的变更意图、业务规则或兼容约束；变更前后实际代码路径；可能产生的可观察差异；业务影响及关联调用方；支持证据；反证条件；尚缺少的证据。重点识别变更说明未提及但 Diff 实际引入的行为变化，以及看似内部调整却可能改变外部结果的路径。

假设没有明确预期或契约支撑时，只能描述为行为差异、潜在影响或待业务确认，不直接定性为缺陷。共享实现调用方和完整影响范围仍按「业务影响与关联调用方」章节核查，不以本节假设分析替代全部实际调用方核对。

### 构造前后对照反例并主动反证

对重要假设按实际触发条件选择最小、有区分度的对照样例，优先让变更前后使用相同输入，再按需要覆盖单条/多条、重复/唯一、NULL/空值/0/负数、边界日期、默认/自定义条件、不同数据粒度、状态、权限或异常分支。不得为了形式完整机械覆盖所有维度。

1. 用前后代码路径推导中间处理和最终可观察结果，定位差异首次出现的环节；涉及计算、聚合或过滤时，按需列出最小输入及关键中间值。
2. 静态推导或人工构造的样例必须明确标记为“静态推导/构造示例”，不能写成真实数据计算、接口执行或运行验证结果。
3. 主动尝试推翻假设：检查其他分支、调用方传参、公共封装、有效配置、接口/数据契约及已知业务例外，确认差异是否确由本次变更引入、是否有明确意图，以及是否实际影响相关消费方。
4. 有证据证明假设不成立时，将其排除并记录依据；证据不足时保留证据边界，不把可能性写成已确认缺陷。

分析等级、自动升级和停止条件统一遵循公共推理方法；本节不重复定义 L1/L2/L3。每次扩大分析范围必须由具体未决问题或新证据触发；适用约束、重要假设、真实调用方和剩余未知项均已处理后停止，不进行无边界扫描。

## 变更性质与意图一致性判断

将实际变化按证据和用户说明分类，至少区分：

行为差异本身不自动等于缺陷；只有证据充分证明其违反明确适用的业务预期、用户已说明的变更目的或必须保持的兼容行为，才可确认缺陷。

- **行为保持型内部调整**：实现结构或技术路径发生变化，但现有证据支持对外业务行为保持一致。
- **符合已说明目的的行为变化**：行为确实变化，且与用户明确说明的变更目的相符；仍需分析影响范围和兼容性。
- **未说明的业务行为变化**：实际行为发生变化，但现有变更说明未解释其目的；说明变化事实及影响，必要时列为待业务确认，不直接判为缺陷。
- **潜在副作用/回归风险**：存在合理影响路径，但现有证据不足以确认实际受影响；说明已证实部分及证据缺口。
- **证据不足**：无法可靠重建前后行为或确认调用关系时，明确限制，不猜测结论。

具体判断原则：
1. 不因代码重构、文件移动、方法拆分或内部实现变化本身判定为业务问题；应比较其对外行为和真实调用影响。
2. 对用户说明为性能优化、等价重构或兼容性整改的变更，重点核对原有业务行为、边界条件和副作用是否保持；不能仅凭代码更短、调用更少或算法复杂度下降就宣称业务等价或性能改善。
3. 对明确希望改变行为的变更，核实实际变化是否与用户说明一致；未说明的规则不自行补齐。
4. Commit message、文件名、代码注释或技术方案不能单独作为业务预期；缺少明确意图时，以客观行为差异和证据边界表达。
5. 只有证据充分证明违反明确适用预期，才定性为已确认缺陷。其余按潜在风险、待业务确认或无问题处理。

## 业务影响与关联调用方

分析重点是代码变化可能作用到哪些真实业务路径，而不是罗列所有修改文件。

1. 从变化的入口、共享实现、接口、组件、配置、任务或数据对象出发，追踪实际关联调用方及其输入输出。
2. 公共接口、公共 SQL、公共组件、共享 Service/函数或其他共享实现发生变化时，必须核查全部实际关联调用方；不得以高风险抽样替代完整相关调用方核查。
3. 对每个实际调用方核实调用条件、传入参数、返回值消费、业务用途和行为差异；注释、测试夹具、文档、死代码或同名文本不作为真实调用方。
4. 沿真实调用或数据依赖追踪至实际业务功能、页面、指标、报表或任务消费点；不强制遍历与本次变更无关的技术层。
5. 将影响分为直接影响、间接影响、潜在影响和无影响。潜在影响必须写明合理关联及尚缺证据；无影响必须有足够证据支持。
6. 动态调用、跨仓库依赖或无法解析的部分，列出已确认调用方、未确认范围及原因；不得把搜索无结果写成没有调用方。
7. 不因文件相邻、关键词相同、Diff 文件数量或目录归属扩大影响范围。

## 按技术层选择 MCP 与证据边界

先根据已定位的代码变化和证据缺口确定技术层，再按需选择公司 MCP；不在任务开始时全量调用 MCP。

- **Git**：负责源码、base/head、分支、Commit、历史和版本差异；不能证明实际部署或运行结果。
- **页面/查询配置**：涉及配置项、列、查询条件或页面展示时，优先核实组织已配置的当前权威来源环境（可选 `config/organization-profile.json`），按当前 MCP Schema 定向取得现值。该环境的当前配置不自动证明其他环境的历史或生产现状；缺少历史证据时记录缺口。
- **ETL/SQL/数据血缘**：按需核实 Git SQL/Groovy 版本源码和 Diff，只有任务/表/字段依赖关系影响判断时才调用当前环境实际可用的血缘工具。有限层级返回不等于完整血缘。
- **其他可选 MCP**：仅当本次业务路径证据确实涉及对应领域且结果有价值时使用；无可用连接时明确缺口，不扩展全量扫描。

MCP 失败、超时或返回不完整时，记录服务/能力、查询对象、环境、实际调用时间、可观察失败现象和受影响的核对项；区分查询成功但无数据、对象不存在、调用失败和返回不完整。保留已有 Git、源码及其他 MCP 证据，继续不依赖该证据的分析，不无限重试，也不把工具故障判为业务问题。

本工作流不执行 SQL、不触发 ETL 调度、不修改配置或平台数据。数据库实际结果、线上性能收益或运行态行为未取得真实运行证据时，不得写成已验证。

## 问题性质、缺陷等级与回归建议

每项业务核对分别记录问题性质和验证情况，按 `references/report-format.md` 的问题性质、证据状态和运行验证边界执行：
- 问题性质：已确认缺陷 / 潜在风险 / 待业务确认 / 无问题。
- 验证情况：静态已核实 / 待人工验证 / 无需人工验证。
- 实际运行验证：未执行时 `NOT_RUN`；真实执行后按证据记录 `PASS` / `FAIL` / `BLOCKED`。
- 缺陷等级只对证据充分确认的缺陷，依据公司现有 P0/P1/P2/P3 标准和实际影响判断；潜在风险、待业务确认事项不得仅凭推测定级。

回归建议围绕变更前后行为差异、已确认的影响范围和真实关联调用方提出，每项关联 CHK，并说明：
1. 回归对象：页面、业务功能、字段、查询条件、接口消费者、任务、数据链路或指标。
2. 具体验证内容：发生变化的行为、原有兼容行为、相关边界/异常分支及必要调用方。
3. 提出原因：对应的代码变化、调用关系或业务影响证据。
4. 明确预期：变更意图已明确时按用户说明及适用业务规则判断；行为保持型变更应说明需要保持的前后行为；意图未明确时列出待确认点，不编造预期。

如果相关的最新有效 P1 正式用例可被可靠定位，可作为回归参考或发现既有场景风险的辅助材料；没有用例不阻断分析。用例不是无需求场景的业务预期来源，不修改或发布 P1 正式用例。P2 只提出回归和用例增量建议。

## 完整报告与人工核对

每项分析均按 `references/report-format.md` 生成完整 `impact-analysis.md`，分析任务类型标记为“无需求代码变更分析”。无需求场景不强行生成需求编号或需求到实现对照；报告应以变更前后实际行为为比较依据。

完整报告应保留：
- 变更目的及来源；未明确时注明未知，不从 Commit message 猜测。
- 仓库、base/head、合并基点（如适用）、完整 SHA、Diff 范围及证据边界。
- 变更概览及变更前后实际行为差异。
- 变更性质、与已说明意图的一致性及未说明的行为变化。
- CHK 业务核对矩阵，包括静态通过项、问题、风险、待确认和无影响项。
- 全部实际关联调用方、直接/间接/潜在影响及证据限制。
- 修复/调整建议（如确有已确认问题）、回归建议、EV 证据索引和未决事项。
- 静态核对与实际运行验证状态；未执行运行验证时标记 `NOT_RUN`。
- 公共业务语义推理摘要：记录 L1/L2/L3、选择依据及自动升级原因、关键适用约束、重要假设和反例/反证结论；只保留可审计摘要，不输出隐藏思维链。

只有存在静态分析无法确认、用户确实能够执行且能回答明确问题的验证事项时，才另生成 `manual-verification.md`。每项使用 MV 编号并关联 CHK，包含核对对象、原因、环境/前置条件、操作步骤、明确预期、状态和实际结果回填位置。没有符合条件的事项时不创建空文件，并在聊天回复中明确说明无需人工核对。MCP 故障或证据缺失本身不自动生成 MV。

## 归档与版本管理

无需求编号的代码变更分析按本节独立任务归档和版本规则执行；不得套用开发提测分析的需求级 Manifest 原位归档旧策略。

- 无需求编号的代码变更分析归档到 `output/impact-analysis/CODE-<主题>-<YYYYMMDD>/vN/`。
- 每个正式版本默认保存完整 `impact-analysis.md`；仅存在符合条件的人工核对事项时，同时保存 `manual-verification.md`。
- 同一代码变更分析任务的后续正式更新在原任务目录下递增 `vN`；新的独立任务新建日期目录并从 `v1` 开始。
- 所有历史正式版本永久保留，不覆盖旧报告；不新增 JSON 证据库、SQLite、数据库或第二套版本账本。

## 完成前检查

交付前逐项确认：
- 本次请求属于无需求代码变更分析，没有误路由为 BUG 排查或开发提测影响分析。
- 已识别变更目的及其证据来源；未知意图没有被 Commit message 或代码注释擅自补成业务规则。
- 已确定并记录比较基线、合并基点（如适用）和所有已提交引用的完整 SHA；若包含未提交工作区，已记录 HEAD SHA、实际纳入的 staged/unstaged/untracked 范围及快照时间，没有伪造 head SHA。
- 已阅读变更前后完整上下文，不只依据 Diff 片段、文件名或提交备注判断。
- 已比较实际行为变化，并区分内部调整、已说明行为变化、未说明行为变化、潜在副作用和证据不足。
- 公共接口、SQL、组件、共享函数等已核查全部实际关联调用方，或明确记录无法确认范围及原因。
- 直接、间接、潜在和无影响范围均有证据依据，没有按文件数量或关键词扩大影响范围。
- MCP 按技术层按需调用；配置和血缘的查询环境、时间、完整性及证明边界已说明；失败没有触发无效重试。
- 问题性质与缺陷等级分开判断；只有证据充分确认的缺陷才按公司 P0/P1/P2/P3 标准定级。
- 回归建议关联 CHK，包含对象、内容、原因和明确预期；没有编造需求或业务预期。
- 已按公共方法选择并记录 L1/L2/L3、选择依据和自动升级原因；重要业务差异已按需推导约束、提出并验证高价值假设，完成针对性反例/反证，未按文件数或 Diff 大小机械分级。
- 已区分变更前事实基线与正确业务预期；未将旧行为、Commit message、代码注释或 P1 用例单独作为正确性依据；已区分行为保持、明确行为调整、缺陷修复及未说明的额外行为变化。
- 完整报告按 `report-format.md` 生成，包含 EV、CHK 和必要 MV；无人工验证事项时未创建空清单。
- 静态核对、实际运行验证和业务验收严格区分；未执行运行验证时标记 `NOT_RUN`。
- 未修改业务代码、P1 正式用例、配置或平台记录；未执行 SQL/ETL、平台导入或 Push。
