# Bug 回归与关闭工作流

## 工作流定位与触发

本文件是 P2 `code-impact-analysis` 下独立的 Bug 生命周期工作流，负责已登记 Bug 的修复影响分析、回归验证、人工待办整理及经授权后的禅道关闭。它不重新承担普通 Bug 根因排查，也不替代开发提测分析。

触发条件：
- 用户提供禅道 Bug ID，并要求回归、复测、验证修复或关闭该 Bug。
- 用户明确要求继续当前 Bug Lifecycle 任务。

**强制重载与规则优先级：** 每次本工作流被路由命中时，必须在本轮任何禅道 MCP 调用前重新读取本文件完整当前内容。MCP Schema 只约束实际调用参数，不替代本工作流的回归准入、完整关闭预览、Draft ID 授权、关闭后状态回读和本地归档。

职责边界：
- `bug-investigation.md`：没有明确修复提测上下文时，根据异常现象定位根因。
- `submission-impact.md`：有需求编号和开发提测点时，分析该次开发提测的整体影响。
- 本工作流：围绕一个已登记 Bug 的修复版本，确认修复是否有效、修复带来的直接/间接影响，以及是否满足关闭条件。
- `bug-submission.md`：创建新的 Bug；本工作流不创建 Bug。若回归发现新的独立缺陷，只提供证据并交接，用户明确要求后再进入提交流程。

## 安全门禁

1. 查询 Bug、读取代码、静态分析和执行安全的只读/非破坏性测试，不等于授权修改禅道状态。
2. 每条 Bug 独立回归、独立关闭预览、独立授权、独立关闭。不允许批量关闭或用一次授权关闭多条 Bug。
3. 只有必要回归项均已通过、没有阻断关闭的 FAIL/BLOCKED，且用户针对当前最终关闭 Draft ID 明确授权后，才允许调用禅道关闭操作。
4. “回归通过”“可以”“确认”“关闭吧”等未明确绑定当前 Bug ID 和当前关闭 Draft ID 的表述，不构成关闭授权。
5. 回归失败、关键验证 BLOCKED、修复版本无法确定或原始 Bug 预期不清楚时，不得请求关闭授权，也不得调用关闭操作。
6. 关闭操作前必须读取当前运行环境提供的禅道 MCP Schema，确认实际关闭工具名称、必填/可选参数、参数类型、状态语义及用户选择字段。不得根据历史记录猜测工具名或参数；工具不存在、Schema 不可读或能力不匹配时，停止写入并明确说明。
7. 按当次真实 Schema 收集所有必填参数。当前 Codex 验收读取到的 closeBug Schema 必填字段为：`id:number`、`belongTo:string`、`tagList:array`；其中 Bug 归属人（belongTo）和标签（tagList）必须由用户明确提供/选择，不得由 AI 自行推断、默认或补选。若运行时 Schema 与此不同，以当次 Schema 为准并重新向用户确认新增或变化的用户选择字段。
8. 关闭预览必须逐项展示实际将提交的完整参数（字段名、值及含义），至少包括 Bug ID、归属人、标签，以及 Schema 要求的其他全部必填参数；同时展示回归结论、证据摘要和关闭动作。任何必填参数缺失、值不合法或含义未确认时，不得生成可授权预览。
9. 一次关闭授权只允许调用一次关闭工具。超时、断连、无回执或结果未知时停止，不自动重试；先用 Bug ID 查询当前状态核查。
10. 关闭调用成功响应不等于最终关闭成功。必须再次按 Bug ID 回读状态，只有实际状态明确为关闭才报告关闭 PASS。
11. 不自动重开 Bug、不修改指派人、不修改 Bug 正文或其他禅道字段。关闭接口要求的归属人字段仅按用户明确选择值提交，不等于授权修改 Bug 指派人；若工具实际会同时修改其他字段，必须在预览中披露并另行确认，否则停止。
12. 不修改业务代码、配置或仓库文件；不执行生产 SQL/ETL，不写入业务数据，不 Push。

## 获取原始 Bug 与修复上下文

1. 先使用当前禅道 MCP Schema 中的 Bug ID 查询能力读取指定 Bug。历史已知 `queryBugs` 的 status 过滤不可靠，不得依赖 status 条件缩小结果或判断最终状态；按 Bug ID 查询后检查返回记录自身的状态和字段。
2. 核对 Bug ID、标题、需求关联、复现步骤、实际结果、期望结果、环境、指派人、当前状态及可用的创建/更新信息。
3. 查询结果缺字段时，区分“查询结果未返回”和“Bug 本身没有内容”；不得伪造原始步骤或预期。缺少会实质影响回归的内容时，只询问最关键的缺失信息。
4. 优先复用当前对话、P2 报告、Bug 正文和用户已提供的修复分支/Commit/提测信息，不要求用户重复提供已有信息。
5. 必须识别本次实际修复版本及其代码基线。优先根据 `config/repositories.json` 定位仓库，缺失时按 `references/git-repository-policy.md` 核实用户提供的本地仓库，按 `references/git-repository-policy.md` 对涉及仓库和远端引用定向 Fetch、记录完整 SHA 并冻结证据。
6. 若用户提供修复 Commit/PR/分支，核实其是否属于目标修复版本；若未提供，使用 Bug 关联需求、代码定位、提交历史和当前任务上下文定向定位。若无法可靠确定修复版本，停止因果性结论并询问最关键的版本/提测信息，不得把最新代码擅自当作已部署修复。
7. 根据 Bug 环境与发布事实选择比较基线。代码已合并不等于目标环境已部署；必须区分源码修复存在、目标环境部署确认和实际运行验证。

## 修复影响分析

本工作流必须使用 `references/analysis-reasoning-framework.md`，由 AI 根据业务复杂度、影响范围和证据不确定性自主选择 L1/L2/L3；不得因任务名称是“回归”而降低分析深度。

分析至少覆盖以下适用内容：

1. 原缺陷路径：复现条件、触发入口、业务对象、输入状态、关键分支、异常行为及修复后的预期行为。
2. 修复改动：修复 Commit/Diff、修改文件、方法、参数、字段、条件、计算/聚合、配置和数据依赖；不能只依据 Commit message。
3. 直接影响：修复代码直接改变的页面、接口、字段、数据处理或业务流程。
4. 间接影响：沿真实调用关系、共享组件/接口/SQL、上下游数据依赖追踪消费方；公共实现必须完整核查全部实际关联调用方，不得抽样代替。
5. 兼容与回归风险：旧场景、其他聚合/查询模式、公共调用方、边界值、空值/异常值、状态迁移、权限及跨模块行为；只纳入有真实依赖或合理影响依据的场景。
6. 无影响判断：重要关联方可以通过代码和依赖证据证明不受影响时，记录证据，不要求用户重复验证。
7. 区分直接影响、间接影响、潜在影响和无影响。潜在影响必须写明关联路径和证据缺口，不得当成已确认问题。
8. 复用 P2 统一报告结构和 CHK/EV/MV 编号，不另建一套分析方法或评分体系。

## 回归范围与 AI 自主验证

### 回归范围

回归范围按证据分组，不机械套用固定测试数量：
- 原缺陷复现与修复验证。
- 修复代码直接影响的业务场景。
- 共享调用方及上下游间接影响场景。
- 兼容性、边界和关键异常场景。
- 与本次修复有明确依赖关系的历史问题或正式用例（如可取得）。

每项回归说明：关联 Bug/CHK、验证对象、操作或输入、预期结果、为什么需要验证、实际执行方式和证据。

### AI 优先完成可验证事项

1. AI 应主动判断并执行当前环境实际支持的验证，包括源码/配置静态核对、现有自动化测试、可安全执行的本地测试、只读接口/API 验证及可用的浏览器验证。
2. 不得仅因为验证工作量较大就转交用户；也不得为了显示自动化而编写无必要的测试框架或业务硬编码脚本。
3. 执行测试前检查测试命令和副作用。只运行可确认安全、范围明确且不会写入生产或修改业务数据的验证；可能产生外部写入、影响共享环境或执行生产 SQL/ETL 时必须停止并取得相应授权。
4. 静态代码能证明的调用关系、参数传递、分支行为和兼容性由 AI 完成分析，不转为人工待办；静态推导不能冒充页面/API/生产运行 PASS。
5. 每项验证记录实际命令/调用方式、目标版本或 SHA、结果和可复核证据。未执行标记 NOT_RUN；执行失败标记 FAIL 或 BLOCKED，并说明原因。
6. 若环境工具不支持真实页面、目标环境或权限验证，只把这些具体缺口列为人工 MV；不得把所有回归项都推给用户。

### 人工验证清单

只有同时满足以下条件才生成 MV：
- 该验证会实质影响修复是否正确或关闭判断；
- 当前 AI 工具、权限或环境无法可靠完成；
- 用户确实能够执行并反馈。

每条 MV 必须给出 Bug ID、关联 CHK、具体页面/环境、前置条件、可照做的操作步骤、预期结果、需要回传的证据，以及不验证的影响。无需人工验证时明确写“无需人工核对（0 项）”。

## 回归结论与关闭准入

每项回归结果使用统一状态：
- PASS：已实际执行且证据支持预期结果。
- FAIL：实际结果与预期不符，或发现修复未解决原问题/引入已确认问题。
- BLOCKED：尝试验证但被环境、权限、数据或工具阻断。
- NOT_RUN：尚未执行；必须说明原因。

关闭准入：
1. 原缺陷验证必须 PASS。
2. 所有根据实际修复影响识别出的必要回归项必须 PASS，或有明确证据证明不适用。
3. 不得存在阻断关闭的 FAIL 或 BLOCKED。
4. 关键 MV 必须由用户反馈验证结果；用户未反馈时保持 BLOCKED/NOT_RUN，不得推断通过。
5. 仅有非关键、明确不影响修复正确性判断的 NOT_RUN 项时，说明范围与风险；不得隐藏。
6. 若发现新的独立缺陷，单独列出证据和业务影响，不得将其混入原 Bug 并自动提交。

未满足关闭准入时，交付回归结论和待办，不进入关闭授权。

## 关闭预览、人工授权与结果回读

满足关闭准入且已取得当次真实 Schema 所需的全部用户选择参数后，先展示一条 Bug 的最终关闭预览，至少包含：
- Bug ID、原始标题、当前状态、关联需求。
- 修复版本/Commit SHA 和环境部署证据（如可取得）。
- 原缺陷验证结果。
- 直接/间接影响范围及回归结果摘要。
- PASS/FAIL/BLOCKED/NOT_RUN 统计和人工核对完成情况。
- 仍存在的限制或非阻断风险。
- **完整实际写入参数**：每个字段的参数名、值、业务含义；至少展示 `id`、用户选择的 `belongTo`、用户选择的 `tagList`，以及当次 Schema 要求的全部其他必填参数和实际将传入的可选参数。
- 明确说明关闭工具是否还会改变归属关系、标签以外的其他字段；若无法确认工具副作用，停止写入。
- 关闭动作及唯一目标 Bug ID。

任何必填参数未齐、归属人/标签未由用户明确选择、参数值不符合 Schema，或工具副作用未确认时，不得请求授权。

生成当前唯一关闭 Draft ID，并将它绑定到该 Bug 的最终预览快照（Bug ID、当前状态、修复 SHA、回归结论、完整写入参数及工具 Schema 版本/读取结果）。只有最终预览展示完成后，用户明确回复“确认关闭 BUG <Bug ID>，Draft ID <当前Draft ID>”才构成授权。授权只适用于该快照和一次关闭调用。

以下情况立即使授权失效，必须重新读取状态/Schema、生成新 Draft ID、展示完整预览并重新授权：任何预览内容或写入参数变化；Bug 当前状态变化；用户取消；用户切换到其他 Bug 或其他任务；当前任务上下文/快照无法可靠恢复；跨新对话继续。旧 Draft ID 永不复用。不得把针对 Bug ID 的泛化确认、旧对话授权或其他 Draft ID 的授权用于当前关闭。

关闭调用后：
1. 明确成功响应：按 Bug ID 回读当前状态。
2. 明确失败响应：报告失败原因，不自动重试。
3. 超时、断连、结果未知：停止写入，先查询 Bug 当前状态；若状态已关闭，按回读证据确认；若仍未关闭或状态不明确，交由用户核查，不自动再次关闭。
4. 最终状态不是明确关闭时，不报告关闭成功。

## 交付与归档

每个 Bug 使用独立归档目录，避免与同一需求的提测分析报告、创建回执或其他 Bug 报告冲突：
`output/【<模块>】/<需求编号>-<需求名称>/analysis/bug-lifecycle/BUG-<BugID>/`（有需求编号时，独立于 `analysis/<YYYYMMDD-vN>/` 和 P1 正式用例版本）

每个 Bug 目录按实际内容创建：
- `impact-analysis.md`：该 Bug 的修复影响分析、直接/间接影响、回归范围、AI 验证结果及证据；每次同一 Bug 后续回归只更新本目录内文件。
- `manual-verification.md`：仅当确有必须由用户执行且影响关闭判断的 MV 时创建；无 MV 不创建空文件。
- `close-receipt.md`：仅在关闭工具明确成功，且随后 `queryBugs(queryType=BUG_ID, queryData=<BugID>)` 回读确认状态为 `closed` 后创建。查询不得传 `status` 参数（当前过滤不可靠）。

关闭回执必须记录 Bug ID、需求、创建来源（CodeBuddy/用户人工/未知）、创建时间、修复 SHA、验证摘要、实际关闭参数（归属人、标签及其他写入字段）、当前 Draft ID、授权原文/时间、关闭工具响应、关闭时间和按 Bug ID 回读的最终状态。字段未从历史证据恢复时写 `NOT_AVAILABLE`，不得推断、补造授权或原始正文。历史补档须明确标记“历史补档”，区分用户提供的创建/关闭来源与平台 openedBy/closedBy 账号字段。

关闭回读确认后，自动生成或更新该 Bug 目录内的 Lifecycle Markdown 文件；不得覆盖其他 Bug、Bug Submission 回执或通用提测报告。关闭失败、状态未关闭、回读失败或结果未知时不得生成成功关闭回执。

### 关闭成功后的本地归档自检

只有关闭工具明确成功且 `queryBugs(BUG_ID)` 回读状态为 `closed` 后，才执行以下本地归档核验：

`python -B skills/code-impact-analysis/tools/verify_bug_archive.py lifecycle <bug_directory> <BugID> [--manual-verification] [--requirement-root <requirement_root>]`

- 必须存在且非空：`impact-analysis.md`、`close-receipt.md`；本轮确有人工核对清单时增加 `--manual-verification`，并要求 `manual-verification.md` 存在且非空。
- 核验器输出每份文件的字节数和 SHA-256；提供 `--requirement-root` 时，还会执行当前需求 Manifest 的 `validate`，但不登记 Lifecycle role。
- 当前 Manifest 不支持 `bug-lifecycle` category，因此 `manifest_registration=NOT_REGISTERED_BY_DESIGN` 是已确认限制，不是文件归档失败；不得要求 `bug-submission-<BugID>` role，也不得复用 `test-impact-analysis` 身份。
- 核验器返回 `BUG_LIFECYCLE_ARCHIVE_PASS` 后才可报告本地归档完成。若关闭已成功但文件核验失败，报告 `CLOSED_ARCHIVE_PENDING`，保留禅道已关闭的事实，不得再次调用 `closeBug`，不得覆盖或伪造文件。

Manifest 使用独立 `category=bug-lifecycle`，并按 Bug ID 使用唯一 role（`BUG-<BugID>-impact-analysis`、`BUG-<BugID>-manual-verification`、`BUG-<BugID>-close-receipt`）。登记前必须以当前 Manifest 工具实际验证 category、role 和多 Bug 并存兼容性。**当前运行模块实测拒绝 `bug-lifecycle` category（`artifacts[].category 不受支持`），因此当前只保存隔离文件，不登记 Manifest；报告 `MANIFEST_REGISTRATION_NOT_SUPPORTED`。**不得改用 `test-impact-analysis` 身份绕过限制，也不得修改 P1 既有 artifact、版本、用例快照、交付状态或其他字段。未来只有 Manifest 明确支持后才恢复登记。

有明确需求编号时使用上述需求根目录下的 Bug Lifecycle 独立目录，不要求存在 P1 正式用例基线；无需求编号时沿用现有 P2 独立 BUG 任务根目录 `output/impact-analysis/BUG-<主题>-<YYYYMMDD>/`，在其下建立 `analysis/bug-lifecycle/BUG-<BugID>/`，根因报告原有 `vN/` 版本规则不变。历史归档不迁移、不覆盖，不得虚构需求编号或版本。
